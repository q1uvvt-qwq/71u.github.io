「能跑通」和「能维护」之间，隔着的正是工程化。

多数项目死在第一阶段之后：代码确实跑起来了，但没人敢改。改一处，不知道会波及哪里；加一个功能，需要先祈祷。此时再回头补工程化，成本往往已经高到不如重写。

三个我反复使用的判断标准

其一，看底层机制是否清楚。调通一个接口不难，难的是知道它在什么条件下会失败。凡是只能用「试出来的」方式使用的组件，都是一个定时炸弹。我会花额外的时间去读一层源码，把边界条件写进注释——这份投入几乎总能在第一次线上故障时回本。

其二，看系统是否对失败有预期。可靠性不是「不出错」，而是「出错之后能收敛」。超时、重试、幂等、降级，这些词在需求文档里通常没有，但它们决定了凌晨三点你要不要起来。

其三，看代码是否可被陌生人维护。这里的「陌生人」就是三个月后的自己。命名、边界、依赖方向、测试覆盖——判断标准很朴素：我需要向别人解释多久，他才能安全地改动这段代码。

慢，是因为在还债

// 快而脆
if (res) { doSomething(res.data) }

// 慢而稳：先收敛不确定性
if (!res || !isValid(res.data)) {
    return fallback(reason);
}

上面这段对比很琐碎，但它代表了一种取舍：把判断成本从「运行时」前移到「编写时」。写的时候多花三十秒，排查的时候少花三小时。

工程化在短期内看上去总是更慢的。它慢，是因为它在偿还此前欠下的债——只不过还债这件事，早还永远比晚还便宜。

内容更看重底层机制、系统可靠性与代码可维护性。

这条标准也会用在写笔记上：能讲清机制的地方，就不停在步骤上。
