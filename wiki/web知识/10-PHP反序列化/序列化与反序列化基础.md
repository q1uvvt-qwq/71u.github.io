## 一句话概括

`serialize()` 把内存里的对象压成一段**可以存、可以传的字符串**，`unserialize()` 再把这段字符串**还原成对象**。危险点在于：还原时「实例化哪个类、每个属性填什么值」全部由这段字符串决定 —— 而这段字符串常常来自用户。

## 原理

### 1. 先分清「概念」和「函数」

- **序列化**是一个概念：把数据结构转成可存储 / 可传输的形式；
- **`serialize()`** 是 PHP 里实现这个概念的**函数**；**`unserialize()`** 是它的逆操作。

所以在 PHP 里，**要拿到（或看懂）这套格式，只能靠 `serialize()`**：格式是 PHP 私有的、不是 JSON 那种通用标准。反序列化则是「按同样的格式把字符串重新拼回对象」。

### 2. 标量类型的序列化格式

```php
<?php
$a = null;
echo serialize($a);          // N;
echo serialize(666);         // i:666;
echo serialize(66.6);        // d:66.6;
echo serialize(true);        // b:1;
echo serialize(false);       // b:0;
echo serialize('benben');    // s:6:"benben";
?>
```

| 数据类型 | 示例值 | 序列化结果 | 说明 |
|---|---|---|---|
| Null | `null` | `N;` | 空值，连分号 |
| 整型 Integer | `666` | `i:666;` | |
| 浮点型 Double | `66.6` | `d:66.6;` | |
| 布尔 Boolean | `true` / `false` | `b:1;` / `b:0;` | |
| 字符串 String | `'benben'` | `s:6:"benben";` | **带长度**，这是后面所有绕过的根 |

注意字符串那一行：`s:6:"benben";` 里的 `6` 是**字节长度**。解析器反序列化时**只按这个长度读，不核对内容真实有多长** —— 后面第 06 篇的「字符逃逸」就是从这一点长出来的。

### 3. 数组

```php
<?php
$a = array('benben','dazhuang','laoliu');
echo serialize($a);
// a:3:{i:0;s:6:"benben";i:1;s:8:"dazhuang";i:2;s:6:"laoliu";}
?>
```

| 片段 | 含义 |
|---|---|
| `a:3:` | `a` = array，后面跟 **3** 个元素 |
| `{` … `}` | 数组内容的起止 |
| `i:0;` | 下标 0 |
| `s:6:"benben";` | 值（字符串，长度 6） |
| `i:1;` / `i:2;` | 下标 1 / 2 |

数组是「下标记号 + 值」成对出现的，对象则是「属性名 + 属性值」成对出现，骨架一样。

### 4. 对象：类名和属性值都被写在字符串里

```php
<?php
class test{
    public $pub = 'benben';
    function jineng(){ echo $this->pub; }
}
echo serialize(new test());
// O:4:"test":1:{s:3:"pub";s:6:"benben";}
?>
```

| 部分 | 含义 |
|---|---|
| `O` | Object，表示这是一个对象 |
| `:4:` | **类名长度** = 4 |
| `"test"` | **类名** |
| `:1:` | **属性个数** = 1 |
| `{` … `}` | 属性列表的起止 |
| `s:3:"pub";` | 属性名（长度 3） |
| `s:6:"benben";` | 属性值 |

这三个字段 —— **类名、属性个数、属性名/值** —— 全部来自字符串本身。攻击者只要改这段字符串，就能决定「反序列化出哪个类的对象」「对象里每个属性是什么」。这就是漏洞的起点。

### 5. 三种属性可见性在序列化里怎么表示

同样是 `private $pub` / `protected $pub`，序列化出来的属性名是不同的：

```php
<?php
class test{
    private $pub = 'benben';
    function jineng(){ echo $this->pub; }
}
echo serialize(new test());
// O:4:"test":1:{s:9:"testpub";s:6:"benben";}
?>
```

| 可见性 | 属性名写法 | 例（类 `test`，属性 `pub`） | 长度 |
|---|---|---|---|
| `public` | `属性名` | `pub` | 3 |
| `protected` | `NUL` + `*` + `NUL` + `属性名` | `\0*\0pub` | 3 + 3 = 6 |
| `private` | `NUL` + `类名` + `NUL` + `属性名` | `\0test\0pub` | 3 + 4 = 7 |

**「为什么是 9 不是 7」** —— 原笔记里的这个疑问，答案就是 `private` 的属性名前后各插了一个 `NUL`（`%00`）字节，再加上类名：

```text
\0 test \0 pub   →  1 + 4 + 1 + 3 = 9 字节
```

`\0` 是不可打印字符，所以在线上的 payload 里通常写成 `%00`，或者用 PHP 拼接 `"\0"`。

> 注意：长度字段数的是**真实字节数**，`%00` 也算一个字节。算错一个字节整串就解析失败。

### 6. 为什么 `serialize()` 能读到 `private` 属性

原笔记问：「private 不是只能类内访问吗，为什么 `serialize()` 能把它输出出来？」

因为这是**两个层面的事**：

| 层面 | 规则 |
|---|---|
| **访问控制**（正常业务代码） | `private` 只能类内访问，`protected` 只能类内及子类访问，`public` 到处都能访问 |
| **序列化机制**（语言底层） | 直接读取对象内存里的全部属性，**不走访问控制这一关** |

可以理解为序列化是一种「反射」式的底层操作：它关心的是「对象里存了哪些数据」，而不是「谁有权调用」。所以 `private` / `protected` 属性照样被完整写进字符串，反序列化时也照样能被重新填回去。

这一点对攻击者很关键：**被 `private` 保护的「敏感属性」，在反序列化里反而是完全可控的。**

```php
<?php
class Test {
    private $secret = '私有数据';
    public $public = '公开数据';
}
echo serialize(new Test());
// O:4:"Test":2:{s:11:"Testsecret";s:12:"私有数据";s:6:"public";s:12:"公开数据";}
?>
```

### 7. 完整的「手工拼 payload → 反序列化」例子

原笔记里那个 `urldecode` 的例子，把三种属性一起编了出来：

```php
<?php
class test {
    public $a = 'benben';
    protected $b = 666;
    private $c = false;
    public function displayVar() { echo $this->a; }
}

// 手工拼出序列化字符串：注意 \0 的位置和长度
$d = 'O:4:"test":3:{s:1:"a";s:8:"dazhuang";'
   . 's:4:"' . "\0" . '*' . "\0" . 'b";i:666;'
   . 's:7:"' . "\0" . 'test' . "\0" . 'c";b:1;}';

$e = urldecode($d);   // 见下面「为什么先 urldecode」
$f = unserialize($e);
var_dump($f);
?>
```

逐段对一下长度：

| 片段 | 属性 | 长度校验 |
|---|---|---|
| `s:1:"a";s:8:"dazhuang";` | `public $a` | `dazhuang` 8 字节 ✓ |
| `s:4:"\0*\0b";i:666;` | `protected $b` | `\0`,`*`,`\0`,`b` = 4 字节 ✓ |
| `s:7:"\0test\0c";b:1;` | `private $c` | `\0`,`t`,`e`,`s`,`t`,`\0`,`c` = 7 字节 ✓ |

**为什么第一步要 `urldecode`**：payload 是通过 URL 传进来的，`O` `:` `"` 这些字符在 URL 里可能被百分号编码：

```text
没解码：O%3A4%3A%22test%22      → 解析器看到的是 %3A，认不出 O:4:"
解码后：O:4:"test"             → 才是合法的序列化格式
```

PHP 的 `$_GET` 会自动做一次 URL 解码，但**当 payload 被套了 base64、或者被写进 cookie 再取出来时**，就需要自己手动 `urldecode()` / `base64_decode()`。做题时判断依据是：**交给 `unserialize()` 的那串东西，必须已经是纯 `O:4:"..."` 形态**，否则就先解码。

## 利用条件

反序列化要变成漏洞，需要同时满足：

1. **入口可控**：存在 `unserialize()`，且它的参数能被攻击者影响（GET/POST/COOKIE 参数、`session`、缓存、API 报文……）
2. **有可用的类**：代码里存在「属性被改了就会变危险」的类（比如属性直接进了 `eval()` / 文件操作 / 命令执行），或者存在魔术方法
3. **能拼出合法字符串**：类名、属性个数、每个长度字段都要算准
4. **（进阶）有魔术方法**：即使攻击者不主动调用方法，反序列化 / 脚本结束时的魔术方法也会自动跑（见 03、04、05 篇）

## Payload 速查

| 目的 | 写法 |
|---|---|
| 空值 | `N;` |
| 整数 / 浮点 / 布尔 | `i:1;` / `d:1.5;` / `b:1;` |
| 字符串（长度必须数准） | `s:6:"benben";` |
| 对象 | `O:<类名长度>:"<类名>":<属性个数>:{<属性名><属性值>...}` |
| `public` 属性 | `s:3:"pub";` |
| `protected` 属性 | `s:6:"\0*\0pub";`（协议里写 `s:6:"%00*%00pub";`） |
| `private` 属性 | `s:9:"\0test\0pub";`（协议里写 `s:9:"%00test%00pub";`） |
| 用 PHP 生成而不是手拼 | `echo urlencode(serialize($obj));` |
| 传参前先解码 | `urldecode($input)` / `base64_decode($input)` |

## 一句话记住分工

> `serialize()` 负责**读**：把对象属性读出来写进字符串（能读 `private`，不受访问控制限制）。
> `unserialize()` 负责**建**：按字符串里写的类名新建一个对象，把属性填进去。
> 攻击者控制的是**字符串**，也就是控制了「建哪个对象、属性是什么」。

## 踩坑与备注

- **序列化一定会创建新对象，而序列化不会**。`unserialize()` 必须新建一个对象来装载数据，这是它的基本行为；这也是「为什么反序列化能触发 `__construct` 之外的魔术方法」的原因。
- **长度必须精确**。原笔记踩过的坑就是「为什么是 9 不是 7」——`%00` 也是字节。手拼时建议先 `serialize()` 一遍再对照着改，别凭空数。
- **`unserialize()` 只认 PHP 私有格式**，`json_decode` 那套不适用。
- **反序列化不改变类的方法代码**。它只能改属性值；因此漏洞是否成立，取决于「这些属性值最终会被哪段方法用到」（见 04、05 篇）。
- **先解码再反序列化**。看见 `%3A`、base64 字符集、或者 cookie 里带 `%22`，先按上下文解码一次；`$_GET`/`$_POST`/`$_COOKIE` 由 PHP 自动解码，但**嵌了一层 base64 的 payload 需要自己 `base64_decode()`**。
