## 一句话概括

本篇收录与注入相关的若干零碎但关键的细节：SQL 关键字为什么习惯大写、一条登录查询是怎么串起来的、`Content-Type` 怎么决定参数解码方式、`WHERE` 后面为什么只能接布尔表达式，以及 `eval` 作为"语言构造器"的本质、PHP 允许用字符串当函数名、取反免杀和字面量这几个概念。

## 原理

### 1. 关键字区分：为什么常大写

SQL 关键字习惯上大写书写。这里有个关键前提：SQL 关键字本身大小写不敏感，`select`、`SELECT`、`SeLeCt` 对数据库来说完全等价。既然等价，大写就纯粹是书写惯例：

- 大写的关键字（`SELECT`、`FROM`、`WHERE`）一眼就能和表名、列名、字符串值区分开，长语句里不容易看花眼；
- 很多文档、教材、现成 payload 都按这个惯例写，抄来抄去就固化了。

对注入的意义：因为大小写不敏感，把关键字写成大小写混写（如 `seT`、`pRepare`、`UnIoN`）可以得到一条语义完全相同、但字面不同的语句，这对付按大小写敏感的正则匹配关键字黑名单特别有用（`SQL注入底层原理-解析与执行的博弈` 第 6.4 节里那串 `seT @a = 0x...; pRepare ...` 用的就是这个思路）。

### 2. 一条登录查询的完整链条

登录功能后端执行的是一条 `SELECT` 查询：它先拿用户提交的用户名去表里查，查到记录就说明这个用户名是存在的，然后应用层再把查出来的密码和用户提交的密码做比对，也就是校验密码。

```php
$sql = "SELECT * FROM users WHERE username = '$username'";
// 查得到  -> 用户名存在 -> 再比对密码
// 查不到  -> 用户名不存在
```

为什么这件事重要：这个链条意味着 `SELECT` 语句天然就是注入最经典的落点，因为它直接吃用户输入（用户名），而且查询的命中与不命中会被应用层翻译成不同的响应（"密码错误"与"用户不存在"）。`布尔盲注-原理与利用` 整篇就是靠这一点，把命中与不命中当成一个可读的比特位。

### 3. POST 与 Content-Type：参数是怎么被解码的

POST 请求体里的参数按什么规则解析，是由 `Content-Type` 决定的。

最常见的 `Content-Type: application/x-www-form-urlencoded` 表示请求体里的参数按 URL 编码规则（百分号编码）来编解码：参数之间用 `&` 分隔、`=` 连接名字与值、空格常被写成 `+`、特殊字符写成 `%XX`。GET 请求的查询串也走同一套规则。

最典型的报文长这样：

```http
POST /login HTTP/1.1
Host: 靶机地址
Content-Type: application/x-www-form-urlencoded

username=admin&password=123
```

对注入的意义（关键）：服务器最终拿到的是解码之后的字符串。所以这里叠了两层编码，初学时特别容易混淆：

| 层 | 你在哪一层 | 举例 |
|---|---|---|
| 传输层 | URL / 请求体里写的字符 | `%27`、`%20`、`+` |
| SQL 层 | 后端拿到、并拼进 SQL 的字符 | `'`、空格 |

这意味着你在请求里写 `%27`，到后端已经变成了 `'`，能让解析器提前闭合的是解码后的 `'`。构造 payload 时必须同时想清楚"这一层该写什么、那一层会变成什么"。

旁注：换成 `multipart/form-data`（文件上传用）或 `application/json` 时，解析规则完全不同，注入点的构造方式也要跟着变。

### 4. `WHERE` 后面只能接布尔表达式

`WHERE` 子句的作用是筛选出哪些行，所以它后面必须是一个求值结果为布尔（真 / 假）的表达式。最经典的例子就是 `id=1`：它对每一行求值一次，为真的行保留、为假的行丢弃。

这条规则直接决定了注入 payload 的形态：

| 情况 | 你想让 `WHERE` 接受的表达式 | 典型 payload |
|---|---|---|
| 恒真（绕过登录） | `1=1` | `' OR 1=1 -- ` |
| 恒假（做对比基准） | `1=2` | `' AND 1=2 -- ` |
| 数值比较（布尔盲注） | `ascii(substr(...))>100` | `' AND ascii(substr(database(),1,1))>100 -- ` |
| 由条件决定真假（可控开关） | `if(条件, ...)` 的结果参与比较 | `if(1=1,0,1)` |

换句话说，想往注入点里塞东西，你要塞的是一个能算出真或假的东西，而不是随便一段字符串。布尔盲注之所以能成立，就是把问题写成一个 `WHERE` 能接受的布尔表达式，再看页面给出的是真还是假。

### 5. `eval`：不是函数，是语言构造器

普通函数（如 `strlen()`、`system()`）是引擎在运行时去函数表里查名字、再调用的，有正常的参数、返回值，也能被"可变函数"的方式调用。

语言构造器（language construct）是由 PHP 解析器直接识别的东西，`eval`、`echo`、`print`、`isset`、`empty`、`unset`、`require`、`include` 等都属于这一类。它不走函数表查找那套机制。

这个区别带来一个非常实际、而且在免杀里反复被利用的后果：

注意：`eval` 不能被"用字符串当函数名"的方式调用。所以 `$f = 'eval'; $f('...');` 这种写法在 `eval` 上行不通；而 `assert`（PHP 8 以前）是普通函数，可以。

关于执行层：PHP 的执行引擎（Zend Engine）本身就是用 C 写的，PHP 代码最终由这一层来解释执行。`eval` 之所以能把字符串变成行为，是因为它把字符串交给了 Zend 引擎去做编译与执行，而不是字面意义上的"把 PHP 翻译成 C 再编译"。

### 6. `@eval` 为什么不回显

PHP 里 `@` 是错误抑制符，写在某个表达式前面，会抑制这个表达式产生的错误信息，不让它输出到页面。

`eval()` 执行出错（比如传入的字符串不是合法的 PHP 代码）时，默认会打出解析错误；前面加了 `@`，这个错误就被吞掉了，页面看上去什么都没发生。

对做题的意义：加上 `@` 之后，"输了什么、错在哪"这条路被堵死，你只能靠页面差异、响应长度、响应时间之类的间接信号来判断，这和盲注的处境是一样的。所以看到 `@` 就要意识到不能用报错来判断了。

### 7. 正则里的 `[]` 与 `+`

这是正则表达式的两个基本构件：

- `[]` 表示字符集合 / 范围：`[A-Za-z0-9]` 的意思是括号里列出的任意一个字符。`A-Z` 是大写字母范围、`a-z` 是小写字母范围、`0-9` 是数字范围，合起来就是任意一个字母或数字。
- `+` 是量词，表示前面的东西出现一次或多次（常被说成"任意多字符"，严格说是一个或多个）。

合起来，`/[A-Za-z0-9]+/` 就是匹配一个或多个连续的字母或数字。

对注入的意义：这类正则常常出现在输入过滤或白名单里。如果过滤规则写成"只允许字母数字"，那么绕过思路自然就是让 payload 里根本没有字母数字（见下面第 11 节的取反技巧）；反过来，如果正则写得不够严密（没有加锚点 `^...$`、漏掉了某种编码形式），就会出现缝隙，比如只匹配了输入的某个片段、或者放过了大小写混写。

### 8. `eval` 与"1+1 是非法输入"

`eval` 接受的是一段完整的、可执行的 PHP 代码字符串。而 `1+1` 只是一个表达式，单独拿出来构不成一条完整语句（PHP 里表达式要成为语句，末尾得有分号）。

所以 `eval("1+1")` 会得到语法错误（parse error），也就是常说的非法输入。

为什么值得记：这解释了代码执行类题目里 payload 的一个常见形态，必须写成带分号、结构完整的语句，比如：

```php
system('id');
phpinfo();
```

而不是只写一个光秃秃的表达式。同理，`布尔盲注-原理与利用` 里 `if(条件,0,1)` 那种写法之所以在 SQL 里合法，是因为 SQL 有另一套语法规则，`SELECT` 后面本来就允许接一个表达式。同一段文本在不同解释器里合法性完全不同，这正是注入类漏洞的共性（见 `与SQL注入相似的其他漏洞`）。

### 9. HTTP 参数只能是字符串：为什么 payload 要"套两层"

先看那段 payload 本身：

```text
(~%9E%8C%8C%9A%8D%8B)(~%9A%89%9E%93%D7%DB%A0%B8%BA%AB%A4%D8%9C%92%9B%D8%A2%D6);

//('assert', "eval(\$_GET['cmd'])");
//传入脚本
//your funtion--assert
//eval(\$_REQUEST['cmd'])

//assert与eval无区别
```

它由两组 `~` 取反的字节组成：

| 部分 | 十六进制字节 | 逐字节取反（`~`）后 | 得到 |
|---|---|---|---|
| 第一组（函数名） | `9E 8C 8C 9A 8D 8B` | `61 73 73 65 72 74` | `assert` |
| 第二组（参数） | `9A 89 9E 93 D7 DB A0 B8 BA AB A4 D8 9C 92 9B D8 A2 D6` | `65 76 61 6C 28 24 5F 47 45 54 5B 27 63 6D 64 27 5D 29` | `eval($_GET['cmd'])` |

连起来读，整段等价于：

```php
( "assert" ) ( "eval($_GET['cmd'])" );
// 也就是：
assert("eval($_GET['cmd'])");
```

这条链的因果可以拆成几层：

1. HTTP 传入的参数只能作为字符串量交给 PHP 引擎，所以传入的任何数据都被自动识别为字符串。`$_GET['cmd']` 拿到的东西永远是字符串类型，PHP 不会因为内容看起来像代码就执行它。
2. 因为最终要执行的是输入参数，而不是把它直接放进去，所以光把字符串放进去没用，必须有一个东西去执行它。这个角色由 `eval` 来扮演：`eval("...")` 会把字符串里的内容当 PHP 代码跑。
3. 于是需要两层：外层 `assert` 负责把字符串当代码执行，内层 `eval` 负责执行真正要执行的那段代码。
4. 在这个场景下 `assert` 与 `eval` 都能把字符串当代码跑，所以可以互换（PHP 8 以后这个前提已经变了，见注意事项）。
5. 注释里的 `//your funtion--assert`、`//传入脚本` 说明这段东西的定位是一段要被写进脚本（或被当作脚本内容送进去）的 PHP 代码，而 `assert` 是要使用的那个函数。
6. 第二组参数用的是 `$_GET['cmd']`，而注释里又写了一个 `$_REQUEST['cmd']`，两者只是取参数的来源不同（`$_GET` 只取 GET，`$_REQUEST` 兼容 GET/POST/Cookie），在这个 payload 里随便用哪个都行。

一句话总结这条链：HTTP 给的只能是字符串，想让字符串变成行为必须 `eval`，但 `eval` 是语言构造器、不能当可变函数调用，于是外面套一层 `assert`（普通函数）来承担"被字符串点名调用"的角色。

### 10. PHP 特性：可以用字符串当函数名

PHP 允许用一个求值结果是字符串的表达式，直接当作函数名来调用。下面三种写法是等价的：

```php
system("whoami");              // 普通写法
"system"("whoami");            // 用字符串字面量当函数名
("sys"."tem")("whoami");       // 先拼出 "system"，再当函数名调用
```

这就是可变函数机制（也常被称作变量函数）。要点是：函数名这个位置不要求写死一个标识符，任何能算出字符串的表达式都行，可以是字符串字面量、可以是拼接结果、也可以是某个变量。

对免杀的意义：既然函数名可以是算出来的，那就可以把函数名拆开、编码、取反，静态特征匹配就抓不到完整的 `system` 或 `assert` 字样了。上一节那段 `(~%9E%8C%8C%9A%8D%8B)(...)` 正是这套机制的直接产物，第一组取反结果 `assert` 就是算出来的函数名。

这也正是为什么外层必须是 `assert` 而不是 `eval`：外层那个位置是函数名，而这个位置要求名字能通过可变函数的方式调用，`assert` 可以（PHP 8 前是普通函数），`eval` 不行（它是语言构造器，见第 5 节）。

### 11. 取反免杀：把 payload 变成"非字母数字"

先看一个问题：是否存在某个字母或数字，对它按位取反之后，得到的仍然是字母或数字？

答案是不存在。推导如下（按 8 位 ASCII，`~x = 0xFF - x`）：

| 原字符范围 | ASCII 区间 | 取反后的区间 |
|---|---|---|
| `'0'`–`'9'` | `0x30`–`0x39` | `0xC6`–`0xCF` |
| `'A'`–`'Z'` | `0x41`–`0x5A` | `0xA5`–`0xBE` |
| `'a'`–`'z'` | `0x61`–`0x7A` | `0x85`–`0x9E` |

三个结果区间（`0x85`–`0x9E`、`0xA5`–`0xBE`、`0xC6`–`0xCF`）与字母数字区间 `0x30`–`0x7A` 完全不重叠。

所以结论是：对字母或数字取反，结果一定不是字母数字，而是高位的非打印字节。反过来看更实用：你只要挑那些取反后仍是可打印字符的字节，就能用一个纯非字母数字的 payload 还原出任意字母数字内容。

```php
// PHP 里 ~ 作用在字符串上时，是逐字节按位取反
~"\x9e\x8c\x8c\x9a\x8d\x8b";   // => "assert"
```

字节写成 `%9E` 这样的 URL 编码形式，是因为 `\x9e` 这类是不可打印字节，没法直接敲进 URL 或文本里；而 `~`、`(`、`)`、`;`、`%` 本身都是可打印字符，保持原样。

这套手法的用途：让最终出现的字符串里不含任何字母和数字，从而绕过"禁止字母数字"这类过滤规则。

### 12. 字面量与符号

- 字面量（literal）：在代码里直接把值写出来的东西，例如 `1`、`'abc'`、`0x41`、`true`。它本身就是数据，不需要再经过求值，看到它就知道它是什么。
- 符号化非字面量：凡是不是字面量的东西，都得用符号（名字）来表示。比如变量 `$a`、常量 `PHP_EOL`、函数名 `system`，写出来都是一个标识符或名字，名字本身不是值，要经过查表、求值之后才有值。
- 常量不是字面量，因为使用时用的是符号名。`PHP_EOL` 这种常量，你在代码里写的是一个符号名，引擎运行时才去查表拿到它的值（换行符），所以它不是字面量。对比一下 `true`：它在 PHP 里是关键字、也可以当值直接写出来，性质更接近字面量，两者的区别就在这里。

为什么这个区分和注入有关：过滤规则大多是在字符类别这一层做文章，允许或禁止数字、字母、某些符号。而非字面量的写法恰好大量依赖 `$`、`[`、`]`、`.`、`~`、`%` 这类符号，天然绕开了按字符类别写的规则。第 11 节的取反 payload 就是活例子：它整段由符号（`~`、`()`、`;`、`%`）和非打印字节构成，一个字母数字都没有。

## 利用条件

| 结论 | 前提 |
|---|---|
| 大小写混写可以绕黑名单 | 过滤规则按大小写敏感去匹配关键字 |
| `Content-Type` 决定解码方式 | 参数以请求体形式提交；两种编码的 payload 形态不同 |
| 注入点落在 `WHERE` 里 | 你构造的东西必须是能算出真或假的表达式 |
| `@eval` 不回显 | 代码里确实有 `@` 抑制符；此时只能靠页面差异判断 |
| `assert` 当可变函数调用 | PHP 版本 ≤ 7.x（PHP 8 起 `assert()` 不再把字符串当代码执行） |
| 取反 payload 不含字母数字 | 过滤规则是按字符类别写的；且 `~` 运算符可用 |
| 用符号绕过字符类过滤 | 过滤规则未把 `$`、`~`、`[`、`]` 等一并封禁 |

## Payload 速查

| 目的 | Payload / 写法 |
|---|---|
| 大小写混写绕关键字黑名单 | `seT`、`pRepare`、`UnIoN`、`sElEcT` |
| URL 编码的引号（传输层 → SQL 层） | `%27` → 后端得到 `'` |
| `WHERE` 里的恒真表达式 | `' OR 1=1 -- ` |
| `WHERE` 里的可控开关 | `if(条件, 0, 1)` |
| 用字符串当函数名 | `"system"("whoami");` 、`("sys"."tem")("whoami");` |
| 逐字节取反还原字符串 | `~"\x9e\x8c\x8c\x9a\x8d\x8b"` → `"assert"` |
| 取反免杀完整形态 | `(~%9E%8C%8C%9A%8D%8B)(~%9A%89%9E%93%D7%DB%A0%B8%BA%AB%A4%D8%9C%92%9B%D8%A2%D6);` |
| 正则匹配字母数字 | `/[A-Za-z0-9]+/` |

## 完整示例

### 示例 1：把那段取反 payload 读懂

```text
原始 payload（URL 编码形式）：
(~%9E%8C%8C%9A%8D%8B)(~%9A%89%9E%93%D7%DB%A0%B8%BA%AB%A4%D8%9C%92%9B%D8%A2%D6);

第一步：URL 解码，还原成原始字节
  (~\x9e\x8c\x8c\x9a\x8d\x8b)(~\x9a\x89\x9e\x93\xd7\xdb\xa0\xb8\xba\xab\xa4\xd8\x9c\x92\x9b\xd8\xa2\xd6);

第二步：`~` 对字符串逐字节取反
  \x9e\x8c\x8c\x9a\x8d\x8b
    -> 0x61 0x73 0x73 0x65 0x72 0x74  -> "assert"

  \x9a\x89\x9e\x93\xd7\xdb\xa0\xb8\xba\xab\xa4\xd8\x9c\x92\x9b\xd8\xa2\xd6
    -> "eval($_GET['cmd'])"

第三步：套用「字符串可以当函数名」这条 PHP 特性
  ( "assert" ) ( "eval($_GET['cmd'])" );
    -> assert("eval($_GET['cmd'])");      // 等价形式

第四步：语义
  外层 assert 把字符串 "eval($_GET['cmd'])" 当代码执行
  内层 eval 再去执行 $_GET['cmd'] 送进来的内容
```

### 示例 2：`WHERE` 后面要接什么

```sql
-- 合法：WHERE 后面是布尔表达式
SELECT * FROM users WHERE id = 1;
SELECT * FROM users WHERE id = 1 OR 1=1;
SELECT * FROM users WHERE id = 1 AND ascii(substr(database(),1,1)) > 100;

-- 不合法：WHERE 后面只给一个值，不构成布尔表达式
SELECT * FROM users WHERE id 1;          -- 语法错误

-- 注入时把「条件」塞进 id 的位置，就能得到一个可控的真/假开关
SELECT * FROM users WHERE id = if(1=1, 1, 0);
```

### 示例 3：同一段文本，不同解释器的合法性不同

```php
eval("1+1");        // PHP：语法错误（表达式不是完整语句）
eval("1+1;");       // PHP：合法
```

```sql
SELECT 1+1;         -- SQL：合法（SELECT 后面本来就允许接表达式）
```

这一对比正是注入类漏洞的共性所在：同一段用户输入，在一个解释器里是数据，在另一个解释器里可能是代码。详见 `与SQL注入相似的其他漏洞`。

## 注意事项

- `assert("...")` 的行为依赖 PHP 版本（重要）：把字符串参数当代码执行是 PHP 8 之前的行为；PHP 8 起 `assert()` 不再对字符串参数求值为代码。所以这条 payload 只在老版本环境（多数 CTF 老题）成立，"assert 与 eval 无区别"这个前提在新版本 PHP 上已经不成立。
- `~` 的逐字节取反是 PHP 字符串运算符的行为，作用在每个字节上，这是上面所有推导的基础。
- 取反在"哪一层"生效要看过滤器的位置：payload 是 URL 编码形式，编码后含有 `0-9`、`A-F` 这些十六进制数字和字母。如果 WAF 检查的是未解码的原始 URL，它仍会看到字母数字；只有当过滤发生在解码之后（或 payload 以原始字节写进脚本）时，"不含字母数字"这个性质才真正成立。实际使用前要先确认过滤器的位置。
- "有没有字母数字取反后仍然是字母数字"的答案是不存在，推导见第 11 节，这是可验证的算术事实，不是推测。
- 常量与关键字的语义差别：`PHP_EOL` 这类常量使用时写的是符号名，要经求值才有值；`true` 在 PHP 里是关键字，可以当值直接写出。`WHERE` 这类写法上的细节容易让人迷糊，区分两者有助于理解"符号化非字面量"的含义。
