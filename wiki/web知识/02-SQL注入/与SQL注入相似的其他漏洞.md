## 一句话概括

SQL 注入的本质是"**把用户输入的数据错误地解释为代码执行**"。凡是符合这个模式的漏洞都属于**注入类漏洞**——它们之间的区别只在于**被骗的是哪一个解释器**：数据库、操作系统外壳、浏览器、模板引擎、目录服务、XML 解析器……

## 原理

### 核心共同点：混淆"数据"与"代码"

上面所有漏洞的根源都是同一件事：

> **程序没有清晰地把用户提供的"数据"和程序要执行的"代码"分离开**，导致攻击者精心构造的"数据"被当作"代码"执行。

用 `SQL注入底层原理-解析与执行的博弈` 的话说：**代码与数据的边界被打破了**。区别只是"边界"由谁划定、由谁打破。

![SQL 注入的本质：数据越过边界变成了代码](../_assets/sql-code-data-boundary.svg)

### 各漏洞对照

| 漏洞类型 | **注入目标（解释器）** | **核心攻击原理** | **类比** |
| :--- | :--- | :--- | :--- |
| **SQLi（SQL 注入）** | **数据库** | 将恶意 SQL 代码注入到数据库查询中 | 伪造指令骗过仓库管理员 |
| **命令注入** | **操作系统外壳（Shell）** | 将恶意系统命令注入到 OS 命令中 | 在交给翻译的纸条里混入对保镖的指令 |
| **XSS（跨站脚本）** | **用户的浏览器** | 将恶意 JavaScript 代码注入到网页中 | 在寄出的信件里混入只有收信人才能执行的指令 |
| **SSTI（模板注入）** | **Web 模板引擎** | 将恶意模板语法注入到模板中 | 在交给印刷厂的稿子里混入只有印刷机才能理解的指令 |
| **LDAP 注入** | **LDAP 目录服务** | 将恶意 LDAP 查询注入到目录查询中 | 类似于 SQLi，但目标是公司的电话簿 |
| **XPath 注入** | **XML 路径语言** | 将恶意 XPath 语法注入到 XML 查询中 | 类似于 SQLi，但目标是查询一个 XML 文件 |

### 1. 命令注入

- **与 SQLi 的相似处**：SQLi 是向**数据库解释器**注入代码；命令注入是向**操作系统外壳**（如 Linux 的 `bash`、Windows 的 `cmd`）注入代码。
- **原理**：应用程序把用户输入**拼接在系统命令中并执行**。
- **例子**：一个网站允许你输入 IP 地址做 Ping 测试。
  - 正常输入：`127.0.0.1`
  - 后台命令：`ping 127.0.0.1`
  - 恶意输入：`127.0.0.1; cat /etc/passwd`
  - 后台命令：`ping 127.0.0.1; cat /etc/passwd`（这里的**分号 `;` 允许执行第二条命令**）
  - 结果：服务器执行了 `cat /etc/passwd`，泄露了系统用户信息。

> 注意这个例子和 `00` 里"堆叠注入"的结构完全同形：**都是用一个"分号"把一条语句劈成两条**。区别只是分号被谁解释——数据库还是 shell。

### 2. 跨站脚本（XSS）

- **与 SQLi 的相似处**：SQLi 是向**数据库**注入代码；XSS 是向**用户的浏览器**注入代码（通常是 JavaScript）。
- **原理**：应用程序把用户输入**未经处理直接输出到网页上**，导致输入中的 JavaScript 代码在**受害者的浏览器**里执行。
- **例子**：一个论坛允许用户发表评论。
  - 正常输入：`这个帖子真好！`
  - 恶意输入：`<script>alert('XSS');</script>`
  - 结果：其他用户访问这个页面时会弹出警告框。更危险的攻击是**窃取用户的 Cookie 会话**。

> **一个关键差异**：SQLi 的"解释器"在**服务器端**，受害者是服务器和数据库；XSS 的"解释器"在**受害者自己的浏览器里**，受害的是**其他用户**。这也是为什么 XSS 常被单独归到"客户端漏洞"里讲。

### 3. 模板注入（SSTI）

- **与 SQLi 的相似处**：SQLi 是向 **SQL 解释器**注入代码；SSTI 是向 **Web 模板引擎**注入代码。
- **原理**：现代网站常用模板引擎（如 Jinja2、Twig、Smarty）动态生成 HTML。如果用户输入被**直接拼接到模板中**，攻击者就可以注入模板的语法代码。
- **例子**（以 Jinja2 为例）：
  - 一个页面欢迎用户：`Hello, {{ username }}!`（这里 `username` 是变量）
  - 正常输入：`Alice`
  - 恶意输入：`{{ 7 * 7 }}`，或更危险的 `{{ config.items() }}`
  - 结果：页面上会显示 `Hello, 49!`，或者**泄露服务器的配置信息**。SSTI 甚至可以导致**远程代码执行（RCE）**。

### 4. LDAP 注入

- **与 SQLi 的相似处**：**几乎与 SQLi 一模一样**，只是目标换成了 **LDAP 目录服务**（常用于企业用户认证）。
- **原理**：在构建 LDAP 查询语句时，**未过滤的用户输入被拼接进去**。
- **例子**：
  - 登录时，后台构建的 LDAP 查询可能是：`(&(username=【输入】)(password=【输入】))`
  - 恶意输入：在用户名输入框里填 `*)(|(uid=*))`，可能构造出 `(&(username=*)(|(uid=*))(...))`，从而**绕过认证**。

> 和 SQLi 的登录绕过对照看，思路完全一致：**用括号和逻辑运算符提前闭合 / 补上一个恒真条件**。

### 5. XPath 注入

- **与 SQLi 的相似处**：可以看作针对 **XML 数据**的"SQL 注入"。
- **原理**：如果应用程序使用用户输入来构建 XPath 查询（用于在 XML 文档里查找信息），攻击者可以注入 XPath 语法来改变查询逻辑。
- **例子**：逻辑与 SQLi 绕过登录**非常相似**。

### 6. 代码注入 / 反序列化漏洞

- **与 SQLi 的相似处**：这是**更广义**的注入，目标是应用程序本身的**编程语言解释器**（如 PHP、Python、Java）。
- **原理**：
  - **代码注入**：用户输入被传递给某些**能执行代码的函数**（如 PHP 的 `eval()`），导致任意代码执行。
    > 这条正是 `SQL注入核心概念速记` 里 `eval` / `assert` 那一大段的归属地。
  - **反序列化注入**：用户可控的**序列化数据**被程序反序列化时，会**触发恶意的对象构造和方法调用**，导致代码执行。

## 利用条件

| 漏洞 | 什么条件下成立 |
|---|---|
| 命令注入 | 用户输入被拼接进要执行的系统命令；拼接位置能让 `;`、`` ` \| ` ``、`&&`、`$()` 等起到"另起一个命令"的作用 |
| XSS | 用户输入被**输出**到 HTML 且未做转义；存在其他用户会看到这个输出 |
| SSTI | 用户输入被**拼进模板字符串**（而不是作为"模板变量"传入）；模板引擎支持执行表达式 |
| LDAP 注入 | 用户输入被拼进 LDAP 查询过滤器；目录服务用的是 LDAP 认证 |
| XPath 注入 | 用户输入被拼进 XPath 表达式；后端用 XML 存数据 |
| 代码注入 | 存在 `eval` 一类的"把字符串当代码跑"的入口 |
| 反序列化 | 存在 `unserialize` / `readObject` 一类的反序列化入口，且**类库里存在可利用的"魔术方法"链** |

它们的共同前提只有一句话：**必须存在"用户可控数据"与"会被执行/解释的代码"之间的直接拼接**，且中间没有做参数化、转义或白名单。

## Payload 速查

| 漏洞 | Payload 示例 |
|---|---|
| SQL 注入 | `admin' OR '1'='1' -- ` |
| 命令注入 | `127.0.0.1; cat /etc/passwd`、`` 127.0.0.1 \| id ``、`` 127.0.0.1 `id` ``、`127.0.0.1 && id` |
| XSS | `<script>alert(1)</script>`、`<img src=x onerror=alert(1)>` |
| SSTI（Jinja2） | `{{ 7*7 }}`、`{{ config.items() }}`、`{{ ''.__class__.__mro__ }}` |
| LDAP 注入 | `*)(\|(uid=*))` |
| XPath 注入 | `' or 1=1 or ''='`、`' or '1'='1` |
| 代码注入 | `eval($_GET['cmd'])`、`assert("eval($_GET['x'])")` |
| 反序列化 | 构造恶意序列化串（PHP `O:...`、Java 序列化字节流） |

> 上表中除 SQL 注入、命令注入、XSS、SSTI、LDAP 之外的行是按各自漏洞的**通用形态**补齐的示例；原文对 XPath 与反序列化只给了原理描述，没有给具体 payload。

## 完整示例：同一个"分号"，骗了两个解释器

**场景一：向数据库注入（SQLi）**

```text
用户输入：1; DROP TABLE users
拼出的语句：SELECT * FROM news WHERE id = 1; DROP TABLE users
分号被谁解释：数据库（需要驱动支持多语句，见 00 第 6.4 节）
```

**场景二：向操作系统外壳注入（命令注入）**

```text
用户输入：127.0.0.1; cat /etc/passwd
拼出的命令：ping 127.0.0.1; cat /etc/passwd
分号被谁解释：shell
```

**场景三：向模板引擎注入（SSTI）**

```text
用户输入：{{ 7*7 }}
拼出的模板：Hello, {{ 7*7 }}!
双花括号被谁解释：模板引擎
```

三段输入的**字符形态几乎不相关**（`'`、`;`、`{{}}`），但**攻击模型完全一致**：

```text
用户可控数据  --拼接-->  解释器输入  --解析-->  其中一部分变成了代码
                          ^
                    问题就出在这一步：
                    拼接时没有把"数据"钉死在数据的位置上
```

## 踩坑与备注

- **原文开篇点明**："**从安全角度来看，SQLi 的本质是将用户输入的数据错误地解释为代码执行**"——这是全篇的立论基础，也是把这一整类漏洞串起来的唯一逻辑线索。
- **原文对 XPath 注入只写了"逻辑与 SQLi 绕过登录非常相似"**，没有给具体例子。本次也没有替它编造 payload 细节，只补了一个通用形态的示例，并在此注明：**XPath 的具体绕过语法请以实际题目为准**。
- **反序列化被原文归入"代码注入"这一大类的子项**，但它在实战里的分量其实很重（有专门的魔术方法链 / gadget 链），这里按原文的归类保留。
- **XSS 和 SQLi 虽然同属"注入"，但受害对象不同**：SQLi 骗的是**服务端的数据库**，XSS 骗的是**受害者的浏览器**。做题时不要把"用的是同一套'数据当代码'逻辑"误当成"利用手法可以照搬"。
- **SSTI 的前提容易被忽略**：只有当用户输入被**拼进模板**（而不是作为模板变量 `{{ username }}` 的值传进去）时才有注入——这一点和 SQL 的参数化查询是同一个道理：**把数据绑定成"值"，它就永远只是值**。
- 相关篇目：`SQL注入底层原理-解析与执行的博弈`（本类漏洞的通用原理）、`SQL注入核心概念速记`（`eval` / 代码注入的细节）。
