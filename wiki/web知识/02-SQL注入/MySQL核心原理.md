## 一句话概括

一条 SQL 语句要经过解析器（词法分析 + 语法分析）和预处理器（语义检查 + 权限验证）才会被执行；注入之所以能发生，就是因为解析发生在拼接之后。反过来，只要代码里用了 prepare 预处理，攻击者就无法提前闭合，SQL 注入不存在。

## 原理

### 1. 整体架构

MySQL 可以粗略地分成上下两层：

| 层 | 组成 | 说明 |
|---|---|---|
| 上层 | 客户端、连接器 | 面向"调用方"的一层 |
| 下层 | 服务器层（服务器本体 + 存储引擎 + 连接管理） | 真正解析与执行 SQL 的一层 |

其中有两个部件常被单独提起：

- 引擎：MySQL 里真正负责存取数据的部件。MySQL 的一大特点是存储引擎可插拔，同一套 SQL 前端，底下可以换不同的引擎。
- 连接池：连接是昂贵的资源，反复"建立—断开"开销很大，所以把连接复用起来，池化保存；应用取用一个、用完归还，而不是每次新建。

### 2. 客户端与连接器

- 客户端是用户与服务器交互的接口，扮演发起请求的角色：它把用户的指令收下来、整理好、交给服务器；服务器算完之后，结果也由它接回来呈现给用户。
- 连接器类似于 `stdio.h`，实现直接调用的功能，而无需管怎么实现。C 语言里写 `printf()` 只需要 `#include <stdio.h>`，不必知道字符最终是怎么落到屏幕上的，stdio 把底层细节包住了。同理，连接器把"怎么和 MySQL 服务端建立连接、握手、认证、收发协议包"这些细节封装起来，上层的调用方只要调用即可，不需要自己实现网络协议。

### 3. 谁在扮演"SQL 客户端"

扮演 MySQL 客户端的是 Web 后端（网页服务器），不是浏览器。

这中间有两套完全不同的"客户端/服务端"关系，初学时最容易把它们混成一件事：

| 关系 | 客户端 | 服务端 | 用什么协议 |
|---|---|---|---|
| Web 请求 | 浏览器（Web 客户端） | Web 后端 / 网页服务器 | HTTP |
| 数据库访问 | Web 后端（此时它是"SQL 客户端"） | MySQL 服务端 | MySQL 自己的协议 |

由此可以看清几件事：

- 浏览器只会说 HTTP，它根本不会说 MySQL 的协议，也没有数据库的账号密码；
- 真正拿账号密码去连数据库、并把 SQL 发过去的是 Web 后端；
- 攻击者做的事情，是通过 HTTP 把恶意内容塞给 Web 后端，再借后端之手把这条被污染的 SQL 发给数据库。

这就是为什么"注入点在参数里"而不是"在浏览器里"：浏览器只是传话的，真正拼接和执行发生在后端。

### 4. 为什么不能从外部直接访问数据库

正常情况下，数据库端口不应该对外网开放。挡住"外部直接访问"的东西有两类：

1. 网络层 / 部署层：数据库通常只监听内网地址，或只允许 Web 后端所在的主机连入，外网根本连不上。
2. WAF 层：应用防火墙会对经过的 HTTP 流量做规则匹配与拦截。这也是为什么注入 payload 常常要变形（编码、大小写混写、十六进制、注释分割）才能穿过去。

反过来说，一旦真的能从外部直接连上数据库（比如弱口令加端口暴露），就不需要"注入"了，直接连上去查就行。注入存在的意义，正是绕过这道"不让我直接连"的墙。

### 5. 解析器 Parser：词法分析与语法树

解析器负责把一串字符变成结构，分两个阶段：

1. 词法阶段（词法分析）：把整条 SQL 字符串扫描一遍，切分成一个个有意义的模块，也就是 token。比如 `SELECT * FROM users` 会被切成 `SELECT`、`*`、`FROM`、`users` 这样的 token。
2. 语法分析（syntax）：把这些 token 组合成一棵解析树，用树形、层次化的结构来描述各 SQL 成分之间的关系，谁是子句、谁是谁的定语。

如果 SQL 语句存在错误，解析器会在这个阶段报错。这也是注入时判断"语句拼得对不对"的主要反馈来源，语法报错注入就建立在这上面。

![SQL 在 MySQL 里的解析与执行流水线](../_assets/sql-parser-pipeline.svg)

关键点在于，解析器面对的只是"字符串"，它不区分字符的来源。所以攻击者只要拼接进来的内容语法合法，就会被一并纳入解析树，这就是 `SQL注入底层原理-解析与执行的博弈` 全篇讲的那件事。

### 6. 预处理器

预处理器接收的是已经成形的解析树（此时语法已经没问题了），它负责语义层面的把关：

1. 语义检查：检查解析树上的内容是否都存在。例如你在语句里引用了 `flag` 这张表，解析器不在乎它存不存在（它只管语法），预处理器才去查，表不存在、列不存在、函数不存在，都是在这一步报错。
2. 权限验证：检查当前这个数据库用户有没有权限去做这件事。例如读某张表、读文件（`FILE` 权限）、写文件，都是在这一步被裁决。

这一步对注入的意义是：语法正确不等于能执行。你拼出来的语句语法一定得过解析器，但过不过得了预处理器，取决于你用的名字是否真实存在、当前账号是否有权限。这就是为什么"报错注入"和"能不能读写文件"是两回事。

### 7. 用"有没有 prepare"判断有没有注入

做代码审计时，看到一个注入点先别急着下结论，先看这个位置有没有用 `prepare`（预处理 / 参数化查询）：

- 如果用了 `prepare`，SQL 模板会先被解析，数据在解析之后才绑定到占位符上，数据永远进不了词法分析；
- 既然数据进不了语法结构，攻击者就无法提前闭合引号（引号也是被绑定的数据的一部分，不再具有语法意义）；
- 因此结论是：用了 prepare 且绑定方式正确的点，不存在 SQL 注入。

反过来，只要看到的是字符串拼接（动态 SQL），就存在注入的可能。

注意措辞：这是一个否定性判据，"有 prepare 就不存在 sqli"是充分条件，不能反过来说"所有注入都是因为没 prepare"。

### 8. 传统手法与堆叠注入

- 报错注入（error）、布尔盲注（bool）、时间盲注（time）是"没有正常回显位"时的三种标准出路，具体做法见 `SQL注入底层原理-解析与执行的博弈` 第 6 节与 `布尔盲注-原理与利用`。
- 堆叠注入用分号 `;` 堆叠多条语句，前提是驱动打开了多语句支持，详见 `SQL注入底层原理-解析与执行的博弈`。

## 利用条件

| 结论 | 前提 |
|---|---|
| 解析器会"照单全收" | 拼接发生在解析之前；注入片段的语法合法 |
| 预处理器会放行 | 引用的表 / 列 / 函数真实存在，且当前用户有权限 |
| 能判断"这里有没有注入" | 代码里是字符串拼接而非 `prepare` |
| 能绕开外部的"墙" | 目标数据库端口不直接对外；payload 需要能穿过后置的 WAF |

## Payload 速查

| 目的 | 做法 |
|---|---|
| 探测注入点是否在语法层可控 | `'` / `"` / `)` 丢进去，看是否触发语法报错 |
| 观察解析器报错（报错注入入口） | `1'` 看措辞是"语法错误"还是"表不存在"，前者来自解析器，后者来自预处理器 |
| 确认参数化是否真的生效 | 用 `'` 试，若始终不报错且行为不受影响，多半是 `prepare` 绑定了 |
| 试探权限（预处理器把关项） | `SELECT LOAD_FILE('/etc/passwd')`、`SELECT ... INTO OUTFILE '...'` |
| 堆叠多语句 | `1'; SELECT ...;--`（需驱动支持） |

## 完整示例：一个 `'` 打过去，报错来自哪一层

```text
输入：1'  （注入点原本是 WHERE id = 1）

情况 A：报错 "You have an error in your SQL syntax near ''1'' at line 1"
        -> 来自【解析器】的语法错误
        -> 说明输入确实被拼进了 SQL，且没有经过 prepare  -> 存在注入

情况 B：报错 "Table 'db.xxx' doesn't exist"
        -> 来自【预处理器】的语义检查
        -> 说明语法已经通过，是名字或权限的问题  -> 语法层可控

情况 C：页面毫无变化、行为与不输入时一致
        -> 很可能用了 prepare，数据被当成纯值绑定
        -> 该点基本不存在注入
```

同样是"报错"，报错来自哪一层给出了完全不同的信息，这是这套架构知识最直接的用处。

```text
数据库视角的一条语句：
   字符串
     |  解析器：词法分析 -> 语法分析（语法错误在这里报）
     v
   解析树
     |  预处理器：语义检查 -> 权限验证（表/列不存在、无权限在这里报）
     v
   执行计划 -> 执行器 -> 结果集
```

## 注意事项

- `prepare` 判据是充分条件而非必要条件：反过来"没有 prepare 就一定有注入"并不总成立，因为还可能存在白名单、强类型转换等其它防护。做审计结论时不要把充分条件和必要条件搞混。
- 存储引擎可插拔、连接池这两个概念属于通用的数据库背景，与注入本身没有直接关系，但理解了"谁在管连接"有助于看清连接池耗尽一类的问题。
