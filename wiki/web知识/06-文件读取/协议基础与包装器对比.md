## 一句话概括

本篇是本分区的**前置章节**：先把「协议」「路径」这两个概念摆正，再对比 `file://`、`dict://`、`ftp://`、`http://` 以及 PHP 的一众**包装器**各是什么、能干什么。理解了这一层，`php://filter`、`data://`、`phar://` 这些名字就不再是死记硬背。

## 原理

### 1. 网络协议是什么

**网络协议决定数据在两台设备之间运输的方式。**

可以把网络协议理解成一本**多国语言对照的物流规则手册**，它规定了：

- **如何打包**：数据如何分成包、如何封装（TCP 分段、IP 分片）；
- **如何写地址**：地址格式是什么（IP 地址、MAC 地址、端口号）；
- **如何交互**：双方如何建立连接、如何确认收货、如何重发丢失的包裹、如何结束对话（TCP 三次握手、ACK 确认、重传机制）；
- **如何路由**：包裹上应该写哪些信息，以便路由器进行转发。

**网络协议共同定义和管理的规则，确保了数据能够在两台设备间有效、可靠、有序地传输。**

### 2. 跨平台与「编译」的直觉

在进入分层模型之前，先建立一个直觉：**同一份代码，在不同平台上的「可执行形态」不同。**

| 语言 | 编译产物 | 跨平台方式 |
|---|---|---|
| C / C++ | 平台对应的**可执行文件** | 换平台要**重新编译** |
| Java | **字节码**（无法直接执行） | 交给目标平台的 **JVM** 加载执行 |

- C/C++ 编译后生成的是**平台专有的可执行文件**，所以「跨平台」要靠**为每个平台各编译一份**；
- Java 编译后的**字节码文件**无法直接执行，需要服务器 / 运行环境**开启自身的 JVM** 来加载它 —— 这就是著名的「一次编译，到处运行」。

> 此处原为「C/C++ 跨平台编译」与「Java 字节码经 JVM 执行」的两张截图，要点即上表内容：编译型语言产出平台原生文件，Java 产出中间字节码由 JVM 承载。

### 3. 服务器、客户端与「协议」

- **服务器与客户端**：网络通信的双方，靠**端口**区分服务、靠**协议**约定格式；
- **协议**：约定**客户端发送请求的格式与方式**。例如 HTTP 规定了请求行、请求头、请求体的写法。

### 4. OSI 七层模型

| 层级 | 名称 | 功能描述 | 关键协议 / 设备 | 数据单位 |
|---|---|---|---|---|
| **7** | **应用层** | 为**应用程序**提供网络服务接口，是用户与网络交互的界面 | HTTP, HTTPS, FTP, SMTP, DNS, SSH | **Data** |
| **6** | **表示层** | 负责**数据格式转换**：加密解密、压缩解压缩、编码转换 | SSL/TLS, MPEG, JPEG | **Data** |
| **5** | **会话层** | 负责建立、管理和终止**会话**，区分不同应用的通信流 | NetBIOS, RPC | **Data** |
| **4** | **传输层** | 提供**端到端**的可靠或不可靠传输，负责流量控制、差错校验、数据重发 | **TCP**（可靠）, **UDP**（不可靠） | **Segment** (TCP) / **Datagram** (UDP) |
| **3** | **网络层** | 负责**逻辑寻址**和**路由选择**，跨网络把数据包送达目的主机 | **IP**, ICMP, RIP, OSPF, **路由器** | **Packet** |
| **2** | **数据链路层** | 负责**同一局域网内**节点间传输，做**物理寻址**（MAC）和差错控制 | Ethernet, PPP, Switch, Bridge | **Frame** |
| **1** | **物理层** | 定义物理设备的电气、机械规格，传输**比特流**（0 和 1） | RJ45, 光纤, 同轴电缆, 集线器 | **Bit** |

**核心思想**：每一层都为其**上一层**提供服务，并且只关心与**对等层**（Peer Layer）之间的通信。例如发送方的「传输层」认为自己在和接收方的「传输层」直接对话；实际上数据是**垂直向下封装**，传输之后在接收端**垂直向上解封**。

### 5. OSI 与 TCP/IP 模型

OSI 是一个**理论模型**；实际中广泛使用的是 **TCP/IP 模型**（互联网协议套件）。

| OSI 参考模型 | TCP/IP 模型 | TCP/IP 协议族 |
|---|---|---|
| 应用层、表示层、会话层 | **应用层** | HTTP, FTP, DNS, SMTP |
| 传输层 | **传输层** | TCP, UDP |
| 网络层 | **网络层** | IP, ICMP |
| 数据链路层、物理层 | **网络接口层** | Ethernet, Wi-Fi |

**一次请求的过程**，概括成六个字：**先封装、再运输、后拆解。**

```text
发送方：应用数据 → 逐层加头封装 → 变成比特流发出
                  ↓ 网络传输
接收方：比特流 → 逐层去头解封 → 还原成应用数据
```

> 此处原为「请求过程封装 / 解封」的截图，要点如上：数据在发送端自上而下逐层封装，在接收端自下而上逐层拆解。

### 6. DNS 与域名

**DNS（域名系统）** 的核心功能是进行**域名与 IP 地址之间的相互解析**。

- **域名**：人类容易记忆的网站地址（如 `www.google.com`）；
- **IP 地址**：计算机在网络上的唯一逻辑地址（如 `142.251.42.206`）。

**DNS 的作用就是充当「翻译官」**，把人类友好的域名转换成机器可识别的 IP 地址，从而建立连接。类比：**域名像通讯录里的联系人姓名，IP 是实际电话号码** —— 你只需记住名字。

以 `www.google.com` 为例，从右往左读：

| 部分 | 名称 | 描述 | 例子 |
|---|---|---|---|
| 最右侧 | **根域** | 通常为空，用点表示，末尾常省略 | （隐含的 `.`） |
| 右侧第一部分 | **顶级域** | 代表国家/地区或组织类型 | `.com` |
| 右侧第二部分 | **二级域** | **你注册的独一无二的域名**，是域名的核心身份 | `google` |
| 左侧部分 | **子域名** | 在域名下创建独立分区或服务 | `www` |

> 此处原为「域名层级结构」的截图，要点即上表：从右向左依次是根域、顶级域、二级域、子域名。

### 7. URL 与路径

**URL** 是完整的网页地址，包含访问资源所需的全部信息：

```text
https://www.google.com/search?q=hello
└─┬──┘ └─────┬──────┘ └──┬──┘└──┬───┘
 协议        域名        路径    参数
```

**路径**是一个字符串，描述文件或目录在文件系统中的**具体位置**，或资源在某服务中的**访问地址**。简单说：**路径就是「怎么找到你想要的东西」的路线说明。** 分两大类：

**① 文件系统路径**

**绝对路径** —— 从**根目录**开始，完整描述文件位置：

| 系统 | 示例 | 起点 |
|---|---|---|
| Linux / macOS | `/home/user/documents/report.pdf` | 根目录 `/` |
| Windows | `C:\Users\User\Pictures\photo.jpg` | 驱动器盘符 `C:\` |

特点：**唯一性** —— 无论当前在哪，绝对路径都指向同一个目标。

**相对路径** —— 以**当前工作目录**为起点描述位置：

```text
documents/report.pdf     # 当前目录下的文件
../downloads/file.zip    # ../ 表示上级目录
./project/script.py      # ./ 表示当前目录（通常可省略）
```

特点：**更简短，但依赖当前所在的位置**。

**② URL 路径（网络路径）**

URL 中位于**域名之后、参数之前**的部分：

| 示例 | 路径 | 指向 |
|---|---|---|
| `https://www.google.com/search` | `/search` | 搜索功能 |
| `https://github.com/torvalds/linux` | `/torvalds/linux` | 特定代码仓库 |
| `https://example.com/images/logo.png` | `/images/logo.png` | 一张图片 |

> **注意**：URL 路径是「相对网站根目录」的，它**不等于**服务器上的物理路径。`/images/logo.png` 在服务器上可能是 `/var/www/html/images/logo.png` —— 两者的对应关系见 `05-文件包含\文件包含题解综合.md`。

### 8. 几种常用命令（DNS 相关）

```bash
ping <域名或IP地址>
```

`ping www.example.com` 实际上在做三件事：

1. **测试连通性**：能否与目标服务器建立通信；
2. **测量延迟**：数据包往返所需时间（毫秒）；
3. **DNS 解析验证**：域名能否被正确解析为 IP。

```bash
ipconfig /displaydns     # 查看 DNS 缓存
ipconfig /flushdns       # 清理 DNS 缓存
nslookup 域名            # 域名解析查询
```

| 特性 | `nslookup 域名` | `ping 域名` |
|---|---|---|
| **核心功能** | **域名解析查询** | **网络连通性测试** |
| **回答的问题** | 「这个域名对应哪个 IP？」 | 「我能和它通信吗？延迟多大？」 |
| **使用协议** | **DNS** | **ICMP** |
| **工作层级** | 应用层 | 网络层 |
| **主要输出** | IP 地址、权威 DNS 服务器、记录类型 | 连通状态、延迟、丢包率 |
| **依赖关系** | —— | 隐含地先做了一次 DNS 查询 |

### 9. `file://` 是协议吗

`file://` 常被叫做「协议」，但它**不涉及网络通信** —— 这是最根本的一点：

| 方面 | 真正的网络协议 | `file` URI 方案 |
|---|---|---|
| **通信范围** | 网络中 between hosts | 单机内部 on the same host |
| **底层机制** | 使用 TCP/IP 等网络栈 | 使用操作系统**文件系统 API** |
| **交互模型** | 客户端-服务器请求/响应 | 本地函数调用 / 资源访问 |
| **功能复杂性** | 相对复杂，特性丰富 | 极其简单，主要是读写 |

| 特性 | `file://` 协议 | `http://` 协议 |
|---|---|---|
| **数据位置** | **本地硬盘**（你自己的 C 盘） | **远程服务器**（对方主机的硬盘） |
| **请求过程** | 调用本地操作系统 API | 通过网络发送 TCP/IP 数据包 |
| **数据所有权** | **你自己的数据** | **对方主机提供的数据** |

`file://` 的主要用途：**在不依赖网络服务器的情况下，直接通过浏览器访问、查看和测试本地文件资源。**

1. **本地 Web 开发与测试**（最核心）：前端写完 HTML/CSS/JS，用 `file://` 打开 `.html` 就能看到渲染效果，不用配服务器；
2. **充当通用文件查看器**：`file:///C:/Reports/report.pdf`、`file:///D:/Videos/my_video.mp4`、`file:///home/user/notes.txt`；
3. **构建简单的本地数据驱动页面**：用 JS 图表库读本地 `data.json` / `.csv` 生成可视化。

### 10. `dict://` 协议

`dict://` 的设计初衷是**查询字典数据库（DICT 服务，默认端口 2629）**：

| 命令 | URL 示例 | 功能 |
|---|---|---|
| **DEFINE** | `dict://server/d:word` | 获取单词的详细定义 |
| **MATCH** | `dict://server/m:word` | 查找拼写相似的词 |
| **SHOW** | `dict://server/show:db` | 显示服务器可用的词典列表 |
| **INFO** | `dict://server/info` | 显示 **DICT 服务器自身**的信息（不是浏览器页面的信息） |

它的「变异」用途出现在安全领域：**把 `dict://` 指向一个非 DICT 服务的主机，它也会尝试建立 TCP 连接** —— 于是可以用来**探测端口是否开放**、或向特定端口的服务发送一段可控数据。

> 注意：`dict://baidu.org/info` 这类请求几乎注定失败 —— `dict://` 要求目标上运行着 2629 端口的 DICT 服务，而 Web 服务器只提供 80/443 的 HTTP/HTTPS。

### 11. `ftp://` 协议

**FTP 的核心工作是「在网络上搬运文件」**：

| 场景 | 具体干什么 |
|---|---|
| 网站更新与维护 | 把网页、图片、代码从本地**上传**到服务器（最经典的用途） |
| 软件下载站 | 提供大型文件（系统镜像、安装包）的下载 |
| 公司内部文件共享 | 内网 FTP 服务器作为公共存储和交换中心 |
| 个人数据备份 | 把重要数据备份到远程 FTP 服务器 |

与 HTTP 的区别，用两个比喻最清楚：

- **HTTP（用于上网）**：像去**书店买书** —— 你告诉店员要哪本，他把书给你看，**重点是「浏览和阅读」**；
- **FTP（用于文件管理）**：像去**仓库管理货物** —— 可以搬进（上传）、搬出（下载）、还能改名 / 删除 / 建目录，**重点是「文件的来回搬运和管理」**。

**URL 格式：**

```text
ftp://[用户名[:密码]@]主机名[:端口]/路径/文件名
```

| 组成部分 | 说明 | 可选性 | 示例 |
|---|---|---|---|
| `ftp://` | **协议标识符** | **必选** | `ftp://` |
| `用户名` | 登录 FTP 服务器的账号 | 可选 | `admin` |
| `密码` | 对应用名的密码 | 可选 | `pass123` |
| `@` | 分隔认证信息和主机 | 与认证信息共存 | `@` |
| `主机名` | 域名或 IP 地址 | **必选** | `ftp.example.com` |
| `:端口` | 控制端口 | 可选（默认 `21`） | `:2121` |
| `/路径/` | 服务器上的目录路径 | 可选 | `/pub/downloads/` |
| `文件名` | 要访问的具体文件 | 可选 | `software.zip` |

### 12. 「HTTP 伪协议」

严格说，HTTP 是标准协议；所谓「HTTP 伪协议」指的是**对 HTTP 的非标准实现 / 滥用**：

- **真正的 HTTP**：双方都严格遵守 RFC —— 客户端发 `GET /index.html HTTP/1.1`，服务器回 `HTTP/1.1 200 OK`；
- **「伪」HTTP**：其中一方（通常是服务端）不按标准来 —— 可能用**自定义请求方法**（不是 GET/POST/PUT）、**自定义协议版本**（如 `CUSTOM/1.0`）、或返回**非标准状态码 / 格式混乱的响应头**。

安全测试里它的价值在于：**用非标准请求去探服务端的容错边界**，往往能发现隐藏的接口或行为。

### 13. PHP 包装器（`php://`）

PHP 官方称这一系列为**「封装协议」**：它们是一批「类 URL 的包装器」，让标准的文件系统函数（`fopen()`、`include()`、`file_get_contents()` 等）能够访问各种数据流和资源。

| 协议 | 功能描述 | 经典利用场景 | 安全风险 |
|---|---|---|---|
| **`php://input`** | 访问**原始 HTTP POST 请求体** | `file_get_contents('php://input')` 拿到请求体后 `eval()` → 代码执行 | **高危**：可直接注入并执行 PHP 代码 |
| **`php://filter`** | 对数据流做**过滤处理**（如 Base64 编码） | `?page=php://filter/read=convert.base64-encode/resource=index.php` → 读源码 | **中危**：信息泄露，可读任意 PHP 文件源码 |
| **`data://`** | 直接嵌入数据，格式 `data://[MIME][;base64],数据` | `?page=data://text/plain,<?php phpinfo();?>` | **高危**：把恶意代码直接嵌入 URL 执行 |
| **`phar://`** | 访问 **PHAR 归档**（PHP 打包格式）内的文件 | `?file=phar:///path/to/a.phar/x.txt`，**即使外层后缀是 `.jpg`**，内容符合 PHAR 格式即可 | **高危**：常用于触发反序列化 |
| **`zip://`** | 访问 **ZIP 归档**内的文件 | `?file=zip:///path/to/a.zip%23shell.php`（`#` 要编码成 `%23`） | **中危**：配合文件上传，绕过对直接上传脚本的限制 |
| **`glob://`** | 查找匹配模式的文件路径 | `foreach(glob("glob:///var/www/tmp/*.txt") as $f){...}` | **低危**：信息收集，探测目录结构 |

**关于 `php://input` 的一个常见误解**：它**本身就是一个完整、独立的资源标识符**，使用方式是**作为 `file_get_contents()` / `include()` 等函数的直接参数**；在漏洞利用中，它是**作为一个「值」通过 GET/POST 参数传给程序**，而不是「挂在某个东西后面」。

### 14. 端口对照

每种应用层协议通常与一个**默认 TCP 端口**绑定：

| 协议 | 默认端口 |
|---|---|
| `http://` | 80 |
| `https://` | 443 |
| `dict://` | 2629 |
| `ftp://` | 21 |

**错误地使用协议去访问**（例如把 `dict://` 指向一个非 DICT 的 IP），它也会尝试与目标建立连接 —— 这个特性可用来**判断端口是否工作**（属于 SSRF 场景的常见技巧，详见 `08-SSRF` 分区）。

## 利用条件（什么时候会用到这些基础）

1. 需要**判断一个 URL / 参数的协议类型**，从而决定走哪条读取路径；
2. 需要**区分绝对路径与相对路径**，避免路径写错（见 `file协议与路径写法.md`）；
3. 需要**理解包装器的能力边界**，从而在 `php://filter`、`data://`、`phar://` 之间做选择；
4. 需要**用错的协议去探端口**（SSRF / 端口探测场景）。

## Payload / 速查

| 目的 | 写法 |
|---|---|
| 读本地文件（最简） | `/etc/passwd` |
| 读本地文件（显式协议） | `file:///etc/passwd` |
| 读源码 | `php://filter/convert.base64-encode/resource=index.php` |
| 内联代码 | `data://text/plain,<?=system("id");?>` |
| 读请求体 | `php://input`（配 POST） |
| 读归档内文件 | `zip:///tmp/a.zip%23shell.php`、`phar:///tmp/a.phar/x.txt` |
| 查目录下文件 | `glob:///var/www/tmp/*.txt` |
| 探端口（SSRF） | `dict://127.0.0.1:2629/info`、`ftp://127.0.0.1:21/` |

- **`file://` 严格说不是「协议」**：它绕过网络栈，直接调用操作系统的文件系统 API。叫它「本地 URI 方案」更准确。
- **端口只是「默认值」**：`http://` 不等于一定走 80，写 `:8080` 就走 8080；端口对照表的用途是「不知道写什么时先试默认值」。
- **`phar://` 的触发与文件后缀无关**：只要**内容**符合 PHAR 格式，即使文件名是 `.jpg` 也能触发反序列化 —— 这是文件上传 + `phar://` 组合拳的基础。
