## 一句话概括

序列构造是把一串标准事件切成模型能吃的固定形状样本：每 N 条消息一个窗口，相邻窗口按 stride 滑动，窗口内每条消息再编码成定长 token 序列。切法的每一步都在拿上下文完整性和样本数量做交换。

## 窗口从哪里切

定义：窗口是一条或若干条连续事件的子序列，是模型一次推理的最小单位。序列异常检测不按单条日志判断，因为单条正常消息放进错误上下文里就是异常，判据只在序列上成立。

切窗的第一个约束是不得跨 group 切。group 可以是 campaign、session、timeline，也可以是 host_id + root_pid。一条窗口里混进两条不相干的时间线，模型会看到一段现实中不存在的因果链。

第二个约束是滑窗参数。常见的一组取值：

- `max_seq_len = 128`
- 其中 126 条真实事件，加上 `[CLS]` 和 `[SEP]` 各一
- `stride = 64`
- `min_real_events = 8`

stride 取窗口的一半，是两个目标的折中。取 stride = 窗口长度就是不重叠切分，样本数最少；取 stride = 1 则相邻窗口几乎相同，样本数暴涨但信息量几乎不增。半窗口重叠让一个事件至少出现在一个完整窗口的中部，不至于永远被切在边界上。

`min_real_events = 8` 管的是尾部。文件末尾常常剩几条事件凑不满一个窗口，直接右补 PAD 会在训练集里塞进大量近乎空的样本，模型会把"窗口很空"当成正常模式学下来。少于 8 条真实事件的窗口直接丢弃。

注意：stride 小于窗口长度时，同一个事件必然出现在多个窗口里，样本之间不再独立。做事件级分析（比如统计某个事件被判定为异常的频次）必须按 event_id 去重，否则重叠区的权重会被重复计算。

窗口长度本身也是取舍。窗口越长，跨事件的因果链越完整，一条攻击链不容易被边界切断；代价是单次推理的算力里注意力项随长度平方增长，且短序列要补更多 PAD。主机行为日志里一次入侵往往横跨几十到上百条事件，窗口长度要能覆盖住这个跨度才有意义。

## 一个窗口长什么样

sequence 记录的字段分组：

| 字段组 | 内容 |
| --- | --- |
| 身份 | `schema_version`、`sequence_id`、`source_dataset`、`split` |
| 窗口元信息 | `strategy`、`group_key`、`timeline_id`、`host_id`、`root_pid`、`start/end_event_index`、`start/end_time`、`max_seq_len`、`stride` |
| 人类可读 | `messages`（规范化后的消息文本）、`tokens`（structured token 串） |
| 模型输入 | `input_ids`、`attention_mask` |
| 追溯 | `event_ids`、`raw_event_ids` |
| 辅助 | `event_type_ids`、`time_delta_ids`、`process_depth_ids` |
| 标签 | `label` |
| 统计 | `stats`（各类型事件计数、`unk_ratio`、`truncated`） |

三条强约束：

- `tokens` / `input_ids` / `attention_mask` / `event_ids` / `raw_event_ids` 五者长度必须相等
- `input_ids[i] == 0` 与 `attention_mask[i] == 0` 必须互为充要（0 是 `[PAD]`）
- special token 位置的 `event_id` 与 `raw_event_id` 必须为 null

前两条保证张量对齐与 mask 语义一致，第三条是追溯性的要求：`[CLS]` 不对应任何真实事件，给它编一个 event_id 会让"这条告警对应哪条原始日志"这个问题得到错误答案。

## 为什么定成 256 × 64

窗口参数最终会落成一组固定的张量形状：

```text
message_input_ids       int64 [B, 256, 64]
message_attention_mask  int64 [B, 256, 64]
sequence_attention_mask int64 [B, 256]
```

固定形状是为了让 ONNX 只把 batch 维留成动态。动态形状会让 ONNX Runtime 无法预先规划内存、无法把形状相关的优化做死，每一次形状变化都可能触发重新分配。序列长度固定在 256、消息长度固定在 64 之后，运行时只剩 batch 一个变量。

代价是变长序列必须补到 256。补齐的消息全为 `[PAD]`，对应的 `sequence_attention_mask` 置 0，`event_id` / `raw_event_id` 为 null。训练时窗口通常是满的，sequence mask 全为 1；上线后遇到不足 256 条的窗口，这条补齐路径才会真正被走到，需要在验收时专门构造这种输入。

## 窗口缓存与预计算

Message Embedding 是可缓存的对象，因为它是单条消息到向量的映射，与窗口里其它消息无关。缓存键：

```text
SHA256(
  canonical_message
  + normalization_version
  + tokenizer_version
  + vocabulary_version
  + message_encoder_version
)
```

四个版本项一个都不能省。少写 tokenizer_version，换词表后旧条目仍然命中，查表会静默取到错行；少写 normalization_version，规范化规则一改，同一个 canonical_message 已经代表不同的原文了。缓存必须报告命中率、内存占用、预计算耗时和未命中推理延迟，没有命中率的缓存无法判断值不值得维护。

预计算名单只能由训练集或历史已完成数据生成，不能用测试集。用测试集决定"哪些消息值得缓存"，等于让测试集的分布泄漏进部署配置。
