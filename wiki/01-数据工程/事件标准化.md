## 一句话概括

事件标准化是把来源各异的日志数据集映射到同一套事件结构的过程。它要解决字段名、时间格式、缺失表示和唯一标识这四类不一致，让模型代码只认一套字段，不必知道数据来自哪个源。

## 为什么要先统一

定义：事件标准化指用独立适配器把每个原始数据集的字段映射到统一 schema，之后的模型、统计、切窗都只消费标准事件。

不做这一步的代价是 N 乘 M 的耦合。上游有 N 个数据集，下游有 M 个模型和实验分支。模型代码直接读原始字段名，每加一个数据集就要改一轮模型代码，每改一次模型就要重新确认它对每个数据集的字段假设还成立。

所以这条通常是硬约束：所有数据集必须先映射到统一标准事件，模型代码不得直接处理各数据集的原始字段。

映射规则本身也是产物，应该写进独立的映射配置文件，不得在代码里散落硬编码。原因很直接：映射是数据知识，写进配置文件它可审计、可复用；写进代码它就只存在于某个函数里，换个模型实现就丢了。

## 事件类型与动作

主线只强制支持四类事件：

- process：进程创建、退出、进程树变化
- network：连接、监听、DNS 查询
- file：创建、读写、改名、删除
- registry：键值创建与修改

扩展类型 auth、module、memory、other 可以保留，但不得阻塞主线。DNS 查询归入 network，动作记为 dns_query。归并的理由是 DNS 也是网络行为，单独成类会多出一个低样本类别，而动作字段已经足够把它和普通连接区分开。

类型与动作分开设计，是因为两者回答不同的问题。类型决定这条事件该读哪个字段组，process 事件才有 process 块；动作决定它生成什么样的 token。动作表是全数据集共用的有限集，典型取值包括 CREATE、START、STOP、CONNECT、ACCEPT、READ、WRITE、RENAME、DELETE、MODIFY、LOAD、EXECUTE、LOGIN、LOGOUT、OTHER。

## 标准事件的字段分组

必备字段可以按职责分成几组：

- 身份组：schema_version、event_id、raw_event_id
- 来源组：source.dataset、source.dataset_version、source.file、source.raw_ref、source.adapter_version
- 时间组：timestamp、timestamp_ms、timestamp_raw、timezone_raw、source_sequence
- 归属组：host_id、session_id、timeline_id
- 内容组：event_type、event_action、event_name，以及 process / network / file / registry 四个按类型填充的字段块
- 下游组：labels、canonical_message、structured_token、raw

分组的用意是每类字段有一致的生命周期。来源组和时间组在标准化时一次写死；内容组由适配器按事件类型填；下游组由后面的阶段追加，标准化阶段允许留空。

## 缺失值的三种语义

缺失必须区分三态：

- null：数据源没有提供该字段
- NOT_APPLICABLE：该字段不适用于当前事件
- UNKNOWN_<FIELD>：数据源提供了值，但无法规范识别

成因：三者在统计上含义完全不同，合并之后缺失率就失去解释力。文件事件没有目标 IP，是 NOT_APPLICABLE，这个缺失是结构性的、可预期的；网络事件的 IP 字符串损坏，是 UNKNOWN_IP，这个缺失本身可能是采集异常甚至是被改写的痕迹；数据源根本没有父进程字段，是 null，这是数据集的覆盖缺口。

如果三者都写成 null，UNKNOWN_IP 占比高会被当成整体数据质量差，而它更可能是某一段采集出了问题；NOT_APPLICABLE 占比高只是事件类型分布的反映，把它当成质量缺陷会让人去修一个本来没坏的东西。

## 唯一标识从哪来

event_id 的生成规则是：

```text
{dataset}:{source_file}:{event_kind}:{sha1(raw_ref)[:16]}
```

配套的禁令是：不要从 PID、排序位置或数组下标推断唯一性。

PID 复用是操作系统的正常行为，进程退出后编号会被回收。用 PID 当唯一键，同一台机器上两个先后出现的不同进程会被认成同一条事件。排序位置和数组下标更脆弱，上游文件顺序一变、中间插入一行，下游 ID 就全错位。

稳定 ID 的第一个用处是幂等，同一输入和同一版本重复运行结果完全一致，ID 稳定才能拿两次运行的结果逐条比对。第二个用处是回溯，ID 里带来源文件与原始引用的哈希，就能从任意一条样本反查到原始记录。

raw_event_id 同理，规则是数据集标识加来源文件加偏移量，来源没有稳定偏移时退化为载荷哈希，并且要处理哈希碰撞。

## 时间与排序

时间处理有四条：

- 统一转 UTC
- 内部统一毫秒
- 保留原始时间和原始时区
- 不用前后记录填充缺失时间

前两条为了跨源可比。不同数据集给的可能是本地时间、不同精度、不同格式，统一到 UTC 毫秒之后才能混排。第三条为了可回溯，原始时区丢了下游没法解释"这条事件为什么落在夜间"。第四条是安全场景的硬要求：时间缺了就标缺失，用邻居时间补出来的是编造的事件顺序。

时间确实缺失但有官方序列位置时可以保留，排序改用 source_sequence，并记入质量报告。

同一 group 内的排序键是三段：

```text
timestamp_ms -> source_sequence -> raw_event_id
```

三段依次降级，保证的是全序。时间戳可能相同，相同时间戳用源序列位置区分，源序列位置也相同时用 ID 兜底。排序键是全序的，切窗结果就唯一确定，重跑也复现。另外不要用文件名顺序代替时间顺序，除非数据集文档明确保证文件顺序就是时间顺序。

## 分组的优先级

切窗之前要先确定哪些事件属于同一个序列，优先级从高到低是四级：

- 官方 session / block / campaign ID：数据集自己定义的边界
- host_id + process_tree / root_pid / process_lifecycle：同一主机同一进程链
- host_id + fixed time window：同一主机固定时间窗
- source_file boundary：来源文件边界

优先级对应"这个边界与行为的相关性有多强"。官方的 campaign 划分直接对应一次攻击活动，是最强的语义边界。进程树是行为自然的容器，一个进程及其子进程的活动天然相关。固定时间窗是兜底，它假定时间邻近即相关。文件边界最弱，只在没有任何其他信息时使用。

跨 group 不允许盲目拼接。跨组拼接会把两条互不相关的行为放进同一个窗口，模型据此学到的上下文是假的。

## 标签

标签状态有六种：

- CONFIRMED_NORMAL、CONFIRMED_ANOMALY：人工或官方确认
- WEAK_NORMAL、WEAK_ANOMALY：规则推导
- SUSPICIOUS：可疑但未定性
- UNLABELED：没有标签

缺失标签禁止自动填成 CONFIRMED_NORMAL。这条和"禁止均值填充"是同一个道理：未标注的样本只是未知样本，混进正常类，正常基线就被污染了。

标签粒度有五种：EVENT、MESSAGE、SEQUENCE、SESSION、HOST_TIME_RANGE。

注意：序列异常不等于其中每条 event 都异常。这句话约束的是标签传播方向。一个窗口被判异常，可能只因其中两条事件构成攻击链，其余事件是完全正常的系统活动。把窗口标签下推到每条事件，会凭空生成一批正类。

label 字段里几个键各司其职：

- gold：官方真值，没有就是 null
- weak：规则推导的 0/1
- train_label：训练用标签，取 gold 优先、缺失时退到 weak
- label_state：六态之一
- label_scope：标签作用的粒度
- label_source：标签从哪来，规则名或来源标识
- confidence：规则置信度
- anomaly_types：异常类别
- rules、rule_version：命中的规则与规则版本

label_source 和 rule_version 是留给复现的。弱标签的规则会迭代，同一份数据用不同版本规则打出来的标签不一样，不记版本就没法解释两次实验的差异。

无标签样本可以用于自监督训练，但不得参与监督词表剪枝统计。自监督只用输入不用标签，无标签样本是资源；监督剪枝依赖标签，无标签样本进去只会稀释统计。
