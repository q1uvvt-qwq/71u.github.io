## 一句话概括

划分决定哪些数据能进训练、哪些只能用来验收。切错的后果不是分数低一点，是验收分数根本不可信：同一台主机、同一条时间线、同一批预处理统计只要跨了集，模型就能靠记住具体环境而不是学会异常模式拿到高分。

## 随机切分为什么在这里错

定义：数据泄漏指训练过程以任何形式接触到了本该只在验收时出现的信息，使验收指标高于真实部署表现。

随机事件级或窗口级切分是通用机器学习里最常见的做法，在日志场景会同时踩三类泄漏。

- 分组泄漏：同一台主机反复出现在训练和测试两边。主机的软件清单、目录结构、用户名、常用进程高度稳定，模型只要记住"这台机器的常态"就能同时答对训练和测试。
- 时间泄漏：同一段时间线被切开。事件前后有因果关系，用后半小时做测试、前一小时做训练，模型见过测试片段的前文。
- 预处理泄漏：词表、归一化统计、分桶边界、高频名单在全量数据上拟合。这些统计量把测试集的分布信息带进了训练流程。

成因：日志样本之间不是独立同分布的。同一个 host、同一个 campaign、同一段攻击时间线内部的样本相关性极高，随机的切分单位如果小于这个相关性结构，测试集就不再是"没见过的数据"。让切分单位与相关性来源对齐，是防泄漏的全部内容。

## 划分的优先级

按可信度从高到低：

```text
官方 split > 时间切分 > group-level random split
```

能用数据集自带的官方划分就用官方的。没有官方划分，按时间切。只能随机时，随机单位必须是 group，不能是 event 或 window。

group 的候选：

- `campaign_id`：一次完整攻击行动
- `session_id`：一次登录会话
- `block_id` / `timeline_id`：一段连续时间线
- `host_id + root_pid`：一台主机上的一个进程树
- `source_file`：最粗糙的兜底

硬约束只有一条：同一个 group 不得跨训练 / 验证 / 测试三集。

落地时的划分记录要能独立复现：

```json
{
  "schema_version": "split.v1",
  "split_method": "group",
  "group_key": "timeline_id",
  "seed": 42,
  "train": ["tl-001", "tl-002"],
  "validation": ["tl-003"],
  "test": ["tl-004"]
}
```

seed 与 group_key 都要写进去。只写结果不写切法，别人复核时无法重现这份划分。

## Train-only 统计清单

以下内容只能在训练集上拟合，验证集与测试集只能套用训练集产出的那份：

- 词表
- token 频率
- 可区分度分数
- 路径 / 进程高频名单
- first_seen 历史
- 数值桶边界
- 归一化统计
- 正常分数阈值
- message cache 预计算名单
- Top-K 剪枝词表

这份清单值得逐条看一眼，因为其中几项容易被当成"无所谓的技术细节"。词表在全集上拟合，等价于告诉模型测试集里会出现哪些 token；高频路径名单在全集上统计，等价于告诉模型测试集里哪些路径常见；first_seen 用到了未来事件，等于让模型提前知道某个进程是首次出现。这四项都会把测试集的答案漏进训练。

数值桶边界和归一化统计是数据泄漏里最隐蔽的一类：它们看起来只是格式转换，但边界值本身是从数据分布里算出来的。

## TEST 只能用一次

测试集不能用来做的事：

- 选模型结构
- 重拟合 reference
- 拟合 Robust-Z 的 median / MAD
- 选特征权重
- 搜索阈值
- 选 Top-K 的 K

一旦用测试集结果回头改了任何一个选择，它就不再是留出集，后续再报的分数只能当作训练集分数看。可行的约束是：对测试集的再次运行仅允许复核、环境迁移复现或量化后等价验证；若用测试结果改动了模型或阈值，后续必须换一批新的测试数据。

阈值这件事要单说。分数可以算，决策不能出。没有冻结阈值之前，只能报告诊断结果，不能报告 Accuracy / F1 / Precision / Recall / FPR / 混淆矩阵。

## 两类留出集不能互相顶替

留出集在实践中分两级用。

一级是训练内部监控集。从训练数据里按主机留出一小批，不参与梯度更新，只用来观察训练健康度、挑最优 checkpoint。它的作用是发现"训练崩了"或"过拟合了"，回答的是训练过程本身好不好。

二级是正式验证集。它用来定阈值、算最终指标，是唯一的性能口径来源。

两者的区别在于用途，不在于大小。拿监控集去宣称检测性能，等于用训练数据的一部分给自己打分；反过来拿正式验证集去挑 checkpoint，则会把验证集也消耗掉，后面再用它定阈值就已经不是留出数据了。顺序是先挑 checkpoint，再定阈值，各用各的集。

## 划分与标签的联动

分层切分要和标签语义一起看。真实场景里通常没有完整的确认正常样本，正常侧多是规则推定的弱标签，异常侧同样是弱标签，只有少量人工核过的样本才算金标。

训练时的口径一般是弱正常加弱异常两类都进自监督候选池，标签只用于数据选择、不进 loss。介于两者之间、无法定性的那类被排除，只留作分析。

用弱标签训练、用金标验收，中间的落差要在划分阶段就留出位置：弱标签不能宣称攻击检测效果，弱正常的分布也不等于真实误报率。把弱标签当金标用来定阈值，阈值会偏松，上线后误报率会高于验收时的数字。

金标集中是另一个要提前设计的问题。如果确认异常只落在极少数主机上，按窗口汇总的单一分数会把主机间差异抹平，看上去很好而实际只在其中一台上有效。这类情况下主表必须同时给出 micro、host-macro 和逐主机三组结果。

金标窗口之间还会因为 stride 小于窗口长度而重叠，事件级分析必须按 event_id 去重，窗口级分析保留原窗口以衡量实际告警单元。同一份数据在两种粒度下要出两种答案，这是重叠切分带来的必然。
