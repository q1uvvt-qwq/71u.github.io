## 一句话概括

用户打开文件时只拿到一个 **`fd` 句柄（一个整数）**，但内核为此维护了**一整套分层的数据结构**。理解这条链，就能明白为什么 `fd` 在 CTF 里常被用来**绕过「只能读指定路径」的限制** —— 因为 `fd` 指向的是**已经打开的文件对象**，而不是路径。

## 原理

### 1. 打开一个文件，内核经历了什么

当用户打开一个文件，用户只得到了一个 `fd` 句柄，但内核做了很多事情。把这条链梳理下来，会得到几个**层次递进**的关键数据结构：

```text
进程 task_struct
   └── task_struct.files
         └── files_struct          （进程打开文件的管理表）
               └── 数组第 N 项 → file 结构   ← 用户拿到的 fd 就是这个 N
                     └── file.f_inode
                           └── vfs inode      （操作系统抽象层）
                                 └── ext4 / minix / … 具体文件系统 inode
```

**逐层说明：**

**① 进程结构 `task_struct`**

表征进程实体，每个进程对应一个 `task_struct`。其中 `task_struct.files` 指向一个管理「本进程打开了哪些文件」的结构体 `files_struct`。

**② 文件表项管理结构 `files_struct`**

用于管理进程打开的 open 文件列表，内部以**数组**实现（静态数组 + 动态数组结合）。

> **返回给用户的 `fd`，就是这个数组的「编号索引」。** 数组的每个索引元素是一个 `file` 结构。

**③ 文件 `file` 结构**

表征**一个打开的文件**，关键字段包括：

- **当前文件偏移**（读到哪了）；
- **inode 结构地址**（指向哪个文件）。

它的生命周期由进程触发创建，但 **`file` 结构可以在进程间共享**（例如 `fork()` 之后父子进程共用同一份打开文件对象）。

**④ vfs `inode` 结构**

`file` 结构指向的是 **vfs 的 `inode`**。这是操作系统**抽象出来的一层**，用于屏蔽后端各种文件系统 `inode` 的差异。

> **`inode` 与具体进程无关，属于文件系统级别的资源。** 一个文件被多个进程打开，它们指向的是**同一个** vfs inode。

**⑤ 具体文件系统 `inode`**

后端文件系统自定义的结构：ext2 有 `ext2_inode_info`，ext4 有 `ext4_inode_info`，minix 有 `minix_inode_info`。这些结构里都**内嵌了一个 vfs `inode`**，原理相同。

### 2. `task_struct` 与 `files_struct` 的对比

| 特性 | `task_struct` | `files_struct` |
|---|---|---|
| **范围** | 描述整个进程 | 仅描述进程的文件相关信息 |
| **大小** | 很大（约 1～2 KB） | 较小（几十字节） |
| **内容** | 进程的所有信息 | 仅文件描述符和文件状态 |
| **数量** | 每个进程 1 个 | 可被多个进程共享 |

另外需要注意：**`files_struct` 只从属于某一个进程**（它挂在 `task_struct` 下面），而它内部指向的 `file` 结构、`inode` 则可能跨进程共享。

### 3. 为什么 `fd` 在 CTF 里能用来绕路径限制

核心在于：**`fd` 指向的是「一个已经打开的文件对象」，而不是「一个路径字符串」。**

Linux 把内核的这些状态通过 `procfs` 暴露出来。对于某个进程自己，可以看到：

```text
/proc/self/fd/           # 当前进程的所有 fd（每个都是一个指向真实文件的符号链接）
/proc/self/fd/0          # 标准输入
/proc/self/fd/1          # 标准输出
/proc/self/fd/2          # 标准错误
/proc/self/fd/3 ...      # 进程后续打开的文件
/dev/fd/                 # 通常是 /proc/self/fd 的符号链接
```

**利用思路**：当一个文件**已经被进程打开**时，`/proc/self/fd/<N>` 就等价于那个文件的路径。于是：

- **绕过「路径关键词」过滤**：过滤规则拦 `flag`、`config` 这些关键词时，`/proc/self/fd/3` 里一个关键词都没有；
- **绕过「路径前缀白名单」**：只允许读某个目录下的文件时，`fd` 路径不在该目录下，但指向的却是同一份内容；
- **读到「已删除 / 无路径」的临时文件**：临时文件被 `unlink()` 后路径消失，但**只要 fd 还开着**，内容就还能通过 `/proc/self/fd/N` 读到。

一个直观例子：题目先 `fopen()` 打开了 `flag.php`（比如为了校验），但只允许我们读 `uploads/` 目录：

```php
$zh = fopen('flag.php', 'r');       // 内核给它分配了某个 fd，假设是 3
readfile('uploads/' . $_GET['f']);  // 只允许读 uploads/ 下的东西
```

此时请求 `?f=../../proc/self/fd/3`（`uploads/` 下没有这个文件？注意：`readfile` 的路径是 `uploads/../../proc/self/fd/3`，会被文件系统归一化成 `/proc/self/fd/3`），就能读到那个**已经打开的 `flag.php` 文件对象**。

> 注意：`fd` 的编号**不固定**（取决于进程此前打开过什么），实战中一般从 `3` 开始逐个试。

## 利用条件

1. **目标文件已被当前进程打开**（否则对应的 fd 不存在）；
2. **能控制一个路径参数**，且可以把路径拼成 `/proc/self/fd/N`（`../` 归一化也算）；
3. **目标环境是 Linux**（`/proc` 是 Linux 特有的虚拟文件系统）；
4. **不依赖文件路径本身**：正因为不依赖路径，才绕得过基于路径的过滤。

## Payload 速查

| 目的 | Payload |
|---|---|
| 读当前进程某个 fd | `?file=/proc/self/fd/3` |
| 顺序探测 fd | `?file=/proc/self/fd/0` … `/proc/self/fd/10` |
| 通过 `dev/fd` 等价写法 | `?file=/dev/fd/3` |
| 用遍历绕过目录前缀限制 | `?file=../../proc/self/fd/3` |
| 读进程信息（辅助判断） | `?file=/proc/self/environ`、`?file=/proc/self/status`、`?file=/proc/self/cmdline` |

## 踩坑与备注

- **`fd` 编号要靠试**：不同题目、不同 PHP-FPM 配置下，`flag.php` 被分配的编号不同。一般从 `3` 开始向上试；`0/1/2` 是标准输入输出错误，通常没有内容。
- **不是所有题目都能用**：前提是**目标文件确实被进程打开过**。如果 flag 只是躺在磁盘上、进程从没 `fopen()` 过它，`/proc/self/fd/` 里就不会有它。
- **`/proc/self` 指代的是「读这个文件的进程」**：在 Web 场景下就是 PHP-FPM 的工作进程。用 `?file=/proc/self/status` 可以确认这条路走得通（会看到 PHP 进程的信息）。
- **这是「文件读取」不是「文件包含」**：这里只是把 `fd` 当**路径**读内容。`fd` 本身不影响内容是否被当代码执行 —— 那是 `include` 与 `php://filter` 的话题（见 `05-文件包含\文件包含漏洞原理与前置条件.md`）。
- **中文术语对照（便于查资料）**：`task_struct` = 进程控制块 / 进程结构；`files_struct` = 打开文件表；`file` = 打开文件对象（file 结构）；`inode` = 索引节点。
