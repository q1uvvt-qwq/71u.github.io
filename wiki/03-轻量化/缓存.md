## 一句话概括

两条分数线里只有 Point 那条能缓存，因为它是单条消息的函数（见 [评分定义](../02-模型/评分定义.md)）。缓存复用的是 Message Encoder 的输出向量，不是窗口分数。整理清缓存什么、键怎么定、多大容量之后，还要算一笔命中率的账：命中率低于某个门槛，缓存带来的查表开销会盖过省下的推理。

## 三块可以缓存的东西

按复用粒度从粗到细：

- 消息 embedding。一条消息过一次 Message Encoder 得到的向量，键是消息文本
- 窗口 embedding。整段 256 条消息的 Message Encoder 输出，键是窗口内容
- 评分类中间量。归一化后的向量、特征聚合结果

三块的复用价值与正确性风险都不同。消息 embedding 是最值得做的一块：它只依赖单条文本，与前后邻居无关，同一条命令行在任意窗口、任意主机上得到的向量都一样。窗口 embedding 的键会非常长，命中条件苛刻。评分类中间量与阈值绑定，一旦阈值或校准参数重算就整批失效。

## 缓存键必须覆盖版本维度

缓存键的设计关键是：任何一个能改变输出向量的东西，都要进键。少进一个维度，换版本时会读到旧向量，结果错了还不报错。

规范化函数的常见形式：

```text
canonical_message = lowercase(collapse_whitespace(trim(message.replace("\\", "/"))))
```

三步都必要。`trim` 去首尾空白，`collapse_whitespace` 把连续空白压成一个空格，`replace("\\", "/")` 统一路径分隔符，`lowercase` 消掉大小写差异。日志文本里这些差异大量存在，却不一定有语义。规范化的作用是提高命中率，代价是把大小写敏感的情况也合并了。

命名空间字段是一份 JSON，跟缓存内容一起存：

```text
cache_schema
contract_id
model_variant_id
message_encoder_version
tokenizer_vocab_version
normalizer_config_version
embedding_dtype           float32 / int8
embedding_dimension
```

这几个字段覆盖的是同一件事的几个版本维度。契约变了，输入输出语义可能变；模型变了，权重变了；tokenizer 或 normalizer 变了，同一条文本切出的 token 序列变了；dtype 变了，存进去的数值精度变了。任何一个不匹配，整份缓存作废，不是逐条淘汰。

注意：Message Encoder 的版本指纹放在键里，意味着量化产生的新模型会得到一套全新缓存，与 FP32 的缓存不共享。这是对的，两种精度的向量本来就不能混。

## 值与容量

缓存条目存的是归一化前的向量。索引结构用 LRU，两个容量上限：

```text
max_entries       条目数上限
max_value_bytes   单条目字节上限
```

`max_value_bytes` 是防单条超大值把内存吃掉的兜底。正常情况下向量维度固定，字节数是常数，这一项不会触发；真触发说明输入异常。

容量策略是缓存设计里最难的取舍。缓存太小，条目刚存进去就被挤掉，命中率上不去还白花写开销；缓存太大，内存占用失控。这个取舍只能靠实测的命中率与内存峰值来定，靠推算定不了。

## 查询算法

一次查询有四步：

1. 对消息做规范化，得到 `canonical_message`
2. 拼出条目键，查索引
3. 命中则返回值，未命中则调 Message Encoder 算一遍，再把结果写回
4. 写回时按 LRU 淘汰，超过容量上限就挤掉最久未用的条目

失败处理采取 fail-open：缓存出错（反序列化失败、条目损坏、索引异常）时按未处理，直接走一次完整推理，不让缓存故障变成请求故障。

这个选择是对的。缓存是纯优化层，它的可用性不该低于模型本身。缓存错了顶多是没有加速，模型推理错了才是结果错。

## 命中率要算的账

缓存是否划算，取决于一条不等式。设命中率为 h，一次缓存查询的耗时为 c，一次完整 Message Encoder 推理的耗时为 m。缓存有收益的条件粗略是：

```text
h * m > c
```

即省下的推理时间要盖过查表与序列化的开销。注意即使 h 很低，只要 m 远大于 c，缓存仍然划算；反过来 h 再高，如果 c 接近 m，也白搭。

经验上把命中率 30% 当作参考门槛。含义是低于这个量级时，缓存带来的查表开销与内存占用不值得，收益被抵消掉了。

## 数据侧重复率不等于命中率

看数据本身有没有可复用的东西，通常会统计消息重复率：同一个窗口里去重后剩多少条唯一消息。日志重复率一般不低，看上去缓存很有空间。

这里有一个必须提前想清楚的落差。数据侧的重复率是全局统计量，它回答的是"整份数据里有多少重复"，而缓存命中率回答的是"在一个容量受限期内存活的条目，能不能赶上它的下一次出现"。两者的差距来自两点：

- 缓存的存活窗口太短。容量限制下条目被频繁淘汰，重复消息再次出现时已经被挤走了。
- 重复是跨批次才显现的。同一批查询内部未必有多少重复，跨批次才有的重复，在线缓存吃不到。

所以数据侧重复率只能是缓存价值的上界，不能当成预期命中率。真实命中率要靠 PoC 在推理链路上实测，且必须记录淘汰次数，淘汰次数高说明缓存一直在抖动。

## 量化与缓存的冲突

缓存能不能跟 INT8 量化叠着用，取决于量化是不是逐条独立。

| 量化路线 | 单条消息路径是否可用 | 说明 |
| --- | --- | --- |
| FP32 | 可用 | 基准 |
| 静态量化 | 可用 | 激活范围在校准时定死，与调用组成无关 |
| 选择性量化 | 可用 | 同上，Message Encoder 可保持 FP32 |
| 动态量化（逐条） | 不可用 | 激活范围随每次调用的组成变化 |

动态量化的激活范围是运行时按当次输入算的。同一条消息与不同的邻居一起进 batch，算出来的缩放系数不同，得到的量化结果就不同。这意味着向量不再是消息文本的纯函数，缓存的前提被打破（见 [INT8量化](INT8量化.md)）。

结论是动态量化下只能按 batch 缓存，不能按单条消息缓存，而按 batch 缓存的命中条件太苛刻，实际价值接近于零。缓存的可行组合是 FP32 Message 或静态量化的 Message Encoder。

## 缓存的验收门禁

一份缓存 PoC 要过的检查项：

- 等价性：开缓存与不开缓存的输出在容差内一致
- 命中率：达到预设门槛（参考值 30%）
- 延迟：开启后每条消息的耗时下降
- 内存：RSS 峰值在预算内
- 淘汰行为：容量受压时 LRU 按预期工作
- 版本隔离：换模型或 tokenizer 后旧条目不再命中
- 失败降级：人为制造缓存故障，请求仍能走通

命中率和延迟这两项是最容易不过的。等价性与版本隔离属于正确性，过了才谈得上加速；命中率与延迟属于收益，过不了就该放弃这条路，而不是硬上。
