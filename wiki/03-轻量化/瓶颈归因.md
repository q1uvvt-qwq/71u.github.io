## 一句话概括

优化之前先要知道时间花在哪。一条评分链的各段耗时通常极不均匀，改错地方就算改得再漂亮也换不来端到端收益。ContraLog 的账算下来，可下手的位置被压缩到很窄的一段：ContextScore 吃掉整条链的绝大部分时间，ContextScore 内部又几乎全花在 Sequence Encoder 的 ONNX 推理上。

## Amdahl 定律：收益的上限由占比决定

定义：Amdahl 定律描述对系统中一部分做加速之后，系统整体加速比的上限。

设被优化部分占总时间的比例为 f，这部分自身的加速倍数为 s，则整体加速比为

```text
Total Speedup = 1 / ((1 - f) + f / s)
```

三条推论。

- f 很小时 s 再大也拉不动整体。一个只占两成的模块，就算把它加速到无限快，整体上限也只有 1.25x。
- 想让整体翻倍，要么让 f 接近一半，要么让被优化部分的绝对耗时大幅下降。前者靠选对模块，后者靠减少计算量。
- 多个小头的收益按乘法叠加，每段各自优化一点的总体效果，通常不如动一个主头。

这条定律的价值在于它把"选哪里下手"变成了算术问题。先量出各段占比，再决定优化谁；顺序反过来的话，很可能花大力气优化了一个占比两成的模块，端到端只快了百分之几。

## 先算账：瓶颈在哪一段

在 ContraLog 的评分链里，两个编码器合起来只占整链的一小部分时间，其余全部落在 ContextScore。这个比例在 batch size 变化时基本稳定：批处理摊薄的是编码器的固定开销，而 ContextScore 在 CPU 上随 batch 近似线性增长。batch 越大，编码器占比越低、ContextScore 占比越高。

PointScore 和 Robust-MAD 加起来的耗时不到百分之一，属于可以忽略的一段。

这条账直接给出结论：只量化编码器的理论上限很低，因为剩下那一大段完全没被碰到。

## 瓶颈内部：钱花在哪

把 ContextScore 摊开看，它由五个阶段组成：构造 leave-one-out 变体、ORT 推理、输出 gather、余弦计算、分数聚合。

成因：ContextScore 对每个窗口要构造 256 个 leave-one-out 变体，每个变体都是一条完整的 256 消息序列，然后把它们逐个（或按 chunk 成批）送进同一个 Sequence Encoder。构造变体是内存写和拷贝，余弦是几十次向量点积，都是微秒到毫秒量级；真正贵的是那 256 次完整前向。按算子估算，单层 Q/K/V/O 投影约 `4·L·D²`、attention 约 `2·L²·D`、FFN 约 `2·L·D·FFN`，L = 256 时 attention 项已经超过其余两项之和（见 [评分定义](../02-模型/评分定义.md)）。

于是优化面很窄。构造变体的那一小段不值得做 buffer 优化或向量化，分数聚合更不值得动手；优化 cosine、SIMD 或 Python gather 同样换不来可观的端到端收益。可动的只有 ORT 推理这一段，手段是调 chunk、调线程、换量化精度。

## 被上游吸收的收益

只量化 MessageEncoder 时，链路加速很小；把两个编码器都量化，加速比也只有百分之十几到几十。原因是编码器省下的绝对时间小于 ContextScore 的运行波动，信号被波动淹没了。

还有一条容易被误读的现象：全量化有时超过 Amdahl 的预测，是因为 INT8 SequenceEncoder 产出的 embedding 数值特征不同，顺带让 ContextScore 算得更快。这条收益不来自量化本身的目的，是一条副产物，不随模型结构稳定。报收益时要把它和"算子真的变快了"分开。

## profiling 怎么做：采样与埋点

定义：profiling 有采样和埋点两条路。采样是周期性中断进程、抓调用栈，按命中频次反推热点；埋点是在关注的代码区间自己打时间戳，直接累加。

两条路的偏差方向相反。

- 采样开销低、覆盖面全，但统计上偏向"帧数多"的函数，单次耗时长的算子若调用次数少容易被低估。
- 埋点精确到区间，但计时器自身有开销，测量点过密会虚增；同时只能看到你插了桩的地方，链上的盲区不会被发现。
- 采样结果在不同运行间有抖动，反复运行的方差本身要当指标看，不能只看单次均值。

要落到算子级，还得让运行时吐算子级的 trace，同时采集 CPU 利用率、RSS 和 allocator 行为。观测阶段只观测，不改评分运算也不改服务行为，否则测出来的就不是原来那条链了。

还有一个原则值得单独写：不要按模块名字猜哪些节点该优化。序列里叫 MatMul 的算子可能根本没被量化上，漂移大的节点也未必是最慢的节点，要靠 activation debugging 一类的工具找出来。

## 冷启动与稳态要分开

定义：冷启动指进程或 session 建立后的头几次调用，稳态指常驻进程在反复调用下的耗时。

冷启动多出来的成本来自 session 初始化、图优化、算子内核首次加载、线程池与内存 arena 的创建，这些在稳态里不再重复。profile 一段稳态路径时，要把 session 初始化和前处理排除在计时之外，否则测出来的是启动成本。

分不清这两者会得出反向结论。把优化后的图离线序列化能降低 session 启动成本，但对稳态耗时未必有帮助，一项优化到底该归到"启动优化"还是"稳态优化"，取决于你测的是哪一段。同理，服务同时常驻主路径和回滚路径两条 session 时，共享内存 arena 的收益也主要在启动和内存侧。

## chunk 与线程：调的是批的形状

`context_chunk_size` 决定一次构造多少个变体、发一次多大的 ORT 调用。窗口内变体总数固定为 256，chunk 只改变调用次数与批形状：调用次数是 `ceil(256 / chunk_size)`，临时变体张量形状是 `[chunk_size, 256, 64]`。

注意 chunk 不是越大越好，也不是越小越好，存在一个折中点。chunk 变大能减少调用开销、让内核有更多活干，但峰值内存随之上升，缓存压力和线程争用会把 p95 推高；chunk 变小内存友好，但调用、循环和分配开销占比上升。

线程数同理。超过物理并行度之后，线程调度与争用开始主导，继续加线程反而退化，存在一个局部最优。

所有 chunk 和线程配置都必须先过分段精确一致，才能进性能比较。准确性不过关的配置，速度再快也没有意义。

## 被否决的近似路线

严格契约要求 256 个位置的 leave-one-out 全部保留，mask token、聚合方式、评分公式都不能动。在这个前提下：

- 只作用于 PointScore 的 FAISS / HNSW / ANN / 相似度缓存全部无效，因为它们不减掉 ContextScore 的 256 次前向，而且 ANN 会改变 PointScore 的最近邻结果。
- sampled / shortened / top-k / adaptive / hierarchical 一律被精确性 gate 否决，因为它们减少的是变体数量，属于改算法而不是改运行时。
- overlapping-window 复用被否，原因是 Sequence Encoder 是双向 attention 且带绝对位置编码，窗口左移会同时改变 token 集与位置编码，没有可直接复用的 hidden state。
- 若真要走近似，必须记为算法变更，新建 scoring spec 并重做阈值校准，不能当轻量化处理。
- 靠换更小的学生模型降本属于另一条路，但模型替换同样要过完整验收。
