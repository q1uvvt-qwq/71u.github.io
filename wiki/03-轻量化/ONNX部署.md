## 一句话概括

把 PyTorch 里训好的模型导成 ONNX 图，用 ONNX Runtime 跑推理，这是轻量化落地的那一步。导出看起来像一次格式转换，实际是一条带验收门禁的流水线：图要能建起来、两根编码器的输出要跟 PyTorch 对得上、分数链路的每一个中间量也要对得上，任何一级不过关就不往下走。

## 为什么要脱离 PyTorch

定义：ONNX 是一种开放的模型交换格式，把计算图结构与权重数值存进同一个文件，推理时不需要原来的训练框架。

训练用 PyTorch 是合理的，它有自动微分、有现成的优化器、调试也方便。但推理阶段这套东西全是负担：PyTorch 运行时体积大、依赖重，部署到生产环境要拖一整套 Python 科学计算栈。ONNX Runtime 是一个只干推理的运行时，它提供三件训练框架给不了的东西：

- 图级优化。加载时能合并算子、消掉常量、把可融合的子图替换成单个高效实现
- 量化支持。INT8 的动态量化、静态量化、混合量化都通过它落地
- 跨平台。同一份 ONNX 文件可以在 CPU、GPU 或嵌入式后端上跑，换的是 provider 不是模型

对这套主机行为日志检测来说，目标是纯 CPU 部署，所以选 `CPUExecutionProvider`。

## 导出出来的两个文件

Message Encoder 与 Sequence Encoder 分开导出，因为评分链路里两者在不同时机被调用（见 [评分定义](../02-模型/评分定义.md)）。

两个文件的体积差两个数量级，根源是词表。Message Encoder 带一张 `50,000 × 64` 的 embedding 表，绝大部分权重在这里；Sequence Encoder 的输入已经是向量，没有 embedding 层，只剩 Transformer 那几层。

这也解释了为什么砍 hidden、砍层数对总体积几乎没影响。那些改动动的是两边的 Transformer 部分，本来就不占大头。Sequence Encoder 单独看可能缩小一大截，放到总量里就是零头。

## 只有 batch 维是动态的

导出的图里只把 batch 维 `B` 设成动态，`L` / `T` / `D` 全部固定。这是契约的要求（见 [ContraLog架构](../02-模型/ContraLog架构.md)），不是导出的默认行为。

固定维度的好处是运行时能提前分配好内存、能把 shape 推导做死在图里，少了动态 shape 带来的一层调度开销。代价是任何长度变化都得在预处理阶段补齐或截断到 256 和 64，模型本身不接受变长输入。

把 `L` 也放成动态看似更灵活，实际得不偿失。这套链路的输入本来就被窗口切法定死成 256 条消息，没有变长的需求；放动态只会让优化器失去部分融合机会。

## 运行时参数

部署侧的运行时配置固定在少数几个开关上：

```text
provider           CPUExecutionProvider
optimization level ORT_ENABLE_ALL
execution mode     ORT_SEQUENTIAL
```

`ORT_ENABLE_ALL` 打开全部图优化，包括扩展级和布局优化。`ORT_SEQUENTIAL` 让算子按图里的顺序一个接一个执行，不尝试跨算子的并行调度。

这两个选择是配套的。批与线程的关系在这套模型上不是单调度器能解好的（见 [批与序列](批与序列.md)），并行放到外层按 batch 和线程数控制，图内就不再做一层并行，避免两层调度互相打架。

## 三级验收

导出完成后要过三道检查，顺序不能颠倒，因为后一级依赖前一级的结论。

第一级是静态检查。图能加载、输入输出名与 shape 与契约一致、算子都在 CPU provider 的支持列表里。这一级不过，后面两级没有意义。

第二级是 PyTorch FP32 与 ONNX Runtime FP32 的等价验证。同一批输入分别喂给两个实现，比输出的差异：

```text
max_abs_error  <= 1e-4
mean_abs_error <= 1e-5
min_cosine     >= 0.99999
```

三个门限一起用。只看最大误差会被个别离群位置卡死，只看平均误差会漏掉少量严重的点，余弦相似度管的是方向有没有偏。三者同时满足才算这根编码器过了。

第三级是分数链路一致性。单看编码器输出等价还不够，因为评分链路在编码器外面还有一整套运算：归一化、最近邻检索、mask 替换、特征聚合、Robust-Z 校准。两个编码器各自都在容差内，不代表拼起来之后窗口分数也在容差内。这一级比的是端到端的 `point_mean / point_max / context_mean / context_max`。

注意：门限的松紧是分级别的。`1e-4` 这样的绝对误差门限适合 FP32 对 FP32 的比较；一旦其中一侧换成 INT8，误差量级完全不同，要另立一套门限（见 [数值等价](数值等价.md)）。

## 图优化做了什么

ONNX Runtime 加载图时会跑一轮优化，最常见的是算子融合：把图里几个小算子替换成一个等价的大算子。典型例子是 LayerNorm、GELU、以及注意力里的 QKV 投影加缩放加 softmax 这一串。

成因：融合之所以快，是因为省掉的是中间张量的读写，不是计算本身。几个算子串起来跑，每一步都要把结果写回内存再读出来；合成一个算子后中间结果留在寄存器或缓存里，计算量没变，访存次数降了。CPU 上的推理瓶颈经常就在访存，所以这一步收益明显。

这里有一个容易踩的坑。ORT 的融合是按子图模式匹配做的，模式对不上就不融。手动展开写的注意力（显式的 matmul、scale、mask、softmax 几个独立算子）跟融合器期待的模式未必一致，尤其是带自定义 mask 语义的写法。所以同一份模型，图长得稍微不一样，融合到的程度就会差一截，最终速度也跟着差。

判断有没有融上，看不了源码，只能拿优化后的图去数算子，或者直接看 benchmark 结果。这也是为什么导出之后的性能必须实测，不能按参数量或 FLOPs 推算。

## 量化在导出之后做

FP32 的 ONNX 图是基准，量化是对这份图的二次加工。动态量化、静态量化、选择性量化、混合量化四条路线，各自改的是图里不同的算子，精度与收益的取舍也不同（见 [INT8量化](INT8量化.md)）。

顺序上，先有 FP32 等价通过的图，才有资格谈量化。反过来先量化再验等价，出了偏差分不清是导出引入的还是量化引入的。

量化之后要重做的事有两件。一是重新跑等价验证，换成 INT8 的门限；二是重算阈值与校准参数，因为分数分布已经移位（见 [阈值与校准](../02-模型/阈值与校准.md)、[漂移度量](漂移度量.md)）。

## 漂移分三层看

量化改动不是一个点的改动，它沿着链路往下传。要看清楚传到哪儿，得把漂移拆成三层：

| 层级 | 比的是什么 | 观测量 |
| --- | --- | --- |
| 编码器层 | 单条消息向量、上下文向量 | 余弦、L2、最大绝对差 |
| 评分层 | 四维特征 | 各特征的分布偏移 |
| 排序层 | 窗口排序、Top-K | Spearman / Kendall、Top-K 重合度 |

编码器层的漂移只是起点，它在评分层被放大或被吸收，最终要看的是排序层还保不保得住。判据的分层与阈值都写在 [漂移度量](漂移度量.md) 里。

三层都看完，才算把这次量化改动验收完。只看编码器层，会漏掉评分链路里累积的偏移。

## 部署路线的完整形状

整条路线可以概括成十步，前后有依赖：

1. 冻结契约与 checkpoint，记下 SHA-256
2. 导出 Message Encoder 与 Sequence Encoder 的 FP32 ONNX
3. 静态检查
4. PyTorch FP32 与 ORT FP32 等价验证
5. 分数链路一致性验证
6. 生成 INT8 变体
7. INT8 等价验证与新门限
8. 三层漂移度量
9. 漂移之后的性能 benchmark
10. 更新阈值包与交付记录

第 4、5 两步都并在同一个 FP32 等价环节里，区别是第 4 步比编码器输出、第 5 步比分数链路输出。第 9 步的 benchmark 必须放在漂移度量之后，因为量化后的性能数字只有在精度可接受的前提下才有意义。

每一级的产物要带来源哈希。导出的 ONNX 绑 checkpoint，INT8 绑 FP32 ONNX，阈值包绑 INT8 ONNX 与 Point reference。任何一层的哈希对不上，下游产物就得重做，不能只换文件不换记录。
