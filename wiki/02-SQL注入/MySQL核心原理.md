## 一句话概括

一条 SQL 语句要经过 **解析器（词法分析 + 语法分析）** 和 **预处理器（语义检查 + 权限验证）** 才会被执行；**注入之所以能发生，就是因为解析发生在拼接之后**。反过来，**只要代码里用了 prepare 预处理，攻击者就无法提前闭合，SQL 注入不存在**。

> 本篇的原笔记是极简速记体（大量单词、半句、无主语），本次按**原意**把每个碎片补成完整段落，补齐主谓宾与因果。凡是原文没写清、只能推测的地方，都在「踩坑与备注」里单独标注了**存疑**，正文不做无依据的发挥。

## 原理

### 1. 笔记记下的整体架构

原笔记第一行只列了几个词：

```text
设计架构——引擎，系统，连接池，客户端（客户端与服务端）
```

按笔记随后的"以上为上层 / 以下为下层"来还原，作者当时画的是**上下两层**结构：

| 层 | 组成 | 说明 |
|---|---|---|
| **上层** | **客户端**、**连接器** | 面向"调用方"的一层 |
| **下层** | **服务器层**（服务器本体 + 存储引擎 + 连接管理） | 真正解析与执行 SQL 的一层 |

另外单独提到了两个名词：

- **引擎**：MySQL 里真正负责**存取数据**的部件。MySQL 的一大特点是**存储引擎可插拔**（同一套 SQL 前端，底下可以换不同的引擎）。
- **连接池**：连接是昂贵的资源，反复"建立—断开"开销很大，所以把连接**复用**起来，池化保存；应用取用一个、用完归还，而不是每次新建。

> 这两条是通用的数据库常识，本次作为**背景补充**补在这里；原笔记只留了词，没有解释。

### 2. 客户端与连接器

原笔记对这两个部件的定义：

- **客户端是用户与服务器交互的接口**，负责**接受指令，并返还给服务器**。
- **连接器——类似于 `stdio.h`，实现直接调用的功能，而无需管怎么实现**。

把这两句讲通：

- **客户端**扮演的是"**发起请求**"的角色：它把用户的指令收下来、整理好、交给服务器；服务器算完之后，结果也由它接回来呈现给用户。原笔记里"返还给服务器"这句是速记的语病，按上下文应当理解为"**把指令交给服务器、并从服务器接收结果**"。
- **连接器**的比喻很贴切。C 语言里写 `printf()` 只需要 `#include <stdio.h>`，**不必知道字符最终是怎么落到屏幕上的**——stdio 把底层细节包住了。同理，连接器把"怎么和 MySQL 服务端建立连接、握手、认证、收发协议包"这些细节**封装起来**，上层的调用方只要"调用"即可，不需要自己实现网络协议。

### 3. 谁在扮演"SQL 客户端"

原笔记在这里有一段自我纠正，很关键：

```text
谁扮演客户端
web服务器（存储，负责接受指令，并返还服务器）--后端--作为sql客户端
纠正——sql注入时并非网页浏览器直接对数据库进行查询
web客户端（浏览器）——http协议的客户端
web后端（网页服务器，如）
```

展开成一句完整的话：

**扮演 MySQL 客户端的是 Web 后端（网页服务器），不是浏览器。**

这中间其实有**两套完全不同的"客户端/服务端"关系**，初学时最容易把它们混成一件事：

| 关系 | 客户端 | 服务端 | 用什么协议 |
|---|---|---|---|
| Web 请求 | **浏览器**（Web 客户端） | **Web 后端 / 网页服务器** | HTTP |
| 数据库访问 | **Web 后端**（此时它是"SQL 客户端"） | **MySQL 服务端** | MySQL 自己的协议 |

所以原笔记特意写下这句"**纠正——SQL 注入时并非网页浏览器直接对数据库进行查询**"：

- 浏览器只会说 HTTP，它根本不会说 MySQL 的协议，也没有数据库的账号密码；
- 真正拿账号密码去连数据库、并把 SQL 发过去的是 **Web 后端**；
- 攻击者做的事情，是**通过 HTTP 把恶意内容塞给 Web 后端，再借后端之手把这条被污染的 SQL 发给数据库**。

**这就是为什么"注入点在参数里"而不是"在浏览器里"** —— 浏览器只是传话的，真正拼接和执行发生在后端。

### 4. 那为什么不能从外部直接访问数据库

原笔记留了一句：

```text
为什么无法外部访问呢——waf
```

展开：正常情况下，**数据库端口不应该对外网开放**。挡住"外部直接访问"的东西有两类：

1. **网络层 / 部署层**：数据库通常只监听内网地址，或只允许 Web 后端所在的主机连入，外网根本连不上（原笔记里写的"waf"是在提醒攻击者——就算端口开着，中间往往还有一层 WAF 在过滤）。
2. **WAF 层**：应用防火墙会对经过的 HTTP 流量做规则匹配与拦截。这也是为什么注入 payload 常常要**变形**（编码、大小写混写、十六进制、注释分割）才能穿过去。

反过来说，一旦真的**能**从外部直接连上数据库（比如弱口令 + 端口暴露），就不需要"注入"了——直接连上去查就行。**注入存在的意义，正是绕过这道"不让我直接连"的墙。**

### 5. 解析器 Parser：词法分析与语法树

原笔记：

```text
parser解析器：词法分析与语法树生成
分为两个阶段
1.词法阶段：解析器将sql字符串，将其分解为一个个有意义模块
2.语法syntax分析：将tokens组合成一颗解析树，参差化的结构来描述sql组分的关系
                               若sql语句存在错误，解析器会在此阶段报错
```

补完整：

**解析器（Parser）负责把一串字符变成"结构"。** 它分两个阶段：

1. **词法阶段（词法分析）**：把整条 SQL 字符串扫描一遍，**切分成一个个有意义的模块**，也就是 **token**。比如 `SELECT * FROM users` 会被切成 `SELECT`、`*`、`FROM`、`users` 这样的 token。
2. **语法分析（syntax）**：把这些 token **组合成一棵解析树**（原文写的"参差化的结构"，就是**树形/层次化结构**的意思），用这棵树来描述各 SQL 成分之间的关系——谁是子句、谁是谁的定语。

**如果 SQL 语句存在错误，解析器会在这个阶段报错**——这也是注入时判断"语句拼得对不对"的主要反馈来源（语法报错注入就建立在这上面）。

![SQL 在 MySQL 里的解析与执行流水线](../_assets/sql-parser-pipeline.svg)

**关键点**：解析器面对的只是"字符串"，它**不区分字符的来源**。所以攻击者只要拼接进来的内容**语法合法**，就会被一并纳入解析树——这就是 `SQL注入底层原理-解析与执行的博弈` 全篇讲的那件事。

### 6. 预处理器

原笔记：

```text
预处理器
1.语义检查：检查解析树上的内容是否都存在
2.权限验证：
```

补完整：

预处理器接收的是**已经成形的解析树**（此时语法已经没问题了），它负责**语义层面**的把关：

1. **语义检查**：检查解析树上的内容**是否都存在**。例如你在语句里引用了 `flag` 这张表，解析器不在乎它存不存在（它只管语法），**预处理器才去查**——表不存在、列不存在、函数不存在，都是在这一步报错。
2. **权限验证**：检查当前这个数据库用户**有没有权限**去做这件事。例如读某张表、读文件（`FILE` 权限）、写文件，都是在这一步被裁决。

> 这一步对注入的意义：**语法正确 ≠ 能执行**。你拼出来的语句语法一定得过解析器，但过不过得了预处理器，取决于你用的名字是否真实存在、当前账号是否有权限——这就是为什么"报错注入"和"能不能读写文件"是两回事。


### 8. 用"有没有 prepare"判断有没有注入

原笔记：

```text
sql审计发现有prepare预处理，导致无法提前闭合，则不存在sqli
```

这是把原理**当成审计方法**用，非常实用。展开：

- 做代码审计时，看到一个注入点时先别急着下结论，**先看这个位置有没有用 `prepare`（预处理 / 参数化查询）**；
- 如果用了 `prepare`，SQL 模板会**先被解析**，数据在解析之后才绑定到占位符上，**数据永远进不了词法分析**；
- 既然数据进不了语法结构，攻击者就**无法提前闭合引号**（引号也是被绑定的数据的一部分，不再具有语法意义）；
- 因此结论是：**用了 prepare 且绑定方式正确的点，不存在 SQL 注入**。

反过来，**只要看到的是字符串拼接（动态 SQL），就存在注入的可能**——这也正是上一篇要点中的"动态 SQL 是万恶之源"。

> 注意措辞：笔记说的是"**有 prepare → 不存在 sqli**"，这是一个**否定性判据**。它是充分条件，不是"所有注入都是因为没 prepare"这种绝对断言。

### 9. 手法与零散备忘

原笔记最后几行：

```text
sql注入传统手法

堆叠注入

十六进制解析条件官方——上下只要不是非二进
```

- **传统手法**：报错注入（error）、布尔盲注（bool）、时间盲注（time）——这三种是"没有正常回显位"时的标准出路，具体做法见 `00` 的第 6 节与 `布尔盲注-原理与利用`。

## 利用条件

| 结论 | 前提 |
|---|---|
| 解析器会"照单全收" | 拼接发生在解析之前；注入片段的语法合法 |
| 预处理器会放行 | 引用的表 / 列 / 函数真实存在，且当前用户有权限 |
| 能判断"这里有没有注入" | 代码里是**字符串拼接**而非 `prepare` |
| 能绕开外部的"墙" | 目标数据库端口不直接对外；payload 需要能穿过后置的 WAF |

## Payload 速查

| 目的 | 做法 |
|---|---|
| 探测注入点是否在语法层可控 | `'` / `"` / `)` 丢进去，看是否触发语法报错 |
| 观察解析器报错（报错注入入口） | `1'` 看措辞是"语法错误"还是"表不存在"——前者来自解析器，后者来自预处理器 |
| 确认参数化是否真的生效 | 用 `'` 试，若始终不报错且行为不受影响，多半是 `prepare` 绑定了 |
| 试探权限（预处理器把关项） | `SELECT LOAD_FILE('/etc/passwd')`、`SELECT ... INTO OUTFILE '...'` |
| 堆叠多语句 | `1'; SELECT ...;--`（需驱动支持） |

## 完整示例：一个 `'` 打过去，报错来自哪一层

```text
输入：1'  （注入点原本是 WHERE id = 1）

情况 A：报错 "You have an error in your SQL syntax near ''1'' at line 1"
        -> 来自【解析器】的语法错误
        -> 说明输入确实被拼进了 SQL，且没有经过 prepare  -> 存在注入

情况 B：报错 "Table 'db.xxx' doesn't exist"
        -> 来自【预处理器】的语义检查
        -> 说明语法已经通过，是名字或权限的问题  -> 语法层可控

情况 C：页面毫无变化、行为与不输入时一致
        -> 很可能用了 prepare，数据被当成纯值绑定
        -> 该点基本不存在注入
```

同样是"报错"，**报错来自哪一层**给出了完全不同的信息——这是这套架构知识最直接的用处。

```text
数据库视角的一条语句：
   字符串
     |  解析器：词法分析 -> 语法分析（语法错误在这里报）
     v
   解析树
     |  预处理器：语义检查 -> 权限验证（表/列不存在、无权限在这里报）
     v
   执行计划 -> 执行器 -> 结果集
```

## 踩坑与备注

- **原文用词说明**："系统的"指 MySQL 服务器层；"引擎"指存储引擎；"连接池"是连接复用设施。三者在原笔记里只有词、没有解释，本节的说明属**背景补充**。
- **原文的"客户端……返还给服务器"是速记语病**：按上下文应读作"把指令交给服务器、并从服务器接收结果"。这是对原文措辞的**订正性理解**，非新增结论。
- **`pid` 与 `gopher://` 两条孤立关键词无法还原**：原文在"为什么无法外部访问呢——waf"之后单独留了 `pid` 和 `gopher://` 两行，没有任何上下文。**此处按原样保留并标注存疑**。可以参考的背景是：`gopher://` 是一种在 SSRF 场景中常被用来"直接向内网服务（包括数据库端口）发送原始字节流"的协议，与上文"外部访问被挡住"的话题可能有关 —— 但**原文没有展开，不能据此断言作者所指**，仅作提示。
- **"十六进制解析条件官方——上下只要不是非二进"**：原文残缺，**含义存疑**，不做推断，按原样记录。
- **"`q`"是原文中的孤立噪声字符**，已删除。
- **`prepare` 判据是"充分"而非"必要"**：原文写的是"有 prepare → 不存在 sqli"。反方向（没有 prepare → 一定有注入）并不总成立，因为还可能存在白名单、强类型转换等其它防护。做审计结论时不要把必要条件和充分条件搞混。
