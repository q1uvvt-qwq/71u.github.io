## 区块、哈希与节点

### 区块

#### 定义

**区块是一批交易及其相关信息组成的数据集合。**区块链不会为每笔交易单独建立一条链，而是先把多笔交易整理到一个区块中，再把新区块接到已有区块之后。

一个区块通常可以分为两部分：

| 部分       | 主要内容                                 |
| ---------- | ---------------------------------------- |
| **区块头** | 前一区块哈希、交易摘要、时间、共识参数等 |
| **区块体** | 区块包含的具体交易                       |

不同区块链的字段不完全相同。例如，比特币区块头包含难度目标和nonce；以太坊区块还需要表达账户状态、Gas使用情况等信息。

### 哈希

##### 介绍

**哈希函数是一种把任意长度的数据转换为固定长度结果的计算方法。**得到的结果称为哈希值，也可以理解为数据的数字指纹。

示意如下：

```
输入：blockchain
输出：一串固定长度的哈希值

输入：Blockchain
输出：另一串完全不同的哈希值
```

即使只改变一个字符，哈希结果通常也会发生巨大变化。

**哈希函数的重要性质**

| 性质         | 含义                             | 安全作用                     |
| ------------ | -------------------------------- | ---------------------------- |
| **确定性**   | 相同输入始终得到相同结果         | 不同节点可以独立核对数据     |
| **固定长度** | 输入再长，输出长度也固定         | 便于存储和比较               |
| **雪崩效应** | 输入稍微变化，输出就明显变化     | 容易发现数据被改动           |
| **单向性**   | 很难从哈希值反推出原始内容       | 防止通过摘要直接还原数据     |
| **抗碰撞性** | 很难找到两份不同数据产生相同哈希 | 降低伪造相同数据指纹的可能性 |

哈希不是加密。加密数据可以使用密钥解密；哈希通常没有“解密”过程。

##### 区块链应用

每个新区块通常会保存前一个区块的哈希：

```
区块100             区块101             区块102
哈希：H100  ←  前块哈希：H100  ←  前块哈希：H101
                   哈希：H101           哈希：H102
```

这种引用关系让区块按照顺序连接起来。

如果区块100中的数据发生变化：

```
区块100数据变化
      ↓
区块100的哈希变化
      ↓
区块101保存的前块哈希失效
      ↓
区块102及后续连接也受到影响
```

因此，修改历史区块会产生明显的不一致。不过，**仅仅把哈希连接起来还不足以阻止篡改**。真正的保护还来自共识机制、全节点验证以及重新构造后续区块所需的成本。

#### 区块摘要

区块中可能包含很多交易。为了用一个固定长度的值代表全部交易，区块链通常会使用**Merkle树**。

假设区块包含四笔交易：

```
交易A → 哈希A ┐
               ├→ 哈希AB ┐
交易B → 哈希B ┘          │
                          ├→ Merkle根
交易C → 哈希C ┐          │
               ├→ 哈希CD ┘
交易D → 哈希D ┘
```

最上方得到的结果叫作**Merkle根**，它会被写入区块头。

任何一笔交易发生变化，都会导致：

```
交易哈希变化
    ↓
中间哈希变化
    ↓
Merkle根变化
    ↓
区块头哈希变化
```

Merkle树还允许节点在不下载全部交易的情况下，验证某笔交易是否被包含在某个区块中。



### 节点

#### 定义

**节点是运行区块链软件并参与网络通信的计算机。**

节点可以接收交易和区块、检查数据是否符合规则，并把有效数据传播给其他节点。节点不是某一台中央服务器，而是分布在网络中的多个独立参与者。

常见节点类型包括：

| 类型         | 作用                                         |
| ------------ | -------------------------------------------- |
| **全节点**   | 保存验证所需的数据，独立检查交易和区块       |
| **轻客户端** | 主要保存区块头，通过证明或全节点获取部分数据 |
| **归档节点** | 除当前状态外，还保存大量历史状态数据         |
| **出块节点** | 在验证基础上参与挖矿或权益证明出块           |

矿工和验证者通常需要节点提供交易及区块信息，但**节点不一定是矿工或验证者**。普通用户也可以运行只负责验证的全节点。

钱包也不一定是节点。很多钱包通过第三方节点查询余额、发送交易和读取区块链状态。



#### 处理过程

交易从发出到写入账本，大致经过以下过程：

```
钱包签署交易
      ↓
发送给某个节点
      ↓
节点检查并传播
      ↓
有效交易进入待处理交易池
      ↓
矿工或验证者组成新区块
      ↓
新区块广播给其他节点
      ↓
各节点独立验证
      ↓
有效区块加入本地账本
```

节点验证的内容可能包括：

- 交易格式是否正确；
- 数字签名是否有效；
- 资产是否可以被使用；
- 是否存在重复花费；
- 智能合约执行结果是否正确；
- 区块是否正确引用前一个区块；
- 区块是否满足当前共识规则。

一个节点发送了区块，不代表其他节点必须接受。其他节点会独立执行检查。



## 本章要点

**区块负责整理交易，哈希负责连接和识别数据，节点负责保存和验证，共识机制负责让节点选择共同认可的历史。**

“区块链难以篡改”来自这些机制的共同作用，并不是单独由哈希实现的。
