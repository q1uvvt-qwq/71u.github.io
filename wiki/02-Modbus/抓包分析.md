## 一句话概括

Modbus 抓包极其好读：链路上没有加密，MBAP 头里的事务标识让请求与响应一一配对，功能码直接告诉你对方在"读"还是"写"，寄存器值就是十六进制明文。学会看一帧 Modbus TCP，等于学会了在链路上判断"谁在控制谁"。

> 素材说明：靶场素材里没有 Modbus 的 pcap 文件（有 pcap 的是 IEC 104，见 `../03-IEC104/抓包分析.md`）。本篇"实测"部分来自平原链指南里 `modpoll` 的真实终端输出与 HMI 观察，帧结构部分按 Modbus 规范推导，两者都已在文中标明归属。

## 原理

### 从抓包能读出什么信息

| 观察点 | 能推断出什么 |
|---|---|
| 谁是请求方 | 主站（合法 SCADA/网关，或攻击者的 Rogue Master） |
| 轮询间隔 | 采集周期，例如每 5 秒读一次 HR0-HR9 |
| 读的地址区间 | 点表：攻击者最想要的东西，不用翻配置文件就能反推 |
| 谁在发 FC06/FC16 | 控制指令；如果不是 SCADA 发的，就是异常 |
| 值的突变 | 例如 HR93 从 100 跳到 0，说明限功率被下发 |
| Unit ID | 网关后面有几台设备、各自编号 |

"谁在发写命令"是 Modbus 检测里最有价值的规则。正常情况写入源应唯一（SCADA 或网关），一旦出现第二个源，基本可判定为 Rogue Master。

## 抓包方法

### 抓包位置的选择

```text
方式一：镜像端口（真实环境常用）
  SCADA ──┐
          ├── 交换机 ──(镜像口)── 抓包机（Wireshark）
  RTU ────┘

方式二：MITM（靶场/教学常用）
  攻击者把自己插进链路中间，同时看到"原包"和"转发包"（详见 山区链 的 ARP 欺骗）

方式三：在主机上直接抓（最省事）
  在 SCADA 网关或通信系统这类"合法主站"上抓本机流量
```

靶场里最典型的是方式三：山区在维护工作站上用 `tcpdump` 抓 IEC 104 的 2404；Modbus 场景直接在被允许访问 RTU 的通信系统（平原链的 `10.0.6.8`）上抓 502。

### 常用命令

```bash
# 抓 502 端口，-nn 不做 DNS/端口名解析，-s0 抓全包，-w 存文件
sudo tcpdump -i ens18 -nn -s0 tcp port 502 -w /tmp/modbus.pcap

# 先看摘要，再决定深挖哪一条流
tcpdump -r /tmp/modbus.pcap -nn | head -30

# 只看某台风机
tcpdump -i ens18 -nn -s0 tcp port 502 and host 10.0.5.6 -w /tmp/wt01.pcap
```

抓包时长要覆盖一个完整轮询周期。IEC 104 的抓包里记录过：`frontend3-lower` 的轮询周期是 60 秒，在周期尾部才开始抓，短时间只能看到最后一台设备。Modbus 同理，抓不足时间会误判"只有一台 RTU 在通信"。

### Wireshark 里怎么看

| 操作 | 用途 |
|---|---|
| 显示过滤器 `modbus` | 只看 Modbus 报文 |
| `tcp.port == 502` | 按端口过滤 |
| `modbus.func_code == 6` | 只看写单个寄存器（找"谁在改参数"） |
| `modbus.func_code == 3` | 只看读保持寄存器（看轮询节奏） |
| `modbus.reference_num` / `modbus.regval_uint16` | 过滤具体寄存器地址与值 |
| 右键 → Follow → TCP Stream | 看这连接上完整的请求响应对话 |

定义：请求与响应的配对依据是 MBAP 事务标识，请求和响应的事务标识必须相同。Wireshark 会自动标注 `[Response in frame: N]` 与 `[Request in frame: M]`，手工看时认这个字段即可。

## 实测过程

平原链第 14 步，在通信系统1 上读三台 RTU 的 HR93：

```bash
modpoll -m tcp -p 502 -a 1 -0 -r 93 -c 1 -t 4 -1 10.0.5.6
modpoll -m tcp -p 502 -a 1 -0 -r 93 -c 1 -t 4 -1 10.0.5.4
modpoll -m tcp -p 502 -a 1 -0 -r 93 -c 1 -t 4 -1 10.0.5.5
```

预期输出：

```text
[93]: 100
```

含义逐层解释：

```text
[93]   → 寄存器偏移 93，也就是点表里的 HR93
100    → 读回的 16 位无符号值 = 100
业务   → ActivePowerLimitPercent = 100%，风机没有被限功率
```

第 15 步写入：

```bash
modpoll -m tcp -p 502 -a 1 -0 -r 93 -c 1 -t 4 -1 10.0.5.6 0
```

输出：

```text
Protocol configuration: MODBUS/TCP, FC6
Written 1 reference.
```

`modpoll` 明确告诉你用的是 FC6（写单个保持寄存器），因为 `-c 1` 只写 1 个寄存器。第 16 步回读得到 `[93]: 0`，协议层写入生效。

业务层验证（第 17 步，回到 HMI）：

```text
场站总有功功率 → 0 kW
ActivePowerLimitPercent 从 100 → 0
三台风机状态 → LIMITED_STOP / 停机
告警 → POWER_LIMIT_ZERO
事件记录 → ActivePowerLimitPercent changed 100% -> 0%
```

完整的证据链是抓包/命令输出（协议层）加 HMI 页面（业务层）。只有协议层成功、业务层没变化，说明还有一道校验挡着，这正是"防非预期"的设计目标。

## 安全视角

- 报文在链路上是明文，这是最直接的问题。Modbus 没有可选的加密模式（Modbus Security 是后来的扩展，部署极少），任何能在链路上看到流量的人都能看到全部点表和值。防护只能靠分区隔离 + 交换机端口安全 + 工业防火墙。
- 抓包本身就是一种侦察手段。攻击者往往不需要点表文件：在镜像口抓一个轮询周期，看读哪些地址、哪些寄存器会变化，点表就自己浮现出来。反过来，防守方也应意识到"点表不是秘密"，边界落在能不能写上。
- MITM 场景下要会辨认重复帧。ARP 欺骗会把同一报文送给攻击者两次（原始帧 + 转发帧），看到"同一 seq 出现两次"别以为设备在重传。这一点在 IEC 104 的 MITM 抓包里被明确记录过（见 `../03-IEC104/抓包分析.md`）。
- 审计要在网关层做。Modbus 设备自身不记日志，所以"谁在什么时候写了 HR93"只能靠 SCADA/网关或工业防火墙记录。没有这层日志，攻击完成后无法回溯。
