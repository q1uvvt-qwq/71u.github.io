## 节点通信

### P2P网络

在普通网站中，客户端通常连接固定服务器：

```
用户 → 中央服务器 → 数据库
```

区块链P2P网络中，每个节点可以同时连接多个节点：

```
节点A ─ 节点B ─ 节点C
  │       │       │
节点D ─ 节点E ─ 节点F
```

一个节点既接收数据，也可以把有效数据继续发送给其他节点。节点不需要与全网每台计算机直接连接，只需连接若干对等节点，信息便能逐步扩散。

这里的**peer**就是当前节点连接的另一个节点。



### 节点连接其他节点

新节点启动时还不知道应该连接谁，因此需要先获得一批节点地址。常见来源包括：

- 软件内置的初始节点；
- DNS种子或引导节点；
- 以前连接过的节点记录；
- 其他节点提供的地址；
- 运营者手动指定的节点。

比特币通常利用DNS种子等方式寻找初始节点。以太坊使用引导节点和节点发现协议；引导节点主要帮助新节点认识其他节点，不负责统一管理网络。

找到候选节点后，双方进行握手，确认：

- 使用的区块链网络；
- 协议版本；
- 支持的功能；
- 当前掌握的区块信息；
- 连接是否满足基本规则。

主网节点不会把测试网数据当作主网数据接受。



**节点通常会**：

- 同时维持多个连接；
- 主动建立一部分出站连接；
- 接受一定数量的入站连接；
- 更换失效或行为异常的节点；
- 限制单个来源占用的资源；
- 拒绝或封禁持续发送无效数据的节点。

连接数量多不等于绝对安全，还需要考虑节点来源、网络位置和客户端是否具有多样性。

### 节点交易传播

一笔签名交易从钱包进入网络，大致经过：

```
钱包构造并签署交易
        ↓
发送给钱包连接的节点或RPC服务
        ↓
节点进行本地验证
        ↓
有效交易进入该节点的内存池
        ↓
节点通知相邻节点
        ↓
其他节点请求并验证交易
        ↓
验证通过后继续传播
```

每个节点都会独立检查交易。某个节点说“这笔交易有效”，其他节点不会直接相信。

节点可能检查：

- 交易格式；
- 数字签名；
- nonce或UTXO；
- 余额和手续费；
- 合约执行的基本条件；
- 是否与已知交易冲突；
- 是否符合本地转发策略。

#### 内存池

**内存池（mempool）是节点暂时保存待处理交易的本地区域。**

内存池不属于已经确认的区块链：

```
内存池中的交易：等待入块
区块中的交易：已经被区块收录
```

每个节点的内存池可能不同，原因包括：

- 接收交易的时间不同；
- 设置的最低手续费不同；
- 内存容量不同；
- 节点重启或删除了交易；
- 某些交易只传播到了部分网络；
- 节点采用了不同的转发策略；
- 节点看到了相互冲突的交易。

所以，“某个节点能查到待处理交易”不代表全网节点都已经看到它。

### 节点数据传播

P2P网络常见两种通信方式。

**广播式传播**

节点把新信息告诉相邻节点，相邻节点再继续传播。这种方式也称为**gossip**。

```
节点A获得新交易
  ├→ 通知节点B
  ├→ 通知节点C
  └→ 通知节点D
```

**请求与响应**

节点先告诉对方“我有某个数据”，对方需要时再请求完整内容，避免重复发送大量数据。

比特币中可以简化为：

```
inv：我有这笔交易或这个区块
getdata：请把完整数据发给我
tx/block：返回交易或区块
```

比特币节点在转发前会验证交易和区块。[比特币P2P网络说明](https://developer.bitcoin.org/devguide/p2p_network.html)描述了这种协作维护方式。



### 区块传播

矿工或验证者产生新区块后，会把新区块发送给相邻节点：

```
区块生产者广播新区块
        ↓
相邻节点检查区块
        ↓
验证交易和状态变化
        ↓
有效区块继续传播
        ↓
节点更新自己认可的链头
```

节点会检查：

- 父区块是否已知；
- 区块结构是否正确；
- 共识证明是否有效；
- 区块中的交易是否合法；
- 执行后的状态是否正确；
- 区块是否符合当前分叉选择规则。

为了减少网络带宽，一些协议只先传播区块摘要、交易编号或压缩区块。接收节点已经拥有的交易不必再次完整下载。

### 比特币与以太坊通信结构的区别

| 比特币                        | 以太坊                                    |
| ----------------------------- | ----------------------------------------- |
| 节点通过P2P协议传播交易和区块 | 执行层和共识层分别拥有P2P通信             |
| 矿工从内存池选择交易          | 执行客户端维护交易池                      |
| 新区块通过节点网络传播        | 共识客户端传播区块、证明和验证者消息      |
| 节点验证工作量证明和交易      | 执行客户端验证交易，共识客户端处理PoS共识 |

当前以太坊节点主要由两个客户端组成：

```
执行客户端
├─ 接收和传播交易
├─ 维护交易池和链上状态
└─ 执行EVM交易

共识客户端
├─ 接收和传播区块
├─ 处理验证者证明
└─ 执行分叉选择规则
```

两个客户端通过本地Engine API通信。验证者软件则负责在被选中时提议区块和提交证明。[以太坊节点架构](https://ethereum.org/developers/docs/nodes-and-clients/node-architecture)对这两套网络进行了区分。

### 常见网络攻击

| 攻击           | 含义                           | 可能影响                           |
| -------------- | ------------------------------ | ---------------------------------- |
| **女巫攻击**   | 创建大量虚假节点身份           | 增加控制连接和信息来源的机会       |
| **日蚀攻击**   | 控制目标节点的全部或大部分连接 | 隔离目标，使其看到片面的区块和交易 |
| **拒绝服务**   | 用大量连接或消息消耗资源       | 导致节点变慢、掉线或无法服务       |
| **网络分区**   | 一部分节点无法与另一部分通信   | 传播延迟、临时分叉或最终性中断     |
| **选择性转发** | 节点故意不传播特定数据         | 交易延迟或局部审查                 |
| **流量分析**   | 观察交易最早从哪里出现         | 推测交易来源和地址与IP的关系       |
| **恶意RPC**    | 向钱包返回错误或不完整信息     | 误导界面、侵犯隐私或阻断广播       |
