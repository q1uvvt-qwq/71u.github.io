## 一句话概括

新增漏洞不应直接写死代码，而要按 Profile 化流程处理：先收集漏洞资料并提取仿真要素，再生成蜜罐侧内部 Profile。定义：Profile 描述的是仿真和捕获，不是漏洞利用代码。当输入来自漏洞库的 Nuclei 模板时，模板要先经过静态校验和转换可行性评估，只有通过校验的模板才进入 Profile 生成环节。

已有项目的可借鉴点与不足见 [建设路径](../00-蜜罐基础/建设路径.md)，本篇只讲新增漏洞时怎么走流程。

## 从一个 CVE 变成蜜罐 Profile 的流程

每新增一个漏洞，不应直接写死代码，而是按 Profile 化流程处理。

### 输入材料

每个漏洞至少收集：

- 官方安全公告
- NVD/CVE 描述
- 厂商修复公告
- ProjectDiscovery Nuclei Template
- IDS/WAF 公开规则
- 公开 PoC 或复现分析
- 威胁情报报告
- 漏洞影响版本和组件指纹

### 提取仿真要素

从资料中提取：

| 要素 | 示例 |
| --- | --- |
| 服务类型 | Next.js、Confluence、Java Web、SharePoint |
| 指纹路径 | `/_next/`、`/confluence/`、`/wiki/`、`/login.action` |
| 请求方法 | GET、POST、PUT |
| 关键 Header | Content-Type、User-Agent、Next-Action、自定义框架 Header |
| 关键参数 | Query 参数、表单字段、JSON 字段、特殊序列化字段 |
| 探测响应 | 200、404、500、特定错误信息、特定 JSON 结构 |
| 利用特征 | JNDI 字符串、OGNL 表达式、文件读取路径、反连命令、下载命令 |
| IOC 提取规则 | URL、域名、IP、Base64、命令片段、文件名 |

### Profile 示例结构

建议用 YAML 或 JSON 描述漏洞仿真 Profile：

```yaml
id: cve-xxxx-yyyy
name: Example Web RCE Honeypot Profile
family: web-rce
product: example-framework
severity: critical
listener:
  protocol: http
  ports: [8080]
fingerprints:
  paths:
    - /example
    - /_framework/static/
  headers:
    server: example-server
routes:
  - method: GET
    path: /example
    response:
      status: 200
      headers:
        content-type: text/html
      body: "<html><title>Example App</title></html>"
  - method: POST
    path: /example/action
    capture_body: true
    response:
      status: 500
      body: "Internal Server Error"
ioc_extractors:
  urls: true
  domains: true
  ips: true
  base64: true
  command_keywords:
    - curl
    - wget
    - bash
    - sh
    - powershell
tags:
  - web
  - rce
  - honeypot
```

注意：Profile 里描述的是"仿真和捕获"，不是"漏洞利用代码"。

## 蜜罐侧处理流程

蜜罐侧处理流程如下：

```text
1. 模板接收
2. 来源校验
3. 文件完整性校验
4. YAML 语法解析
5. Nuclei Schema 静态校验
6. 安全风险扫描
7. 协议和能力识别
8. 转换可行性评估
9. 特征抽取
10. 生成内部 Profile
11. Profile 静态校验
12. 生成仿真响应策略
13. 加载到蜜罐 Sensor
14. 采集 HTTP 流量
15. 记录 JSONL 日志
16. Payload/IOC 分析
17. 输出分析报告和检测规则参考
18. 向漏洞库反馈转换结果和状态
```

### 模板接收

蜜罐侧接收：

- 单个模板文件
- 模板目录
- Git 提交
- API 上传包
- 模板清单 Manifest

接收后必须先进入隔离的待处理区，不允许直接进入运行区。

### 静态校验

校验内容：

- YAML 是否可解析。
- 是否包含 `id`。
- 是否包含 `info.name`。
- 是否包含 `info.severity`。
- 是否包含至少一个协议块。
- 是否包含危险协议块，例如 `code`、`javascript`、`headless`。
- 是否包含 `flow`、动态变量、函数调用、OAST、fuzzing。
- 是否包含外部文件引用。
- 是否包含无法静态解释的 Payload 生成逻辑。
- 是否包含模板签名或 digest。

### 转换可行性评估

转换结果分为：

| 状态 | 含义 |
| --- | --- |
| auto_convertible | 可自动转换 |
| partial_convertible | 可部分转换，需要人工补充 |
| manual_review_required | 必须人工审核 |
| unsupported | 不支持转换 |
| rejected | 因安全或格式问题拒绝 |

### Profile 生成

蜜罐内部 Profile 应包含：

- 漏洞基础信息
- 产品信息
- 协议类型
- 仿真路径
- 请求方法
- Header 特征
- Query/Body 特征
- 响应状态码
- 响应 Header
- 响应 Body 模板
- Payload 捕获规则
- IOC 提取规则
- 行为分类规则
- 安全限制
- 来源模板追溯信息

### 运行与采集

运行时只加载蜜罐内部 Profile，不加载原始 Nuclei 模板。
运行服务只接收外部请求，不向真实目标发送模板中的请求。
所有请求均记录结构化日志，Payload 受控留存。
