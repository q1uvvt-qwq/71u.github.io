## 一句话概括

**协议是「两台设备之间怎么对话」的规则手册；DNS 则是这本手册的「通讯录」，负责把人类记得住的域名翻译成机器认得的 IP。** 一次访问从敲下域名到看到页面，中间要经过「DNS 解析 → 分层封装 → 逐层解封」三步。

## 原理

### 1. 什么是网络协议

网络协议决定数据在两台设备间运输的方式。它更像是一本**多国语言对照的物流规则手册**，规定了：

- **如何打包**：数据如何分成包、如何封装（TCP 分段、IP 分片）。
- **如何写地址**：地址格式是什么（IP 地址、MAC 地址、端口号）。
- **如何交互**：双方如何建立连接、如何确认收货、如何重发丢失的包裹、如何结束对话（TCP 三次握手、ACK 确认、重传机制）。
- **如何路由**：包裹上应该写哪些信息以便路由器进行转发。

**网络协议共同定义和管理的规则，确保了数据能够在两台设备间进行有效、可靠和有序的传输。**

### 2. 跨平台：为什么同样一份代码能跑在不同系统上

#### C/C++ 的跨平台原理

**跨平台**指代码可在多个平台实现基本大差不差的功能。C/C++ 的路线是：**编译后直接生成平台对应的可执行文件**。

```text
源码 (hello.c)
   │  在 Windows 上编译
   ├──────────────► hello.exe   （Windows 可执行文件）
   │  在 Linux 上编译
   └──────────────► hello       （Linux ELF 可执行文件）
```

也就是说，**源码是跨平台的，编译产物不是**。你必须在目标平台上（或交叉编译）重新编译一次，才能得到能被那个平台直接执行的二进制。

#### JAVA 的跨平台原理

JAVA 编译后的**字节码文件无法直接执行**，而是需要服务器通过开启自身的 **JVM** 功能对其进行加载才能执行。

```text
Hello.java ──javac──► Hello.class（字节码，平台无关）
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
          JVM(Windows) JVM(Linux)  JVM(macOS)
              │           │           │
              ▼           ▼           ▼
           各自能执行的机器码
```

> **两条路线的本质区别**：C/C++ 把「翻译成机器码」这件事放在**编译期**，做一次、针对一个平台；Java 把它推迟到**运行期**，由 JVM 在目标机器上临场翻译。多了一层抽象 = 跨平台，代价是多了一个运行时的解释/编译开销。
>
> 在 Web 安全里的直接体现：**PHP 属于「解释执行」这一类**，源码永远不会被编译成二进制，`highlight_file()` / `php://filter` 才能读到明文源码；如果 PHP 是编译型语言，读源码这类漏洞就不存在了。

### 3. 服务器与客户端、端口与访问、协议

- **服务器与客户端**：一次通信中，主动发起请求的一方是客户端，被动等待并响应的一方是服务器。
- **端口与访问**：IP 定位到**哪台机器**，端口定位到**机器上的哪个服务**。同一台机器上 80 是 Web、3306 是 MySQL、22 是 SSH，靠端口区分。
- **协议**：**约束客户端发送请求的格式与方式**。

### 4. OSI 模型

| 层级 | 名称 | 功能描述 | 关键协议/设备 | 数据单位 |
| :--- | :--- | :--- | :--- | :--- |
| **7** | **应用层** | 为**应用程序**提供网络服务接口。是用户与网络交互的界面。 | HTTP, HTTPS, FTP, SMTP, DNS, SSH | **Data** |
| **6** | **表示层** | 负责**数据格式转换**，如加密解密、压缩解压缩、编码转换。确保应用层数据能被对方理解。 | SSL/TLS, MPEG, JPEG | **Data** |
| **5** | **会话层** | 负责建立、管理和终止**会话**（Session）。区分不同应用程序的通信流。 | NetBIOS, RPC | **Data** |
| **4** | **传输层** | 提供**端到端**的可靠或不可靠数据传输。负责**流量控制**、**差错校验**和**数据重发**。 | **TCP**（可靠）, **UDP**（不可靠） | **Segment** (TCP) / **Datagram** (UDP) |
| **3** | **网络层** | 负责**逻辑寻址**和**路由选择**，将数据包从源主机跨越多个网络发送到目的主机。 | **IP**, ICMP, RIP, OSPF, **路由器** | **Packet** |
| **2** | **数据链路层** | 负责在**同一局域网内**的节点间传输数据。进行**物理寻址**（MAC 地址）和差错控制。 | Ethernet, PPP, Switch, Bridge | **Frame** |
| **1** | **物理层** | 定义物理设备的电气、机械规格，传输**比特流**（0 和 1）。 | RJ45, 光纤, 同轴电缆, 集线器 | **Bit** |

**核心思想**：每一层都为其上一层提供服务，并且只关心与**对等层**（Peer Layer）之间的通信。例如，发送方的“传输层”认为它是在与接收方的“传输层”直接对话，实际上，数据是垂直向下封装，然后传输，再在接收端垂直向上解封。

OSI 是一个**理论模型**，而实际中广泛使用的是 **TCP/IP 模型**（也称为互联网协议套件）：

| OSI 参考模型 | TCP/IP 模型 | TCP/IP 协议族 |
| :--- | :--- | :--- |
| 应用层、表示层、会话层 | **应用层** | HTTP, FTP, DNS, SMTP |
| 传输层 | **传输层** | TCP, UDP |
| 网络层 | **网络层** | IP, ICMP |
| 数据链路层、物理层 | **网络接口层** | Ethernet, Wi-Fi |

#### 请求过程：先封装再运输后拆解

原文此处为一张「请求过程」截图，其含义用文字描述如下：

```text
发送方（自上而下逐层加头）              接收方（自下而上逐层去头）
 ┌──────────────┐                       ┌──────────────┐
 │ 应用层  HTTP  │ ─┐                    │ 应用层  HTTP  │ ← 拿到原始请求
 ├──────────────┤  │ 加 TCP 头           ├──────────────┤
 │ 传输层  TCP   │ ─┤                    │ 传输层  TCP   │
 ├──────────────┤  │ 加 IP 头             ├──────────────┤
 │ 网络层  IP    │ ─┤                    │ 网络层  IP    │
 ├──────────────┤  │ 加帧头帧尾            ├──────────────┤
 │ 链路层  Frame │ ─┘                    │ 链路层  Frame │
 └──────────────┘                       └──────────────┘
        │                                       ▲
        └────────── 物理链路传输 ───────────────┘
```

一句话：**发送方先封装（每层各加一个头）再运输，接收方逐层拆解（每层各剥一个头）**。所以抓包时看到的「原始 HTTP」其实是剥掉下面所有层之后剩下的部分 —— 这也解释了为什么 Wireshark 里 HTTP 流是干净的，而底层帧里全是各层头。

### 5. DNS

**DNS（域名系统）** 核心功能是进行**域名与 IP 地址**之间的相互解析。

- **域名**：人类容易记忆的网站地址（如 `www.google.com`）。
- **IP 地址**：计算机在网络上的唯一逻辑地址（如 `142.251.42.206`）。

**DNS 的作用就是充当“翻译官”**，将人类友好的域名转换为机器可识别的 IP 地址，从而建立连接。

#### 域名

**域名**是用于在互联网上定位计算机（通常是服务器）的、便于人类记忆和识别的**字符串序列**。它对应的是网络上设备的**数字 IP 地址**。

- **简单比喻**：域名就像你的**手机通讯录里的联系人姓名**，而 IP 地址则是这个联系人的**实际电话号码**。你不需要记住一长串数字，只需要记住名字（域名）就可以找到他（访问网站）。

原文此处为一张「域名层级」截图，其结构用下表还原。以 `www.google.com` 为例：

| 部分 | 名称 | 描述 | 在 `www.google.com` 中的例子 |
| :--- | :--- | :--- | :--- |
| 最右侧 | **根域** | 通常为空，用点表示，在域名末尾通常省略。 | （隐含的 `.`） |
| 右侧第一部分 | **顶级域** | 代表国家/地区或组织类型。 | `.com` |
| 右侧第二部分 | **二级域** | **你注册的独一无二的域名**。这是域名的核心身份。 | `google` |
| 左侧部分 | **子域名** | 用于在域名下创建独立的分区或服务。 | `www` |

> **子域名为什么要单独收集？** 因为主站往往加固得最好，而 `test.`、`dev.`、`admin.` 这类子域名常常是疏于维护的入口 —— 这正是 OneForAll 这类工具存在的意义（见 `01-信息收集/子域名-OneForAll.md`）。

- **URL**：是完整的**网页地址**，包含了访问资源所需的全部信息。
  - 示例：`https://www.google.com/search?q=hello`
  - 分解：
    - `https://` —— **协议**
    - `www.google.com` —— **域名**
    - `/search` —— **路径**
    - `?q=hello` —— **参数**

**简单说：域名是 URL 的一部分。**

#### 路径

**路径**是一个字符串，它描述了文件或目录在文件系统中的**具体位置**，或者资源在某个应用程序或服务中的**访问地址**。

简单来说，**路径就是“怎么找到你想要的东西”的路线说明**。根据目标位置的不同，路径主要分为两大类：

##### 1. 文件系统路径

**a) 绝对路径**

- **定义**：从文件系统的**根目录**开始，完整地描述文件位置的路径。
- **特点**：具有唯一性，无论当前你在什么位置，绝对路径都能指向同一个目标。
- **示例**：
  - **Linux/macOS**：`/home/user/documents/report.pdf`（从根目录 `/` 开始）
  - **Windows**：`C:\Users\User\Pictures\photo.jpg`（从驱动器盘符 `C:\` 开始）

**b) 相对路径**

- **定义**：以**当前工作目录**为起点，来描述目标文件的相对位置。
- **特点**：更简短，但它的有效性依赖于当前所在的位置。
- **示例**：假设当前目录是 `/home/user/`
  - `documents/report.pdf` —— 指向同一个文件
  - `../downloads/file.zip` —— `../` 表示上级目录
  - `./project/script.py` —— `./` 表示当前目录（通常可省略）

##### 2. URL 路径（网络路径）

这是在互联网上，用于定位特定资源（如网页、图片、API 接口）在服务器上的位置。

- **定义**：URL 中位于**域名之后**、**参数之前**的部分。
- **结构**：`https://www.example.com/**路径/到/资源.html**`
- **示例**：
  - `https://www.google.com/search` —— 路径是 `/search`，指向搜索功能
  - `https://github.com/torvalds/linux` —— 路径是 `/torvalds/linux`，指向一个特定的代码仓库
  - `https://example.com/images/logo.png` —— 路径是 `/images/logo.png`，指向一张图片

#### 为什么 `/search` 这个路径相当于「查找功能」

`/search` 这个路径**确实相当于**触发了查找功能，但这是一种**约定、映射和抽象**，并没有改变「路径本身是参数」的本质。

**路径是「功能的钥匙」**：当服务器收到一个带有特定路径的请求时，它会根据预设的**路由规则**，将这个路径**映射**到后端一个真正的功能函数上。

1. **声明一个“约定”**：开发者在服务器端预先定义好：“凡是访问 `/search` 这个路径的请求，都去执行 `searchProducts()` 这个函数。”
2. **用户触发约定**：您在浏览器地址栏输入 `.../search` 或点击一个指向它的链接。
3. **服务器执行映射**：服务器（如 Nginx、Apache，或 Node.js/Spring/Django 等 Web 框架）接收到请求，解析出路径 `/search`，然后根据规则找到并调用对应的 `searchProducts()` 函数。
4. **功能执行**：`searchProducts()` 函数开始执行，它可能会查询数据库，然后生成一个 HTML 页面或 JSON 数据返回给浏览器。

- **静态路径**（如 `/about.html`）更接近“路径作为位置”的原始含义，它直接指向一个物理文件。
- **动态路径**（如 `/search`）则是一个**抽象的逻辑端点**，它背后没有叫 `search` 的文件，它的意义完全由服务器端的路由配置决定。

> **对做题的意义**：拿到一个路径先判断它属于哪种。**静态路径 → 想目录扫描、备份文件、路径遍历；动态路径 → 想它对外暴露了哪些参数、路由有没有隐藏分支**。很多题目一个 `?` 参数就是全部入口。

#### 路径 vs 路由

| 特性 | **路径** | **路由** |
| :--- | :--- | :--- |
| **本质** | 一个**字符串**，一个**标识符** | 一个**过程**或一套**规则/映射关系** |
| **角色** | **被动**的，它是被处理的对象 | **主动**的，它是处理和执行的过程 |
| **类比** | **街道地址**（如“人民路 1001 号”） | **GPS 导航系统**或**邮递分拣流程** |
| **功能** | 回答“**在哪里？**”或“**是什么？**” | 回答“**怎么去？**”或“**交给谁处理？**” |
| **表现形式** | **URL 中的一部分**（如 `/products/123`） | 服务器或框架中的代码和配置（路由表） |

**1. 路径 —— “目标的地址”**

路径是一个描述性的信息，它指明了资源的位置或身份。

- **在文件系统中**：`C:\Users\Doc\report.pdf` 是一个路径，它告诉你文件在磁盘上的具体位置。
- **在 URL 中**：`https://example.com/products/shoes` 中的 `/products/shoes` 是一个路径，它标识了你想要访问网站上的哪个资源（“鞋子”产品分类）。

**路径的核心是标识，它本身不做任何事。**

**2. 路由 —— “寻址的规则”**

路由是一个动态的过程，它根据“路径”这个地址，决定下一步该做什么。

- **在网络中**：路由器查看数据包的目标 IP 地址（类似于“路径”），然后根据其内部的**路由表**，决定将这个数据包从哪个端口发送出去。**这个查表并转发的动作就是路由**。
- **在 Web 开发中**：当请求 `https://example.com/products/shoes` 到达服务器时，**路由系统**会解析路径 `/products/shoes`，然后根据预先配置的规则（路由表），将这个请求**映射**到相应的处理函数（Controller）上。**这个匹配和分发的动作就是路由**。

### 6. 回到 DNS：几个相关命令

#### `ping <域名或IP地址>`

`ping www.example.com` 实际上是在做以下几件事：

1. **测试连通性**：检查你的电脑能否与目标服务器建立通信。这是最基本、最快速的网络故障排查方法。
2. **测量延迟**：计算数据包从你的电脑到目标服务器再返回所需的**时间**，这个时间称为**延迟**，单位是毫秒。
3. **DNS 解析验证**：验证域名能否被正确解析为 IP 地址。如果 `ping` 能显示 IP 地址但无法连通，说明问题可能出在网络路由上；如果连 IP 都解析不出来，那就是 DNS 出了问题。

**常见应用场景**

1. **网站打不开时**：
   - 先 `ping` 一下那个网站。如果不通，说明是你的网络问题或者对方服务器宕机。
   - 再 `ping` 一个你知道肯定在线的网站（如 `www.baidu.com`）。如果这个也不通，那肯定是你的本地网络连接出了问题。
2. **玩网络游戏卡顿时**：`ping` 游戏服务器的地址，查看延迟和丢包率。高延迟和丢包是导致游戏卡顿的元凶。
3. **验证 DNS 是否工作**：如果 `ping 域名` 能显示出 IP 地址，说明 DNS 解析是正常的。

#### `nslookup 域名`

| 特性 | `nslookup 域名` | `ping 域名` |
| :--- | :--- | :--- |
| **核心功能** | **域名解析查询** | **网络连通性测试** |
| **回答的问题** | “这个域名对应哪个 IP 地址？” | “我能和这个域名的服务器通通讯吗？延迟多大？” |
| **使用协议** | **DNS** | **ICMP** |
| **工作层级** | 应用层 | 网络层 |
| **主要输出** | **IP 地址**、权威 DNS 服务器、所有记录类型 | **连通状态、延迟时间、丢包率** |
| **依赖关系** | `ping` **依赖** `nslookup` 的第一步结果 | 它**隐含地**执行了 DNS 查询（你能看到 IP） |

## 利用条件

- **DNS 存在的地方就有攻击面**：内网里如果目标是靠域名区分的（虚拟主机），Host 头、子域名枚举都会用到这一层。
- **改了 hosts 就能改变解析结果**：本地测试、DNS 重绑定、绕过域名白名单都靠它。
- **`ping` 能出 IP 只能证明 DNS 通，不能证明服务可用**：端口可能被防火墙挡着，这时要换 nmap 扫端口。

## Payload 速查

| 目的 | 命令 |
| :--- | :--- |
| 看域名解析到哪 | `nslookup 目标.com` |
| 看解析细节（指定记录类型） | `nslookup -type=ANY 目标.com` |
| 测连通性与延迟 | `ping 目标.com` |
| 看/清本机 DNS 缓存 | `ipconfig /displaydns`、`ipconfig /flushdns` |
| 验证 DNS 服务器是否被篡改 | `nslookup 目标.com 8.8.8.8` |

## 完整示例

一次访问「从域名到页面」的完整链路：

```text
① 浏览器拿到 URL：https://www.example.com/index.php?id=1
② DNS 解析：www.example.com  →  93.184.216.34
③ TCP 三次握手：本机:<随机端口> → 93.184.216.34:443
④ TLS 握手（因为 https）：协商密钥、验证证书
⑤ 应用层发出 HTTP 请求：GET /index.php?id=1 HTTP/1.1
⑥ 服务端路由：/index.php → 交给 PHP 处理
⑦ 响应沿原路逐层封装返回
⑧ 浏览器渲染
```

## 踩坑与备注

- **原文里三张「跨平台」与「请求过程」截图已删除**，内容分别改写为上面的 ASCII 流程图和文字说明。
- **OSI 是理论模型**，不要拿它去对照真实协议栈；实际以 TCP/IP 四层为准。
- **`ping` 用的是 ICMP，`nslookup` 用的是 DNS**，两者协议和层级都不同，排查时结果要分开看。
- **域名的层级是从右往左读**：`www.google.com` 是 `com` 下的 `google` 下的 `www`，写脚本枚举子域名时别读反了。
