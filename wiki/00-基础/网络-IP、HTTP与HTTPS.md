## 一句话概括

**IP 负责「找到哪台机器」，HTTP 负责「在两台机器间怎么说话」，HTTPS 就是在 HTTP 下面套了一层 TLS，把这句悄悄话变成密文。** 理解这三层的分工，是看懂后面所有抓包内容的前提。

## 原理

### 1. IP 地址的分配

- **静态 IP 地址**
  - 手动设置
  - 适用场景：不怎么挪动的台式机（如机房）、服务器（使访问地址稳定）
- **动态 IP 地址**
  - 从 DHCP 服务器自动获取 IP 地址
  - 适用场景：移动设备、无线设备（防止与其他 IP 冲突）

> **为什么服务器要静态、终端要动态？** 服务器的地址会被写进 DNS、被客户端硬编码、被防火墙放行，地址一变这些配置全废，所以必须钉死。而手机、笔记本在不同网络间漫游，如果每处都手填地址，极易和别人的地址撞车 —— 交给 DHCP 统一分配、冲突检测、到期回收，才是省事的做法。

### 2. DHCP

动态主机配置协议。

**DHCP 核心要点**

| 项目 | 说明 |
| :--- | :--- |
| **全称与翻译** | Dynamic Host Configuration Protocol，译为**动态主机配置协议** |
| **底层协议与端口** | 基于 **UDP** 协议；客户端端口 **68**，服务器端口 **67** |
| **工作机制** | 1. DHCP 服务器从 **IP 地址池**中选取一个 IP 地址；2. 将该 IP「**出租**」给客户端**一段时间**；3. 租期**到期后回收** IP 地址 |
| **常见实例** | **家用路由器**通常内置并充当 DHCP 服务器，提供用户上网 IP |

**相关命令**

| 命令 | 功能描述 |
| :--- | :--- |
| **`ipconfig /all`** | 查看网络适配器的**所有**详细信息，包括 DHCP 服务器地址、IP 地址租约的**获得时间**与**过期时间** |
| **`ipconfig /release`** | **释放**当前从 DHCP 服务器获取的 IP 地址租约。执行后，计算机将失去其 IP 地址。 |
| **`ipconfig /renew`** | **重新申请** IP 地址，或向 DHCP 服务器**申请续约**，以**延长** IP 地址的租用期。 |

> **为什么是 UDP 而不是 TCP？** 客户端要拿 IP 之前**还没有 IP**，没有 IP 就没法完成 TCP 三次握手。UDP 无连接、可以直接广播，是唯一可行的选择。

### 3. URI

**URI** 代表**统一资源标识符**。它是一个字符串，用于**唯一地标识一个资源**，或者**同时标识并定位一个资源**。

简单来说，**URI 是资源的“身份证”或“详细地址”**：

- **“标识”**：给资源一个独一无二的名称。
- **“定位”**：提供找到该资源的方法和位置。

组成：

```text
[协议]://[认证信息]@[主机名]:[端口]/[路径]?[查询字符串]#[片段标识符]
```

| 组成部分 | 说明 | 示例 |
| :--- | :--- | :--- |
| **方案** | 访问资源使用的协议。 | `https` |
| **认证信息** | 可选的用户名和密码。 | `john:password@` |
| **主机名** | 资源所在服务器的域名或 IP。 | `www.example.com` |
| **端口** | 服务器上服务的端口号。 | `:443` |
| **路径** | 资源在服务器上的具体位置。 | `/search/products` |
| **查询字符串** | 传递给资源的参数，以 `?` 开头。 | `?category=books&sort=price` |
| **片段** | 指向资源内部的某个锚点，以 `#` 开头。 | `#top` |

> **`#` 后面的片段永远不会发给服务器**。浏览器拿到整串 URL 后，只把 `#` 之前的部分放进请求行，片段留给本地做锚点跳转 —— 所以把 payload 写在 `#` 后面，服务端根本收不到。

URI 包含两个主要的子集：

#### 1. URL

- **功能**：**既标识，又定位**。它提供了资源的**访问机制和确切位置**。
- **焦点**：**如何**以及**在哪里**访问这个资源。

#### 2. URN

- **功能**：**只标识，不定位**。它给资源一个永恒不变的、唯一的名称，但不关心资源在哪里以及如何获取。
- **焦点**：这个资源**是什么**（它的永久身份）。

### 4. HTTP

HTTP 的核心功能可以概括为：**在客户端与服务器之间，通过请求和响应的模式，传输超媒体资源（如 HTML、图片、JSON 等）**。它决定了我们如何与网站进行交互。

#### 4.1 建立通信与传输数据

这是最基础的功能。HTTP 定义了客户端（如浏览器）如何向服务器请求资源，以及服务器如何将资源返回给客户端。

- **请求**：客户端发送一个 HTTP 请求报文，包含想要执行的操作（如获取页面、提交表单）和资源路径。
- **响应**：服务器处理请求后，返回一个 HTTP 响应报文，包含状态码（成功或错误）和请求的资源（如 HTML 代码）。

#### 4.2 明确的无状态性

HTTP 是一种**无状态协议**。

- **功能**：服务器的每个请求都被视为一个独立的、全新的请求，它不会记住之前任何请求的信息。
- **优点**：简化了服务器设计，降低了服务器资源消耗。

> **无状态的代价与补丁**：服务器不记事，那“登录过”这件事就无从记起。于是有了 `Cookie`+`Session`：服务器发一个编号给浏览器，浏览器每次自动带回来，服务器凭编号去查自己的存储 —— **状态是「外挂」上去的，不在协议里**。这也正是 Cookie 篡改、Session 固定、JWT 伪造这类题目存在的原因。

#### 4.3 支持多种请求方法

HTTP 定义了一组“动词”来表明对资源的不同操作意图。

| 方法 | 功能描述 | 典型场景 |
| :--- | :--- | :--- |
| **GET** | **获取**资源。 | 访问网页，查看图片。 |
| **POST** | **提交**数据，通常用于创建新资源或触发一个处理过程。 | 用户登录，发表评论。 |
| **PUT** | **更新**一个已存在的资源（整体替换）。 | 更新用户个人资料。 |
| **PATCH** | **部分更新**一个已存在的资源。 | 只修改用户的邮箱地址。 |
| **DELETE** | **删除**指定的资源。 | 删除一篇文章。 |

> **安全上的意义**：`PUT`/`DELETE` 在 CTF 里是常客。如果服务器没关掉 `PUT`，你可以直接把 shell **PUT 上传**上去；这也是「PUT 上传」类题目的全部原理。

#### 4.4 使用状态码进行状态指示

服务器通过三位数的状态码快速告知客户端请求的结果。

| 状态码范围 | 类别 | 常见例子 | 功能描述 |
| :--- | :--- | :--- | :--- |
| **1xx** | 信息性 | 100 Continue | 请求已收到，客户端可继续发送。 |
| **2xx** | **成功** | **200 OK** | 请求成功。 |
| **3xx** | **重定向** | **301 Moved Permanently** | 资源已永久移动到新 URL。 |
| | | **304 Not Modified** | 资源未修改，可使用缓存。 |
| **4xx** | **客户端错误** | **404 Not Found** | 请求的资源不存在。 |
| | | **403 Forbidden** | 服务器理解请求但拒绝授权。 |
| **5xx** | **服务器错误** | **500 Internal Server Error** | 服务器内部发生错误。 |

> **信息收集时最该盯的几个**：`200`（存在）、`301/302`（目录或跳转，可能藏后台）、`403`（存在但被拒，往往有源码泄露）、`500`（代码出错，可能能报出路径）。扫目录时用 `-i 200,301,302` 就是在筛这些。

### 5. HTTPS

**HTTPS 与 HTTP 的区别**是网络基础中一个非常核心的问题。它们的核心区别就在于一个字母 **S**，这个 **S** 代表了 **Security**。

| 特性 | HTTP | HTTPS |
| :--- | :--- | :--- |
| **协议与安全** | **超文本传输协议**，明文传输，无任何加密 | **超文本传输安全协议**，在 HTTP 基础上增加了 **SSL/TLS 加密层** |
| **默认端口** | **80** | **443** |
| **数据传输方式** | **明文** | **加密的密文** |
| **安全性** | **不安全**，存在三大风险：1. **窃听** 2. **篡改** 3. **冒充** | **安全**，解决了三大风险：1. **防窃听** 2. **防篡改** 3. **身份认证** |

**三大风险的具体含义：**

| 风险 | 含义 | TLS 用什么对付它 |
| :--- | :--- | :--- |
| **窃听** | 中间人在链路上直接看明文 | 对称加密（会话密钥） |
| **篡改** | 中间人改掉报文内容 | 完整性校验（MAC / AEAD） |
| **冒充** | 中间人假装是目标网站 | 证书 + 非对称加密验身份 |

## 利用条件

- **HTTP 明文** → 内网抓包、ARP 欺骗、中间人改包都能直接得手；这也是很多内网演练题「抓一下就有」的原因。
- **HTTPS 只能保护传输过程**，保护不了服务端逻辑：SQL 注入、XSS、文件包含在 HTTPS 站点上一样成立。
- **HTTPS 会挡住自签名证书的抓包**：代理工具要正常用，得先在客户端信任它的 CA，否则请求在 TLS 握手阶段就断了。

## Payload 速查

| 目的 | 写法 |
| :--- | :--- |
| 指定端口访问 | `http://x.x.x.x:8080/` |
| 带认证信息访问 | `http://user:pass@x.x.x.x/` |
| 走 443 仍用 http 协议 | `http://x.x.x.x:443/`（协议与端口可以错配，服务端可能仍响应） |
| 锚点不进请求 | `http://x.x.x.x/a.php#?id=1`（`#` 后不发） |
| 查看本机 DHCP 租约 | `ipconfig /all` |

## 踩坑与备注

- **原文的「请求体，状态体，响应体」是笔误**，正确的三段是**请求行 / 状态行（首行）、头部（header）、消息体（body）**。
- **URI 不等于 URL**：URL 是 URI 的子集，URN 也是。做题时见到 `urn:` 开头的资源，不要当成 URL 去访问。
- **HTTP 无状态是协议设计，不是缺陷**；出现安全问题的是后面外挂的 Cookie/Session 机制。
- **HTTPS 只是「传输层安全带」**：把站点的 http 换成 https，并不会让注入、上传、包含这些漏洞消失。
