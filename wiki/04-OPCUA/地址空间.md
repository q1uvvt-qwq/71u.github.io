## 一句话概括

OPC UA 把设备数据组织成一棵"树形目录"，每个数据点或可调用功能都是树上的一个节点（Node），用 NodeId 唯一定位。攻击者能 Browse 这棵树，就等于拿到了完整资产清单和点表。

## 原理

### 它要解决的问题

工业现场设备来自不同厂家：风机主控、PLC、变流器、传感器、SCADA、AGC/AVC、数据网关。各家数据格式、命名习惯、通信方式都不同，同样一个"有功功率"，厂家 A 叫 `ActivePower`，厂家 B 叫 `P`，厂家 C 叫 `ActPwr`，上位系统每对接一家就要重写一遍适配代码。

OPC UA 的作用就是：

```text
让不同设备和系统用统一方式交换工业数据
```

它的做法是先规定"数据长什么样"（信息模型 + 地址空间），再规定"怎么传"（二进制协议 + 安全通道）。

### 地址空间 Address Space

OPC UA Server 把自身的数据、类型、方法都挂在一棵树上，这棵树就是地址空间，可以类比成一台文件服务器：根目录固定，下面按设备、部件、功能层层分文件夹，文件夹里放变量和方法。最上层固定是标准定义的几个入口，最常打交道的是 `Objects`：

```text
Objects
  WindFarm                 <- 风场
    Offshore               <- 海上场站
      Turbine07            <- 风机（一台一个子树）
      Turbine08
      Turbine09
```

### 节点 Node 与 NodeClass

树上每个位置都是一个节点，节点有一个类别 NodeClass，决定这个节点能干什么：

| NodeClass | 含义 | 靶场例子 |
|---|---|---|
| Object | 对象节点，代表一个实体或容器，本身不带值 | `WindFarm`、`Offshore`、`Turbine08`、`Protection` |
| Variable | 变量节点，承载一个可读（可写）的值 | `Telemetry.Temperature`、`Protection.TemperatureLimit`、`Grid.State` |
| Method | 方法节点，服务端暴露的一个可调用功能，本身不带值 | `Protection.SetTemperatureLimit`、`Protection.ResetProtection` |

这三类正好对应攻击者最关心的三件事：对象节点给出资产结构，变量节点给出点表和当前值，方法节点给出可执行的控制动作。

### NodeId 的两种写法

NodeId 由"命名空间索引 + 标识符"两部分组成，标识符有两大类写法。

字符串型（s = string），可读性好，工程上最常见：

```text
ns=2;s=WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit
ns=2;s=WindFarm.Offshore.Turbine08.Protection.TemperatureLimit
ns=2;s=WindFarm.Offshore.Turbine08.Telemetry.Temperature
```

结构拆解：

```text
ns=2                                 命名空间索引
;
s=                                   标识符类型为字符串
WindFarm.Offshore.Turbine08...       路径式标识符（由服务端自定义命名规则）
```

数值型（i = numeric），紧凑、省带宽，是 OPC UA 规范里标准节点的默认形式：

```text
i=85         Objects 文件夹
i=2253       Server 对象
i=2255       ServerStatus
ns=2;i=1001  服务端在 ns=2 里自分配的某个节点
```

两种写法区别只在服务端怎么编号：数值型短，适合机器内部索引；字符串型长，但人能直接看懂，工程上常用来表示"设备.部件.功能"的层级含义。

### 命名空间 Namespace

成因：不同厂家、不同标准各自给节点编号，不隔离就会撞号。命名空间用来隔离"谁定义的节点"，服务端启动后会返回一张命名空间表（NamespaceArray），索引就是 NodeId 里的 `ns=`。

### Attributes 属性

节点还带一组标准属性（Attribute），描述元信息。安全评估和写操作前必看的几个：

| 属性 | 含义 | 为什么要看 |
|---|---|---|
| `NodeId` | 节点唯一标识 | 构造 Read / Call 请求的目标 |
| `BrowseName` | 浏览时显示的名字，含命名空间 | 拼对象树路径 |
| `DisplayName` | 给人看的名称 | 资产梳理 |
| `NodeClass` | Object / Variable / Method | 判断是可读值还是可调用功能 |
| `DataType` | 值的数据类型（Double、Boolean、String…） | 决定 Write / Call 传参类型 |
| `ValueRank` | 标量还是数组（-1 为标量） | 判断是不是数组型点 |
| `AccessLevel` | 可读 / 可写 / 可历史读等权限位 | 判断能否直接 Write |
| `Historizing` | 是否记录历史 | 判断是否存在历史数据面 |

对安全测试特别关键的组合是 `NodeClass=Method` 加对应的 `Executable` / `UserExecutable` 属性。当前会话 `UserExecutable=true` 就说明这个身份可以直接调用该方法；海上链里低权限维护账号能调 `SetTemperatureLimit`，就是因为这个位对当前角色没有收紧。

## 结构

### 对象树对应的业务含义

完整对象树（含每个节点的类型与取值）见"实测过程"的 Browse 输出，这里只看各层对应的业务含义：

```text
Telemetry   -> 遥测：温度、有功、无功、风速、电压、电流
Grid.State  -> 并网状态：ON_GRID / OFF_GRID
Protection  -> 保护：阈值是可读变量，改阈值和复位都是方法
State       -> 机组状态：RUNNING / PROTECTION_STOP
Alarm       -> 告警：NONE / TEMP_THRESHOLD_TRIP
```

这套命名与 IEC 61400-25 的风机信息模型思路一致：把风机拆成测量、控制、状态、告警四类数据，只是承载协议换成了 OPC UA。

## 报文/字段对照

NodeId 在请求报文里以"命名空间索引 + 标识符类型 + 标识符"编码，对照关系：

| 工程写法 | 命名空间索引 | 标识符类型 | 标识符内容 |
|---|---|---|---|
| `ns=2;s=WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit` | 2 | `s` 字符串 | `WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit` |
| `ns=2;s=WindFarm.Offshore.Turbine09.Protection.SetTemperatureLimit` | 2 | `s` 字符串 | 同上，换成 Turbine09 |
| `ns=2;i=1001` | 2 | `i` 数值 | 1001 |
| `i=85` | 0（缺省） | `i` 数值 | 85 |

注意：`ns=` 省略时默认是 0，即规范命名空间。攻击者想访问风机业务节点，前缀必须是 `ns=2;`，写错会直接返回 `BadNodeIdUnknown`。

## 实测过程

Step 12 从维护工作站执行 `discover.py`，拿到命名空间表（`NamespaceArray`）：

```text
CONNECTED opc.tcp://10.0.12.8:4840/windfarm/offshore/
Namespaces:
  ns=0 http://opcfoundation.org/UA/
  ns=1 urn:freeopcua:python:server
  ns=2 urn:windfarm:njust:offshore:opcua-gateway
```

| 索引 | URI | 含义 |
|---|---|---|
| ns=0 | `http://opcfoundation.org/UA/` | OPC UA 规范保留，标准节点都在这里，不允许厂商改 |
| ns=1 | `urn:freeopcua:python:server` | 服务器软件厂商（此处是 FreeOpcUa / asyncua 库）自己的节点 |
| ns=2 | `urn:windfarm:njust:offshore:opcua-gateway` | 本工程自定义节点，风机对象树全部在 ns=2 下 |

这张表的攻击价值很高：`ns=2` 的 URI 里有 `windfarm`、`offshore`，等于直接确认了"这是风电场海上场站的网关"，再往下 Browse 就是业务点表。

Step 13 执行 `browse.py`，从 `ns=2;s=WindFarm` 起浏览，发现三台风机与 `Protection` 下的两个方法。改造后的网关从单台 Turbine08 扩展为三台独立风机，每台结构完全对称：

```text
Objects
  WindFarm
    Offshore
      Turbine07
        Telemetry
          Temperature          (Variable, Double)
          ActivePower          (Variable, Double)
          ReactivePower        (Variable, Double)
          WindSpeed            (Variable, Double)
          Voltage              (Variable, Double)
          Current              (Variable, Double)
        Grid
          State                (Variable, String: ON_GRID / OFF_GRID)
        Protection
          TemperatureLimit     (Variable, Double)
          SetTemperatureLimit  (Method)
          ResetProtection      (Method)
        State                  (Variable, String: RUNNING / PROTECTION_STOP)
        Alarm                  (Variable, String: NONE / TEMP_THRESHOLD_TRIP)
      Turbine08
        Telemetry / Grid / Protection / State / Alarm   （同构）
      Turbine09
        Telemetry / Grid / Protection / State / Alarm   （同构）
```

对称结构意味着同一套攻击手法对三台都成立，玩家必须先用 Browse 确定要打哪一台，再拼出那一台的 Method NodeId。部署记录也要求后续文档不得再写成"海上 OPC UA 只控制 Turbine08"。

Step 14 执行 `read.py --turbine Turbine08`，把变量节点读成业务值：

```text
[Turbine08]
temperature=73.0
temperature_limit=95.0
active_power=342.0
grid_state=ON_GRID
turbine_state=RUNNING
alarm=NONE
```

自检工具 `offshore_opcua_check.py` 也做过同样两件事（`--action browse` / `--action read`），确认 `WindFarm / Offshore / Turbine08 / Protection / SetTemperatureLimit` 可被发现，是靶场里"信息暴露面"的实证。

## 安全视角

- 地址空间是攻击者的第一张地图。匿名或低权限即可 Browse，等于把资产树、点表、方法清单一起交出，防护上应按角色裁剪可见子树，只读账号不应看到 `Protection` 下的 Method 节点。
- NodeId 命名过于语义化（`WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit`）方便了调试，也让攻击者无需点表文档就能推断控制点含义；对外暴露的网关建议改用无业务含义的数值型 NodeId，把语义映射留在工程侧。
- `Protection` 下把"阈值变量"和"改阈值方法"并列暴露，变量只读、方法可调，看似权限收紧，真正危险的是方法。节点级权限必须落到 `UserExecutable` 上，而不只是限制变量写权限。
- 三台风机完全对称，风险可批量复制：一处方法级鉴权缺失，等于三台机组同时可被停。
- 规范与素材的关系：命名空间表、对象树、Read 返回值来自海上链实测输出；NodeClass、Attributes 定义来自 OPC UA 规范，靶场配置未逐项给出其取值。
