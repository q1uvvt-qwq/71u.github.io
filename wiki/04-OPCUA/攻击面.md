## 一句话概括

海上链能在 OPC UA 这一段一路走通，靠的是六个弱点同时存在：匿名可连、明文可读、低权限可调控制方法、网关在边界上直接可达、端点凭据硬编码在维护站上、诊断工具随维护站泄露。

## 原理

OPC UA 的设计目标里有很大一块是"安全通信"：它规定了应用实例的证书校验、消息签名与加密、用户身份令牌、以及节点级访问控制（AccessLevel / UserAccessLevel / Executable / UserExecutable）。定义：协议本身的能力是够的，现实里的问题几乎都出在配置和集成层面：

```text
协议给了 > 部署时没开 > 集成时放行了不该放行的角色和网络
```

把这条链路里的弱点按"协议配置 → 权限模型 → 网络位置 → 工程实现 → 运维侧"分层，就是下面这几类。

## 结构

### 协议配置

#### 弱点一：匿名 Browse 泄露资产树与点表

`GetEndpoints` 返回的 `UserIdentityTokens` 里如果包含 `AnonymousIdentityToken`，任何能连到 4840 的人都能建立会话并 `Browse`。

海上链的实际表现：从维护工作站执行 `browse.py`，直接把整棵树摊开：

```text
WindFarm
  Offshore
    Turbine07 / Turbine08 / Turbine09
      每台下挂 Telemetry / Grid / Protection / State / Alarm
      Protection 下暴露 TemperatureLimit / SetTemperatureLimit / ResetProtection
```

一次 Browse 就同时拿到设备数量与编号、每台机的测量点位、控制方法名、方法所属对象，加起来等于一份完整点表，而且自描述、比任何导出的 Excel 点表都准确。

危险的是它的"低成本"：匿名 Browse 不需要凭据，不触发登录失败告警，行为看起来和正常客户端探测完全一样。

#### 弱点二：SecurityMode=None

靶场网关的端点未启用签名与加密。后果是四连击：

```text
1. 证书不被校验           任何客户端应用都能建通道
2. 报文明文               节点名、读取值、用户令牌在 pcap 里可读
3. Call 入参可被篡改      中间人可以把 40.0 改成任意值
4. 请求可被重放           没有新鲜度校验，历史请求可复用
```

对攻击者来说，这意味着他能直接用标准客户端工具连上去，不处理证书信任链、不逆向任何东西。`opcua-tools/` 里那几个基于 `asyncua` 的脚本能即拿即用，正是因为这条路没有任何阻碍。

### 权限模型

#### 弱点三：低权限角色可调用控制方法

整条链的权限缺陷就出在这里："只校验登录，不校验 method 级权限"：

```text
校验了   你是谁（JWT 签名有效、scope 含 maintenance.connect）
没校验   你被允许调用哪些 Method
```

OPC UA 规范为此专门提供了 `Executable` / `UserExecutable` 属性和节点级访问控制：一旦 `UserExecutable` 对当前角色返回 true，`Call` 就会执行。海上链里的 `remote-maintainer` 是维护身份，却被允许调用业务保护方法：

```text
call_method.py --node "ns=2;s=WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit" --value 40
-> StatusCode: Good, action = PROTECTION_STOP
```

攻击链在进入维护工作站之前已经做了一次权限提升（viewer 的 JWT 被扩出 `maintenance.connect`）。若 OPC UA 侧再做一层方法级授权，即使攻击者拿到维护会话也只能做诊断类操作，无法改保护定值，这就是纵深防御在协议层的具体含义。

### 网络位置

#### 弱点四：服务暴露在边界导致直接可达

部署记录明确写了正确的网络约束：

```text
海上攻击链要求玩家不能从攻击机直接访问 OPC UA Gateway。
正式链路必须是：
SSRF -> JWT Secret -> forged JWT -> maintenance-gateway -> offshore-maint-ws
-> OPC UA Browse/Read/Method Call -> offshore-opcua-gateway。
```

攻击机在 `10.0.11.0/24`，网关在 `10.0.12.0/24`，两段之间有隔离，攻击者必须借道维护工作站才能摸到 4840。注意：这个隔离是刻意设计的，用来体现分区分域，不是部署疏漏。

反面情形是 4840 与办公网/管理信息区平铺可达，攻击链短得只剩两步（扫描 → 调用）。真实工程里的要求是：4840 只允许指定的采集主机、工程师站、HMI 聚合服务访问，用工业防火墙做白名单，禁止跨区间直接放通。

### 工程实现

#### 弱点五：端点与凭据硬编码在客户端 profile

维护工作站 home 目录里放着 OPC UA 诊断配置：

```text
~/opcua-profiles/offshore-gateway.profile
  endpoint=opc.tcp://10.0.12.8:4840/windfarm/offshore/
  asset_hint=WindFarm.Offshore asset tree
```

这条弱点的性质是"信息资产未受保护"：端点地址、路径、资产提示写在明文文件里，任何能登录维护站的人（在靶场里就是拿到维护终端的攻击者）都能 `cat` 出来。若 profile 里再写入用户名密码或客户端证书口令，问题更严重：这类文件在运维交接、镜像打包、备份中被反复复制，泄露面远大于它本身的价值。

工程上的正确做法是：连接信息集中管理（配置中心 / 受控凭据库），profile 只保留非敏感的显示名，敏感项走运行注入；同时把 `~/opcua-profiles` 这类目录的权限收紧到实际需要的服务账号。

### 运维侧

#### 弱点六：诊断工具目录随维护站泄露

维护工作站的 home 目录里预置了完整工具链：

```text
~/opcua-tools/
  discover.py     连通性 + 命名空间发现
  browse.py       地址空间浏览
  read.py         变量读取（默认输出三台，也可 --turbine 指定）
  call_method.py  方法调用
```

这是靶场为了教学便利做的预置，但反映了一个真实模式：运维/诊断工具随维护主机一起被攻陷。这些工具本是给工程师快速排障用的，一旦主机失守就成了攻击者的现成武器库，而且走合法协议、合法端口、合法账号，流量在监控上很难与正常运维区分。

防护上要把"工具存在"和"工具可用"分开：工具本身留着（运维需要），但要用独立的最小权限凭据、限制可连目标（白名单）、并对工具发起的 Call 做集中审计。

## 报文/字段对照

| 弱点 | 协议层可观测点 | 现状 | 应配置为 |
|---|---|---|---|
| 匿名 Browse | `GetEndpoints` 的 `UserIdentityTokens` 含 Anonymous | 允许匿名 | 只保留 UserName / X509 |
| 明文通信 | `GetEndpoints` 的 `SecurityMode` / `SecurityPolicyUri` | `None` / `None` | `SignAndEncrypt` + `Basic256Sha256` 及以上 |
| 方法级越权 | Method 节点的 `Executable` / `UserExecutable`、`Call` 的 `ServiceResult` | 维护角色可执行控制方法 | 按角色把控制类方法 `UserExecutable` 置 false |
| 边界可达 | TCP 4840 的可达范围 | 隔离，须经维护工作站 | 工业防火墙白名单，仅放行授权采集端 |
| 凭据硬编码 | profile 中的 endpoint / 凭据字段 | 明文写死 endpoint 与 asset_hint | 敏感项运行注入，profile 只留显示名 |
| 工具随主站泄露 | `Call` 请求的来源主机 | 工具预置在维护主机 | 工具绑定最小权限凭据 + 目标白名单 + Call 审计 |

## 实测过程

把海上链中与 OPC UA 相关的步骤串起来，可以看到每个弱点分别被用在哪一步：

```text
Step 11  在维护站发现 opcua-profiles/offshore-gateway.profile
         -> 弱点五：端点与资产提示明文暴露
         -> 拿到 endpoint=opc.tcp://10.0.12.8:4840/windfarm/offshore/

Step 12  探索 ~/opcua-tools/，执行 discover.py
         -> 弱点六：诊断工具随维护站泄露
         -> 拿到命名空间表（ns=0/1/2）

Step 13  执行 browse.py
         -> 弱点一：匿名 / 低门槛 Browse 泄露完整资产树

Step 14  执行 read.py --turbine Turbine08
         -> 读到 temperature=73.0、temperature_limit=95.0、active_power=342.0
         -> 确定攻击判据：把阈值设到低于当前温度

Step 15  call_method.py --value 40
         -> 弱点三：低权限角色可调用控制方法
         -> 弱点二：SecurityMode=None，整个调用无需处理任何加密协商
         -> StatusCode: Good, action = PROTECTION_STOP

Step 16  curl http://10.0.11.5:8080/api/state
         -> WT08 PROTECTION_STOP / OFF_GRID / power_kw 0.0 / TEMP_THRESHOLD_TRIP
```

网络位置（弱点四）体现在整条链的前提上：

```text
攻击机 10.0.11.x  ---(不能直连)--->  网关 10.0.12.8:4840
      |                                        ^
      |  SSRF -> JWT -> 维护网关                |
      +--> Web Terminal -> offshore-maint-ws ---+
```

必须借道维护工作站，前面几步"发现 profile、发现工具、Browse、Call"才成为可能，这条链也才具备"边界穿越"的教学含义。

## 安全视角

- 开启 SignAndEncrypt 并选用较强的 SecurityPolicy，把 `SecurityPolicy=None` 从候选列表移除，避免降级协商；证书要有明确的信任列表和有效期管理。
- 方法级授权要按角色来分：控制类 Method（改定值、复位、启停）必须与只读/诊断角色彻底分离，用 `UserExecutable` 表达边界，而不是只在应用层做一次登录校验。
- 网络白名单要做起来。4840 只对指定采集主机、工程师站、HMI 聚合服务开放，跨安全区必须经工业防火墙，不允许平铺可达。
- `Call` 服务单独审计。记录会话身份、来源主机、MethodId、InputArguments、OutputArguments 与时间，把"Read/Browse 属信息面、Call 属控制面"作为监控分级依据。
- 写操作的范围与参数合理性都要限制：定值类写入应校验取值范围以及与当前工况的逻辑一致性（例如拒绝"阈值低于当前温度"的配置），把不合逻辑的请求挡在网关侧。
- 地址空间按最小可见收敛。只读账号不应看到 `Protection` 下的 Method 节点；暴露面较大的网关可用无业务含义的数值型 NodeId 替代语义化 NodeId。
- 客户端 profile 与工具链也要管好。连接信息集中管理、凭据运行注入、profile 目录权限收紧；诊断工具用最小权限凭据并对目标做白名单。
- 交叉取证能力要建起来。OPC UA Call 日志、网关控制日志、Modbus 寄存器写入记录、HMI 状态变化四段互证，才能事后追溯"谁改了阈值、什么时候、影响了哪台机组"。
- 定位说明：本篇围绕授权靶场与教学环境整理弱点与防护，所用端点、账号角色、命令与返回值均来自靶场实测记录，不对应任何真实生产系统。
