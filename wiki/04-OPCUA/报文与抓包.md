## 一句话概括

OPC UA 是二进制协议，但二进制不等于不可读：SecurityMode=None 时，报文里仍能看到 `opc.tcp://` 这类明文字符串、`SetTemperatureLimit` 这类节点名和用户令牌内容；抓包分析要做的是定位到"哪个会话、调了哪个方法、传了什么参数"。

## 原理

### 为什么 OPC UA 报文不好读

OPC UA 的编码规则（UA Binary）用紧凑二进制表达数据结构：整数用小端定长、字符串用"长度 + 内容"、数组用"元素个数 + 元素序列"、结构体按固定顺序拼接。好处是带宽小、解析快，坏处是没有自描述标签，人眼分不清某个字节是长度还是类型。

这带来一个常见误解：把"二进制"直接等同于"安全"。实际的关系是：

```text
二进制编码      -> 只影响可读性，不提供任何安全属性
SecurityMode=None -> 报文完全明文，字符串仍可被工具提取
SecurityMode=Sign -> 有签名，但内容依旧可读，不可篡改
SecurityMode=SignAndEncrypt -> 内容才真正不可读
```

只要服务端跑在 None 上，抓包工具里就能直接搜到业务字符串。海上链的网关就是这种情况，抓包里直接看到明文节点名是成立的。

## 结构

### 传输层：TCP 之上的消息头

`opc.tcp` 的报文在 TCP 载荷里自带一层消息头。消息头的前 3 个字节是 ASCII 消息类型，随后是长度等字段。常见类型：

| 消息类型 | 全称 | 作用 | 出现时机 |
|---|---|---|---|
| `HEL` | Hello | 客户端打招呼，声明协议版本、缓冲区大小、最大消息长度 | TCP 连接建立后第一包 |
| `ACK` | Acknowledge | 服务端回应 Hello，给出自己的缓冲区与消息大小 | 紧随 HEL |
| `ERR` | Error | 任一方报错 | 协商失败时 |
| `OPN` | OpenSecureChannel | 打开 / 续期安全通道，携带安全策略、证书、Nonce | 每次通道建立或续期 |
| `MSG` | Message | 承载业务服务请求 / 响应，是数据面的主体 | Browse / Read / Call 等全部业务 |
| `CLO` | CloseSecureChannel | 关闭安全通道 | 会话结束 |

一个可记的简化模型：

```text
TCP 三次握手
  -> HEL / ACK        协商缓冲区
  -> OPN / OPN        建立安全通道（交换安全策略与证书）
  -> MSG / MSG ...    业务服务往返（Browse / Read / Call / Publish）
  -> CLO              关闭通道
```

`MSG` 是抓包里出现最多、也最值得看的类型：头部含通道 ID 和序号，用于在通道内定位请求与响应；长度字段告诉解析器后续有多少字节属于本消息。响应报文还可能分片，承载超出单包大小的数据。

### 服务层：RequestHeader / ResponseHeader + 服务体

`MSG` 里装的是具体服务。OPC UA 的所有服务请求遵循同一套外壳：

```text
MSG 消息头
  └── 服务请求
        ├── RequestHeader
        │     ├── AuthenticationToken   会话令牌，标识是哪个会话发来的
        │     ├── Timestamp             请求时间
        │     ├── RequestHandle         客户端自用的请求序号
        │     ├── ReturnDiagnostics     要求服务端回带诊断信息
        │     ├── AuditEntryId          审计条目 ID
        │     └── TimeoutHint           超时提示
        └── 服务体
              例如 ReadRequest 的 NodesToRead 列表
                    CallRequest 的 ObjectId / MethodId / InputArguments
```

响应侧对称：

```text
MSG 消息头
  └── 服务响应
        ├── ResponseHeader
        │     ├── Timestamp
        │     ├── RequestHandle         与请求对应
        │     ├── ServiceResult         服务级 StatusCode
        │     ├── ServiceDiagnostics    诊断信息
        │     └── StringTable           字符串表（诊断用）
        └── 服务体
              例如 ReadResponse 的 Results（含每个节点的 StatusCode 和 Value）
                    CallResponse 的 StatusCode / OutputArguments
```

这个外壳决定了抓包时的读法：先看是哪个服务（Read 还是 Call），再看服务体里的 NodeId 和参数，最后看 ResponseHeader 的 `ServiceResult` 判断成败；海上链里 `StatusCode: Good` 就是 `ServiceResult` 层面的成功。

### 各服务的服务体要点

| 服务 | 请求体关键字段 | 响应体关键字段 |
|---|---|---|
| `Browse` | `NodesToBrowse`（起始 NodeId）、`BrowseDirection`、`RequestedMaxReferencesPerNode` | `References`（含 `ReferenceTypeId`、`IsForward`、`TargetNodeId`、`BrowseName`、`NodeClass`） |
| `Read` | `NodesToRead`（每个含 NodeId + AttributeId，如 Value / DisplayName） | `Results`（每项含 `StatusCode` 与 `Value`，`Value` 内带 `DataType` 和时间戳） |
| `Write` | `NodesToWrite`（NodeId + AttributeId + Value） | `Results`（每项一个 StatusCode） |
| `CreateSubscription` | `RequestedPublishingInterval`、`RequestedLifetimeCount`、`RequestedMaxKeepAliveCount` | `SubscriptionId`、`RevisedPublishingInterval` |
| `CreateMonitoredItems` | `SubscriptionId`、`ItemsToMonitor`（NodeId + AttributeId + 采样与队列参数） | `Results`（含 `MonitoredItemId`） |
| `Call` | `ObjectId`、`MethodId`、`InputArguments` | `StatusCode`、`OutputArguments` |
| `GetEndpoints` | `EndpointUrl`、`LocaleIds`、`ProfileUris` | `Endpoints`（含 `EndpointUrl`、`SecurityMode`、`SecurityPolicyUri`、`ServerCertificate`、`UserIdentityTokens`） |

### 一个 Call 请求要带什么

Method Call 的语义是"在某个对象上调一个方法"，请求里必须同时给两个 NodeId：

```text
ObjectId   方法所属的对象节点
           例如 Protection 对象，或直接给出 Method 节点的父对象
MethodId   方法节点本身的 NodeId
           例如 ns=2;s=WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit
InputArguments  参数列表，每项带类型与值
           例如 Double: 40.0
```

响应里对应：

```text
StatusCode       方法执行结果（海上链实测为 Good）
OutputArguments  返回参数列表，海上链返回 4 个：
                 old_limit_c = 95.0
                 new_limit_c = 40.0
                 evaluation  = 61.0 > 40.0
                 action      = PROTECTION_STOP
```

这 4 个返回值直接证明方法执行了、业务逻辑落地了，比只看 `StatusCode: Good` 更有说服力。

### 明文字符串出现在哪里

SecurityMode=None 时，以下内容以明文出现在 TCP 载荷里，可直接解析或字符串搜索命中：

```text
opc.tcp://10.0.12.8:4840/windfarm/offshore/       端点 URL
windfarm/offshore                                  路径段
WindFarm.Offshore.Turbine08.Protection.SetTemperatureLimit   字符串型 NodeId
SetTemperatureLimit / TemperatureLimit / ResetProtection      方法名与变量名
UserNameIdentityToken 携带的用户名                 身份字段
/publish 之类服务名                                服务标识
```

这些字符串不需要任何解码器就能命中，"二进制所以抓不到东西"在这里不成立。

## 抓包分析

依据说明（重要）：素材中没有提供海上链 OPC UA 的 pcap 文件，因此本篇不给出任何抓包十六进制内容，也不编造帧时间戳、序号或字节偏移。本篇的"报文结构"依据 OPC UA 规范（UA Binary 编码、消息头类型、RequestHeader/ResponseHeader、各服务字段定义），"实测"依据海上链的命令输出与返回值记录。实际教学中若需要逐字节证据，正确做法是在维护工作站侧对 `opc.tcp://10.0.12.8:4840` 抓包后自行取证，而不是引用本文档。

### Wireshark 识别要点

```text
1. 协议筛选
   opcua                        只看 OPC UA 流量
   tcp.port == 4840             按端口收敛
   opcua.servicenodeidnumeric == 428 只看 GetEndpoints（服务节点号）
   opcua.servicenodeidnumeric == 527 只看 Browse
   opcua.servicenodeidnumeric == 631 只看 Read
   opcua.servicenodeidnumeric == 673 只看 Write
   opcua.servicenodeidnumeric == 712 只看 Call

2. 按 NodeId 过滤
   利用字符串型 NodeId 明文可直接搜索：
   frame contains "SetTemperatureLimit"
   frame contains "Turbine08"
   frame contains "opc.tcp"

3. 追踪会话
   Follow -> TCP Stream 观察一次完整会话的 HEL/ACK -> OPN -> MSG 序列
   tcp.stream == N              锁定单条会话

4. 关注点
   HEL/ACK 协商出的缓冲区大小
   OPN 中的 SecurityPolicy 字段（是否 None）
   MSG 中的 RequestHeader.AuthenticationToken（会话复用线索）
   Call 的 ObjectId / MethodId / InputArguments
   ResponseHeader.ServiceResult（Good 还是有错误码）
```

在具备 pcap 的前提下，推荐的分析路径是：

```text
1. 过滤 tcp.port == 4840，确认 HEL/ACK 与 OPN 的存在，判断 SecurityPolicy
2. 用 frame contains "Turbine" 快速定位包含业务节点名的 MSG
3. 定位 Call 服务，读出 MethodId 与 InputArguments
4. 回到响应包，读 ResponseHeader.ServiceResult 与 OutputArguments
5. 与业务侧日志交叉：网关 opcua-control.log 的 OPCUA_METHOD_CALL、
   Modbus 子站的 HR96 写入记录、HMI /api/state 的状态变化
```

第 5 步是工控场景特别强调的一点：网络证据必须与业务证据对齐，才能证明"这个协议报文导致了这次状态变化"。

## 安全视角

- 明文不等于安全。`SecurityMode=None` 下节点名、用户名、数据值全部可读，攻击者不用主动 Browse，被动监听就能还原资产树。
- 字符串型 NodeId 提高了攻击效率。语义化的 NodeId 让抓包分析几乎不需要点表文档，`frame contains` 一条过滤就能找到控制方法名；暴露面较大的网关可考虑用无业务含义的数值型 NodeId。
- `Call` 服务应单独重点监控。Read / Browse 属信息面，Call 属控制面。建议在网络侧对 `Call` 请求告警，并把 `ObjectId` / `MethodId` / `InputArguments` 落日志。
- 开 SignAndEncrypt 才能同时解决窃听与篡改。只开 Sign 能防篡改但防不住窃听，对"读取阈值"这类敏感值仍不够。
- 抓包取证要成链。单靠一条 OPC UA 报文不足以定责，需要"OPC UA Call → 网关日志 → Modbus FC06 写 HR96 → HMI 状态变化"四段互证。
