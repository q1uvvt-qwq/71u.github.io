## 一句话概括

**fenjing** 是一个针对 **SSTI（服务器端模板注入）** 的自动化工具：它替你完成「**探测模板引擎 → 找注入点 → 生成能绕过 WAF 的 payload**」这三件最费时的事，把手工构造 payload 的过程压缩成一条命令。

## 原理

### 1. 为什么 SSTI 需要一个自动化工具

SSTI 的手工会话非常「体力活」：

| 手工要做的判断 | 为什么麻烦 |
|---|---|
| 用的是哪个模板引擎？ | 每个引擎的语法不同，猜错就全错 |
| 注入点在哪？ | URL 参数、Cookie、Header、POST 字段都得试一遍 |
| 哪个 payload 不被过滤？ | 关键字被 WAF 拦了要换编码、换语法、换等价写法 |
| 回显在哪？ | 结果可能不回显，得靠盲注式的差异判断 |

而这些问题**每一个都有固定套路**，换句话说，**都是可以自动化的**。fenjing 做的就是把这些套路固化下来。

### 2. fenjing 的工作流程

它的执行顺序和手工排查的顺序完全一致，只是每一步都由程序完成：

```text
① 探测模板引擎
        ↓
② 定位注入点
        ↓
③ 构造并生成可用 payload
        ↓
④ 自动化利用（执行命令 / 读文件）
```

#### ① 探测模板引擎

原理是**发一组「只有某个引擎才会把它求值」的探针**，然后看响应变没变。

```text
发送 {{7*7}}  → 响应里出现 49？   → 更像 Jinja2 / Twig 一类
发送 ${7*7}   → 响应里出现 49？   → 更像 Mako / Freemarker 一类
发送 {7*7}    → 响应里出现 49？   → 更像 Smarty 一类
```

判断依据：**同一个表达式，在不同引擎下的语法不同；只有正确的引擎语法才会被求值。** 把几种语法依次试一遍，谁被求值了，就是谁。

同时它会识别**模板引擎的版本** —— 版本决定了哪些语法可用（比如某些属性在旧版本里可以直接访问，新版被禁掉了）。

#### ② 定位注入点

一个请求里有太多地方可能被拼进模板：

```text
URL 参数   →  ?name=xxx
Cookie     →  Cookie: session=xxx
Headers    →  User-Agent: xxx / X-Forwarded-For: xxx
POST 数据  →  form 字段 / JSON 字段
文件上传   →  文件内容或文件名
```

fenjing 的方式是**逐个位置注入探针、再看响应有没有被求值**：只有「探针被求值了」的那个位置，才是真正的注入点。

这一步非常重要 —— 手工排查时最常见的错误就是**只盯着 URL 参数**，而注入点其实在 `User-Agent` 或某个 Cookie 上。

#### ③ 生成能绕过 WAF 的 payload

这是它最有价值的部分。当注入点被确认，但 payload 被过滤（返回 400/403，或者求值失败）时，手工要去试探各种变形；fenjing 会**自动生成候选池**：

| 绕过维度 | 手法举例 |
|---|---|
| 编码变形 | URL 编码、Unicode 编码、十六进制编码 |
| 语法等价替换 | 用 `attr` 过滤器代替 `.`、用 `\|attr("...")` 代替下标 |
| 关键字拆分 | 用字符串拼接拼出被过滤的关键字 |
| 空白替换 | 用 `/**/`、换行、Tab 替代空格 |

它会**逐个尝试并验证效果**，把「能通过」的那个留下来。

#### ④ 自动化利用

注入点打通后，通常要做两件事：**执行命令**和**读文件**。fenjing 的 `crack` 模式会基于已确认的注入点自动完成这一步。

### 3. 它解决不了的部分

需要明确：**自动化工具替代的是「试错」，不是「理解」。**

| 工具能做 | 只能靠人 |
|---|---|
| 快速判断引擎和注入点 | 判断这个漏洞**值不值得打**、影响面多大 |
| 生成大量候选 payload | 理解**为什么**某个 payload 能绕过 |
| 跑通到「能执行命令」 | 目标**没有回显**时怎么外带数据 |
| — | WAF 有**行为检测**（频率、特征）时怎么降低存在感 |

## 本题情景与解题手法

### 题目形态

一道 SSTI 题目：给了一个 Web 靶场地址，页面上有一个会把用户输入「渲染出来」的功能（例如注册/查询后页面显示你输入的内容）。目标是拿到执行能力。

抽象后的目标地址形如：

```text
https://<靶场地址>/
```

### 第一步：启动 fenjing

两种用法，先起交互界面：

```bash
py -m fenjing webui
```

启动后在本机浏览器里操作，适合需要反复调试的场景。

### 第二步：scan —— 先扫描，把情况摸清

```bash
py -m fenjing scan https://<靶场地址>
```

**这条命令的作用是：自动化检测目标网站是否存在 SSTI 漏洞。**

它的具体功能对应到前面讲的流程：

| 功能 | 具体做什么 |
|---|---|
| **自动探测模板引擎** | 检测是 Jinja2、Twig、Smarty、Mako 等中的哪一种，并识别版本 |
| **尝试各种注入点** | URL 参数、Cookie、Headers、POST 数据、文件上传等 |
| **生成绕过 WAF 的 payload** | 自动生成各种编码和变形的 payload，绕过常见 WAF 规则 |
| **验证漏洞是否存在** | 发送测试 payload，分析响应判断是否执行成功 |

扫描结果会告诉你四件事：

```text
是否存在 SSTI 漏洞
是什么模板引擎（Jinja2 / Twig / ...）
可用的 payload
如何进一步利用
```

### 第三步：crack —— 确认存在后再利用

扫描确认存在 SSTI 之后，用 `crack` 针对**具体那个被注入了参数的处理脚本**继续利用：

```bash
py -m fenjing crack https://<靶场地址>/check.php
```

判断依据：`crack` 的输出里应该能看到**命令执行的结果**（例如 `id`、`whoami` 的返回）。看到真实回显，才算利用成功。

> 注意 `scan` 和 `crack` 的目标 URL 往往是**同一个站点的不同路径**：`scan` 扫的是「整个站点的所有可能注入位置」，`crack` 打的是「那个真正处理注入点参数的脚本」。原文里 `scan` 用的是站点根地址，`crack` 用的是 `check.php`，就是这个道理。

### 使用手法一句话总结

> **`webui` 起界面或 `scan` 直接扫** → 由工具替你**探测引擎 + 逐个位置找注入点** → 看结果确认「有没有 SSTI、是哪个引擎」→ 再用 **`crack` 指定真正的处理脚本**，让工具生成绕过 WAF 的 payload 并跑出命令回显 → 拿到回显才算成功。

## 常用命令速查

| 目的 | 命令 |
|---|---|
| 启动 Web 界面（推荐，便于反复调试） | `py -m fenjing webui` |
| 扫描目标是否存在 SSTI | `py -m fenjing scan <URL>` |
| 对确认存在漏洞的脚本做利用 | `py -m fenjing crack <URL>` |
| 查看全部参数 | `py -m fenjing --help` |

## 踩坑与备注

- **先把工具跑起来，再谈理解**：`py -m fenjing webui` 是最省心的入口 —— 界面上你能看到它每一步发了什么、收到了什么，比只看命令行的最终结论更容易建立直觉。
- **`scan` 扫不到不等于没有 SSTI**：注入点可能出现在工具没覆盖的位置（例如某个自定义 Header、JSON 的深层字段），或者目标的回显方式特殊（盲注、只有状态码差异）。扫描失败时，手工从「哪个输入被渲染到了页面上」这个角度重新找入口。
- **原文给出的靶场地址里带有一段随机标识（uuid 形式的子域名）**，属于一次性环境信息，本文已统一写成 `<靶场地址>`；原文中的 `check.php` 属于题目结构，予以保留。
- **注意 `crack` 的目标路径**：直接对站点根路径 `crack` 往往会失败，因为根路径不处理注入参数。**注入点是哪个脚本，`crack` 就打哪个脚本。**
- **工具跑通了也要能讲清楚**：拿回显只是第一步。真正要掌握的是「为什么是 Jinja2」、「为什么这个 payload 绕过了过滤」—— 换一道题、换一个引擎、换一层 WAF，工具的输出就不再适用了。
- **控制请求频率**：自动化工具会**大量发请求**，在真实目标上很容易触发频率限制或告警。在靶场里没关系，但这是工具与手工之间一个必须意识到的差别。
