## 一句话概括

`ps aux` 是**某一瞬间的进程快照**（执行完就退出，适合留证），`top` 是**持续刷新的实时监控台**（自带系统概览和交互按键，适合现场盯）。排查挖矿这类恶意进程时两者配合：先用 `top` 看谁在跑满 CPU，再用 `ps aux` 把现场固定下来。

## 原理

### 1. `ps aux` —— 进程快照

`ps` 是 process status。单独敲 `ps` 只显示当前终端自己那几个进程，加上 `aux` 三个参数才是"看全机"：

```bash
ps aux
```

- `a` = 显示所有用户的进程（all users）
- `u` = 以面向用户的格式输出详细信息（user-oriented，多出 `%CPU`、`%MEM`、`VSZ`、`RSS` 等列）
- `x` = 连同**没有控制终端的进程**一起显示（后台进程、守护进程）

其中 `x` 最容易漏：不加 `x`，那些没有 TTY 的守护进程根本不出现 —— 而恶意进程往往正是以守护进程的形态常驻的，漏了 `x` 就等于放跑了重点排查对象。

#### 输出各列的含义

以原笔记里的现场输出为例：

```text
USER    PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root    954 99.0  0.9  296324  8780 ?       S    Dec17 138:19 watchdog
```

| 列名 | 说明 | 示例值解释 |
| :--- | :--- | :--- |
| `USER` | 进程所有者 | `root` —— 由 root 用户运行 |
| `PID` | 进程 ID | `954` —— 进程唯一标识 |
| `%CPU` | CPU 占用率 | `99.0` —— 占用 99% 的 CPU |
| `%MEM` | 内存占用率 | `0.9` —— 占用 0.9% 的物理内存 |
| `VSZ` | 虚拟内存大小（KB） | `296324` —— 约 296 MB 虚拟内存 |
| `RSS` | 常驻物理内存大小（KB） | `8780` —— 约 8.6 MB 物理内存 |
| `TTY` | 关联的终端 | `?` —— 没有关联终端（守护进程形态） |
| `STAT` | 进程状态 | `S` —— 睡眠状态（可中断） |
| `START` | 启动时间 | `Dec17` —— 12 月 17 日启动 |
| `TIME` | 累计 CPU 时间 | `138:19` —— 量级异常，见「踩坑与备注」 |
| `COMMAND` | 命令名称 | `watchdog` —— 进程名称 |

#### 进程状态（`STAT`）代码

| 代码 | 含义 |
| :--- | :--- |
| `R` | 运行中（Running） |
| `S` | 睡眠中（Sleep，可中断） |
| `D` | 不可中断睡眠（通常是在等 I/O） |
| `Z` | 僵尸进程（Zombie） |
| `T` | 已停止（Stopped） |
| `<` | 高优先级 |
| `N` | 低优先级 |
| `s` | 会话领导者（Session leader） |
| `l` | 多线程进程 |
| `+` | 前台进程 |

前 5 个是**主状态**，后 5 个是**附加修饰符**，实际输出里常常组合出现（例如 `Ss`、`Rl`、`S<l`）。所以看 `STAT` 不能只认一个字符，要按"首字符是状态、后面是修饰"来读。

### 2. `top` —— 实时动态监控

```bash
top
```

直接运行即进入**实时交互界面**，默认每 3 秒刷新一次。

#### 界面结构

```text
top - 11:57:38 up 30 days,  2:34,  1 user,  load average: 1.05, 0.98, 0.75
Tasks: 125 total,   1 running, 124 sleeping,   0 stopped,   0 zombie
%Cpu(s): 12.3 us,  5.6 sy,  0.0 ni, 81.8 id,  0.0 wa,  0.0 hi,  0.3 si,  0.0 st
MiB Mem :   7824.8 total,    324.5 free,   4321.2 used,   3179.2 buff/cache
MiB Swap:   2048.0 total,   2048.0 free,      0.0 used.   3129.4 avail Mem

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
    954 root      20   0  296324   8780   3052 S  99.0   0.9 138:19.28 watchdog
  10450 root      20   0  164700   2832   1540 R   1.0   0.3   0:00.12 top.orig
```

**上半部分 —— 系统概览**

| 区域 | 说明 |
| :--- | :--- |
| 第一行 | 系统时间、运行时间、登录用户数、负载平均值（1 / 5 / 15 分钟） |
| 第二行 | 进程总数、运行中、睡眠中、已停止、僵尸进程数量 |
| 第三行 | **CPU 使用情况**：`us` 用户态、`sy` 内核态、`ni` 低优先级、`id` 空闲、`wa` I/O 等待、`hi` 硬中断、`si` 软中断、`st` 被虚拟机偷取的时间 |
| 第四行 | **内存使用**：总量、空闲、已用、缓存（buff/cache） |
| 第五行 | **交换分区**：总量、空闲、已用、可用内存（avail Mem） |

**下半部分 —— 进程列表**

与 `ps aux` 类似，但**实时刷新**，且列名略有不同：

```text
PID    USER     PR  NI   VIRT    RES    SHR  S %CPU %MEM   TIME+   COMMAND
```

| 列名 | 说明 |
| :--- | :--- |
| `PR` | 优先级（Priority），值越小优先级越高 |
| `NI` | Nice 值，用户可调整的优先级（-20 到 19） |
| `VIRT` | 虚拟内存总量（对应 `ps` 的 `VSZ`） |
| `RES` | 常驻物理内存用量（对应 `ps` 的 `RSS`） |
| `SHR` | 共享内存大小 |
| `S` | 进程状态（同 `ps` 的 `STAT`） |
| `TIME+` | 累计 CPU 时间（比 `ps` 的 `TIME` 更精确） |

#### `top` 交互快捷键

| 按键 | 作用 |
| :--- | :--- |
| `h` 或 `?` | 显示帮助 |
| `q` | 退出 top |
| `k` | 杀死进程（会提示输入 PID 和信号） |
| `r` | 更改进程优先级（renice） |
| `P` | 按 CPU 使用率排序（默认） |
| `M` | 按内存使用率排序 |
| `N` | 按 PID 排序 |
| `T` | 按运行时间排序 |
| `1` | 展开显示所有 CPU 核心的使用情况 |
| `c` | 切换显示完整命令路径 |
| `z` | 彩色 / 黑白显示切换 |
| `x` | 高亮显示当前排序列 |
| `b` | 高亮显示运行中的进程 |
| `W` | 把当前配置保存到 `~/.toprc` |

排查挖矿时最常用的是 `P`（CPU 排序，默认就是它）、`M`（内存排序）、`c`（看命令的完整路径）、`1`（看是不是单核被一个进程占满）。

### 3. `ps aux` 与 `top` 对比

| 特性 | `ps aux` | `top` |
| :--- | :--- | :--- |
| 类型 | 静态快照 | 实时监控 |
| 刷新 | 一次性输出 | 持续刷新（默认 3 秒） |
| 交互性 | 无，执行后即退出 | 有丰富的交互命令 |
| 排序 | 需指定参数（`--sort`） | 实时按键排序（`P` / `M` / `N` / `T`） |
| 操作功能 | 仅查看 | 可杀死进程（`k`）、调整优先级（`r`） |
| 系统概览 | 只显示进程列表 | 显示系统整体状态（CPU、内存、负载） |
| 适用场景 | 脚本中采集、获取某一时刻的状态 | 交互式监控、故障诊断 |
| 资源占用 | 低（运行后退出） | 持续占用少量资源 |

## 适用场景与利用条件

### 什么时候用

- **主机变卡/负载高**：风扇狂转、网页变慢、`load average` 居高不下，第一步就是 `top` 看谁在吃 CPU。
- **应急响应**：接到"主机疑似被入侵/被植入挖矿"的告警，落地第一件事就是 `top` / `ps aux` 列出可疑进程。
- **拿到 shell 后摸底**：确认这台机器上到底跑着什么，有没有不认识的常驻进程。

### 前提与局限

- 只要能在机器上执行命令（SSH 登录、反弹 shell、本地终端）就能用；`ps aux` 默认不需要 root 也能看到全机进程。
- **`top` 的交互界面需要有终端**；另外它依赖采样时机，**跑一下就退出的短命进程可能抓不到** —— 这正是要和 `ps aux` 配合的原因。
- **输出本身可能不可信**：恶意程序会替换或包装 `ps`、`top` 来隐藏自己（现场出现 `top.orig` 就是这种痕迹，见下文），所以结论要和其他证据交叉验证。

### 怎么从一屏输出里认出可疑进程

这是应急排查里真正要练的一步 —— 命令谁都会敲，难的是扫一眼就知道该盯谁。回到原笔记的那个现场：

```text
    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
    954 root      20   0  296324   8780   3052 S  99.0   0.9 138:19.28 watchdog
  10450 root      20   0  164700   2832   1540 R   1.0   0.3   0:00.12 top.orig
```

逐列拆开看：

| 观察点 | 本例的值 | 怎么判断 |
| :--- | :--- | :--- |
| `%CPU` | `99.0` | 单核被**长期跑满**。挖矿的本质就是拿 CPU 换币，CPU 贴顶且不回落，是最直接的特征 |
| `TIME+` | `138:19:28` | **累计 CPU 时间异常大** —— 说明它不是"刚忙了一会儿"，而是长时间持续占用 CPU（量级问题见「踩坑与备注」） |
| `STAT` | `S` | 睡眠。这只是**采样瞬间**的状态，单独看说明不了任何问题，必须配合 `%CPU`、`TIME+` 一起读 |
| `TTY` | `?` | 没有控制终端。守护进程同样显示 `?`，所以它**不是罪证**，只能说明"不是有人在终端里手动跑的" |
| `VIRT` / `RES` / `SHR` | `296324` / `8780` / `3052` | 真内核线程这三列显示为 `0`；这里**非零**，说明 `watchdog` 是个**用户态进程** |
| `COMMAND` | `watchdog` | 内核线程的名字习惯上带方括号（`[kthreadd]`、`[rcu_sched]`、`[watchdog/0]`），且不占用户态内存。**「名字像内核线程 + 内存非零」** 就是典型的伪装 |
| 同屏另一条 | `top.orig` | 系统自带的命令叫 `top`，不叫 `top.orig`。`.orig` 这类后缀通常意味着**命令文件被替换过、原文件被改名保留**，是得顺着查的痕迹 |

**一句话总结判断法：把几列串起来看，任何单独一列都不足以定性。**

- `TTY ?` 只说明它在后台；
- `STAT S` 只说明采样那一下它在睡；
- 真正露馅的是这个组合：**`%CPU` 贴满 + `TIME+` 巨大 + 名字长得像内核线程却实实在在占着内存**。

再多说一句：这类伪装的进程，往往是配合"把 `ps`、`top` 换成自己的包装脚本"一起出现的 —— 所以看到 `top.orig` 就该意识到，**这台机器上 `ps` / `top` 的输出去查证时不能全信**，要换手段交叉验证。

## 速查表

| 目的 | 命令 |
| :--- | :--- |
| 全机进程快照（所有用户、含无终端进程） | `ps aux` |
| 同上，且不截断命令行 | `ps auxww` |
| 按 CPU 占用从高到低排序，只看前几名 | `ps aux --sort=-%cpu \| head` |
| 按内存占用从高到低排序 | `ps aux --sort=-%mem \| head` |
| 找名字里含关键词的进程 | `ps aux \| grep <关键词>` |
| 进入实时监控台 | `top` |
| 只盯某个 PID | `top -p <PID>` |

在 `top` 界面内的按键（`P` / `M` / `c` / `1` / `k` / `q` 等）见上文「`top` 交互快捷键」表。

## 踩坑与备注

- **`138:19` 的单位要先说清**：原笔记把 `ps` 的 `TIME` 记作"累计 CPU 时间 138 分钟"；但 `top` 里同一进程显示的是 `138:19:28`，按 `TIME+` 的时分秒格式读则是 138 小时 19 分。两种读法都**远超正常服务该有的量级**，不影响"这个进程可疑"的结论 —— 但引用这组数据时不要把单位写死。
- **原笔记的示例来自一张现场截图**（`屏幕截图 2025-12-18 115738`），上文的终端文本是按截图里的输出还原的，截图本身未保留在正文中。
- **`STAT` 是采样瞬间的值**，进程状态一直在变，别只看一眼就下结论。
- **`ps` 的 `%CPU` 不是瞬时值**，而是"累计 CPU 时间 ÷ 进程存活时间"的平均。所以真要衡量"到底烧了多少 CPU"，看 `TIME` / `TIME+` 最实在，两者对着看。
- **`TTY` 为 `?` 不代表恶意**：所有守护进程都是 `?`；反过来有 TTY 也不代表安全。
- **不能只凭进程名定罪**：`watchdog` 这个名字本身在系统里是存在的（内核线程 `[watchdog/0]`，也有同名的用户态守护进程）。本例能下判断，靠的是"命名形态 + 内存非零 + CPU 跑满"三点合起来，而不是名字本身。
- **确认某个 PID 可疑之后，先记下它的 PID、启动时间（`START`）和命令路径**，再决定怎么处理，不要一上来就删文件。
- 原文中没有出现真实 IP、域名、账号密码等需要打码的信息，靶机侧细节无需抽象处理。
