## 一句话概括

在工控靶场里，tcpdump 负责"把流量原样存成 pcap"，Wireshark 负责"把 pcap 里的协议字段翻译成人看得懂的东西"。抓工控流量的核心纪律是按端口过滤、抓够一个完整轮询周期，否则看到的可能只是链路的一个尾巴。

## 原理

### 为什么要抓包

工控协议的点号、地址、命令值通常藏在流量里，不写在文档中。靶场的设计原则是：

```text
IOA、COT、SBO、命令值必须来自任务模板、点表、事件日志或 pcap。
```

pcap 是玩家推导攻击参数的合法证据来源之一，不能靠猜。

### 抓包位置决定你能看到什么

```text
直接在被测主机上抓  -> 看到的是"本机视角"的原始报文
在 MITM 中间人上抓  -> 看到的是"转发后"的报文，同一报文会出现两次
```

素材中的实例（山区链）：

```text
frontend3-lower (10.0.4.2)  ->  conpot RTU (10.0.4.5)   tcp/2404
维护工作站 (10.0.4.6) 通过 ARP MITM 插在两者之间
```

## 报文/字段对照

### tcpdump 常用参数逐项解释

素材中的原命令：

```bash
sudo timeout 90 tcpdump -i ens18 -nn -s0 tcp port 2404 -w /tmp/iec104_capture.pcap
```

| 参数 | 含义 | 为什么要加 |
|---|---|---|
| `-i ens18` | 指定抓包网卡 | 多网卡主机上不指定会抓错接口 |
| `-nn` | 不解析主机名、不解析端口名 | 避免 DNS 反查拖慢抓包，端口直接显示 2404 而不是协议名 |
| `-s0` | 抓取完整报文（snaplen=0 表示不限长） | 默认只抓包头，会截断应用层数据导致解析失败 |
| `-w 文件` | 把原始报文写入 pcap | 供 Wireshark 或 `-r` 离线分析 |
| `-r 文件` | 读取已有 pcap | 离线回看，不占现场 |
| `timeout 90` | 限时 90 秒后自动结束 | 防止前台抓包一直挂着 |

### Wireshark 侧要点

```text
1. 用 display filter 而不是 capture filter 做二次筛选，
   例如只显示某个地址对：ip.addr==10.0.4.2 && tcp.port==2404
2. 右键 -> Follow -> TCP Stream，看一整条会话的交互顺序
   （STARTDT -> Select -> Execute -> 遥测上报）
3. 让 Wireshark 把工控协议解析成字段，而不是当裸 TCP 看
```

把三类协议解析出来的关键字段列出来：

IEC 104（C_SC_NA_1 单点遥控）

```text
TypeID   报文类型，45 = C_SC_NA_1
CA       Common Address 公共地址，素材实例 = 3
IOA      Information Object Address 信息对象地址
         IOA=10488 -> WT07
         IOA=10490 -> WT08
         IOA=10492 -> WT09
COT      Cause Of Transmission，6 = activation
Test bit 测试位，1 = 测试命令（不应产生物理动作）
SBO      Select Before Operate，先选择再执行
SCS      状态值，0 = 分/停
```

Modbus TCP

```text
Function Code  功能码，03 读保持寄存器 / 06 写单个寄存器
Unit ID        从站编号，素材实例 = 1
Address        寄存器地址（PDU 口径）
Value          写入值
Exception      异常码，如 0x86 / 0x02 表示非法地址
```

GOOSE

```text
IEC 61850 GOOSE 是二层以太网报文，不走 TCP/IP，实时性强，
常用于升压站保护跳闸、闭锁、保护联动。
解析重点是数据集、状态号、时标等，属于升压站保护联动的教学范畴。
说明：本笔记库的素材未包含 GOOSE 实测抓包，
上述为协议定位描述，字段解析需另行参考 IEC 61850 资料。
```

## 用法

### 抓工控流量的端口过滤

```bash
# 抓 IEC104
tcpdump -i ens18 -nn -s0 tcp port 2404 -w /tmp/iec104.pcap

# 抓 Modbus TCP
tcpdump -i ens18 -nn -s0 tcp port 502 -w /tmp/modbus.pcap
```

端口依据（素材）：

```text
IEC 104   常见 TCP 端口 2404
Modbus    常见 TCP 端口 502
OPC UA    常见端口 4840
IEC 61850 MMS  常见端口 102
```

### 抓包时长：必须覆盖一个完整轮询周期

这是素材里最重要的一条实测经验：

```text
frontend3-lower 的自动测试流量周期 = 60 秒
建议抓包时长 >= 75 秒
```

原因（原文）：

```text
如果刚好在一个周期尾部开始抓包，
短时间抓包可能只看到最后一个 IOA。
```

故障现象就是只看到：

```text
fc 28 00 -> IOA=10492 -> WT09
```

而看不到：

```text
f8 28 00 -> IOA=10488 -> WT07
fa 28 00 -> IOA=10490 -> WT08
```

修复方式是让发送端改成单条持久 IEC104 TCP 会话（STARTDT 后依次 WT07/WT08/WT09 的 Select/Execute），这样一次 MITM 抓包就能稳定看到三台。修好后 MITM pcap 中三个 IOA 各出现 20 次。

### MITM 场景：同一报文出现两次如何辨别

素材明确记录了这个现象：

```text
10.0.4.2 → 10.0.4.5:2404   （frontend3-lower → conpot）
同一 seq 的包出现两次       （ARP 转发生效）
length 6 = STARTDT，length 16 = Select/Execute 帧
```

辨别方法：

```text
1. 看是否在同一抓包点同时出现"入"和"出"两个方向的同 seq 报文。
2. 中间人转发时，报文先到达攻击机（第一次），再被转发出去（第二次）。
3. 因此 MITM pcap 里每个逻辑报文的计数是直连抓包的约 2 倍：
   素材实测 WT07/WT08/WT09 在 RTU 侧直抓各 10 次，
   在 MITM 侧各 20 次。
4. 分析时要去重：按 TCP seq + 方向筛选，或只保留一个方向。
```

### MITM 环境的前置条件

```bash
sudo sysctl -w net.ipv4.ip_forward=1
sudo arpspoof -i ens18 -t 10.0.4.2 10.0.4.5 &
sudo arpspoof -i ens18 -t 10.0.4.5 10.0.4.2 &
```

素材中的清理要求：

```text
验证完成后无残留 arpspoof / tcpdump 进程
/proc/sys/net/ipv4/ip_forward 已恢复为 0
```

### 离线回看

```bash
tcpdump -r /tmp/iec104_capture.pcap -nn | head -30
```

## 安全视角

- 抓包是取证与验证手段。授权靶场里，pcap 既是玩家的证据链，也是验题者的回归依据（确认 Test=1 的流量不触发停机）。
- 明文协议可被监听。IEC104、Modbus 明文传输，中间人不仅能看，还能改；真实环境需要纵向加密认证装置、工业防火墙。
- 抓包要在授权范围内做。ARP 欺骗会打断或改写现场通信，只允许在隔离的靶场/仿真环境里做；真实生产系统的测试必须经过书面授权。

注意：抓包看起来毫无副作用，但收工必须清理残留进程与转发开关。忘记关闭 ip_forward 或残留 arpspoof 会让现场处于"被持续中间人"的状态，这一条最容易漏。
