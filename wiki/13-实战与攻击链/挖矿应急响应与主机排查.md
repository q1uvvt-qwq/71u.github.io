## 一句话概括

Linux 主机被植入挖矿木马后的处置主线是：**用 `top` / `ps` 认出 CPU 异常的进程 → 用 `rpm -Vf` 校验系统命令是否被做过手脚 → 拆穿 `ps`/`top` 的包装脚本与 `/etc/ld.so.preload` 劫持 → `lsof -p` 定位落盘文件 → `chattr` 去掉不可变属性后删除 → 最后把 cron / at / 启动项 / SSH 公钥 / 环境变量 / sysctl 等所有持久化点一并清掉**。

否则删掉的可执行文件会被定时任务每分钟拉起来，属于白删。

## 本题情景与解题手法

### 题目形态

一台对外服务的 Linux 主机（CentOS，最小化安装）出现异常。登上去之后，症状不是报错、不是告警，而是**"看起来一切正常但机器很卡"**：

- `top` 能正常打开、正常刷新，命令本身没坏；
- 但列表里有一个 `watchdog` 进程几乎占满一个核，累计运行时间长得离谱；
- 直接 `grep watchdog /usr/bin/ps` 之类的常规怀疑点全都"干净"——因为 `ps` 本身的输出已经被过滤过了。

也就是说，这是一次**已经完成潜伏、并且专门对抗排查命令**的挖矿事件。所以这道"题"真正的考点不是找文件，而是**先确认手上的工具还可不可信**。

### 第一步：从 top 里认出那个不该在的 watchdog

先看 `top` 的实时进程列表：

> 此处原为 top 输出截图，要点：进程 `watchdog` 的 `%CPU≈99%`，`TIME+` 累计到 `138:19:28`，且 `VIRT` / `RES` / `SHR` 三列均为非零值。

两条判断依据：

1. **`%CPU≈99%` 且 `TIME+` 极大**（138 小时 19 分 28 秒）。一个正常的看门狗进程不可能持续吃满一个核、并且连续跑这么久——这是挖矿程序的典型特征。
2. **它有非零的 `VIRT` / `RES` / `SHR`**，说明它是一个**用户态进程**，而不是内核线程。

第 2 点是最关键的区分点。`top` 列表里同样带 "watchdog" 字样的 `watchdog/0`，以及 `kthreadd`、`rcu_sched` 这些，都是**内核线程**，它们**没有独立的用户态地址空间，内存列一般显示为 0**。所以：

| 名字 | 内存列 | 性质 |
|---|---|---|
| `watchdog/0`、`kthreadd`、`rcu_sched` | VIRT/RES/SHR = 0 | 真内核线程，正常 |
| `watchdog`（本次遇到的） | VIRT/RES/SHR 非零 | **用户态进程**，伪装成内核线程名，异常 |

挖矿木马喜欢把自己命名成 `watchdog`、`kworker`、`ksoftirqd` 这类内核线程的名字，就是想让管理员扫一眼 `ps` 时觉得"这是系统的"。**但内核线程的内存列是 0，用户态进程不是**——这一个细节就能把它揪出来。

### 第二步：先把维护入口留住，再切断外联（iptables）

确认有恶意进程之后，第一时间**断网隔离**，防止它继续挖矿、外传数据、下载后续 payload，或者把内网其他机器当跳板。但断网必须按顺序做，否则会把自己关在门外：

```bash
# 1. 允许维护人员的IP访问（必须第一步执行！）
iptables -I INPUT -s xx.xxx.xx.xx -p tcp -j ACCEPT
# -I INPUT：在INPUT链的最前面插入规则（优先级最高）
# -s xx.xxx.xx.xx：源IP地址（维护人员的公网IP）
# -p tcp：只允许TCP协议
# 目的：确保你还能通过SSH等连接主机，避免把自己锁在外面

# 2. 禁止所有入站流量
iptables -A INPUT -p tcp -j DROP
# -A INPUT：在INPUT链末尾追加规则
# 注意：这会阻止所有TCP入站连接，包括SSH、HTTP等
# 因为是追加，所以前面允许维护IP的规则仍然有效

# 3. 禁止所有出站流量
iptables -A OUTPUT -p tcp -j DROP
# 阻止主机向外发起TCP连接
# 有效防止恶意软件：
#   - 对外发送窃取的数据
#   - 下载更多恶意代码
#   - 作为跳板攻击其他主机
#   - 进行挖矿通信

# 4. 清除所有规则（危险！）
iptables -F
# -F：清空所有链的所有规则
# 这会立即移除所有防火墙规则，包括你刚才设置的隔离规则
# 只有在确认安全后恢复服务时才使用
```

**为什么第 1 步必须排在第 2 步前面**：iptables 的规则是**按顺序逐条匹配、命中即生效**的。第 1 步用 `-I`（insert）把维护 IP 的 ACCEPT 插到链的**最前面**，第 2 步用 `-A`（append）把 DROP 追到**末尾**——这样维护 IP 的包先命中 ACCEPT 直接放行，不会走到后面的 DROP。

如果反过来写（先 DROP 再放行自己的 IP，或者放行也用 `-A` 追加在 DROP 后面），DROP 会先命中，你的 SSH 立刻断掉，而且**远程再也连不上**，只能去机房或者走带外管理。这就是"把自己锁在外面"。

> 顺序口诀：**先 insert 放行自己，再 append 拒绝所有人。**
>
> 第 4 步的 `iptables -F` 会连第 1 步的保命规则一起清掉，所以只能在确认处置完毕、要恢复服务时才执行。

### 第三步：校验系统命令有没有被改（`rpm -Vf`）

`ps`、`top` 的输出不可信之后，下一步就是**校验二进制文件本身有没有被动过**。CentOS / RHEL 系可以用 rpm 的校验功能：

```bash
rpm -Vf /usr/bin/*
rpm -Vf /usr/sbin/*
#rpm -Vf /usr/bin/xxx
```

`-V` 是 verify（校验），`-f` 是 file（指定文件），合起来就是"校验这个文件相对于 RPM 数据库里记录的信息有没有变化"。输出为**空 = 没被改**；有任何字符输出 = 该维度不一致。

输出的每一行是 8~9 个字符，**位置固定的位的含义如下，未变化的位显示 `.`**：

| 字符 | 含义 |
|---|---|
| `S` | 文件大小（Size）改变 |
| `5` | MD5 校验和改变（数字 5，不是字母 S） |
| `L` | 符号链接（Link）改变 |
| `T` | 修改时间（mTime）改变 |
| `D` | 设备（Device）号改变 |
| `U` | 用户（User）所有者改变 |
| `G` | 用户组（Group）改变 |
| `M` | 文件模式（Mode/权限）改变 |
| `?` | 不可读（rare） |

行首还可能带几种标记：

| 行首标记 | 含义 |
|---|---|
| `missing` | 文件不存在（被删除了） |
| `c` | 该文件是**配置文件**（后续会有提示，配置文件被改是"常见且相对可接受"的，需要人工判断） |

> 阅读方法：**按字母对号入座，不要背位置号**。本次关心的就是那个 `5`——**MD5 变了，说明文件内容被替换过**。

**处置方式：直接删除被修改过的命令文件，从 backup 文件夹里面复制提前备份好的命令文件。**

（所以理想的应急准备是事先在做好的系统镜像里留一份 `/backup` 的原生命令副本；本次就是靠它把 `ps` / `top` 换回干净版本的。）

### 第四步：拆穿 `ps` / `top` 的包装脚本

上一步的校验会指向 `/usr/bin/ps` 和 `/usr/bin/top` 这两个文件。看一眼它们的真实内容：

> 此处原为被修改文件的截图，要点：`/usr/bin/ps` 与 `/usr/bin/top` 都已被替换成**包装脚本**，脚本内先调用 `/var/hide.sh`，再执行原本的二进制 `ps.orig`、`top.orig`。

也就是说：

```text
/usr/bin/ps   （脚本）──调用──> /var/hide.sh   （过滤/干脏活）
                    └──exec──> /usr/bin/ps.orig （真正的 ps，被改名备份）
```

- 这是典型的**进程隐藏 / 持久化手法**：攻击者把原二进制改名成 `*.orig` 留用，再用同名**脚本**占住这个路径。管理员敲 `ps` 走的是脚本，脚本先把输出"洗"一遍（把挖矿进程从列表里删掉），再把 `ps.orig` 的结果吐给你；
- 所以**功能是正常的、命令也不报错**，只是关键的那几行被吃掉了——这就是为什么第一步里 `ps` 看不出问题，而 `top` 里能看到（`top` 的脚本版处理不干净，或者 `top` 那条路径没被完全接管）；
- 它通常和 `ld.so.preload` 劫持、伪装内核线程名、定时任务回写等手法**组合出现**，不要只清一个就以为完事。

**查看被指向的脚本，根据脚本内容进行清除：**

```bash
cat -n /var/hide.sh
```

`-n` 带行号，方便按行定位脚本里的清理逻辑和引用到的其他文件路径。

### 第五步：检查 `/etc/ld.so.preload`

`ld.so.preload` 是动态链接器的"预加载"配置文件，优先级比 `LD_PRELOAD` 环境变量还高。**查看是否存在、存在则查看内容**：

```bash
cat /etc/ld.so.preload
```

**处置：删除 `/etc/ld.so.preload` 文件后，再删除其中记录的动态链接库文件。**

顺序不能反——它是全局生效的，留着它一边删库，一边还有新的进程持续被劫持。

### 第六步：`lsof` 定位落盘文件，`chattr` 解属性后删除

回头收网，先精确定位恶意进程：

- 用 `ps aux` 查看占用 CPU、内存异常的进程；
- 用 `top` 命令查看占用 CPU、内存异常的进程；
- 判断异常的外连：用微步等情报源判断外连 IP 是否为恶意 IP；
- **暂停找到的恶意进程 ID，防止它继续执行**。

拿到 PID 之后，**用 PID 反查进程打开的所有句柄（包括文件句柄），从而定位到文件的落盘路径**：

```bash
# 最小化安装的centos你需要提前安装好lsof
yum -y install lsof
# lsof -p <进程号>
lsof -p 82766
```

**找到调起恶意进程的文件后，进行删除。**

> 此处原为截图，要点：删除时遇到**权限问题**——明明 root 身份，`rm` 依然失败。

这时候**先用 `lsattr` 查看文件属性，如果发现有特殊属性，用 `chattr` 命令去掉属性**，再去删：

```bash
lsattr <恶意文件路径>
# 若输出里出现 i 或 a，说明属性被加了锁
chattr -i <恶意文件路径>    # 去掉不可变属性
rm -f <恶意文件路径>        # 现在才能删
```

`lsattr` 的输出是一串定长字符，每个位置对应一位属性，**`-` 表示该位未设置，出现字母表示该属性已开启**（例如 `----i--------e--` 就表示开启了 `i` 和 `e` 两位）。

| 字母 | 含义 | 字母 | 含义 |
|---|---|---|---|
| `a` | 只能追加（Append only） | `j` | 数据日志（data journaling） |
| `A` | 不更新访问时间（no atime） | `N` | 内联数据（inline data） |
| `c` | 压缩（Compressed） | `P` | project hierarchy |
| `d` | 不备份（no dump） | `S` | 同步更新（Synchronous updates） |
| `D` | 同步目录更新（Dir sync） | `s` | 安全删除（secure deletion） |
| `e` | extent 格式（ext4 特性） | `t` | 尾部不合并（no tail-merging） |
| `F` | 不整理碎片（no defrag） | `T` | 顶层目录（top of dir hierarchy） |
| `i` | **不可变（Immutable）** | `u` | 不可删除（undeletable） |
| `I` | 索引目录（indexed dir） | `x` | 直接访问（direct access） |

**安全相关的重点关注 `i`（不可变）和 `a`（只能追加）**——这两个是攻击者最常用来锁死恶意文件的属性。

`i - Immutable` 的效果：

```bash
# 设置了 i 属性的文件：
chattr +i /tmp/important.txt

# 效果：
rm -f /tmp/important.txt             # ❌ 失败：不能删除
echo "test" > /tmp/important.txt     # ❌ 失败：不能修改
mv /tmp/important.txt /tmp/new.txt   # ❌ 失败：不能重命名
ln /tmp/important.txt /tmp/link      # ❌ 失败：不能创建链接

# 只能：
chattr -i /tmp/important.txt         # 先去掉 i 属性
# 然后才能操作
```

**为什么加了 `i` 就删不掉**：`i` 属性是**内核在文件系统层（VFS）强制拦截**的，不是普通权限位（rwx）能比拟的——即使你是 `root`、即使权限是 `777`，内核也会拒绝写、删、改名、建链接这些操作。所以处理顺序永远是**先 `chattr -i` 解属性，再 `rm`**，直接 `rm` 只会一直失败。

### 第七步：清掉所有持久化点（防止"删了又回来"）

**这是二阶段的核心：防恶意文件恢复。** 只删文件不删定时任务，结果就是删一次回来一次。

#### 一、cron

先查计划任务里有没有指向恶意文件：

```bash
#1. 查看所有 cron 配置目录
ls /etc/cron.*
# 2. 查找最近1天修改过的文件
find /etc/ -mtime -1
# 3. 在所有cron配置中搜索"king"关键词
grep king /etc/cron.*/*
```

发现可能存在 crontab 计划任务在帮忙恢复。逐层查：

**（1）root 用户的 crontab**

```text
[root@theon ~]# cat /var/spool/cron/root
*/1 * * * * nohup /var/lib/king &
```

这是恶意任务：**每分钟执行一次 `nohup /var/lib/king &`**。`*/1` 就是"每分钟"，`nohup ... &` 是后台忽略挂断运行——删掉 `/var/lib/king` 后，一分钟内它就会被重新拉起来。

```bash
# rm -rf /var/spool/cron/root
```

删除 root 用户的 crontab 文件。

> 此处原为截图，要点：`/var/spool/cron/root` 中确认存在上述每分钟拉起的恶意任务，删除后该文件消失。

**（2）系统级 cron 任务**

```bash
# cat /etc/cron.daily/nginx
返回：nohup /var/lib/king &
```

攻击者伪装成 nginx 的日常任务，同样执行 `/var/lib/king`。

尝试删除时——**这里可能遇到单去掉文件属性仍然无法删除的情况**——那就**尝试去掉整个目录的属性**：

```bash
# chattr -asi /etc/cron.daily
```

```bash
# rm -rf /etc/cron.daily/nginx
//删除成功
```

（`-a` 去掉 append-only、`-s` 去掉 secure-deletion、`-i` 去掉 immutable。目录自身带了锁属性时，目录内的条目根本不允许被删除，光解文件的锁没用。）

**（3）系统主 crontab 文件**

查看系统的**主计划任务配置文件**。这个文件定义了系统级的定时任务，格式与用户 crontab 不同：

```bash
# cat /etc/crontab
发现有攻击者添加的挖矿任务
```

删除——直接编辑：

```bash
vim /etc/crontab
#直接编辑
```

**（4）再次复查**

```bash
grep king /etc/cron.*/*
```

无输出 = **通过**。

#### 二、atq

一次性定时任务（`at`）也是常见的复活手段：

```bash
1. 发现任务
atq
2. 查看内容
at -c 1 | tail -10
3. 删除任务
atrm 1
```

#### 三、rc.local 与 systemd 启动项

检查各个启动项位置：

```bash
# 1. 传统System V init的启动脚本
/etc/rc.local                    # 系统启动后执行的脚本
/etc/rc.d/rc0.d/                 # 运行级别0（关机）的启动项
/etc/init.d/                     # init脚本目录

# 2. systemd的启动服务（现代系统）
/usr/lib/systemd/system/         # systemd服务单元目录

# 3. 查找最近一天修改的systemd服务
find /usr/lib/systemd/system -mtime -1
# -mtime -1：查找最近24小时内修改的文件
# 攻击者可能最近添加了恶意服务
```

**删除**与之前操作相似（同样注意 `chattr` 属性问题）。

> 此处原为截图，要点：删除过程中出现**软链接（symlink）相关的问题**——被删除对象是符号链接，直接删会连带影响到链接目标或提示删除失败，需要先确认链接指向再处理。原文未展开具体回显。

#### 四、SSH 公钥

查有没有异常公钥（攻击者留下的免密后门）：

```bash
cat ~/.ssh/authorized_keys
```

#### 五、环境变量配置文件

检查 Linux 中主要的环境变量配置文件：

1. `/etc/profile` —— 系统全局环境变量（对所有用户生效）
2. `/etc/profile.d/*` —— 系统全局环境变量脚本目录
3. `/etc/bashrc` —— 系统全局 bash 配置
4. `~/.bashrc` —— 当前用户的 bash 配置
5. `~/.bash_profile` —— 当前用户的登录环境配置

检查恶意关键字：

```bash
grep king /etc/profile
```

（这类文件会在每次登录 / 开 shell 时被执行，攻击者常在这里塞下载器或者持久化命令。）

#### 六、系统内核参数配置文件

直接查看该文件内容，看是否有异常的内核参数设置：

```bash
cat /etc/sysctl.conf
```

### 处置手法一句话总结

**先确认工具可不可信（`rpm -Vf`），再清理；删文件之前先解属性（`chattr -i`），删文件之后必清持久化（cron / at / 启动项 / 公钥 / 环境变量）——顺序颠倒一次，前面的活就白干。**

## 原理

### 1. 为什么"内存列为 0"能区分内核线程

内核线程（`kthreadd`、`rcu_sched`、`watchdog/0` 等）只在内核地址空间里跑，**没有属于自己的用户态地址空间**，所以在 `top` / `ps` 里 `VIRT` / `RES` / `SHR` 都是 0。用户态进程无论如何都会映射一份地址空间，内存列必然非零。挖矿木马能把**进程名**伪装成 `watchdog`，但改不掉这个内核层面的差别——所以它是最好用的识别点。

### 2. 包装脚本 + `.orig` 是什么套路

正常的"替换二进制"是把原文件删掉放新的，缺点是功能容易出问题、容易被发现命令坏了。攻击者用的是更隐蔽的一招：

| 步骤 | 动作 | 效果 |
|---|---|---|
| ① | `mv /usr/bin/ps /usr/bin/ps.orig` | 原程序**完整保留**，功能不丢 |
| ② | 在同路径写一个 shell 脚本 `/usr/bin/ps` | 占住调用入口 |
| ③ | 脚本内先执行恶意逻辑（如 `/var/hide.sh`），再 `exec` 到 `ps.orig` | 输出被过滤，但格式、用法看起来一切正常 |

好处有三：**命令不会报错、输出格式正确、管理员很难察觉**；同时 `.orig` 让攻击者自己也能正常使用原命令。这次是 `/var/hide.sh` 负责在输出里删掉挖矿进程，`ps` 和 `top` 都是这套结构。

### 3. `/etc/ld.so.preload` 劫持

`/etc/ld.so.preload` 是动态链接器（`ld.so`）读取的**预加载库清单**。进程启动时，`ld.so` 会先把这里列出的 `.so` 加载进内存，优先于程序本身的依赖。

因为它写死在文件里、对**所有**动态链接的程序生效，所以攻击者把自己的库写进去后，可以实现：

- 劫持 `readdir` —— 让 `ls` / `find` 看不到恶意文件；
- 劫持 `readlink` —— 让 `ls -l` 里的路径显示成假的；
- 劫持 `open` / `stat` —— 让清理工具读不到、动不了目标文件。

因为它是全局且优先于环境变量的，所以处置顺序是**先删 `ld.so.preload`，再删它引用的那个 `.so`**：反过来的话，在文件仍在的这段时间里，新起的每个进程都还会被劫持一遍。

### 4. 为什么 `rm` 删不掉：`i` / `a` 属性在内核层拦截

`chattr +i` 设置的 `i`（immutable）属性由**文件系统内核代码直接检查**，优先级高于 Unix 权限模型。root 的"无所不能"来自权限位检查，而 `i` 属性在每个写/删/改名/建链的系统调用入口就返回 `EPERM` 了，根本走不到权限判断。所以：

- 文件的 `i` → 必须先 `chattr -i` 才能操作；
- **目录**的 `i` / `a` → 目录内的条目不允许被增加或删除，此时**光解文件自身的锁没有用**，必须对目录本身执行 `chattr -asi` 才可以删掉里面的文件。

### 5. 为什么 `find /etc/ -mtime -1` 好使

`-mtime -1` 表示"修改时间在最近 24 小时以内"。这个筛法的信噪比很高，原因在于：

- 正常的系统配置文件大多是**装机那天**写进去的，`mtime` 是几个月甚至几年前；
- 攻击者落盘的时间**就是入侵时间**，必然集中在最近这一段；
- 所以"最近 1 天被动过"的 `/etc` 文件，列表通常很短，一眼能看完。

同理，第三步的 `rpm -Vf` 也是利用"和金标准对比"的思路——在动态线索不可信时，退回**静态比对**。

### 6. 为什么必须先放行维护 IP 再 DROP

见「第二步」里的说明，这里再明确一次判断依据：iptables 是**有序规则链**，匹配是**从头到尾、命中即停**。因此规则的效果不只取决于它写了什么，还取决于它排在谁前面。`-I`（插最前）与 `-A`（追加末尾）的差别，在这个场景下就是"能不能保住自己的 SSH 连接"。

## 处置前提/适用范围

这套流程适用于**Linux 主机已被确认植入恶意程序、且攻击者可能已对排查工具做过手脚**的场景，使用前提是：

1. **有 root（或等效）权限**，且能登入系统本身（若已无法登录，要先走救援模式 / 挂载系统盘离线排查）；
2. **主机允许必要时断网隔离**——第二步的 OUTPUT DROP 会切断主机所有对外 TCP 连接，正在跑的业务会立刻中断，需要提前和业务方确认；
3. **有可用的干净参照物** —— `rpm -Vf` 依赖未被篡改的 RPM 数据库，`lsof` 等工具最好来自可信安装源（最小化 CentOS 需自行 `yum -y install lsof`）；
4. **有备份可回滚**（虚拟机快照 / 数据备份），因为删文件、`chattr` 都是不可逆操作；
5. **不要一边排查一边继续用被污染的 `ps` / `top` 下结论** —— 先用第三步验证命令可信度，再采信它们的输出。

不适用/需另作考虑的情况：攻击者已取得内核级权限（真 rootkit 加载了内核模块）时，上述用户态校验手段都可能被绕过，应改为**离线取证**（挂载磁盘到干净环境分析）或**直接重装**。

## 踩坑与备注

- **判断坑**：别被进程名骗。真正的内核线程内存列是 0，`watchdog` 有非零内存 → 用户态进程。
- **删除坑（重点）**：`lsattr` 看到 `i` 就必须先 `chattr -i` 再删，root 也没用。
- **删除坑（重点）**：**去掉文件属性后仍然删不掉，就去掉整个目录的属性** —— `chattr -asi /etc/cron.daily` 之后 `rm -rf /etc/cron.daily/nginx` 才删除成功。这是本次实际踩到的。
- **顺序坑**：`iptables` 的放行规则必须插在最前（`-I`），拒绝规则追加在末尾（`-A`）；写反就断线。
- **顺序坑**：`ld.so.preload` 要先删配置文件、再删引用的库。
- **工具坑**：被改过的 `ps` / `top` 输出不可信，先 `rpm -Vf` 校验，再从 `/backup` 恢复干净的命令文件。
- **工具坑**：最小化安装的 CentOS 默认没有 `lsof`，需提前 `yum -y install lsof`。
- **持久化坑**：只删 `/var/lib/king` 没用，`*/1 * * * *` 的 cron 一分钟内就会把它拉回来；必须把 cron / at / rc.local / systemd / ssh 公钥 / 环境变量 / sysctl 全部过一遍。
- **复核动作**：清完 cron 后用 `grep king /etc/cron.*/*` 再确认一遍，无输出才算通过。
- **软链接**：删除过程中遇到过符号链接相关的问题，处理时要先确认链接的真正指向再删（原文未展开具体回显）。
