## 一句话概括

**预认证（pre-auth）RCE** = 攻击者**不需要任何账号、Cookie 或令牌**，直接向一个未授权接口发一个请求，就能让服务器执行自己的代码。React2Shell 是 React Server Components 的 Flight 协议在反序列化阶段出现问题，从而形成的一条**预认证**利用链。

## 原理

### 1. 什么叫「预认证」，为什么它比普通 RCE 可怕得多

「认证」指的是「证明你是谁」这一步 —— 登录、校验 Cookie、验签 token。绝大多数漏洞都发生在**认证之后**，因为要利用它，你得先有一个账号。

`pre-auth`（预认证 / 认证前）指的是：**漏洞代码在「检查你是谁」之前就已经被执行了。**

| 对比项 | 认证后漏洞 | 预认证漏洞 |
|---|---|---|
| 利用门槛 | 需要有效账号（或先拿下别人的账号） | **完全不需要凭据** |
| 攻击来源 | 通常是内部、已在册的用户 | **互联网上任何一个人** |
| 前置动作 | 先注册 / 先爆破 / 先钓鱼 | 无，直接打 |
| 危害量级 | 单个用户/租户受影响 | **整个实例 / 整台服务器** |
| 典型后果 | 越权读数据 | 服务器被控、内网被打穿 |

一个需要登录的 RCE，攻击面已经被「你得先能登录」收窄了一大圈；而 pre-auth RCE 的面是**整个互联网**。这就是为什么同一段漏洞代码，带上「预认证」三个字之后，评级会从「高危」直接跳到「严重」（Critical）。

判断一个 RCE 是不是预认证，看的不是漏洞类型，而是**触发它所需的最早的那个处理阶段**：

```text
请求到达 → 路由分发 → 【框架层解析请求体】← 漏洞常常在这里
                              ↓
                      认证 / 鉴权中间件
                              ↓
                         业务逻辑
```

只要漏洞点位于「认证中间件」之前，它就是预认证的 —— 因为服务器在处理它的时候，**根本还没走到检查身份的那一步**。

### 2. RCE 的三种常见成因

「远程代码执行」是一个**结果**，不是一个原因。导致它的常见原因有三类：

| 成因 | 说明 | 直觉理解 |
|---|---|---|
| **反序列化** | 程序把用户提交的数据「还原成对象」，还原过程中被还原出的对象带有副作用（例如一个 `then` 属性被当作可调用对象执行） | 你把一段伪造的「施工图纸」交给工人，工人照着图纸把一间本不存在的房间盖了出来 |
| **命令注入** | 未过滤的用户输入被拼接到系统命令里执行 | 你在「文件名」里塞了 `; rm -rf /`，程序把它当命令跑了 |
| **认证绕过** | 身份验证逻辑本身有缺陷，被直接跳过 | 门口保安在打瞌睡，你直接走进去 |

本文的重点是第一类 —— **React2Shell 属于反序列化导致的预认证 RCE**。

### 3. React 与 Next.js

- **React** 是 Facebook 开发并维护的、用于构建用户界面的 JavaScript 库。它专注于构建可复用的 UI 组件，采用声明式编程范式。
- **Next.js** 是构建在 React 之上的全栈框架，走「服务端优先」路线，深度集成了 React Server Components（RSC），提供 SSR（服务端渲染）、静态生成和一体化后端 API 支持，是目前最主流的全栈 React 框架。

一句话分工：**用 React 组件来构建用户界面，用 Next.js 来实现其他功能和优化。**

### 4. React Flight 协议

传统的前后端传数据用的是 JSON。Flight 不一样，它是 React 团队为 **React Server Components** 专门设计的**二进制流式传输协议**，可以理解为 RSC 的「语言」或「通信标准」，专门解决服务端组件如何与客户端「对话」。

它的核心思想是：**不序列化对象本身，只序列化数据 —— 只传数据，不传对象结构。**

为什么需要另造一套？因为传统序列化处理不了这些东西（原文列出的一长串）：

```text
非序列化字段、单例破坏、循环引用、动态代理、Lambda/匿名类、
框架对象、不可变对象构造绕行、资源句柄、线程对象、复杂枚举状态、
闭包环境、数据库连接、网络 Socket、图形上下文、运行时依赖、
外部系统状态、事务上下文、安全上下文、类加载器依赖……
```

**这里埋下了后面所有问题的根**：为了能「只传数据、不传结构」，Flight 就必须定义一套自己的「引用标记」语法，让接收端能根据标记**把数据重新还原成对象**。而「按标记把数据还原成对象」这件事，本质就是**反序列化** —— 反序列化一旦对输入不加限制，就是 RCE 的温床。

同一份数据，两种协议的表达差别：

```text
传统序列化（JSON）：
{
  "users": [
    {"id": 1, "name": "Alice", "age": 25},
    {"id": 2, "name": "Bob", "age": 30},
    {"id": 3, "name": "Charlie", "age": 35}
  ]
}
→ 文本格式，字段名重复，解析慢

Flight（列式二进制）：
┌─────────┬─────────────┬─────────┐
│ id:int32│ name:string │ age:int │
├─────────┼─────────────┼─────────┤
│    1    │   "Alice"   │   25    │
│    2    │   "Bob"     │   30    │
│    3    │   "Charlie" │   35    │
└─────────┴─────────────┴─────────┘
→ 二进制列式存储，字段名不再重复
```

### 5. Flight 的流式格式与特殊前缀

传输时，一条响应被切成若干个 **Chunk** 依次下发：

```text
┌─────────────────────────────────────────────────────┐
│  Header: 版本、压缩类型等元信息                        │
├─────────────────────────────────────────────────────┤
│  Chunk 1: 组件类型定义                                │
│  [type: 'PostList', id: 1]                          │
├─────────────────────────────────────────────────────┤
│  Chunk 2: 数据引用                                    │
│  [ref: 'author', id: 101, data: {name: '张三'}]      │
├─────────────────────────────────────────────────────┤
│  Chunk 3: 复用引用                                    │
│  [use_ref: 'author', at: 'posts.0.author']          │
├─────────────────────────────────────────────────────┤
│  Chunk 4: 更多数据...                                 │
└─────────────────────────────────────────────────────┘

相比 JSON：字段名被省略，改用短标记 + 引用编号
```

注意 Chunk 里出现的 `$`、`@`、`$F`、`$K` 这些**短标记** —— 它们是「引用标记」，接收端看到它们就知道要去别处取真实对象。**这套标记就是攻击者要伪造的对象。**

#### 组件与 UI 相关

| 前缀 | 含义 | 编码示例 | 解码结果 | 使用场景 |
|---|---|---|---|---|
| `$` | React 元素 | `["$","div",null,props]` | `React.createElement("div", props)` | 普通 UI 元素 |
| `@` | 客户端组件引用 | `["$","@1",null,props]` | `lazy(() => import("./Button"))` | 客户端组件懒加载 |
| `@` | 服务端组件引用 | `["$","@S1",null,props]` | `resolveServerComponent("Component1")` | 服务端组件 |
| `S` | Symbol 引用 | `["S","Symbol(react.element)"]` | `Symbol.for("react.element")` | React 内部 Symbol |

#### 异步与流式数据

| 前缀 | 含义 | 编码示例 | 解码结果 | 使用场景 |
|---|---|---|---|---|
| `$@` | Chunk / Promise 引用 | `"$@1"` | `getChunk(response, "1")` | 异步数据分块 |
| `P` | Promise 占位符 | `["P","data_1",fallback]` | `Suspense` 包装的 Promise | 流式渲染 |
| `$R` | ReadableStream（文本） | `"$R1"` | `response._chunks.get("1")` | 文本流数据 |
| `$r` | ReadableStream（字节） | `"$r1"` | `response._binaryChunks.get("1")` | 二进制流数据 |
| `$X` | AsyncIterable | `"$X1"` | `async function*(){...}` | 异步迭代器 |

#### 二进制与文件数据

| 前缀 | 含义 | 编码示例 | 解码结果 | 使用场景 |
|---|---|---|---|---|
| `$K` | FormData 引用 | `"$K1"` | `response._formData.get("1")` | 文件上传表单数据 |
| `$B` | Blob 引用 | `"$B1"` | `new Blob([...])` | 二进制大对象 |
| `$U` | ArrayBuffer 引用 | `"$U1"` | `new ArrayBuffer(...)` | 原始二进制数据 |

#### 函数与 Action（本节最关键的一组）

| 前缀 | 含义 | 编码示例 | 解码结果 | 使用场景 |
|---|---|---|---|---|
| `$F` | Server Action 引用 | `"$F1"` | `async function serverAction(){...}` | 服务端函数调用 |
| `H` | 客户端函数引用 | `["H","client:onClick"]` | `window.__CLIENT_FUNCTIONS["onClick"]` | 客户端事件处理 |
| `$T` | 临时引用 | `"$T1"` | `createTemporaryReference(...)` | 临时数据引用 |

> 看 `$F` 这一行：**Flight 里存在「引用一个可执行的函数」这种类型**。它本来是为了让客户端能调用服务端函数而设计的，但如果反序列化时对引用的目标不加限制，攻击者就能让服务器「引用」到不该引用的东西。

#### 特殊 JavaScript 对象

| 前缀 | 含义 | 编码示例 | 解码结果 | 使用场景 |
|---|---|---|---|---|
| `$Q` | Map 对象 | `"$Q1"` | `new Map([["key","value"]])` | Map 数据结构 |
| `$D` | Date 对象 | `"$D2024-01-01T00:00:00.000Z"` | `new Date("2024-01-01")` | 日期时间 |
| `$n` | BigInt | `"$n12345678901234567890"` | `12345678901234567890n` | 大整数 |
| `$Z` | Error 对象 | `"$ZError: Something went wrong"` | `new Error("Something...")` | 错误对象 |
| `$Set` | Set 对象 | `"$Set[1,2,3]"` | `new Set([1,2,3])` | Set 数据结构 |
| `$RegExp` | 正则表达式 | `"$RegExp/^test$/gi"` | `/^test$/gi` | 正则表达式 |

#### 转义与特殊处理

| 前缀 | 含义 | 编码示例 | 解码结果 | 使用场景 |
|---|---|---|---|---|
| `$$` | 转义的 `$` | `"$$hello"` | `"$hello"` | 字面量美元符号 |
| `null` | 空值 | `null` | `null` | 空值（无前缀） |
| `undefined` | 未定义 | `undefined` | `undefined` | 未定义值 |

### 6. Server Action：把后端 API 写成前端函数的样子

**Server Action = 把后端 API 写成前端函数的样子。**

前端只显示「调用这个函数」，不显示函数的具体实现：

```text
客户端序列化 → 创建 HTTP 请求 → 服务器接收 → 服务器反序列化
      → 执行函数 → 序列化结果 → 返回给客户端
```

注意这条链路里出现了**「服务器反序列化」**这一步 —— 它正是 Flight 协议在服务端一侧的解析入口，也是 React2Shell 的攻击面所在。（这次请求具体带什么头部、服务器怎么识别它，见本文末的「关联阅读」。）

### 7. 三种渲染模式对比

| 特性 | 传统 React (CSR) | Next.js SSR | Next.js RSC |
|---|---|---|---|
| 渲染位置 | 客户端浏览器 | 服务器（每次请求） | 服务器（默认） |
| 首次加载 | 白屏时间长 | 快速显示内容 | 最快显示内容 |
| SEO 友好 | 差 | 优秀 | 优秀 |
| 数据获取 | 客户端获取 | `getServerSideProps` | 组件内直接 `fetch` |
| 代码拆分 | 需要配置 | 自动 | 自动 + 精细 |
| 状态管理 | `useState` / `Context` | `useState` / `Context` | 服务器状态 + 客户端状态 |
| 客户端 JS 体积 | 大（包含所有逻辑） | 中（部分预渲染） | 小（仅客户端组件） |

**RSC 的「服务端优先」是它高效的来源，也是它攻击面变大的来源** —— 因为服务器必须**接收并解析**客户端发来的、用于驱动服务端组件的结构化数据。

## 本题情景与解题手法

### 题目形态

一份公开的漏洞公告，核心信息是：

```text
受影响的包：react-server-dom-webpack / react-server-dom-parcel / react-server-dom-turbopack
受影响版本：19.0.0 ～ 19.2.0
基于 RSC 构建的框架同样受影响：Next.js 15.x / 16.x、
支持 RSC API 的 React Router、Expo、Redwood SDK、Waku，
以及各种 Vite / Parcel 插件
危害：预认证远程代码执行
```

**判断入口的第一步是「版本」**：先确认目标跑的是不是这个区间。

### 第一步：确认目标在受影响区间

```bash
# 看 package.json / lock 文件里的版本
grep -r "react-server-dom" package.json
# 或看页面里暴露的构建信息
curl -s http://靶机地址/ | grep -i next
```

判断依据：**只有在 19.0.0～19.2.0（或对应的 Next.js 15.x / 16.x）区间内，后面的利用才有意义**。不在区间里，直接结束，不要浪费时间尝试 payload。

### 第二步：找到那个「无需认证」的入口

RSC 应用的每个页面流量里，都带着框架自己的请求标识。用代理工具（Burp）随便点几下页面、抓一个正常的 RSC 请求，就能看到它的长相：

```http
POST / HTTP/1.1
Host: 靶机地址
Content-Type: text/plain;charset=UTF-8
Next-Action: <Action 的构建期标识>
Next-Router-State-Tree: [...]
```

判断依据：

- **这个 POST 请求不带任何认证信息**（没有登录态也行），说明服务端处理它的时候**还没走到鉴权**，即 pre-auth；
- 请求体的 Content-Type 是 `text/plain`、内容是一段**怪异的、带 `$` 标记的文本** —— 这就是 Flight 格式，说明服务器会把它当序列化数据解析。

### 第三步：构造恶意的 Chunk

既然服务器会反序列化 Flight 数据，那我们就不发「合法的组件数据」，而是发一个**伪造的 Chunk**：

```http
POST / HTTP/1.1
Host: 靶机地址
Next-Action: <Action 的构建期标识>
Content-Type: text/plain;charset=UTF-8

{"then":"$1:__proto__:then",
 "_response":{"_prefix":"<此处原为待执行的命令表达式>"}}
```

各字段的用意：

| 字段 | 作用 |
|---|---|
| `then` 指向 `$1:__proto__:then` | 让解析结果被当成一个 **thenable**（带 `then` 方法的对象）。JavaScript 在 `await` 一个对象时会去调用它的 `then`，这就给了攻击者一个**触发执行的时机** |
| `_response` | 伪造解析器内部持有的「响应对象」 |
| `_response._prefix` | 解析器会把这段前缀当成**要拼接进代码里的字符串**，从而变成可执行内容 |

这一条链的巧妙之处在于：**攻击者没有直接提交代码，而是提交了「数据结构」**，由框架自己的解析逻辑把这段数据「翻译」成执行动作。这就是反序列化类漏洞的共同套路。

### 第四步：看框架是怎么把数据「还原」成可执行对象的

漏洞出在 Flight 解析器的 `initializeModelChunk` 这个函数上：

```javascript
function initializeModelChunk(chunk) {
  var resolvedModel = chunk.value;        // 取得 JSON 字符串，如 ["$K1"]

  chunk.status = "cyclic";                // 标记为"处理中"，防止循环引用

  try {
    // [1] JSON 解析
    var rawModel = JSON.parse(resolvedModel);   // ["$K1"] → ["$K1"]

    // [2] 关键！恢复特殊引用
    var value = reviveModel(response, ..., rawModel);

    // [3] 标记完成
    chunk.status = "fulfilled";
    chunk.value = value;

    // [4] 唤醒等待的 Promise
    wakeChunk(resolveListeners, value);

  } catch (error) {
    chunk.status = "rejected";
  }
}
```

逐步翻译它在干什么：

1. **取出一段 JSON 字符串** —— 这段字符串的来源就是请求体，**完全由用户控制**；
2. **`JSON.parse`** —— 这一步本身无害，只是把文本变成 JS 对象；
3. **`reviveModel`（关键）** —— 把对象里的 `$`、`$@`、`$F` 之类**特殊标记「复活」成真正的对象**。攻击者伪造的 `_response`、`then` 就是在这里被还原成真家伙的。**这一步没有对「被还原的目标」做限制，是本漏洞的根因**；
4. **`wakeChunk`** —— 唤醒前面处于等待态的 `await`。而前面说过，`await` 一个对象时会去调它的 `then`，于是伪造的 `then` 被执行。

一句话：**`reviveModel` 把攻击者控制的「数据」，还原成了攻击者控制的「对象」和「行为」。**

### 第五步：验证代码执行

和所有复现一样，验证一定要用**客观、无破坏性**的判据：

```bash
# PoC 中让服务器创建一个文件
ls -la /tmp/poc.txt        # 文件出现了吗？
# 或者让服务器回显自身身份
# 观察响应中是否带回了 id / whoami 的结果
```

### 攻击手法一句话总结

> **确认版本落在受影响区间** → 抓一个**不带认证**的 RSC 请求，确认入口是 Flight 反序列化 → 把请求体换成**伪造的 Chunk**，用 `then` 让结果被当作 thenable、用 `_response._prefix` 注入待执行内容 → 服务端在 `initializeModelChunk` 里调用 `reviveModel` 把「数据」还原成「对象」并触发执行 → 用 **文件落盘 / 命令回显** 证明 RCE 成立。

## 受影响版本与修复

| 受影响产品 | 需升级到的安全版本 |
|---|---|
| **React**（react-server-dom-*） | 19.0.1+ / 19.1.2+ / 19.2.1+ |
| **Next.js** | 15.0.5+ / 15.1.9+ / 15.2.6+ / 15.3.6+ / 15.4.8+ / 15.5.7+ / 16.0.7+ |

官方安全公告（react.dev）：https://react.dev/blog/2025/12/03/critical-security-vulnerability-in-react-server-components

处置思路（按优先级）：

1. **升级到上表的安全版本**（首选，且要连 `react-server-dom-*` 一起升级）；
2. 无法立即升级时，用 **WAF** 拦截发往 Server Function 端点的畸形请求；
3. 限制网络访问（ACL / 防火墙），不要把 RSC 应用直接暴露在公网；
4. 确认**没有显式 Server Function 端点**的应用也可能受影响 —— 不要以此为由跳过修复。

## 利用条件

1. **版本在受影响区间**：React `react-server-dom-*` 19.0.0～19.2.0，或 Next.js 15.x / 16.x
2. **存在可访问的 RSC / Server Action 端点**（通常就是站点根路径或某个 `POST` 入口）
3. **服务端会解析请求体里的 Flight 数据**（Content-Type 为 `text/plain`，请求体是带 `$` 标记的序列化文本）
4. **无需认证**：入口不要求登录态 —— 这正是它被列为 pre-auth 的原因

## 踩坑与备注

- **「预认证」不等于「无差别」**：即使是 pre-auth 漏洞，也可能依赖某个特定路由被访问到；扫描时不要只看首页，要把所有能触发 RSC 的路径都过一遍。
- **版本号必须看精确版本**：`19.1.0` 与 `19.1.1` 同在受影响区间，但 `19.1.2` 已修复。用 `^19.0.0` 这类宽松写法很容易装到已修复版本。
- **不要只盯 Next.js**：React Router、Expo、Redwood SDK、Waku、Vite/Parcel 的 RSC 插件都在影响范围内，只是 Next.js 最常见。
- **Flight 那套 `$` 前缀表是理解这类漏洞的钥匙**：看不懂 `$@`、`$F`、`$Q` 的含义，就很难理解为什么「发一段看起来像 JSON 的文本」能让服务器执行代码。
- **原文对漏洞成因的描述集中在「原型污染 → 代码注入 → RCE」三步**（见「漏洞复现的方法论」一文中的示例），本文在此基础上补充了 `reviveModel` / `initializeModelChunk` 这一层的解释。若某一步的细节要从 PoC 反推，务必以官方公告和实际环境中的验证结果为准，不要凭记忆下结论。

关联阅读：本文提到的 `Next-Action` 请求头具体是什么、为什么它会成为攻击面，见《Next-Action 头部与框架漏洞》。
