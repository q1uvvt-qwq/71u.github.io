## 权限、业务逻辑与合约升级

智能合约代码能够自动执行，但它通常不会允许所有地址执行所有功能。合约需要规定：

```
谁可以调用什么功能
在什么条件下调用
调用后允许怎样修改状态
合约规则以后能否改变
```

这一章讨论三类风险：**权限设置错误、业务规则错误和升级机制被滥用。**



### 合约权限

合约权限决定某个地址可以执行哪些敏感操作。

常见角色包括：

| 角色         | 可能拥有的能力           |
| ------------ | ------------------------ |
| **Owner**    | 修改配置、转移所有权     |
| **Admin**    | 分配和撤销其他角色       |
| **Minter**   | 增发代币                 |
| **Burner**   | 销毁代币                 |
| **Pauser**   | 暂停或恢复合约           |
| **Operator** | 执行日常协议操作         |
| **Upgrader** | 更换合约实现代码         |
| **Guardian** | 紧急暂停或限制高风险操作 |

一个地址可以拥有多个角色，一个角色也可以分配给多个地址。



### 检查权限

最简单的权限检查是比较调用者地址：

```
require(msg.sender == owner);
```

含义是：

```
当前调用者等于owner
→ 继续执行

当前调用者不是owner
→ 交易回滚
```

复杂合约通常使用角色表：

```
地址A：管理员
地址B：铸币角色
地址C：暂停角色
```

调用敏感函数时，合约查询调用者是否拥有相应角色。



### 常见权限漏洞

#### 缺少权限检查

敏感函数被任何地址调用：

```
function withdrawAll() external {
    // 没有检查调用者
}
```

攻击者可能直接调用提款、增发、升级或修改价格等函数。

#### 检查了错误的身份

合约之间连续调用时，`msg.sender`会变化。错误使用调用者信息，可能让中间合约绕过权限。

尤其需要谨慎使用`tx.origin`。它表示整条调用链最初发起交易的外部账户，可能被恶意中间合约利用。

#### 角色配置错误

代码中的权限检查正确，但部署后把角色分配给了错误地址，或给某个角色过大的权限。

#### 初始化函数未保护

可升级合约常通过`initialize`函数设置管理员。如果该函数可以被再次调用，或部署后没有及时调用，攻击者可能把自己设置成管理员。

#### 权限撤销不完整

表面上转移了所有权，但旧管理员、升级角色或其他特殊角色仍然存在。



### 降低单一管理员风险

**多签钱包**

多签要求多个签名者共同批准操作，例如：

```
3个签名者中至少2个同意
→ 才能执行管理员操作
```

它可以降低单个私钥泄露带来的风险，但仍需考虑：

- 签名门槛是否合理；
- 签名者是否真正独立；
- 多个密钥是否保存在同一设备；
- 多签合约本身是否安全；
- 签名者能否及时响应紧急事件。

**时间锁**

时间锁让敏感操作在提交后等待一段时间才能执行：

```
提交升级
   ↓
等待48小时
   ↓
允许执行
```

等待期间，用户和监控系统可以发现异常，并决定撤资或采取其他措施。

时间锁无法阻止所有攻击，但能减少管理员瞬间修改规则的风险。



### 业务逻辑

**业务逻辑是合约为了实现具体应用目标而制定的规则。**

例如：

```
存入多少资产，应获得多少凭证？
抵押率低于多少时允许清算？
奖励可以领取几次？
谁承担亏损？
提款时应该扣除多少余额？
```

业务逻辑漏洞不一定违反Solidity语法，也不一定涉及典型代码错误。程序可能完全按照代码执行，但代码表达的规则本身存在缺陷。



### 常见业务逻辑错误

| 类型               | 可能结果                       |
| ------------------ | ------------------------------ |
| 余额先后更新错误   | 重复提款或错误记账             |
| 奖励状态更新不完整 | 同一奖励被多次领取             |
| 份额计算错误       | 少量存款换取过多权益           |
| 舍入处理错误       | 通过大量小额操作积累收益       |
| 抵押率计算错误     | 超额借款或错误清算             |
| 状态转换缺失       | 在不允许的阶段执行操作         |
| 边界条件错误       | 零值、最大值或首次存款产生异常 |
| 操作顺序组合错误   | 单独安全的函数组合后产生漏洞   |
| 外部价格假设错误   | 使用可操纵价格计算资产价值     |

### 安全不变量

分析业务逻辑时，经常先定义系统必须始终满足的条件，称为**不变量**。

例如：

```
用户不能提取超过自己权益的资产
合约负债不能无故超过实际资产
同一奖励不能重复领取
代币总量变化必须符合发行规则
清算后抵押和债务必须正确更新
普通用户不能获得管理员权限
```

攻击者会尝试寻找一系列合法操作，使某个不变量被破坏。



### 智能合约需要升级

普通合约部署后，代码通常固定。实际项目可能需要：

- 修复漏洞；
- 增加功能；
- 修改业务规则；
- 适配其他协议；
- 进行紧急响应。

因此，很多项目使用**代理合约**实现升级。



### 智能合约升级

代理结构通常包含两个合约：

```
用户
  ↓
代理合约 Proxy
  ├─ 保存资产
  ├─ 保存状态
  └─ 保存实现合约地址
          ↓
     实现合约 Implementation
     └─ 提供执行代码
```

用户一直调用代理地址。代理通过`delegatecall`执行实现合约中的代码，但读取和修改的是代理自身的存储。

因此：

```
地址和资产留在代理合约
实现代码可以被替换
```

管理员升级时，只需要把代理记录的实现地址改为新的实现合约。



### 升级机制风险

**升级权限被盗**

攻击者获得升级角色后，可以把实现地址改成恶意合约，再转走代理持有的资产。

**恶意管理员升级**

管理员本来就拥有升级权。如果项目方主动部署恶意实现，链上权限可能允许其合法执行。

**初始化错误**

新实现或代理没有正确初始化，攻击者可能抢先设置管理员或关键参数。

**存储布局冲突**

代理的数据保存在固定存储位置。如果新旧实现对这些位置的解释不同，升级后可能发生：

- 余额被错误读取；
- 管理员地址被覆盖；
- 状态变量相互冲突；
- 资产无法正常提取。

**升级后的代码未经审计**

旧版本通过审计，不代表后续实现也安全。升级会改变实际执行的代码。



## 本章要点

智能合约安全不仅是检查代码有没有语法错误，还要检查：

```
权限是否正确
业务规则是否完整
关键状态是否始终一致
管理员是否权力过大
升级机制是否可能改变安全假设
```

**权限决定谁能操作，业务逻辑决定操作应产生什么结果，升级机制决定这些规则以后能否被改变。**下一章将进入常见智能合约漏洞，包括重入、外部调用、输入验证和拒绝服务。
