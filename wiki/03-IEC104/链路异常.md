## 一句话概括

IEC 104 在 TCP 之上又自建了一层链路状态（APCI 序号 + 会话状态机）。只改报文内容（COT 的 Test 位）往往不够，很多实现要求你先让链路进入"异常/降级"状态，之后的重放或注入才会被接受。这一类攻击面不在 ASDU 里，而在 APCI 序号与 `HEALTHY / DEGRADED` 会话状态上，对应 CrySyS 那套 `IEC-104-Attacks` 里的 starvation、TCP/APCI poisoning、packet injection 三条思路。

> 本篇内容对应的是授权靶场里模拟协议处理缺陷的演练方法，不涉及真实生产设备的操作。

## 原理

### 1. 为什么协议栈之上还要一层"链路状态"

TCP 已经保证"字节不丢不乱"，为什么远动还要自己管序号和会话状态？

```text
TCP 保证的：  字节流可靠（重传、去重、有序）
IEC 104 要的：ASDU 级别的收发计数 + 明确的"允许/停止传输"状态
```

远动是双向往复的控制回路：主站发命令、从站回确认，双方都要独立核对"我发了几条、你确认到几条"。这套 `发送序号 / 接收序号`（各 15 位，左移 1 位存放）就是应用层的第二道账本。

攻击面正来自这里：TCP 账本由内核维护、改不动；IEC 104 账本由应用维护，一旦被扰动链路就进入异常态。很多实现为容错和重连恢复放宽校验，这就给了重放与注入的空间。

### 2. 三类链路层异常

素材参考的 CrySyS `IEC-104-Attacks` 把这类攻击归为三条：

| 类型 | 手段 | 后果 |
|---|---|---|
| IEC104 starvation |  flooding 式占用链路 / 让从站忙于应答，挤掉正常轮询 | 遥测上送延迟或断档，调度侧看到"数据停滞" |
| TCP/APCI poisoning | 人为扰动 APCI 的发送序号，制造序号漂移 | 链路被判定失步 → 复位重连，或进入降级容错态 |
| Packet injection | 在既有会话里插入伪造的 ASDU（如一条 Execute） | 若校验被放宽，注入的命令被当作合法命令执行 |

三者可以叠加：先 poison 出一个降级态，再 injection 一条正式命令，这是山区链"新测试方法"的核心思路。

本篇往后展开的主线是 poisoning 与 injection：§3 讲序号怎么被扰动到失步，§4 讲失步打开的 `replay_window` 如何让旧报文重新生效，§5 讲在既有会话里注入新的 ASDU。starvation（flooding 式占用链路、让从站忙于应答，挤掉正常轮询，后果是遥测上送延迟或断档）不单独展开，它只在 §7 的历史库事件 `IEC_STARVATION` 里露一次面。

### 3. APCI 序号漂移（APCI Counter Drift）

定义：序号漂移指人为让某一侧的发送序号跳变。正常流量的序号是严格交替递增的（见 `抓包分析.md` 第 7 节）：

```text
正常：  主站 send_seq  0 → 1 → 2 → 3 …
漂移：  主站 send_seq  0 → 1 → 5 → 6 …      ← 跳了 +4，从站账本对不上
```

素材里靶场用的参数就是：

```text
operation            APCI_POISON
apci_send_seq_delta   4            ← 发送序号一次性偏移 +4
```

成因：序号对不上有多种可能原因，链路抖动、设备重启、NAT 超时都算，所以实现通常不会立刻断链，而是先进"降级/容错"状态，放宽部分校验等待恢复。这个降级态正是攻击者要的窗口。

```text
session_state:  HEALTHY  ──(APCI drift)──►  DEGRADED
                                            replay_window = open
                                            apci.drift = 4
```

`DEGRADED` 是为容错而存在的，但它同时意味着降低安全校验。这是设计权衡被滥用成漏洞的典型：降级本该只放宽性能相关的校验，绝不应该是命令合法性校验。

### 4. 重放窗口（Replay Window）

序号漂移打开 `replay_window` 之后，此前观察到的合法报文就可以被重新提交：

```text
攻击者抓到  →  一条 COT=test 的 C_SC_NA_1（合法测试命令）
             （因为 Test 位为 1，正常通道下不落地）
漂移链路    →  让从站进入 DEGRADED，重放窗口打开
重放        →  提交这条命令（或改成 COT=execute 后提交）
结果        →  从站失去"这条命令是不是新鲜的"的判断依据
```

为什么要先漂移？从站靠序号判断命令是新的还是重复的；序号一旦漂移，这个基础就失效了，重放窗口就是新鲜度校验失效的那段区间。

### 5. 报文注入（Packet Injection）

注入是在既有会话里插入一条此前没出现过的 ASDU，与重放的区别：

```text
重放：提交一条曾经合法的帧（序号旧）
注入：构造一条新的帧（序号需要"接得上"当前链路状态）
```

注入的难点在于序号要接得上，所以顺序通常是"先漂移、后注入"：链路进入 DEGRADED 后序号校验被放宽，注入帧更容易被接受。

靶场里的注入演练就是把 SBO 流程完整走一遍，Select 再 Execute：

```text
step 1  precheck  { type_id: C_SC_NA_1, ioa: 10490, cot: test, select: true,  value: 1 }
        → stage = select
        → message = "select accepted; send execute with select=false"

step 2  precheck  { type_id: C_SC_NA_1, ioa: 10490, cot: test, select: false, value: 1 }
        → 命令落地
```

注意 `select: true → select: false` 就是 SCO 的 bit7（S/E 位），与 `报文结构.md` 里 `0x80 → 0x00` 完全对应。靶场把它抽象成 JSON 字段，底层语义不变。

### 6. 负向验证：只改 COT 是不够的

素材明确设计了一步"反例"，用来证明链路异常是必要条件：

```text
① 未降级时，直接发 COT=test 的命令
   → 返回 stage = simulation_only
   → PLC2.status 仍为 RUNNING（不落地）

② 先让 session_state = DEGRADED
   → 同样一条命令再发
   → PLC2.status = STOPPED / active_power_kw = 0 / alarm = REMOTE_STOP
```

这一步的教学价值极高：它把"漏洞"从"随便发个包就行"纠正成"必须理解会话状态机"，也对应靶场设计原则：不允许靠猜测或暴力试出攻击路径。

### 7. 靶场里的异常状态与恢复

```text
初始 / 恢复后     session_state = HEALTHY，replay_window 关闭，drift = 0
攻击后            session_state = DEGRADED，replay_window = open，apci.drift = 4
```

对应的事件记录（历史库里的三类关键事件，可作真实 SIEM 规则的模板）：

```text
MNT-EVT-104-113   IEC_STARVATION
MNT-EVT-104-115   IEC_APCI_COUNTER_DRIFT   VS 漂移 +4，replay window 进入 DEGRADED
MNT-EVT-104-117   IEC104_TEST_COMMAND_OBSERVED
```

这三类事件正是链路层攻击的三个观测点：链路饥饿、序号漂移、测试命令出现。做成告警规则就能覆盖本类攻击的全部阶段。

## 报文/字段对照：异常在字段上长什么样

| 异常 | 在链路上可观测的字段 | 正常值 | 异常值 |
|---|---|---|---|
| 序号漂移 | I 帧控制域的发送序号 | 逐帧 +1 | 跳变（如 +4） |
| 链路饥饿 | ASDU 到达间隔 | 固定轮询周期 | 超期/断档 |
| 重放 | I 帧序号重复出现 | 严格递增 | 旧序号重现 |
| 注入 | 出现新的 TypeID 或新 IOA | 只有已知点 | 陌生 IOA（如非 10488/10490/10492） |
| 测试命令进生产 | COT 的 bit7 | `0x06` 正式 | `0x86` 出现在生产链路 |

> 素材内部有一处说法不一致需要留意：`SCR`（SCS）位与停/启的对应关系，`报文结构.md`/Rogue Master 脚本写的是 SCS=0 = 停，而会话异常文档里的靶场 JSON 用的是 `value=1 表示停止`。以实测 pcap 与脚本为准，实机核对时务必先做一次"选择→执行"确认方向（靶场里可用 reset 接口反复验证）。

## 安全视角

- 降级态必须收敛校验范围，不能放宽命令合法性。`DEGRADED` 应只影响性能类参数（重传间隔、超时），绝不能让"新鲜度校验"或"Test 位拒绝"失效。多数真实漏洞就出在这条边界没画清。
- 新鲜度校验要独立于序号。序号是"相对"的，会漂移、会重连；应叠加时间戳/挑战值（命令携带一次性 ticket 或有效期），这样即使序号失效，重放依然会被识别。
- 检测规则应覆盖三个阶段：`IEC_STARVATION` → `APCI_COUNTER_DRIFT` → `TEST_COMMAND_OBSERVED`，逐级升级告警。单独看任何一条都可能误报，三条成链就是高置信度攻击。
- `replay_window` 本身应该是可审计的状态。"窗口被打开"比"窗口里的攻击"更早、更容易检测，且不依赖对报文的深度解析。
- 短连接 + 频繁 STARTDT + 序号漂移 = 脚本特征。真实调度主站的长连接序号是平滑的；一旦出现"重连即漂移"，应直接排查是否有人在中间做会话操纵。
- "只改一个比特就能落地"的前提是链路已被降级。反过来看，只要把 Test 位拒绝策略硬编码在转发组件里，攻击者即使漂移了链路也白搭，纵深防御的价值就在于让单点绕过失效。
