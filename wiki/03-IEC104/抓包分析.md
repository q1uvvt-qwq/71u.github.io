## 一句话概括

本篇是唯一有真实 pcap 支撑的抓包篇。素材里 5 个 pcap 记录的是山区链的自动测试流量：`frontend3-lower`（10.0.7.133）向 conpot RTU（10.0.7.131:2404）先 STARTDT 拉手，再对 WT07/WT08/WT09 依次做 Select→Execute，一台约 1.7 秒、三台合计约 3.3 秒，然后关连接重开。读懂这组帧，等于读懂一条遥控在链路上的样子。

## 原理

### 素材：5 个 pcap 各自能看什么

| 文件 | 抓包方式 | 连接方式 | 用途 |
|---|---|---|---|
| `iec104_3fan_single_direct_20260726.pcap` | 直连（非 MITM） | 单连接串行打三台 | 本篇主样本，最干净 |
| `iec104_3fan_direct_20260726.pcap` | 直连 | 多连接 | 对照连接模型差异 |
| `iec104_3fan_single_mitm_20260726.pcap` | MITM | 单连接串行 | 看 ARP 转发造成的重复帧 |
| `iec104_3fan_mitm_20260726.pcap` | MITM | 多连接 | — |
| `iec104_3fan_mitm2_20260726.pcap` | MITM | 多连接 | — |

注意：全部是"自动测试流量"，不是攻击流量。里面 COT 恒为 `0x86`（Test=1），也就是维护测试通道打出来的、不落地的命令。攻击链做的事就是把这个 `0x86` 改成 `0x06` 再重放。

### 抓包：怎么抓全一个轮询周期

素材里没有 tshark，本次分析用自写的极简 pcap 解析脚本（Python，处理大小端 magic + 提取以太网/IP/TCP 载荷）：

```bash
# 生产环境里更常用 tshark / tcpdump
sudo tcpdump -i ens18 -nn -s0 tcp port 2404 -w /tmp/iec104.pcap
# 只看某对主机
sudo tcpdump -i ens18 -nn -s0 'tcp port 2404 and host 10.0.7.131' -w /tmp/rtu.pcap
```

抓包时长要覆盖一个完整轮询周期。素材里的教训：`frontend3-lower` 的轮询是固定间隔重复整轮，从周期尾部才开始抓，短时间只能看到最后一台风机。实测每个 pcap 都抓了 10~11 秒、覆盖 2~6 个连接，才拿到完整三台轮次。

Wireshark 里对应的过滤器与技巧：

| 过滤器 / 操作 | 用途 |
|---|---|
| `iec60870_104` 或 `tcp.port == 2404` | 只看 104 流量 |
| `iec60870_104.type == 45` | 只看单点遥控（C_SC_NA_1） |
| `iec60870_104.cause == 6` | 只看激活命令（下行） |
| `iec60870_asdu.ioa` | 按点号过滤到某台风机 |
| 右键 → Follow → TCP Stream | 看整条会话的 STARTDT→SBO→FIN 全流程 |

## 报文/字段对照

一条 IEC 104 报文 = 起始符 `68` + 长度 + 4 字节控制域（合称 APCI）+ ASDU。本节按字段拆一条遥控命令，实测一节再放整轮帧表。

### APCI：起始符、长度、控制域

以 STARTDT 的两帧为例：

```text
68          起始符，IEC 104 恒定
04          长度 = 4（控制域 4 字节，无 ASDU）
07 00 00 00 控制域 = U 帧 STARTDT act（功能码 0x07）
0b 00 00 00 控制域 = U 帧 STARTDT con（功能码 0x0B）
```

### ASDU 逐字段还原（以帧 8 为例）

帧 8 就是实测一节里 WT07 的 Select 帧。

```text
2d 01 86 00 03 00 f8 28 00 80
│  │  │  │  └──┬──┘ └──┬──┘ └── 信息元素 SCO
│  │  │  │     │       │
│  │  │  │     │       └────── IOA = f8 28 00 → 小端 0x0028f8 = 10488（WT07）
│  │  │  │     └────────────── CA  = 03 00    → 小端 = 3（厂站 3）
│  │  │  └──────────────────── OA  = 00（源发站地址）
│  │  └─────────────────────── COT = 86 = 1000 0110 → Test=1, COT=6（激活）
│  └────────────────────────── VSQ = 01 → SQ=0、对象个数 1
└───────────────────────────── TypeID = 0x2d = 45 = C_SC_NA_1（单点遥控）
```

SCO 拆位：

```text
Select  80 = 1000 0000 → S/E=1（选择）、SCS=0（停）
Execute 00 = 0000 0000 → S/E=0（执行）、SCS=0（停）
```

CA / IOA / SCS 三个字段合起来就是命令的落点：厂站 3 → 点号 10488（WT07）→ 停。

### IOA 映射：三台风机是连续的

```text
WT07  f8 28 00  →  0x0028f8  =  10488
WT08  fa 28 00  →  0x0028fa  =  10490
WT09  fc 28 00  →  0x0028fc  =  10492
```

点号间隔为 2，三台连续，是设计上的规律（一台风机占一对点号，可能是"停机命令 / 启机命令"）。抓到一台就能推出整厂映射，所以"点表式的证据"比"暴力遍历点号"重要。

## 实测过程

### 第一步 建链：TCP 握手 + STARTDT

以主样本 `iec104_3fan_single_direct_20260726.pcap` 开头为例：

```text
[1]  10.0.7.133:38046 → 10.0.7.131:2404  [S]         TCP SYN
[2]  10.0.7.131:2404  → 10.0.7.133:38046 [SA]        SYN+ACK
[3]  10.0.7.133:38046 → 10.0.7.131:2404  [A]         ACK
[4]  10.0.7.133:38046 → 10.0.7.131:2404  [PA]  6804 07 000000   ← U 帧 STARTDT act
[5]  10.0.7.131:2404  → 10.0.7.133:38046 [A]
[6]  10.0.7.131:2404  → 10.0.7.133:38046 [PA]  6804 0b 000000   ← U 帧 STARTDT con
```

控制域的拆法见上一节。TCP 握手只是把管道接上，STARTDT 才是"允许传数据"的开关。没有 STARTDT 就发 I 帧，多数实现直接丢弃。

### 第二步 一轮三台：Select→Execute 的 SBO 序列

帧 8~14 是对 WT07 的一次完整遥控。把三轮的"帧序号 / 控制域 / ASDU / 含义"列在一张表里：

```text
环境：frontend3-lower 10.0.7.133:38046  ⇄  conpot RTU 10.0.7.131:2404（单条持久 TCP 会话）
```

| # | 方向 | 控制域 | ASDU（十六进制） | 含义 |
|---|---|---|---|---|
| 8 | → | `00000000` | `2d 01 86 00 0300 f82800 80` | WT07 Select |
| 9 | ← | `00000200` | `2d 01 07 00 0300 f82800 80` | ACT_CON（回显） |
| 11 | → | `02000200` | `2d 01 86 00 0300 f82800 00` | WT07 Execute |
| 12 | ← | `02000400` | `2d 01 07 00 0300 f82800 00` | ACT_CON（回显） |
| 14 | ← | `04000400` | `2d 01 0a 00 0300 f82800 00` | ACT_TERM（执行完毕） |
| 16 | → | `04000600` | `2d 01 86 00 0300 fa2800 80` | WT08 Select |
| 17 | ← | `06000600` | `2d 01 07 00 0300 fa2800 80` | ACT_CON |
| 19 | → | `06000800` | `2d 01 86 00 0300 fa2800 00` | WT08 Execute |
| 20 | ← | `08000800` | `2d 01 07 00 0300 fa2800 00` | ACT_CON |
| 22 | ← | `0a000800` | `2d 01 0a 00 0300 fa2800 00` | ACT_TERM |
| 24 | → | `08000c00` | `2d 01 86 00 0300 fc2800 80` | WT09 Select |
| 25 | ← | `0c000a00` | `2d 01 07 00 0300 fc2800 80` | ACT_CON |
| 27 | → | `0a000e00` | `2d 01 86 00 0300 fc2800 00` | WT09 Execute |
| 28 | ← | `0e000c00` | `2d 01 07 00 0300 fc2800 00` | ACT_CON |
| 30 | ← | `10000c00` | `2d 01 0a 00 0300 fc2800 00` | ACT_TERM |

（帧 10/13/15/18/21/23/26/29/31 是纯 TCP ACK，无载荷，见第三步解释。）

三台报文结构一样，只有 IOA 和序号逐台推进，下面不再逐帧重复拆解。

### 第三步 读序号：I 帧的"心跳"

定义：I 帧控制域 = `发送序号<<1` + `接收序号<<1`（各 2 字节小端，低 15 位有效）。把上表还原：

| 帧 | 控制域 | 发送序号 | 接收序号 | 谁发的 |
|---|---|---|---|---|
| 8 | `00000000` | 0 | 0 | 主站 |
| 9 | `00000200` | 0 | 1 | RTU |
| 11 | `02000200` | 1 | 1 | 主站 |
| 12 | `02000400` | 1 | 2 | RTU |
| 14 | `04000400` | 2 | 2 | RTU |
| 16 | `04000600` | 2 | 3 | 主站 |

规律非常干净：

```text
一方发一帧 → 自己的发送序号 +1
一方收一帧 → 自己的接收序号 +1（下一帧体现）
两边的序号交替推进，任何跳变都意味着链路层异常
```

序号是 IEC 104 特有的"链路层审计线索"。TCP 序号管字节流，IEC 104 序号管 ASDU 个数；两者都在 pcap 里可见，是判断"重放/注入"的关键。

### 第四步 读时序：三台 3.3 秒，然后断连重开

```text
帧 8  (WT07 Select)    ts=239.321
帧 16 (WT08 Select)    ts=241.032   → 相隔约 1.7s
帧 24 (WT09 Select)    ts=242.745   → 相隔约 1.7s
帧 32 (FIN, 关连接)     ts=244.456
帧 35 (新连接 SYN)      ts=244.560   → 立刻重开
```

- Select → Execute 的间隔约 0.85 秒（帧 8 到帧 11）。
- 一台风机走完一轮约 1.7 秒，三台合计约 3.3 秒。
- 整条 TCP 连接活约 5.3 秒，关闭后立即用新端口重开（38046 → 38054）。

> 这个"短连接 + 快速重连"的节奏本身就是检测线索。真实调度主站通常维持长连接（这正是"长连接"设计的初衷）；频繁短连接 + STARTDT 重放，是自动化测试脚本或攻击脚本的特征。

### 对照一 MITM 抓包：每帧出现两次

用 MITM 样本 `iec104_3fan_single_mitm_20260726.pcap` 对照，同一个 STARTDT act 出现了两次：

```text
[7] ts=...302.904391 ... [PA] PAYLOAD(6)=680407000000
[8] ts=...302.904396 ... [PA] PAYLOAD(6)=680407000000   ← 同 seq、同载荷，仅差 5µs
```

成因：ARP 欺骗把攻击者插进链路后，同一报文会先被攻击者收到（原始帧），再被攻击者转发（转发帧），网卡两次都抓到了。所以：

```text
看到"同一 seq 出现两次" ≠ 设备重传
看到"源和目的 IP 相同、seq 相同" = MITM 转发痕迹
```

辨别方法：真正的重传有超时（毫秒级以上）且伴随重传标志或丢失的 ACK；MITM 重复帧间隔是微秒级（本例 5~70µs）。这一点在 Modbus 的 MITM 场景里同样成立（见 `../02-Modbus/抓包分析.md`）。

### 对照二 字节序陷阱：手册的单行命令 vs 实测 pcap

素材里平台给的单行测试命令是：

```text
680e000000002d01060003000028fa80
```

拆开看 IOA 部分：`00 28 fa`。若按大端读是 `0x0028fa = 10490`；而实测 pcap 里同一个点号 10490 写作 `fa 28 00`（小端）。

```text
手册写法  00 28 fa   → 大端读法
实测写法  fa 28 00   → 小端读法（规范 & pcap 一致的写法）
```

结论：IEC 104 的多字节字段（CA、IOA、序号）都是小端。遇到与文档不一致时以抓包为准，不要照抄文档里的字节串。手拼报文最容易错的地方就是 IOA：数值对、字节序错，命令就落到别的设备上或被拒。

## 安全视角

- 抓包本身就是从"合法流量"里学参数。攻击者不需要猜 CA/IOA，只要在同一二层网段抓一个轮询周期，TypeID、CA、IOA、SBO 流程全部暴露。这就是"测试流量走生产链路"属于高危设计的原因：等于把正式命令的模板（只差一个 Test 位）挂在网上。
- COT 的 `0x86` → `0x06` 是整条链最便宜的攻击。pcap 里全轮都是 `86`（Test=1），说明自动测试通道与生产通道共用同一条 TCP 连接、同一个 CA/IOA。防护上必须物理/逻辑分离测试与生产，或在转发组件里硬拒绝 `COT & 0x80` 的命令。
- 序号是重放检测的抓手。合法流量的 `发送序号/接收序号` 严格交替递增；重放旧 I 帧会让接收序号倒退，注入新帧会让序号跳变，两类偏差都能在 pcap 里直接看出来（见 `链路异常.md`）。
- 短连接 + 高频 STARTDT 是脚本特征。真实调度主站用长连接；链路上出现"每几秒关一次、重开就 STARTDT + 连续 SBO"，基本可判定是自动化工具而非人工操作。
- MITM 重复帧是"有人在中间"的铁证。交换机镜像抓包不会产生重复帧，只有 ARP 欺骗式转发才会。看到微秒级重复帧就应立刻排查二层网关/ARP 表。
- 点表泄露的严重性高于单个点号。三台风机的 IOA 连续（10488/10490/10492），泄露一台等于泄露全部；CA 又固定为 3，一次抓包就能复制出完整的"三台批量停机"脚本，这正是山区链能一台不改地打三台的原因。
