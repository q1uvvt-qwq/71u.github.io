## 一句话概括

IEC 104 的攻击面一句话说清：任何能连上 2404 的进程都能自称"调度主站"，按规范发出完整合规的遥控命令，因为协议不认证、不加密、也不区分"测试"与"生产"。相比 Modbus 后果更重（直接面向调度控制），路径却更"讲究"：必须理解 TypeID / COT / IOA / SBO 的语义才能打出有效命令，不像 Modbus 随便写个寄存器就行。防护战场同样是三层：网络边界（谁能到 2404）、应用层深度解析（放行哪些字段组合）、流程审计（谁在何时动了哪个点）。

> 本篇只讨论授权靶场与教学环境下的协议弱点与防护思路，不提供可直接用于真实生产系统的攻击操作。

## 原理

### 1. 七类典型弱点

#### ① 无认证：Rogue Master（伪造主站）

定义：IEC 104 的"主站/从站"是角色，不是身份。任何能建立 TCP 到 2404 的程序，按规范走完 `STARTDT → Select → Execute` 就是功能完整的主站。

```text
合法：frontend3-lower 10.0.7.133  ──STARTDT/SBO──►  conpot RTU 10.0.7.131:2404
攻击：自写 Rogue Master 脚本      ──STARTDT/SBO──►  同一台 RTU   ← 设备无法区分
```

攻击者就是在维护工作站上自写脚本当主站；设备侧看到同一个 CA、同一个 IOA、同一种流程，没有任何异常信号。

防护：只允许调度主站/前置机的 IP 访问 2404（网络白名单）+ 纵向加密认证装置。

#### ② 实现不拒绝 Test 命令：COT 的 bit7 被放过

这是 IEC 104 最典型的实现缺陷类型：规范定义了 COT 的 Test 位（bit7），但没规定收到 Test=1 该怎么处理。

```text
维护测试通道发的：  COT = 0x86 = 1000 0110   Test=1, 激活
攻击者改成的：      COT = 0x06 = 0000 0110   Test=0, 激活
                    ↑ 只差最高位一个比特
```

转发组件若把 `Test=1` 的命令"照常下发、只标记为测试"，这条命令就越过了它本该有的屏障。

防护：在转发组件里硬编码拒绝 `COT & 0x80` 的命令进入生产通道，不是靠运维规范，是靠代码。测试通道与生产通道应物理/逻辑分离。

#### ③ SBO 是流程设计，不是安全机制

"先选后控"只防误操作，不防恶意，攻击者完全可以按规范先 Select 再 Execute。

```text
规范流程：  Select(0x80) → ACT_CON → Execute(0x00) → ACT_CON → ACT_TERM
攻击者的：  同样的流程，一字不差，照样通过
```

SBO 的价值在于提供异常检测的基线：

```text
跳过 Select 直接 Execute          → 异常
Select 与 Execute 走不同 TCP 连接  → 异常
Select 与 Execute 的 IOA/SCS 不一致 → 异常
同一个 IOA 短时间内反复 Select     → 异常（探测或批量攻击）
```

防护：把"SBO 流程完整性"做成检测规则，而不是当作访问控制。

#### ④ 链路层可被扰动：序号漂移与重放窗口

IEC 104 在 TCP 之上自建了一层 APCI 序号账本，由应用维护，可以被扰动：

```text
扰动发送序号（如 +4）
    → 从站账本对不上
    → 判定失步，进入 DEGRADED 容错态
    → replay_window 打开
    → 新鲜度校验失效，旧命令 / 注入命令可被接受
```

成因：这类弱点的入口是"容错逻辑"，而容错逻辑通常不被当作安全边界来审。

防护：降级态只放宽性能参数（重传、超时），绝不放宽命令合法性校验；叠加命令级的时间戳/一次性 ticket，让新鲜度独立于序号。详见 `链路异常.md`。

#### ⑤ 报文可被篡改与伪造（明文）

IEC 104 通常明文传输（或只做隧道级加密），链路上的人可以：

```text
读到    TypeID / CA / IOA / COT / SCS   ← 全部参数，等于拿到命令模板
改成    改 IOA 换目标设备、改 SCS 换动作方向、改 CA 换厂站
插一条  在既有会话里注入新的 ASDU
```

注意：改完还要保持 APCI 长度字段一致，否则可能触发解析异常而不是生效。这既是利用门槛，也是检测信号（畸形长度）。

防护：分区隔离 + 纵向加密认证装置（电力行业标准做法）；工业防火墙做深度解析，只放行指定字段组合。

#### ⑥ 点表可被推理：IOA 是连续的

实测三台风机的 IOA 是 `10488 / 10490 / 10492`，间隔为 2 的连续点号。

```text
拿到一台 → 推出三台
拿到一个厂站的 CA=3 → 推出相邻厂站很可能也是小整数
```

一次抓包就能复制出完整的批量停机脚本，所以"点表泄露"远重于"泄露一个点号"。

防护：点表属于敏感工程资料，不应出现在 Web 可枚举的对象/备份包里；不同厂站的点号分布应避免可预测（这一条在工程上常被牺牲，属于现实权衡）。

#### ⑦ 无审计：事后无法回溯

IEC 104 设备/RTU 不记录"谁在什么时候对哪个 IOA 做了什么"，攻击完成后设备侧没有痕迹。

防护：审计只能在前置机 / SCADA / 工业防火墙 / 历史库做，记录：源 IP、TypeID、COT、CA、IOA、SCS、时间戳、会话状态。靶场里的历史库事件（`IEC_STARVATION` / `IEC_APCI_COUNTER_DRIFT` / `IEC104_TEST_COMMAND_OBSERVED`）就是这些审计规则的原型。

#### 速查表：弱点与防护对照

| 弱点 | 直接后果 | 主要防护手段 |
|---|---|---|
| 无身份认证 | 任何主机都是合法主站 | 网络白名单、纵向加密认证装置 |
| 无加密 | 命令模板在链路上明文可读 | 分区隔离、隧道封装 |
| Test 位不被拒绝 | 测试命令落地成正式控制 | 转发组件硬编码拒绝 `COT & 0x80` |
| SBO 非安全机制 | 攻击者可完整复现流程 | SBO 完整性作为检测规则 |
| 序号可扰动 | 链路降级、重放窗口打开 | 降级不放宽合法性；命令级时间戳/ticket |
| 无完整性保护 | 命令可篡改、可注入 | 应用层签名（非协议内） |
| IOA 连续可推理 | 泄露一台等于泄露全部 | 点表列为敏感资料、点号分布不可预测 |
| 无审计 | 无法追溯 | 前置机/防火墙/历史库记录变更日志 |
| 短连接高频重连 | 脚本/攻击特征 | 长连接基线 + 重连频率告警 |

## 在攻击链里的位置

山区链把 IEC 104 的弱点串成一条完整链路：

```text
工单系统 D50003（存储型 XSS）              ← Web 层入口
      │  泄露维护工作站凭据
      ▼
山区运维门户 / 历史事件浏览器               ← 越权读取链路诊断（scope=all）
      │  学到链路拓扑与 IEC104 会话诊断接口
      ▼
维护工作站（SSH，sudo NOPASSWD）            ← 借合法位置（弱点①）
      │  ARP MITM + tcpdump 抓包
      ▼
从真实测试流量里"学到"协议参数
      │  TypeID=45 / CA=3 / IOA=10490 / COT=test / SBO
      ▼
让前置机3会话进入 DEGRADED                  ← 弱点④（序号漂移）
      │  APCI_POISON，apci_send_seq_delta=4，replay_window=open
      ▼
发正式遥控（Test 位清掉，走完整 SBO）        ← 弱点②③
      │  STARTDT → Select → Execute
      ▼
PLC2 / SCADA2 停机，功率归零               ← 业务影响
```

这条链最有教学价值的三个点：

- 参数全部来自证据，不是猜的。CA、IOA、SBO 流程都来自抓包与历史事件，对应"不允许靠猜点号制造难度"的设计原则。
- 只改一个比特不够，必须叠加会话异常。负向验证那一步（未降级 → `simulation_only`）把"漏洞"从"随便发包"纠正成"理解会话状态机"。
- 协议知识决定成败：不理解 TypeID / COT / IOA / SBO / APCI 序号，抓到包也不知道该改哪个字节、该先做哪一步。

## 靶场设计的"防非预期"约束

协议攻击点布设模板对 IEC 104 场景规定了明确边界，这些约束本身就是最好的防护清单：

```text
1. 不把 RTU 的 2404 直接暴露给玩家（攻击要通过 D5000/前置机业务链路）。
2. 参数（CA、IOA、SBO 流程）必须来自场景证据，不能靠猜或遍历。
3. 单改 COT 不足以成功，必须叠加会话异常（负向验证设计）。
4. 命令落点必须可恢复（靶场用 reset 接口恢复 HEALTHY / RUNNING）。
5. 命令的影响范围要有限（只影响目标风机的指定控制点）。
```

## 安全视角

### 检测思路

| 检测点 | 规则 |
|---|---|
| 异常主站 | 非调度主站/前置机 IP 发起 STARTDT |
| 测试命令进生产 | 生产链路上出现 `COT & 0x80`（Test=1） |
| 序号漂移 | I 帧发送/接收序号跳变（非 +1 递增） |
| 链路饥饿 | ASDU 到达间隔超过轮询周期的 N 倍 |
| 重放 | I 帧序号重复、或同一命令内容在短时间内重现 |
| 畸形 SBO | 无 Select 的 Execute；跨连接 Execute；IOA/SCS 不一致 |
| 陌生 IOA | 出现未在资产台账中的 IOA |
| 频率异常 | 同一 IOA 短时间内反复 Select；连接建立频率异常高 |
| 会话降级 | `session_state` 从 HEALTHY 变为 DEGRADED 并伴随命令下发 |

### 设计观念

1. 协议无法保护自己，边界才能。IEC 104 的安全等于"谁能到 2404" + "放行哪些字段组合"。
2. "测试"与"生产"必须是两条路；靠 Test 位在同一通道里区分，是把安全托付给实现者的自觉。
3. 容错态是安全边界的薄弱点。DEGRADED 只应放宽性能，不应放宽合法性；这条边界要在设计文档里写死。
4. SBO 是检测基线，不是访问控制。把它当安全机制会给人虚假的安全感。
5. 审计是唯一的事后答案：设备不记事，前置机/历史库必须记事。
