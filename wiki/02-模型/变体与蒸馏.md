## 一句话概括

同一套架构会按内部宽度和层数分几档，各档共用同一份数据、契约、tokenizer 和词表。大档做教师自监督训练，小档在同样的自监督任务上再加一路蒸馏损失，向大档的表示对齐。

## 变体分档的原则

分档只允许动内部宽度和层数，其余全部冻结。共享的部分包括 embedding 维度、attention head 数、消息与序列的最长长度、词表、normalizer、tokenizer、契约 ID 和数据划分。档位表见 [ContraLog架构](ContraLog架构.md)。

这条界线是为了让对照有意义。如果分档时连词表或窗口长度也一起改，分数变化就归因不到结构上。变体之间的唯一自变量应当是容量。

分档的收益不能按参数量的缩水比例来预期。embedding 表是 `词表 × d_model`，在大词表下它占了绝大部分参数，把 hidden 减半、层数减半动的是 Transformer 那一小块，总参数量几乎不动。想靠改结构显著瘦身不现实，词表才是那根主杠杆。

既然小档用了更小的 batch，为了保持每轮覆盖的窗口数一致，它的 step 数会比大档多出近一倍。这是数据覆盖对齐的结果，不是调参偏好。

## 自监督目标：遮蔽重建

定义：自监督指训练信号由数据本身构造，不依赖人工标签。这里的信号是"把一条消息藏起来，看模型能不能根据上下文把它找回来"。

流程：

```text
message_input_ids
  → MessageEncoder
  → message embeddings
  → 随机遮蔽若干位置
  → SequenceEncoder 预测被遮蔽位置
  → 与真实 message embedding 做双向对比交叉熵
```

被选中的位置换成 SequenceEncoder 的 mask embedding。遮蔽规模用固定条数而不是固定比例：

```text
mask_count       = 38
mask_probability = 38 / 256 = 0.1484375
```

用固定条数的好处是每个窗口的监督信号量恒定，短窗口不会被过遮蔽。用比例的话，一个只剩几十条真实事件的窗口会被盖掉大半，重建目标失去上下文。

三个设计点。第一，预测目标是连续的 message embedding 而不是离散的模板 ID，所以损失是"预测向量与真实向量的对比"而不是分类。第二，相似度在 `normalize` 之后计算，模型比的是方向不是模长，模长交给前面的 `sqrt(d_model)` 缩放管。第三，温度系数把 logits 分布压得更尖锐，等价于把负样本的权重调高，这在小 batch 的对比学习里是常用手段。

```text
scores          = normalize(prediction) @ normalize(targets).T * temperature_scale
temperature_scale = 4.0
loss            = 0.5 * ( CE(prediction → target) + CE(target → prediction) )
```

双向交叉熵是为了对称。只算一个方向时，损失函数对 prediction 与 target 的地位不对等，梯度会偏向一边。取平均消掉这个不对称。

## 用蒸馏把小模型拉向大模型

知识蒸馏的基本思路是让小模型学大模型的输出分布而不是只学硬标签。在分类任务里这体现为软标签：教师给出的概率分布包含了"这个样本更像 A 类而不是 B 类"这类暗知识，比 one-hot 标签信息量大得多。这里没有分类头，蒸馏发生在表示层：学生不需要自己从零探索一个好的向量空间，而是被拉向教师已经找到的那个空间。学生容量小，直接对齐一个成熟的空间比自己去优化对比目标容易得多。

做法是自监督损失之外再加两路对齐损失：

```text
message_distill = mean(1 - cosine(student_message, teacher_message))
context_distill = mean(1 - cosine(student_context, teacher_context))

total_loss = 1.00 * self_supervised
           + 0.25 * message_distill
           + 0.25 * context_distill
```

教师取大档的最佳 checkpoint，在学生训练期间冻结，不参与更新。两路蒸馏的权重都退到自监督的 1/4，比例说明蒸馏是辅助项。如果蒸馏权重压过自监督，学生可能只学会了模仿教师的输出而不真正学到重建能力，在教师没见过的输入上会退化。

注意：师生表示层维度不同时，余弦不能直接算。实现上学生侧要有一个投影把维度对齐，这一层不参与最终推理，只用于训练对齐。

## 变体怎么评：Hit@10 与 Recall@10

变体之间的比较不能只看一个总分。逐位置定位的两类指标含义不同：

- Hit@10：Top-10 里至少命中一个金标位置，是"有没有找到"
- Recall@10：全部金标位置中进入 Top-10 的平均比例，是"找全了没有"

这两个数要分开读。Context Hit@10 可以很高而 Recall@10 很低，意思是几乎每个窗口都能报出至少一个可疑点，但一个窗口里通常有多个金标位置，Top-10 覆盖不全。造成这个落差的一是 Top-K 的截断，窗口里若有 50 个金标位置，Recall@10 的理论上限就只有 20%；二是逐位置定位本身是多目标排序，难度天然高于窗口级命中。

Context 的定位指标普遍低于 Point，也是两类任务难度不同造成的。Point 分数问单条消息像不像正常，是窗口内的独立判断；Context 分数要在 256 长的序列里挑出若干个正确位置，判据更苛刻。

蒸馏的效果会集中体现在 Context 上，因为 `context_distill` 直接对齐上下文表示，正是 Context 分数依赖的那一层。这一点值得作为分档验证的一条预期：如果小档在加了 context 蒸馏后 Context 指标没有提升，说明对齐没有生效。

## 检查点选择的一个坑

最佳 checkpoint 通常按训练 loss 选，而训练 loss 是自监督 / 蒸馏损失，不是攻击日检测指标。训练 loss 正常不代表定位效果好，"训练收敛但召回偏低"是可能发生的。

所以变体之间的最终比较不能停在训练曲线上，必须在留出的诊断集上跑一遍逐位置指标。监控集只负责回答训练过程健不健康，性能口径要另算。
