## 一句话概括

ContraLog 出两种分数：Point 分数问"这条消息像不像正常消息"，Context 分数问"这条消息在这个位置上像不像上下文该有的样子"。两条路线互补，最后合成一个四维特征向量。

## Point 分数：到最近正常参考的距离

```text
point_i = 1 - max cosine(message_embedding_i, normal_reference)
```

实现上先把 query 和 reference 都做 L2 归一化，算相似度矩阵，取最近邻，再用 `1 - 余弦` 转成距离。

用余弦而不是欧氏距离，前提是方向承载语义、模长不承载。embedding 的模长受序列长度、token 数、训练时的归一化方式影响，如果把这个也当异常信号，模型会去学"这条消息看起来长不长"，而长不等于异常。归一化之后只剩下方向，比的是语义朝向。

用"到最近正常参考的距离"而不是"到所有正常样本中心的距离"，是因为正常行为本身是多模态的。一台主机既有浏览器的正常行为，也有计划任务的正常行为，还有 ping 的正常行为。这些行为的 embedding 分布在向量空间里并不围绕一个中心，硬算一个质心，质心会落在几条正常模式的中间空地上，所有正常样本到它的距离都很大。取最近邻等于问"它像不像我已经见过的某一类正常"，这在多模态分布下才是对的判据。

reference 集合必须是正常样本，且不能来自测试集。reference 与 message encoder 绑定，不能跨模型复用。

## Context 分数：遮蔽重建

```text
context_i = 1 - cosine(masked-context prediction_i, message_embedding_i)
```

做法是把第 i 个位置换成 Sequence Encoder 的 mask token，让编码器在看不到这条消息的情况下，根据其余位置把它预测回来，再比预测与原向量的余弦距离。预测得越不准，说明这条消息越不符合它在上下文里的位置。

实现上有一个关键技巧：

```text
variants = sequence_embeddings.unsqueeze(0).repeat(N, 1, 1)
variants[indices, indices, :] = encoder.get_mask_token(norm=False)
prediction = encoder(variants.transpose(0, 1))
prediction = prediction[indices, indices, :]
```

一次构造全部 N 个 leave-one-out 变体，组成一个 batch 喂进去，只取对角线上的预测结果。naive 做法是循环 N 次、每次单独前向，那样要把同一段序列编码 N 遍。批量构造把 N 次前向合成一次，代价是显存里同时放 N 份输入。

这个技巧把逐位置评分从"循环里放大 O(N)"压到了"一次前向加 N 倍输入内存"，但计算量本身没变。这也解释了为什么逐位置评分是整条链路里最贵的一步。

对角线替换用的是未归一化的 mask token。如果传归一化版本，后续 `sqrt(d_model)` 缩放和位置编码的尺度会与训练时不一致。

## 四维特征与顺序

每个窗口的分数聚合成四个数：

```text
point_mean, point_max, context_mean, context_max
```

顺序是冻结的，任何改动都算接口变更。

取均值和最大值放一起，是因为两者回答不同问题。均值反映整个窗口的整体偏离程度，一条消息异常会被所有位置平摊掉；最大值反映窗口里最可疑的那一个位置，是"这个窗口值不值得人来看一眼"的信号。只用均值会漏掉单点攻击，只用最大值会让噪声顶着分数走。

聚合发生在特征层，不是先合成一个总分再判。四个数一起进后面的 Robust-Z，阈值判定在归一化之后（见 [阈值与校准](阈值与校准.md)）。

## 逐位置评分的算力代价

逐位置全量模式下，一个窗口要跑 N 个变体，N 等于序列长度。按 `L = 256`、`D = 64` 估算单层的浮点运算量：

| 计算 | 公式 | 量级 |
| --- | --- | ---: |
| Q/K/V/O 投影 | `4·L·D²` | 4.19M |
| Attention 矩阵 | `2·L²·D` | 8.39M |
| FFN | `2·L·D·FFN` | 4.19M |
| 每层合计 | | ≈16.78M |

4 层单变体约 67.11M FLOPs，全量单窗口约 17.18G FLOPs。这几个数是从形状算式直接乘出来的，不依赖任何实测。

要抓的是 Attention 项里的 `L²`。它随序列长度平方增长，在 256 这个长度上已经超过其余两项之和。序列再长一档，这一项会更快地把总成本拉开，这也是长序列场景下算子融合与近似注意力受关注的原因。

这个估算解释了后面的优化路线为什么集中在 Sequence Encoder 的 ONNX 推理上（见 [瓶颈归因](../03-轻量化/瓶颈归因.md)）：一个窗口的计算量差不多全花在这 N 次变体前向上。

## 两条分数线的分工

| 维度 | Point | Context |
| --- | --- | --- |
| 问的问题 | 这条消息本身是否常见 | 这条消息在此处是否合理 |
| 参照物 | 全局正常参考集 | 同一个窗口的其余消息 |
| 是否需要序列 | 不需要，单条即可 | 需要，依赖上下文 |
| 能否缓存 | 可以，与窗口无关 | 不可以，每个窗口重算 |

Point 分数可以离线预计算，因为它是单条消息的函数；Context 分数必须在线算，因为它依赖窗口里的邻居。这个差别直接决定了缓存策略只能作用在 Message Encoder 上，Sequence Encoder 这一段优化不掉。
