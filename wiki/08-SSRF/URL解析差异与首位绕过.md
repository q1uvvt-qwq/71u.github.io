## 一句话概括

后端用正则规定 URL **必须以 `http://ctf.` 开头、以 `show` 结尾**。但**正则看到的是整条字符串，URL 解析器看到的是结构化字段** —— 把"满足正则的那部分"塞进 `userinfo` 和 `query` 这些**语义盲区**，就能既满足正则、又把请求真正打向 `127.0.0.1`。

## 本题情景与解题手法

### 题目形态

源码里是一道**格式白名单**检查：

```php
if (preg_match('/^http:\/\/ctf\..*show$/i', $url)) {
    // 通过，去请求 $url
} else {
    die('error');
}
```

### 第一步：把正则拆成三个硬性约束

| 片段 | 含义 | 带来的约束 |
|---|---|---|
| `^` | 字符串开始 | 必须从**第一个字符**就匹配 |
| `http:\/\/ctf\.` | 字面量 `http://ctf.` | **必须以 `http://ctf.` 开头**（`\/` 是转义 `/`，`\.` 是转义 `.`，因为两者在正则里有特殊含义） |
| `.*` | 任意字符，零次或多次 | 中间随便填 |
| `show$` | 以 `show` 结尾 | **整条字符串必须以 `show` 结尾** |
| `/i` | 不区分大小写 | `HTTP://CTF.` 也能过 |

于是这道题的"明面要求"就两条：**开头 `http://ctf.`，结尾 `show`**。

### 第二步：先想最直白的写法，看它为什么不行

直觉上会想：让域名长得像 `ctf.` 开头不就行了？

```text
http://ctf.127.0.0.1.show/flag.php
```

- 开头 ✓ 是 `http://ctf.`
- 但结尾是 `/flag.php`，**不是 `show`** ✗

而且就算结尾改了，URL 解析器会把 `ctf.127.0.0.1.show` 整个当成**主机名**去解析 —— 这个域名不存在，请求根本发不出去。**把目标藏进域名本身是行不通的。**

### 第三步：把 `http://ctf.` 塞进"用户名字段"

URL 标准里，`@` 之前的部分是**用户信息（userinfo）**，`@` 之后的才是**主机**：

```text
http://用户名@主机/
```

所以：

```text
http://ctf.@127.0.0.1/flag.php
```

两个视角看到的东西完全不同：

| 视角 | 看到的内容 |
|---|---|
| 正则 | 整条字符串以 `http://ctf.` 开头 ✓ |
| URL 解析器 | 用户名 = `ctf.`，**主机 = `127.0.0.1`** ✗ 打到内网了 |

**正则以为你在访问 `ctf.` 域名，实际网络请求会去访问 `127.0.0.1`。** 这一步实现了"偷偷把目标指向内网"。

### 第四步：用 query 满足"结尾是 show"

还差最后一条约束：整条字符串必须以 `show` 结尾。

直接写 `/flag.php` 结尾不行；但如果把 `show` 放进 **query**：

```text
http://ctf.@127.0.0.1/flag.php?show
```

- 对正则：整条字符串确实以 `show` 结尾 ✓
- 对服务器：`?` 之后是**查询参数**，不影响路径：

```http
GET /flag.php?show HTTP/1.1
Host: 127.0.0.1
```

于是两个约束同时满足，而真正请求的还是 `/flag.php`。

### 解题手法一句话总结

> **正则规定"整条字符串"的形状** → 用 `@` 把 `http://ctf.` 降级成 userinfo（正则满意，解析器把 `127.0.0.1` 当主机）→ 用 `?show` 满足结尾锚点（正则满意，query 不影响请求路径）→ **两次都过了正则，实际请求打向内网。**

## 原理

### 1. 完整的 URL 结构

```text
scheme://userinfo@host:port/path?query#fragment
        └──────┘ └──┘      └──┘ └────┘
       用户名/密码  主机    端口  路径
```

| 部分 | 本题里的值 | 作用 |
|---|---|---|
| `scheme` | `http` | 协议 |
| `userinfo` | `ctf.` | 用于 HTTP Basic 认证的用户名/密码（`user:pass@host`） |
| `host` | `127.0.0.1` | **真正的连接目标** |
| `port` | 省略 → 80 | 端口 |
| `path` | `/flag.php` | 请求路径 |
| `query` | `show` | 查询字符串，服务端从 `$_GET` 取 |
| `fragment` | 无 | 锚点，**不会发给服务器** |

**关键点**：`userinfo` 和 `fragment` 对服务端几乎不可见 —— 前者的作用只是给认证用，后者根本不参与网络请求。**它们是"正则能看见、但请求不关心"的天然盲区。**

### 2. 根本矛盾：字符串匹配 vs 结构化解析

| | 正则 `preg_match` | URL 解析器（`parse_url` / curl） |
|---|---|---|
| 输入 | 一整个**字符串** | 一个**结构** |
| 关注点 | 首尾、顺序、字面量 | scheme / host / path 的语义 |
| 对 `@` 的理解 | 一个普通字符 | **userinfo 与 host 的分隔符** |
| 对 `?` 的理解 | 一个普通字符 | **path 与 query 的分隔符** |

只要这两者对同一段文本的理解不一致，**就存在"两边都觉得自己看对了、但结论不同"的空隙**。这类绕过不限于 SSRF：URL 过滤、重定向白名单、CSP 配置里都会出现同型问题。

### 3. 锚点约束的通用突破思路

凡是正则用 `^` 或 `$` 卡首尾的，都可以按"**把满足条件的内容放进 URL 的语义盲区**"这个思路来想：

| 约束 | 盲区 | 做法 |
|---|---|---|
| 必须以 `http://ctf.` 开头 | `userinfo` | `http://ctf.@真实主机/...` |
| 必须以 `show` 结尾 | `query` | `.../flag.php?show` |
| 必须以某字符串结尾 | `fragment` | `...#show`（但 fragment 不发给服务器，需确认对服务端无影响） |
| 必须包含某白名单域名 | `userinfo` 或 `query` | `http://白名单域名@内网IP/`、`http://内网IP/?u=白名单域名` |

在本题里 `?show` 是最干净的解法 —— 它满足锚点的同时还**不影响服务端取到的路径**。

### 4. 与"IP 变形绕过"的区别

04 讲的是**同一个 IP 的多种字面量**；本篇讲的是**同一个 URL 的多重解读**。

| 维度 | IP 变形（04） | URL 解析差异（本篇） |
|---|---|---|
| 绕过对象 | 字符串黑名单 / 数值区间 | 正则格式白名单 |
| 做法 | 换写法（`127.1`、十进制……） | 换字段位置（userinfo / query） |
| 解决的问题 | "不能出现 `127.0.0.1`" | "必须形如 `http://ctf.*show`" |
| 能否绕过 `filter_var` | 不能 | 不能（域名不是 IP 字面量） |

## 利用条件

1. **校验用正则（或字符串函数）在整条 URL 上做首尾/包含匹配**，而不是用 `parse_url` 取 host 判断
2. **后端真正发起请求时会按标准 URL 语法解析**（curl / `file_get_contents` 都会）
3. **`@` 与 `?` 没有被额外过滤**
4. 目标主机可达（本题是 `127.0.0.1`）

## Payload 速查

| 目的 | Payload |
|---|---|
| 满足 `^http://ctf.` | `http://ctf.@127.0.0.1/...` |
| 满足 `show$` | `.../flag.php?show` |
| 两者合一（本题答案） | `http://ctf.@127.0.0.1/flag.php?show` |
| 换真实内网目标 | `http://ctf.@内网IP:端口/flag.php?show` |
| 带认证信息（顺带说明 userinfo 用途） | `http://user:pass@127.0.0.1/flag.php?show` |

## 完整示例

```http
POST / HTTP/1.1
Host: 靶机地址
Content-Type: application/x-www-form-urlencoded
Content-Length: 45

url=http://ctf.@127.0.0.1/flag.php?show
```

后端实际发出的请求：

```http
GET /flag.php?show HTTP/1.1
Host: 127.0.0.1
```

响应即是 `127.0.0.1` 上该文件的内容（`?show` 只是查询串，不影响取到 `/flag.php`）。

## 踩坑与备注

- **`@` 前面必须像个"用户名"**：`http://ctf.@127.0.0.1/` 里 `ctf.` 被当作 userinfo。如果写成 `http://ctf.127.0.0.1/`（没有 `@`），整个 `ctf.127.0.0.1` 就是主机名，解析不了。
- **`?show` 与 `/show` 完全不同**：`/flag.php?show` 请求的是 `flag.php`，`show` 只是参数名（值为空）；写成 `/flag.php/show` 就变成请求子路径了，会 404。
- **正则里的转义符别漏看**：`\/` 是 `/`（因为 `/` 是正则定界符），`\.` 是 `.`（`.` 在正则里表示任意字符）。不转义的话 `ctf.` 会匹配 `ctfX`。
- **`/i` 让大小写通吃**：`HTTP://CTF.@127.0.0.1/flag.php?SHOW` 同样满足正则，但 URL 里的 scheme 和 host 本来就大小写不敏感，所以没什么额外收益。
- **原文记录的两次失败尝试**（保留作为推导过程）：先试 `http://ctf.127.0.0.1.show/flag.php`（域名解析失败，且结尾不满足），后试 `http://ctf.aaa.show@127.0.0.1/flag.php`（结尾不是 `show`，不满足锚点）。两次都不符合约束，最终收敛到 `@` + `?show` 的组合。
- **一个正则可被两个字段同时"喂饱"**：本题的教训是，**能用结构化解析（`parse_url`）判断的地方就不要用正则匹配整条字符串** —— 正则是"看字面"，URL 是"讲语法"。
